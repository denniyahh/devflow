# Phase 37.1: Pi Subagent-Extension Spike (research) - Research

**Researched:** 2026-08-17
**Domain:** Pi coding-agent extension architecture; subagent/dispatch mechanisms; DevFlow's `AgentDriver`/`MonitorLaunch`/`CloseRule` contract
**Confidence:** HIGH (all core claims verified against the live-installed `pi` binary and the bundled npm package source, not training data)

## Summary

Pi (`@earendil-works/pi-coding-agent`) ships **no built-in subagent/dispatch tool**. Its
core toolset is `read`/`bash`/`edit`/`write` only — confirmed both from the installed binary's
own `--help` banner ("AI coding assistant with read, bash, edit, write tools") and from a
public statement of Pi's design philosophy: "no subagents, no plan mode, no approval prompts,
no MCP, no governance in core." Subagent dispatch is exclusively an **extension-provided**
capability, via `pi.registerTool()`.

Exactly one credible implementation of that capability exists: the `subagent` **example
extension** bundled inside the `@earendil-works/pi-coding-agent` npm package itself
(`examples/extensions/subagent/`), present at the exact version this machine has installed
(0.84.1). It registers a `subagent` tool that spawns additional `pi` child processes (single/
parallel/chain modes, markdown-defined agents with their own model/tool/system-prompt config)
and streams their `--mode json` output back into the parent Pi's own tool-result. This is
functionally analogous to Claude's Task tool **from the LLM's perspective**, but it is not a
maintained, installable product — the README's own installation instructions are "symlink
these files from a `pi` source checkout," not `pi install <package>`. It is not currently
installed anywhere in this environment (`pi list` → "No packages installed"). A search for
alternative third-party npm packages turned up six candidates, and **every one of them fails
the package-legitimacy gate** (too-new and/or low-downloads, one with no source repository at
all) — none is a defensible dependency for DevFlow today.

The decisive finding for the phase's gate is architectural, not "does the feature exist":
Pi's internal subagent dispatch (whether from the bundled example or a hand-rolled equivalent)
happens **entirely inside one already-running top-level `pi` process's own tool-call loop**. It
produces no distinguishable event vocabulary that DevFlow's existing `CloseRule`/`PipeOwning`
drain-gate machinery can recognize — that machinery is hard-coded to Claude's
`task_started`/`task_progress`/`background_tasks_changed` subtype strings
(`crates/devflow-core/src/monitor.rs:582-609`), and the Phase 38 adversarial review already
established, against the same installed `pi` 0.84.1 binary, that Pi's top-level `--mode json`
is **single-shot print mode, not a stream** — `PipeOwning`'s stdin-pipe wire protocol deadlocks
it outright. A vendored `subagent` extension would make its dispatch visible only as an
ordinary named `tool_call`/`tool_result` pair in whatever output mode the top-level process
already uses — invisible to `CloseRule` without new, Pi-specific code.

**Primary recommendation:** The verdict is **NOT VIABLE for a "full-dispatch arm" that reuses
DevFlow's existing `PipeOwning`/`CloseRule` machinery.** Ship Phase 39's already-scoped
reduced-capacity baseline (D-02: `Legacy`/`-p` + a new Pi-specific structured-completion
parser) as the only arm for Pi in the current milestone. Treat "Pi subagent dispatch with real
DevFlow drain-gate coverage" as an independently-scoped future phase, not a same-effort
follow-on — it requires (a) vendoring or authoring a `registerTool`-based dispatch extension
installed strictly at **user scope** (never project-local, to preserve `PiDriver`'s existing
`--no-approve` trust boundary — see `crates/devflow-core/src/agents/pi.rs:1-17`), and (b) a
new Pi-specific drain predicate that watches for a named `subagent` tool call/result pair,
since Pi has no task-lifecycle event vocabulary to reuse.

The key point the diagram is built to make legible: **DevFlow never spawns, sees, or gates on
the child `pi` processes.** They are wholly contained within, and only visible to, the single
top-level `pi` process DevFlow already launched. Any drain-gate coverage would have to be built
by teaching DevFlow's monitor to recognize a *generic named tool call* as a proxy for
"subagent work is pending," which is a materially different (and currently unbuilt) predicate
from `CloseRule`'s Claude-specific task-subtype scan.

### Pattern 1: Extension-registered tool as the only dispatch mechanism
**What:** Pi extensions call `pi.registerTool({ name, description, parameters, execute, ... })`
during load (or later, via `session_start`/command handlers); registered tools appear in
`pi.getAllTools()` and become callable by the model like any built-in tool.
**When to use:** This is the *only* way to add dispatch-like capability to Pi — there is no
config flag, no `--enable-subagents` switch, no core feature toggle.
**Example (the actual bundled reference implementation, read verbatim from the installed
package):**
```typescript
// Source: @earendil-works/pi-coding-agent@0.84.1
// examples/extensions/subagent/index.ts (read directly, this session)
export default function (pi: ExtensionAPI) {
	pi.registerTool({
		name: "subagent",
		label: "Subagent",
		description: [
			"Delegate tasks to specialized subagents with isolated context.",
			"Modes: single (agent + task), parallel (tasks array), chain (sequential with {previous} placeholder).",
		].join(" "),
		parameters: SubagentParams,
		async execute(_toolCallId, params, signal, onUpdate, ctx) {
			// ... spawns child `pi --mode json -p --no-session ...` processes
		},
	});
}
```

### Pattern 2: Child-process isolation, not in-process agent objects
**What:** Every dispatched subagent is a **separate OS process** (`spawn("pi", ["--mode",
"json", "-p", "--no-session", ...])`), not an in-process sub-loop. Each child gets its own
context window, and optionally its own `--model`/`--tools`/`--append-system-prompt`.
**When to use:** This is structurally identical to how DevFlow itself launches agents (one
process per unit of work) — but it is nested one level deeper than DevFlow's own process tree,
and DevFlow has no visibility into it.
**Example** (from the same file, read verbatim, this session):
```typescript
const args: string[] = ["--mode", "json", "-p", "--no-session"];
if (agent.model) args.push("--model", agent.model);
if (agent.tools && agent.tools.length > 0) args.push("--tools", agent.tools.join(","));
// ...
const proc = spawn(invocation.command, invocation.args, {
	cwd: cwd ?? defaultCwd,
	shell: false,
	stdio: ["ignore", "pipe", "pipe"],
});
```

### Anti-Patterns to Avoid
- **Assuming `--mode json` on the top-level DevFlow-launched process gives streaming,
  pipe-driven completion detection like Claude's `stream-json`.** It doesn't — the Phase 38
  review read Pi's own `print-mode.js` source and confirmed `--mode json` processes the
  positional prompt and exits; it never consumes the stdin protocol `PipeOwning` writes. This
  applies to the top-level process regardless of whether a subagent extension is installed.
- **Installing a dispatch extension project-locally (`.pi/agents/*.md` with `agentScope:
  "project"` or `"both"`).** `PiDriver`'s own docstring establishes that DevFlow deliberately
  passes `--no-approve` specifically because "a fresh per-phase worktree establishes no trust
  decision — that is a security boundary, not a convenience" (`crates/devflow-core/src/agents/pi.rs:5-8`,
  quoted verbatim). Any vendored dispatch extension MUST install at user scope
  (`~/.pi/agent/agents/`) only, matching the default `agentScope: "user"` the example itself
  documents, or it silently reintroduces the exact trust hole `--no-approve` exists to close.
- **Treating `InteractivityMode::RequiresTypedSubagents` as already wired up for this.** The
  enum variant exists (`crates/devflow-core/src/agents/mod.rs:102-103`, comment: "The stage
  needs typed-subagent dispatch (e.g. `multi_agent_v2`)") but **no driver returns it today** —
  `ClaudeDriver` does not override `interactivity_mode` at all (default `HeadlessSafe` for
  every stage), and `CodexDriver` only ever returns `RequiresExistingArtifact` or
  `HeadlessSafe` (`crates/devflow-core/src/agents/codex.rs:87-96`, read directly). It is a
  currently-dead landing spot, not a proven integration point.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Spawning + supervising child `pi` processes with streaming NDJSON capture | A bespoke process-pool/JSON-line reader | Vendor the bundled `examples/extensions/subagent/index.ts` pattern (`spawn` + `stdout.on("data")` NDJSON line splitting) | It already handles partial-line buffering, abort propagation (`SIGTERM` then `SIGKILL` after 5s), and per-task output truncation (50KB cap) — a hand-rolled version would need to re-derive all three from scratch |
| Discovering/validating agent definition files (`name`/`description`/`tools`/`model` YAML frontmatter) | A custom frontmatter parser | The bundled `agents.ts`'s `discoverAgents()` | Already handles user-vs-project scope precedence and the trust-confirmation UI prompt for project-local agents |

**Key insight:** Everything needed to give Pi Claude-Task-like dispatch already exists as
working, MIT-licensed-alongside-the-CLI source inside the exact npm package DevFlow already
depends on for Pi support. The gap is not "build a dispatch mechanism" — it's "make DevFlow's
own monitor able to see it," which is a different, harder, and currently unscoped problem.

## Common Pitfalls

### Pitfall 1: Conflating "Pi *can* dispatch subagents" with "DevFlow can gate on it"
**What goes wrong:** Concluding the spike gate as VIABLE purely because an extension mechanism
exists, then discovering during Phase 39-follow-on execution that `CloseRule`/`PipeOwning`
still can't observe any of it.
**Why it happens:** The phase's own framing ("which subagent/dispatch extensions exist for
Pi") reads as a feature-existence question. The gate DevFlow actually needs answered is a
*visibility* question — extension existence is necessary but not remotely sufficient.
**How to avoid:** Treat "full-dispatch arm" as requiring three independently-buildable pieces:
(1) a vendored/authored dispatch extension, (2) a new Pi-specific parser recognizing that
extension's tool-call shape, (3) a new drain predicate — none of which exist today.
**Warning signs:** A plan that says "enable Pi subagent dispatch" as a single task, with no
separate task for teaching `agent_result.rs`/`monitor.rs` to recognize it.

### Pitfall 2: Reusing `PipeOwning` for Pi "once dispatch is available"
**What goes wrong:** Assuming a positive dispatch verdict unlocks the same `PipeOwning`
transport Claude uses.
**Why it happens:** `PipeOwning` is the transport that carries `CloseRule`'s drain-gate
coverage for Claude, so it's tempting to treat "give Pi drain-gate coverage" and "route Pi
through `PipeOwning`" as the same task.
**How to avoid:** They are unrelated. `PipeOwning` deadlocks Pi at the wire-protocol level
(stdin turn envelope, `stream-json` shape) independent of whether a subagent tool is
registered — established by the Phase 38 review reading Pi's own `print-mode.js` source. Any
future drain-gate coverage for Pi has to be built on top of `Legacy` + NDJSON tail-reading
(the same transport the `subagent` extension's own child-process management already uses
internally), not `PipeOwning`.
**Warning signs:** A plan task titled "route Pi through PipeOwning" with no separate
acknowledgment that this was already proven to deadlock.

### Pitfall 3: Installing the vendored extension project-locally
**What goes wrong:** Copying the `subagent` extension into `.pi/extensions/`/`.pi/agents/`
(project scope) for convenience during development, silently changing DevFlow's Pi trust
boundary for every future phase-worktree run.
**Why it happens:** Project-local install is the path of least resistance when developing
inside a single repo, and the example's own `agentScope: "both"` flag makes it a one-line
change.
**How to avoid:** Install (or generate, mirroring `gsd.js`'s own installer pattern) strictly
under `~/.pi/agent/extensions/` and `~/.pi/agent/agents/`. Never grant `agentScope: "project"`
or `"both"` from DevFlow-launched runs.
**Warning signs:** Any `.pi/agents/*.md` or `.pi/extensions/` files appearing inside a
DevFlow-managed worktree.

## Open Questions

1. **Does DevFlow actually need Pi subagent dispatch, or does baseline (D-02) satisfy the
   milestone's real goal?**
   - What we know: Phase 39's D-01 already scopes "full parity" as incremental, with baseline
     landing now and full-dispatch explicitly deferred and gated on this spike.
   - What's unclear: Whether "full-dispatch arm" is still a planned near-term follow-on phase
     after this spike's negative verdict, or whether it should move to the backlog given the
     now-quantified cost (three separately-buildable pieces, not a toggle).
   - Recommendation: Surface this as an explicit decision point in Phase 39's discuss-phase or
     roadmap update — this research treats "ship reduced-capacity" as settled by Phase 39's
     existing D-02, but whether a follow-on phase gets scheduled is a roadmap call, not a
     research one.

2. **What does Pi's raw `--mode json` NDJSON actually look like when a registered extension
   tool (not a built-in) is called?**
   - What we know: The built-in tool JSON shapes (`message_end`, `tool_result_end`) are
     documented and were read directly from the bundled example's own consumption of them.
   - What's unclear: Whether an extension-registered tool's `tool_call`/`tool_result` events
     carry any distinguishing field (e.g., a `source: "extension"` marker) that would make a
     future Pi-specific `CloseRule` predicate cheaper to write, versus needing to match on the
     tool `name` string alone (fragile — any extension author could name a tool "subagent").
   - Recommendation: A short live smoke test (install the bundled example at user scope, run
     one `pi --mode json -p` invocation that triggers it, capture the raw stdout) would answer
     this in under 15 minutes and should precede any Phase 39-follow-on planning, not substitute
     for it here since this phase's mandate is a comparison + recommendation, not an
     implementation spike.
