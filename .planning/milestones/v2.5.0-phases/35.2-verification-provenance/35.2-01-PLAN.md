### P-01 — Capture site: `launch_stage_inner`, once per Validate dispatch (resolves RESEARCH Open Question 1)

**Chosen:** `crates/devflow-cli/src/pipeline_launch.rs`, inside `launch_stage_inner`, gated on
`state.stage == Stage::Validate`, immediately before the existing `state.checkpoint_resumes = 0`
(line 139).

**Rejected:** `crates/devflow-cli/src/commands.rs:387-401` — the site CONTEXT.md called "the natural
one". Verified this session: that block sits inside `start()` and fires exactly once per
`devflow start` invocation, before Define/Plan/Code/Validate have run at all. A marker written there
and never refreshed cannot discriminate the second Validate dispatch of a run from the first, and
999.89's scenario is precisely a checkout landing *between* two Validate dispatches within one run.

**Why `launch_stage_inner` is reachable for every dispatch, verified not assumed:** `transition()`
(pipeline_gate.rs:52-112) sets `state.stage = to` at line 95 and calls `launch_stage` as its last
statement at line 111, on every hop including every Code→Validate loop-back. The same call site
already carries a per-dispatch reset precedent — `state.checkpoint_resumes = 0` — documented as
"Only `launch_stage_inner` resets this counter". Persistence is free: `spawn_agent_and_record` calls
`workflow::save_state` on the line below, writing to `.devflow/state-{N}.json`, which is gitignored
and therefore survives the checkouts the marker exists to detect.

**Bonus, and it is load-bearing for sequencing:** this choice means the plan does **not** edit
`commands.rs` at all. RESEARCH Pitfall 2 found that the unmerged `feature/phase-35.1` branch inserts
a new block immediately before `commands.rs:355`, the exact region the rejected site occupies. Not
touching that file removes the merge conflict from this phase's path entirely.

### P-02 — What the nonce is compared against (resolves RESEARCH Open Question 2)

RESEARCH was right that D-01's literal formulation is inoperative on its own: the nonce lives in
`.devflow/`, which nothing external can reach, so it can never "differ from what was written". And a
nonce alone cannot answer "who wrote these bytes", because every `select_loop_back_fix` call is
already downstream of a Validate dispatch — the marker would be freshly stamped in the failing case
too.

**What actually does the work is the observation *window*, and the nonce is what makes that window
checkable.** The mechanism, in two co-located halves:

1. **Narrow the window.** At the Validate dispatch site, re-observe the artifact into
   `last_verification_fingerprint` / `last_verification_mtime_nanos` and set
   `verification_baseline_captured = true`. The freshness comparison is thereby scoped to *this
   Validate dispatch* rather than to the whole `devflow start` run. A branch checkout performed by
   the Code stage happens **before** the next Validate dispatch, so it is absorbed into the new
   baseline and reads as unchanged — `FullExecute`. That is criterion 2, closed in production and
   not merely in a fixture.

2. **Stamp the window.** At the same instant, set `verification_run_nonce` to
   `previous.unwrap_or(0).saturating_add(1)`. A `Some` value means DevFlow itself dispatched a
   Validate agent and the baseline on record belongs to that dispatch. `None` means it did not — a
   pre-35.2 state file, or a state that never reached a stamped dispatch — and the artifact's
   provenance is therefore unknown.

The predicate then becomes `nonce.is_some() && <existing fingerprint/mtime body, unchanged>`. The
existing body is retained verbatim, which is D-02 ("augmented, not replaced") and keeps all seven
committed truth-table rows meaningful as fingerprint/mtime regression coverage.

**One new field, not two.** A companion "last observed nonce" was considered and rejected: because
the stamp and the re-observation are co-located in a single statement block, the two values would
always agree at the decision point, making the comparison a check that cannot fail — the exact
defect 999.86 cost this project one phase earlier. The co-location is pinned by a test in Task 3
instead, which is a check that *can* fail.

**Reading of D-04, flagged for review.** D-04's scenario A reads "nonce matches, fingerprint
unchanged → returns `true`". Implemented here as: nonce present, content byte-identical, **mtime
advanced** → `true` — the WR-06 idempotent-rewrite case, where the agent genuinely re-authored the
artifact inside its own window. A matching nonce with an artifact that was not written *at all*
during the window means the Validate agent wrote nothing, and calling that "authored" would dispatch
`--gaps-only` off an inherited verdict — verbatim the 999.79 stall this family of fields exists to
close. Both D-04 directions still fire in one `#[test]` (Task 2), which is what criterion 4 asks for.

### P-03 — What this does NOT establish

State it in the doc comments; do not let the phase close claiming more than it delivers.

- A write to `{N}-VERIFICATION.md` that lands *during* the Validate window from something other than
  the agent (concurrent external tooling, an operator editing mid-stage) still reads as authored.
  The window is narrowed from a whole run to one stage dispatch, not to zero.
- No adversarial property is claimed. `agent_result.rs:2840-2844` already records that an actor who
  can write the artifact can write whatever verdict they like into it; the same posture applies to
  the nonce, and an actor who can write `.devflow/state-{N}.json` can set the stage directly.
- This phase closes an *accidental* drift class (checkouts, merge-backs, cross-repo convention
  mismatch), not an adversarial one.
