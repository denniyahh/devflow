# Phase 35.2: Verification Provenance — Context

**Gathered:** 2026-08-12
**Status:** Ready for planning

<domain>
## Phase Boundary

A loop-back decision knows whether *this run's* Validate agent authored
`{N}-VERIFICATION.md`, rather than inferring it from whether the bytes changed.
The decision is made on a run-owned marker DevFlow itself stamps around the
Validate stage — not on a content fingerprint, and not on a field the agent is
asked to embed. The cross-repo branch-naming coincidence that currently keeps
the byte-inference safe is pinned by a test.

**In scope:**
- A run-owned nonce (stored in State) written before Validate launch
- `verification_authored_this_run` augmented to consult the nonce as authoritative
- Existing fingerprint/mtime fields retained as secondary signals for staleness
- Branch-naming test: format-string assertion (always) + conditional GSD verification
- Unit test demonstrating both dispatch directions in one test function

**Out of scope:**
- Changing the format of `{N}-VERIFICATION.md`
- Asking GSD to write anything — this is DevFlow-closed
- Replacing the fingerprint/mtime fields entirely
- End-to-end agent-driven test for the dispatch — unit-level is sufficient
</domain>

<decisions>
## Implementation Decisions

### Run-owned marker shape

- **D-01:** The run-owned marker is a `verification_run_nonce: Option<u64>` field on `State`, written before the Validate stage is launched and read after it completes. A nonce that differs from what was written means Validate did not run (the agent did not author the artifact). A matching nonce means it did.

  This shape was chosen over a separate marker file (adds lifecycle management for no benefit) or an evidence-root marker (lives in the same tree a checkout replaces, defeating its purpose). State is already the home of the fingerprint/mtime fields and their observation site; the nonce joins them there.

  — **Reversibility:** reversible — the field is local to State; removing it restores the pre-35.2 fingerprint-only behavior.

### Relationship to existing provenance fields

- **D-02:** The nonce is **authoritative** for provenance ("did this run's agent author this?"). The fingerprint and mtime remain as **secondary signals** for staleness ("did the content change?"). They are augmented, not replaced.

  A nonce tells you Validate ran this cycle; a fingerprint tells you the artifact's content matches what was observed before. Both answer different questions. Replacing fingerprints would lose the staleness detection that underpins the plan-count comparison. Letting them coexist keeps both signals working.

  — **Reversibility:** costly — the fingerprint/mtime fields have callers in `select_loop_back_fix` and `verification_authored_this_run`; removing them would require restructuring those functions rather than adding a condition.

### Branch-naming test

- **D-03:** Two tests. (1) A format-string assertion on `PhaseId`'s branch name — verifies that `PhaseId::new(7)` produces `feature/phase-07`, `PhaseId::new(35)` produces `feature/phase-35`, and `PhaseId::new(35.2)` produces `feature/phase-35.2`. This catches DevFlow-side drift on every CI run with no external dependency. (2) A conditional verification that GSD computes the same branch name — invoked via `gsd-tools` when available, skipped with a notice when not.

  The single-digit padding case (criterion 3's explicit requirement) is covered by the format-string test alone — that's the DevFlow-side half we control. The GSD-side test is defense-in-depth for the cross-repo invariant.

  — **Reversibility:** reversible — tests only.

### Criterion 4 — both directions in one run

- **D-04:** A single `#[test]` in `pipeline_outcomes.rs` exercising `verification_authored_this_run` (or the dispatch function that reads the nonce) with two scenarios: (A) nonce matches, fingerprint unchanged → the function returns `true` (authored this run, dispatch `GapsOnly`); (B) nonce absent or mismatched → returns `false` (not authored this run, dispatch `FullExecute`).

  Both assertions fire in one test invocation — "demonstrated in the same run." No agent or e2e harness needed; the dispatch decision is a pure function of State fields.

  — **Reversibility:** reversible — tests only.

### mtime rejection

- **D-05:** mtime is stated as rejected for provenance, with the reason recorded in source: `phase_verification_mtime_nanos` already exists but a checkout or merge-back updates mtime exactly as it updates content, so it fails on the identical scenario the nonce is designed to catch. This is criterion 5 and is documentation, not code.

  — **Reversibility:** not applicable — this is a negative decision (what NOT to do).

### Claude's Discretion

- The exact capture site for the nonce (where it gets written before Validate launch) — the code already has a natural site at the same place `verification_baseline_captured` and the fingerprint/mtime are set. The planner should verify this site is correct and adapt if the evidence says otherwise.
- The nonce value itself — a monotonically incrementing counter is simpler than a random value and equally discriminative for the "did this run launch Validate?" question. The planner may choose either.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`verification_authored_this_run`** — the function this phase augments. Currently reads `(current_hash, current_mtime)` vs `(baseline_hash, baseline_mtime)` plus `baseline_captured`. Adding a nonce parameter is a one-argument change; the existing 7 tests provide a regression net for the fingerprint/mtime paths.
- **`select_loop_back_fix`** — the caller that dispatches `GapsOnly` vs `FullExecute` based on the provenance decision. The nonce affects only the `verification_authored_this_run` call within it; the rest of the function is unchanged.
- **`State::new`** — already zeroes fingerprint/mtime/baseline_captured; the nonce joins that same initialization block.

### Established Patterns
- **`#[serde(default)]` for new State fields** — every field added since 17-01 uses this pattern for backward compatibility. The nonce follows it: absent in older state files → `None`, which is the conservative ("not authored this run") default.
- **`(current, baseline, captured)` tuple pattern** — `verification_authored_this_run` already takes its arguments as a tuple pair plus a bool. Adding the nonce follows the same shape.
- **Conditional GSD verification in tests** — entry #4 in UPSTREAM-GSD-ISSUES.md records the pattern: run the check when gsd-tools is available, skip with a notice when not.

### Integration Points
- **`verification_authored_this_run`** in `pipeline_outcomes.rs` — the primary change site: add nonce parameter, add nonce check to the decision logic
- **`select_loop_back_fix`** in `pipeline_outcomes.rs` — pass the nonce from State into the augmented function
- **State capture site** — where `last_verification_fingerprint` and `verification_baseline_captured` are set (in `launch_stage` or `evaluate_agent_result`). The nonce is written at the same point, before Validate launch.
- **`State` struct** in `state.rs` — add `verification_run_nonce: Option<u64>` with `#[serde(default)]`
- **`PhaseId` branch name** in `phase_id.rs` — the format-string test pins the existing behavior
- **7 existing tests** for `verification_authored_this_run` — must continue to pass after the augmentation
</code_context>
