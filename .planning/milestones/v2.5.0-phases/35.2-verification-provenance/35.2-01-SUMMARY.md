# Phase 35.2 Plan 01: Run-Owned Verification Nonce Summary

**`verification_authored_this_run` now refuses to read provenance from a content fingerprint alone: a `verification_run_nonce` DevFlow stamps per Validate dispatch gates the decision, and its absence forces a full execute — closing 999.89's residual without changing the artifact format or asking GSD to write anything.**

## Performance

- **Duration:** ~4h
- **Tasks:** 3
- **Files modified:** 3 (`state.rs`, `pipeline_launch.rs`, `pipeline_outcomes.rs`)

## Task Commits

1. **Task 1 (tracer, TDD)** — nonce field, launch stamp, nonce guard, end-to-end test
2. **Task 2 (TDD)** — extended truth table, `both_dispatch_directions_are_demonstrated_in_one_run`
3. **Task 3 (TDD)** — serde round-trip tests, co-location test, mtime rejection docs

## The write site: extracted into a helper

The Validate-gated stamp block was extracted into `stamp_validate_dispatch_window(state: &mut State)` rather than driven through `launch_stage_inner` directly in a process-spawning fixture. The behaviour under test is pure state mutation plus two filesystem reads; a process-spawning fixture would have cost what `launch_stage_inner_resets_checkpoint_resumes_counter` already shows without buying any coverage the helper-level test cannot. The helper is called from `launch_stage_inner` at the same position.

## The one deviation the plan's criteria turn on

**P-02's reading of D-04 was revisited against the code, and the revisit produced a second stamp site.**

The plan's `launch_stage_inner` stamp covers the launch path. But five pre-existing integration tests (`verification_written_this_run_dispatches_gaps_only`, `an_uncaptured_baseline_does_not_claim_an_inherited_artifact`, and three others) exercise the **already-running** Validate-failure path — `handle_validate_outcome` → `select_loop_back_fix` — where `launch_stage_inner` has already run for the *current* dispatch and will not re-stamp before the loop-back decision. With the nonce guard in place, those tests saw `verification_run_nonce = None` and dispatched `FullExecute` where they expected `GapsOnly`.

The fix: `handle_validate_outcome`'s Validate-failure arm stamps the nonce before its `save_state`, so the loop-back decision always sees a stamped dispatch. This is not scope creep — it is the same mechanism completing its coverage of the second entry point into the dispatch decision.

## Mutation checks

The three mutation checks named in the plan's acceptance criteria were performed, with both directions observed:

1. **Deleting the nonce guard** (`validate_dispatch_nonce.is_none()` → always-false): the two new dispatch tests and `a_checkout_between_dispatches` go red (FullExecute becomes GapsOnly on the None-nonce rows). Restored → green.
2. **Removing the `Stage::Validate` gate** on the stamp: the co-location test's non-Validate arm goes red (nonce advances on every stage). Restored → green.
3. **Pre-implementation RED of Task 1's end-to-end test**: the checkout-between-dispatches test failed against the unmodified fingerprint-only predicate (dispatched `GapsOnly`), observed before the nonce field existed.

## What this plan does NOT establish

- **A write landing *during* the Validate window from something other than the agent still reads as authored.** The window is narrowed from a whole run to one stage dispatch, not to zero (P-03).
- **No adversarial property is claimed.** An actor who can write `.devflow/state-{N}.json` can set `stage` or `consecutive_failures` directly; the nonce adds no attack surface (P-03).
- **The cross-repo branch-naming coincidence is not yet pinned by a test** — that is plan 35.2-02, criterion 3.
