<objective>
Pin the cross-repo branch-naming coincidence that currently keeps `{N}-VERIFICATION.md` from being
routinely replaced by a checkout between stages.

Purpose: DevFlow and GSD independently compute the phase branch name from the same phase number
using the same template. Nothing enforces agreement — two conventions in two repositories. If
either side changes its padding or decimal format, branches diverge, a checkout replaces the
verification artifact, and `select_loop_back_fix` dispatches `--gaps-only` against zero matching
plans. That is 999.84's failure, and it is currently held off only by coincidence. Plan 35.2-01
closes the detection side; this plan pins the prevention side so drift is loud instead of silent.

Output: two tests in `crates/devflow-core/src/phase_id.rs` — one format-string assertion (always
runs) and one conditional GSD verification (runs when `gsd-tools` is available).
</objective>

## Planner decision record

### P-01 — Where the tests live: `phase_id.rs`'s existing test module

The format-string test goes alongside the existing `PhaseId` tests at
`crates/devflow-core/src/phase_id.rs:240-380`. The module already exercises `new`, `with_minor`,
`padded`, `Display`, and `FromStr`. The branch name is a function of `Display` + the template
prefix; testing it here keeps the format and its downstream consumer co-located.

The GSD-verification test goes in the same module. It is a single `#[test]` that shells out to
`gsd-tools` and asserts the output matches; when the tool is absent, it prints a notice and passes
(best-effort defense-in-depth, not a hard gate). Isolating it from the format-string test means a
missing `gsd-tools` does not hide a format-string regression.

### P-02 — How the branch name is constructed

The branch name is `feature/phase-{Display}` where `Display` is `PhaseId`'s `fmt::Display`
implementation. `padded()` is NOT the branch name — it pads to two digits (`07`, `35.2`) but the
branch template substitutes the raw phase number (`7` → `feature/phase-7`, never
`feature/phase-07`). The single-digit case is therefore *uncovered by the existing test suite*:
`PhaseId::new(7).padded()` returns `"07"` but the branch name for phase 7 is `feature/phase-7`,
not `feature/phase-07`. This is exactly the kind of drift this plan exists to catch.

**Confirmed this session.** `rg 'feature/phase' crates/devflow-core/src/` returns zero matches
outside test fixtures and doc comments. The template lives in the git config in
`.planning/config.json` as `"feature/phase-{phase}"`, read by `GitConfig::feature_branch` in
`crates/devflow-core/src/config.rs`, which substitutes `{phase}` with `phase_id.to_string()` —
i.e., `fmt::Display`, not `padded()`.

### P-03 — The GSD verification is conditional, and the condition must be testable

The test guards on `which gsd-tools` or an equivalent PATH probe. When the tool is absent, it
prints `NOTICE: gsd-tools absent — cross-repo branch-name parity NOT verified by this gate` and
returns `Ok(())`. When the tool is present, it invokes `gsd-tools query config-get
git.branching_strategy 2>/dev/null` to confirm the tool is functional, then for each of the three
phase numbers computes the branch name GSD would use and asserts it matches DevFlow's output.

The notice path must itself be verified: the test must be observed printing the notice when
`gsd-tools` is deliberately removed from `PATH`. Restore `PATH` and confirm the matching branch
runs. This is the negative control for the conditional — a test that passes vacuously because the
tool is absent is not a test, and the notice's presence in output is what distinguishes it from
one.
