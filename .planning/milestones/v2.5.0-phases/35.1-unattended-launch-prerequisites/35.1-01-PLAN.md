<objective>
TRACER-FIRST. Prove the whole chain-flag mechanism end to end on one path — a Code-stage,
`Mode::Auto`, pipe-owning-monitor launch — before expanding it sideways.

Purpose: DevFlow spawns Claude to run GSD slash commands but has never touched
`.planning/config.json`, so `workflow._auto_chain_active` stays `false` for every DevFlow-driven run
and GSD's `checkpoint_handling` never auto-approves an ordinary `gate="blocking"` checkpoint. Two
mechanics defeat a naive fix and are the reason this is a tracer rather than three independent
edits: GSD wipes the flag at the top of every invocation whose `$ARGUMENTS` lacks `--auto`
(Pitfall 1), and the flag's true-window must span the detached monitor's lifetime, not the CLI
invocation's (Pitfall 2). Only an end-to-end run through both distinguishes a working mechanism from
a plausible-looking one.

Output: `devflow_core::gsd_config` (the sole writer), `serde_json`'s `preserve_order` feature,
`AUTO_CHAIN_ELIGIBLE_STAGES` + `auto_chain_flag_eligible`, an `AutoChainGuard` bound inside
`run_monitor`, the flag-preserving token on the Code and fix prompts, and a real-binary end-to-end
test with its supervise-mode negative control.
</objective>

<planner_findings>
Six findings resolved during planning that are NOT in CONTEXT.md. Read them before starting.

**F-1 — RESEARCH.md Open Question 1 / Assumption A1 is DECIDED here: the chain flag is engaged only
when `state.mode == Mode::Auto`.** CONTEXT.md's D-01–D-06 describe *when in the run* (Code stage,
gaps-only loop) but never name a DevFlow `--mode`. The phase goal names `devflow start --mode auto`,
D-08 splits auto-vs-supervise for the preflight on exactly this reasoning, and
`preflight_interactivity_check` (`preflight.rs:610-623`) is the file's existing precedent for a
`state.mode == Mode::Auto` condition. Auto-approving checkpoints on a run the operator chose to
supervise would be a silent behaviour change to an already-shipped mode that nobody asked for.
Rated `reversible` — this is one boolean condition in one predicate.

**F-2 — the prompt token is UNCONDITIONAL; only the config write is mode-gated. This asymmetry is
deliberate and load-bearing.** `--auto` in `$ARGUMENTS` cannot by itself enable checkpoint bypass:
`check auto-mode` reads `.planning/config.json` and nothing else
(`check-command-router.cjs:95-111`, verified). A full grep of `execute-phase.md` for `--auto` /
`--chain` / `AUTO_CHAIN` / `auto_advance` returns exactly three hits, all inside the sync-clear block
at `:161-165` — so within `execute-phase.md` the token's ONLY effect is to skip that clear. It does
not chain, and it does not set anything. Threading `mode` into `prompt::stage_prompt_for_project`
would instead mean a signature change to a `pub` function of the published `devflow-core` crate —
the exact class of break Phase 35 had to enumerate in a changelog — to buy a property the config
gate already provides.

**What F-2 gives up, and how it is paid for.** GSD's sync-clear is a safety net: it wipes a stale
`true` left by a previous interrupted run. Sending `--auto` on every Code launch disables that net.
It is replaced by DevFlow's own force-clear (plan `35.1-02`, D-01), which is strictly stronger — it
runs at `start` and `resume`, and it also repairs a value that reached a commit, which GSD's clear
never could. **And it is further closed inside this plan:** the guard is symmetric. On an INELIGIBLE
launch it does not "do nothing"; it actively asserts `false`. So a leaked `true` that somehow
survives to a supervise Code launch is overwritten by DevFlow before the agent starts, not merely
left for GSD to notice.

**F-3 — the guard is symmetric, and the write is conditional on the value differing.** `engage`
takes the value the stage requires (`true` when eligible, `false` when not) and `Drop` always writes
`false` (D-06: `false` is always correct on exit; unlike `LegacyEnvOverride`, there is no meaningful
prior value to restore). `set_auto_chain_active` reads before writing and reports whether it changed
anything, so the ineligible path is a genuine no-op on an already-`false` file rather than a
tracked-file rewrite on every single stage launch. That no-op property is what keeps CONTEXT.md
D-01's "the happy path leaks too, and it leaves the tree dirty" cost bounded to the Code stage's own
duration instead of spreading it across all five stages.

**F-4 — `run_monitor` is structurally pipe-owning-only, so the guard needs no agent/launch-shape
condition.** `run_monitor` is the body of the hidden `__monitor` subcommand
(`main.rs:130-135,561-568`), and `monitor::spawn_monitor` re-execs that subcommand only on its
`MonitorLaunch::PipeOwning` arm. Being inside this function already implies Claude + stream launch.
Do NOT re-check `state.agent` or `state.legacy_claude_launch` in the guard predicate; state that
reasoning in a comment instead. The consequence — a Legacy-arm or non-Claude Code launch never gets
the flag — is RESEARCH Pitfall 4's gap, accepted here per Assumption A3 and turned into a LOUD
preflight refusal by plan `35.1-03`, not left silent.

**F-5 — `PATTERNS.md`'s "No Analog Found" row for PLAN.md checkpoint parsing is obsolete.**
`devflow_core::verify::phase_plan_files` and `phase_has_blocking_human_checkpoint`
(`crates/devflow-core/src/verify.rs:37,131`) already do exactly that scan, decimal-phase-aware, with
seven existing tests. Plan `35.1-03` reuses them. Nothing in THIS plan needs them; recorded here so
no one builds a second scanner.

**F-6 — the eligibility set will be a single element, and that is correct.** `stage.rs`'s `Stage`
enum has five variants and no gaps-only variant; the Validate→Code loop-back changes only the prompt
text at the same `state.stage == Stage::Code` (`pipeline_outcomes.rs:317-395`,
`select_loop_back_fix` returns a `FixType`, never touches `Stage`). Build
`&[Stage::Code]`. Do NOT build a `(Stage, FixType)` lookup table for a distinction the source does
not have (RESEARCH Pitfall 5).
