# Phase 35.1 Plan 04: Unattended-Mode Drill Summary

**The chain-flag mechanism works. The drill was run end-to-end against a real Claude agent. Auto-approval is blocked by a GSD orchestrator behavior (upstream #3370) that conflates `gate="blocking"` with `gate="blocking-human"` — a narrow edge case in practice because GSD's default `end-of-phase` mode suppresses the checkpoint tasks that trigger it.**

## Key Findings

### What works

DevFlow's chain-flag mechanism is confirmed working by four independent pieces of evidence from Arm A's capture:

1. `git status` showed `modified: .planning/config.json` with the false→true diff
2. `gsd_run query config-get workflow._auto_chain_active` returned `true`
3. The `--auto` token was present in the Code stage prompt
4. Config mtime confirms the set-then-restore cycle (touched during the run, 180s delta matches gate timeout)

### What doesn't

The GSD `execute-phase.md` orchestrator injects a `<critical_gate>` instruction into the executor subagent prompt that says `gate="blocking"` checkpoints must never auto-approve. This contradicts GSD's own gate semantics where `blocking` (not `blocking-human`) is the auto-approvable default. The executor follows this instruction over its own `<checkpoint_protocol>`, the checkpoint surfaces as a gate, and the run stalls.

Filed upstream: [open-gsd/gsd-core#3370](https://github.com/open-gsd/gsd-core/issues/3370).

### Practical impact

Narrow. GSD's default `human_verify_mode = end-of-phase` (#3309) suppresses `checkpoint:human-verify` tasks from plans. A normal unattended run never contains these tasks and never triggers the orchestrator's `<critical_gate>` injection. The drill fixture only hits this because its D-1 locked decision demands the checkpoint exist.

### Drill script measurement bugs found

Two bugs in the original drill script (from the stranded executor), both fixed in `51178b4`:

1. **Fixture `auto_mode: true`** — GSD's `checkpoint_handling` reads "chain flag OR user preference — same boolean." With `auto_mode: true`, the persistent preference alone caused auto-approval in BOTH arms, making the ephemeral chain flag — the thing under test — irrelevant.
2. **`reached_validate` in the comparison string** — A downstream consequence, not a checkpoint observation. Including it let the arms register as "different" for a reason unrelated to auto-approval, silencing the negative-control check on a run where both arms had auto-approved.

One additional bug found during post-run forensic analysis and NOT yet fixed:

3. **`captures_contain` false positives** — The drill greps agent capture files for "Auto-approved" and "CHECKPOINT REACHED," but these strings appear in GSD reference documentation (`ui-brand.md`, `execute-phase.md`) fed to every agent during the Plan stage. The matches are from documentation, not from actual auto-approval events. This caused FALSE `auto_approved=yes` reports on BOTH arms, including the supervise arm where auto-approval is impossible.

## Deviations from Plan

**1. [GSD upstream] The orchestrator blocks auto-approval of `gate="blocking"` checkpoints**

- **Found during:** Task 2, post-run forensic analysis
- **Issue:** The GSD `execute-phase.md` orchestrator injects `<critical_gate>` text telling the executor to never auto-approve `gate="blocking"` checkpoints, contradicting GSD's own rules where only `blocking-human` prevents auto-approval.
- **Impact:** ROADMAP criterion 1 (auto-approval) not established; criterion 1 fix-loop half not established; criterion 6 observation not produced; negative control did not discriminate.
- **Filed:** [open-gsd/gsd-core#3370](https://github.com/open-gsd/gsd-core/issues/3370)
- **Mitigation in this plan:** Documented the finding honestly rather than reshaping the fixture. The realistic unattended path is unimpeded because `end-of-phase` mode suppresses the checkpoint tasks that trigger this.

**2. [Infrastructure] Three drill attempts killed by Claude API rate limits**

- **Found during:** Task 2, all three execution attempts on 2026-08-12
- **Issue:** The first attempt (the one producing `35.1-DRILL.md`) completed but produced false positives. Two subsequent attempts (probes) were killed by `rate_limit_resume_scheduled` during the Define and Code stages respectively.
- **Impact:** Could not complete the probe to confirm that the default `end-of-phase` path works without D-1's checkpoint. Analysis is based on GSD source/docs rather than observation.

**3. [Drill script] Capture detection produces false positives from documentation**

- **Found during:** Task 2, post-run forensic analysis
- **Issue:** `captures_contain` matches "Auto-approved" and "CHECKPOINT REACHED" against GSD reference docs in agent context, not against actual auto-approval events.
- **Impact:** Self-reported `auto_approved=yes` on both arms, including the supervise arm. The drill's automated assertions are not trustworthy until this is fixed.
- **Not yet fixed.** Left as known debt for whoever re-runs the drill after GSD #3370 is resolved.

**Total deviations:** 3 (1 upstream, 1 infrastructure, 1 measurement bug in the drill). No scope creep beyond documenting all three honestly.
