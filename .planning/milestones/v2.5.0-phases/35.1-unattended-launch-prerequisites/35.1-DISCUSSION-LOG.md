## Chain-flag lifetime & leak repair

**Q: How should `_auto_chain_active` be guaranteed to end up false, given a Drop guard cannot survive SIGKILL?**

| Option | Description | Selected |
|--------|-------------|----------|
| Guard + repair-on-start | RAII guard on every in-process exit, AND force-clear on every start/resume. Two independent mechanisms. | ✓ |
| Repair-on-start only | Single code path; leaves the flag true on disk between a kill and the next start, which `commit_docs` can commit. | |
| RAII guard only | Smallest change, accepts that SIGKILL leaks — arguably fails criterion 2. | |

**Q: Which failure path must the test actually exercise?**

| Option | Description | Selected |
|--------|-------------|----------|
| Both kill and error | Separate tests per mechanism, so a regression in either is attributable. | ✓ |
| SIGKILL only | Harshest path only; a broken Drop guard would pass silently. | |
| Error path only | Cheapest, fully in-process; never demonstrates the committed-leak scenario. | |

**Q: When repair-on-start finds a stale `true`, should that be visible?**

| Option | Description | Selected |
|--------|-------------|----------|
| Event + stdout notice | Stale flag is evidence a prior run was killed; log it loudly. | ✓ |
| Event only, no stdout | Recoverable after the fact, invisible during a live run. | |
| Repair silently | A repeatedly-killed run would look identical to a healthy one. | |

**Notes:** Not discussed, offered and declined: whether the flag's window should wrap the whole
stage or only the agent launch, and how it interacts with a concurrent `devflow parallel` run
touching the same `config.json`. The latter is recorded as a deferred idea.

## Which stages get auto-mode

**Q: Criterion 1 names Code and the `--gaps-only` fix loop. Should the Plan stage also get checkpoint auto-approval?**

| Option | Description | Selected |
|--------|-------------|----------|
| Plan, Code, and gaps-only | Define is a no-op, so Plan is the first stallable stage; covering only Code leaves the earliest stall unfixed. | ✓ |
| Code and gaps-only only | Literal reading of criterion 1; run would still stall at Plan. | |
| Every stage in the pipeline | Simplest rule; hands checkpoint approval to Ship where a wrong answer is expensive. | |

**Q: How should the stage set be expressed in the code?**

| Option | Description | Selected |
|--------|-------------|----------|
| Named const stage set | Follows the existing `STREAM_JSON_STAGES` precedent; greppable policy. | ✓ |
| Per-stage match arm at the call site | No new constant, but policy becomes implicit in control flow. | |
| Config-driven, operator-settable | Speculative configurability; adds a way to silently disable the fix. | |

**Notes:** This choice widens the phase beyond criterion 1's literal wording. Flagged in CONTEXT.md
and as a deferred item for the roadmap text.

## Preflight refusal policy

**Q: How should the preflight treat a condition it cannot determine?**

| Option | Description | Selected |
|--------|-------------|----------|
| Unknown refuses too | Fail closed; report three states but refuse on anything not a definite pass. | ✓ |
| Unknown proceeds with a loud notice | A warning is read by nobody in an unattended run. | |
| Unknown refuses only in auto mode | A supervise rehearsal would not reproduce what an auto run does. | |

**Q: Which launches does the preflight gate?**

| Option | Description | Selected |
|--------|-------------|----------|
| Gate auto, report on supervise | One code path, two consequences; supervise keeps a cheap viability rehearsal. | ✓ |
| Gate every launch | Would block supervise runs that are fine with a human present. | |
| Auto only, silent on supervise | Removes the rehearsal path. | |

**Q: Should an operator be able to override a preflight refusal?**

| Option | Description | Selected |
|--------|-------------|----------|
| No override | Refusal is final; fix the condition or use supervise. | ✓ |
| `--force-unattended`, logged loudly | Matches the `--legacy-claude-launch` escape-hatch precedent. | |
| Env-var override only | Undiscoverable, and therefore unauditable. | |
