<objective>
Refuse an unattended launch, loudly and before any agent time is spent, when the conditions that make
it able to finish do not hold.

Purpose: this phase makes checkpoint auto-approval possible; it does not make it universal. Three
things can each silently defeat it — a config DevFlow cannot write, a launch shape with no process to
bound the flag's lifetime, and a plan carrying a checkpoint GSD will never auto-approve in any mode.
Each of those turns an overnight run into a stall discovered the next morning. D-07's answer is a
fail-closed probe: report per condition, refuse on anything that is not a definite pass, and warn on
nothing — a warning is read by nobody in an unattended run.

Output: `verify::phase_has_human_only_checkpoint`, `preflight_unattended_launch_check` with its
three-state per-condition report and mode-gated disposition, its line in `generic_preflight_checks`,
and three NOT-viable fixtures each demonstrated failing.
</objective>

**F-12 — the concrete condition list is DECIDED here (CONTEXT.md Claude's Discretion, item 2).**
Three conditions, chosen because each one, alone, is sufficient to make an unattended run stall, and
because each is observable rather than inferable:

| # | Condition | Why it is a prerequisite | Determinable at |
|---|---|---|---|
| C1 | The GSD config at the launch root exists, parses, and is a JSON object | DevFlow cannot set the chain flag in a file it cannot read or write, and `check auto-mode` reads nothing else | every stage |
| C2 | The Code stage would launch on the pipe-owning arm — Claude, no legacy opt-out | The chain-flag guard lives in a Rust process; the legacy arm is a detached shell script with no stack frame to hang a `Drop` on (RESEARCH Pitfall 4) | every stage |
| C3 | No plan for this phase declares a checkpoint GSD never auto-approves | Those two markers block in every mode, so their presence makes an unattended stall certain regardless of everything this phase builds (`checkpoints.md` rule 6) | only once plans exist |

Candidates considered and NOT included: "the agent binary resolves" is already covered by
`ensure_agent_binary`, which runs earlier and harder, and duplicating it would give two answers to
one question; "the network is up" is unobservable in advance and would be a predictor, not a probe.

**F-13 — RESEARCH.md Open Question 4 is DECIDED: `--yes-ship` does not interact with auto-mode, and
that non-interaction is pinned by a test.** `state.yes_ship` authorizes the Ship gate and nothing
else. Making it influence this preflight would turn a Ship authorization into a launch-prerequisite
bypass, which is D-09's prohibition arriving through a side door. The existing
`run_preflight_major_bump_gate_not_auto_approved_by_yes_ship` (`preflight.rs:1408`) is the precedent
and the shape to copy. A run that reaches Ship unattended and stalls there is a real gap, and it is
NOT this phase's — criteria 1 through 5 are all scoped to Code-stage and gaps-only checkpoints.

**F-14 — C3's match must be anchored to a task element, and this plan file is why.** GSD emits a
checkpoint task's markers as attributes on its own `<task ...>` opening tag. A plain substring scan
over `*-PLAN.md` — which is what the existing `phase_has_blocking_human_checkpoint`
(`verify.rs:131`) does — also matches a plan that merely *discusses* the marker in prose. This very
plan file discusses both markers, so a plain scan run against DevFlow's own repository for phase 35.1
would report this phase NOT viable for reasons that do not exist. Anchor the match: the marker must
appear on a line that also opens a task element. Leave `phase_has_blocking_human_checkpoint`
untouched — it has a different caller (the 28-03 auto-decide route) and seven existing tests, and
widening it is not this phase's business.

**F-15 — what "refuses" actually means here, stated rather than assumed.** This check plugs into
`generic_preflight_checks`, so a refusal takes the framework's existing disposition: the agent is
never spawned (`run_preflight` returns `Ok(false)` and `launch_stage` returns without reaching
`launch_stage_inner`), and the run parks at a named preflight gate + notify, bounded by
`state.preflight_retries` / `MAX_PREFLIGHT_RETRIES`, after which it aborts with a logged
`preflight_retry_ceiling_reached`. It is NOT a process exit. That is the correct fail-closed answer —
a run that cannot proceed unattended should summon a human rather than push on — but it means the
unattended run stops and waits, and the plan says so out loud instead of implying a clean exit.
Phase 17's own decision 15 — a different decision namespace from this phase's D-01..D-11 — forbids a
hard exit from this framework, and this check does not get an exception.

**F-16 — where the report is actually seen.** `run_preflight` runs from `launch_stage`, which runs in
the operator's own `devflow start` process for the FIRST stage and in the detached `__monitor`
process for every later one. So the Define-stage report prints to the operator's terminal — which is
what makes D-08's supervise-mode rehearsal useful — and the Code-stage report prints to the monitor
log. Note this in the check's doc comment so nobody later "fixes" a report they could not find.
