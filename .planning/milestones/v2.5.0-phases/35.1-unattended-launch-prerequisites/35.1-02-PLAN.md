<objective>
Close the leak the in-process guard structurally cannot: a SIGKILL between `engage` and `Drop`.

Purpose: `Drop` covers normal return, `?` and panic-unwind, and nothing else. A killed monitor leaves
`_auto_chain_active: true` in a **tracked** file that `commit_docs` and any sweeping `git add` can
carry into a commit, onto `develop`, and into the next phase's `plan-phase` invocation — where the
same flag no longer means "bypass a checkpoint" but "chain into execute-phase"
(`plan-phase.md:1564`, G-01/G-03). D-01 answers with a second, independent mechanism: a force-clear
on every `devflow start` and `devflow resume`, repairing forward rather than carrying the leak.

Output: `gsd_config::force_clear_auto_chain` with a reported outcome, both entry points wired to it,
D-03's stdout notice and `events.jsonl` event, and D-02's kill-path regression test — built on a
demonstrated leak, not an assumed one.
</objective>

<planner_findings>
**F-7 — the committed-tree repair is detected by diffing against HEAD, not by parsing HEAD's copy.**
After the working-tree value is corrected, `git diff --quiet HEAD -- .planning/config.json` answers
"does the branch tip still disagree with the corrected file?" in one call, and it answers it
correctly in both directions that matter: a working tree that was already clear but a HEAD that
carries the leak still shows a difference and still gets committed. Parsing `git show
HEAD:.planning/config.json` would work too but adds a second parser for the same fact.

**F-8 — the commit is refused, loudly, when the file carries changes beyond the flag.** A
path-scoped `commit_path` still commits whatever else is dirty *in that path*. This repository has
already had an incident where an in-progress evidence file was swept into an unrelated commit
(`CLAUDE.md`), and the correct posture is to refuse rather than to sweep. Compare HEAD's parsed copy
against the corrected working copy with `workflow._auto_chain_active` removed from both: if the
remainder differs, do not commit — clear the working tree, set `commit_refused` with a reason, print
it, and put it in the event. The working-tree clear alone already disarms the bypass for THIS run;
what is deferred is only the branch-tip repair, and deferring it visibly is strictly better than
committing an operator's unfinished edit.

**F-9 — a commit failure is a loud warning, not a run-killer.** Hooks, a detached HEAD, an
unexpected git state: any of these can make `commit_path` fail. The run must not die for it — the
working tree is already repaired, so the bypass is already off. Emit the failure into the event and
print it. Recorded here so the executor does not "harden" this into a `?`.

**F-10 — `start`'s repair targets the worktree, and must run AFTER the worktree exists.** `start`
creates the worktree at `commands.rs:328-334` and only then knows the launch root. The repair
therefore goes after that block and before the first `workflow::save_state` (`commands.rs:459`),
matching the file's own "combine before the first `save_state`" idiom
(`commands.rs:234-245`). A freshly forked worktree inherits whatever `develop` carries, so this
placement is what catches a leak that already reached the base branch.

**F-11 — the root resolution must agree across four sites, or the repair and the guard will write to
different files.** Verified at plan time: `spawn_monitor` computes `--workdir` as
`state.worktree_path.as_deref().unwrap_or(&state.project_root)` (`monitor.rs:317-321`), and
`run_monitor` receives exactly that. `start` and `resume` must resolve the same way, and `35.1-03`'s
preflight must too. Use the existing `state.worktree_path.as_deref().unwrap_or(project_root)` idiom
(the same one at `pipeline_launch.rs:1069` and `preflight.rs:733`); do not introduce a second
spelling.
</planner_findings>
