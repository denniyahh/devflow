## User Constraints (from CONTEXT.md)

### Locked Decisions

**Chain-flag lifetime and leak repair**

- **D-01:** `_auto_chain_active` is cleared by two independent mechanisms: an RAII guard that fires
  on every in-process exit (normal, error, panic-unwind), and a force-clear on every `devflow start`
  / `devflow resume` before launching. A SIGKILL between them is repaired by the next run rather
  than carried forward. The guard alone was rejected: it cannot survive SIGKILL, and a leaked `true`
  is exactly the committed-and-fires-next-phase failure criterion 2 names. Two review additions:
  (1) the repair must reach the *committed* tree, not only the working tree (`devflow resume`
  continues a killed run, so a leak can propagate branch → merge → `develop`); (2) the happy path
  leaks too and leaves the tree dirty for the whole Code stage duration — a sweeping `git add -A`
  could sweep the `true` into a commit (already happened once, per `CLAUDE.md`), and `git reset
  --hard` restores a committed `true`. The claim that GSD auto-commits `config.json` via
  `commit_docs` was checked and does not hold — the risk is a sweeping `git add`, not an automatic
  GSD commit.
- **D-02:** Regression tests must exercise both failure paths as SEPARATE cases — one SIGKILLs the
  process mid-stage and asserts the next start clears the stale flag, one forces an in-stage error
  and asserts the guard cleared it. A single combined test was rejected — a regression in either
  mechanism must be attributable, not masked by the other.
- **D-03:** A repaired stale flag is not silent: emit an event to `.devflow/events.jsonl` and print
  a notice on stdout. A stale flag is evidence a prior run was killed; repairing it quietly discards
  that signal.

**Auto-mode stage set**

- **D-04 (REVISED 2026-08-07 after adversarial review):** Checkpoint auto-approval covers the Code
  stage and the `--gaps-only` fix loop ONLY. The Plan stage is EXCLUDED — reversed from the original
  decision after both external review lanes and an independent source trace agreed it is
  unimplementable: the flag that enables checkpoint auto-approval at Plan is the SAME flag that
  makes plan-phase chain into execute-phase (`check-command-router.cjs:107`:
  `active: autoChainActive || autoAdvance` — no third key for "bypass without chaining";
  `plan-phase.md:1564` chains via `Skill(skill="gsd-execute-phase", ...)` when `AUTO_CHAIN`/`AUTO_CFG`
  is true; `plan-phase.md:540`/`:555` — the same flag selects the branch that evaluates blocking
  gates; G-03 blocks clearing the flag after launch, because the decision at `:1564` reads the value
  loaded into INIT at step 1, before the clear at `:1547`; `plan-phase.md:1560` blocks passing
  `--auto`, which SETS the flag to true). **Known limitation, stated plainly, not papered over:** an
  unattended run can still stall at a Plan-stage checkpoint — closing it needs an upstream GSD
  change splitting `_auto_chain_active` into separate bypass/chaining flags (tracked upstream as
  G-01); the operator declined to make that a dependency of 35.1.
- **D-05:** The stage set is a named constant consulted by the launch path, following the
  `STREAM_JSON_STAGES` precedent (`pipeline_launch.rs:541`). One greppable place to read and change
  it — an inline per-stage match or config-driven toggle were both rejected. **Required doc
  comment:** the `STREAM_JSON_STAGES` analogy is imperfect and must say so — that constant's five
  stages have no upstream side effects, whereas THIS constant's flag has different upstream effects
  per stage (harmless at Code, chaining at Plan) — without the note, a future contributor could
  "complete" it by adding `Stage::Plan` and silently reintroduce the D-04 defect.
- **D-06:** This is checkpoint approval ONLY. `workflow.auto_advance` is still NOT set persistently
  (criterion 3, upstream G-01) — stage-chaining stays banned. Corrected framing: `_auto_chain_active`
  is safe to set for Code because execute-phase does not chain from it; unsafe for Plan because
  plan-phase does — the separation is per-stage behaviour, not per-flag.

**Preflight refusal policy**

- **D-07:** The preflight reports three distinct per-condition states — holds / does not hold /
  could not determine — and refuses on anything that is not a definite pass. Fail closed. Applies
  the 999.86 lesson (a predictor that guessed rather than probed false-negatived twice) and the
  "unreachable ≠ absent" rule. Warn-and-proceed was rejected: a warning is read by nobody in an
  unattended run.
- **D-08:** The preflight gates `--mode auto` and reports on `--mode supervise`. One code path, two
  consequences: refusal only where prerequisites actually matter, but the per-condition report still
  prints in supervise so an operator can rehearse viability. Gating every launch was rejected — it
  would block supervise runs that are fine with a human answering checkpoints.
- **D-09:** No override. No `--force-unattended` flag, no environment variable. A refusal is final;
  fix the condition or launch in supervise. Reversibility: costly — removing an override after
  operators build habits around it is not easy, and the standing principle is that DevFlow advances
  as far as the rules permit and stops at the first hard gate. The `--legacy-claude-launch`
  loudly-logged-escape-hatch precedent was considered and explicitly declined here. **Objection on
  record from both review lanes; the decision stands** — recorded so the planner does not silently
  "fix" this by adding the override the operator declined.

**The simulated unattended run**

- **D-10:** Criterion 5's run drives a throwaway fixture project with one trivial plan carrying one
  real GSD `blocking` checkpoint, launched against a real Claude agent. Three review-added
  constraints: (1) the fixture must actually enter the `--gaps-only` fix loop — a plan that passes
  Validate on the first try never exercises it; (2) the fixture needs a negative control — run with
  the flag NOT set and require the checkpoint to actually block; (3) it does not establish DevFlow's
  own flag management — a pre-baked config proves GSD auto-approves when the flag is true, not that
  DevFlow sets/clears it at the right moments (D-01/D-02 need their own coverage).
- **D-11:** The fixture is pre-baked through CONTEXT.md; Plan and Code run live, since criterion 5
  names Plan → Code as the seam. Pre-baking the plans was rejected (skips Plan, the first stallable
  stage per D-04). Running from Define was rejected as exercising nothing new.

## Summary

This phase closes a specific, narrow gap: DevFlow spawns a Claude agent running GSD slash commands,
but never touches `.planning/config.json`, so GSD's own `workflow._auto_chain_active` /
`workflow.auto_advance` flags — the ONLY signal `execute-phase.md`'s checkpoint handling consults to
decide whether to auto-approve an ordinary `gate="blocking"` checkpoint — stay `false` for every
DevFlow-driven run. An unattended Code-stage run that hits a checkpoint therefore stalls forever.
D-01 through D-09 already settle *what* to build; this research settles *where in the existing
source it plugs in* and surfaces two mechanics the discussion did not resolve that will silently
defeat the feature if the planner doesn't account for them:

1. **The prompt text itself must carry `--auto`.** `execute-phase.md`'s own "sync chain flag with
   intent" step unconditionally clears `workflow._auto_chain_active` to `false` at the start of
   every run whose `$ARGUMENTS` lacks `--auto`/`--chain` — and DevFlow's current Code-stage prompt
   (`"/gsd-execute-phase {N}"`, no flags) is exactly that shape. Setting the flag in
   `.planning/config.json` before spawning the agent, without also changing the prompt string, would
   have the flag wiped out before `checkpoint_handling` ever reads it. This is the single most
   important, easy-to-miss finding in this research — see Pitfall 1.
2. **The RAII guard belongs in the detached `__monitor` process, not in the CLI-invocation
   function.** `devflow start`/`resume` return to the shell almost immediately after spawning a
   detached `__monitor` subprocess (or, on the Legacy launch arm, a detached `sh` script); the
   actual Claude agent — the process whose checkpoint-handling actually needs the flag true — runs
   for the run's full duration under that detached process, not under the CLI invocation. A guard
   scoped to `launch_stage_inner`/`spawn_agent_and_record` would clear the flag milliseconds after
   setting it. See Pitfall 2 and the Architecture Patterns section.

Because gaps-only loop-backs dispatch through the identical `state.stage == Stage::Code` value (a
different prompt, `FixType::GapsOnly`, not a different `Stage` enum variant — `stage.rs` has no
"gaps-only" stage), D-05's "named stage-set constant" most likely collapses to a single-element
list, `&[Stage::Code]`, rather than a multi-stage table — worth confirming at plan time rather than
over-building a lookup structure for stages that will never be added to it (D-04's own doc-comment
requirement already forbids a future contributor "completing" it toward Plan).

`.planning/config.json` is genuinely virgin surface for DevFlow: a full-repo grep across `crates/`
found zero reads, writes, or `gsd-tools` invocations touching it or GSD's config at all — DevFlow's
own config lives in a separate file (`devflow.toml`, TOML) with no code path in common. The planner
should treat the read/patch/write path as new code, and should reuse the one existing precedent in
this codebase for editing a JSON file this way — `workflow::save_state`'s atomic
temp-write-then-rename idiom — plus serde_json's `preserve_order` feature (not currently enabled in
this workspace), because without it a `serde_json::Value` round-trip through `.planning/config.json`
re-sorts every top-level and nested key alphabetically on write, turning every DevFlow-driven run
into a full-file diff on a tracked, committed file.

**Primary recommendation:** implement the chain-flag lifecycle as a small new module
(e.g. `gsd_config.rs`) with a single `set_auto_chain_active(path, bool) -> io::Result<()>` function
built on `serde_json::Value` (with `preserve_order` enabled) plus the existing
`write_state_atomic`-style temp+rename; wrap its "set true" call and the flag's "set false" call in
an RAII guard that lives inside `run_monitor`/`run_pipe_owning_monitor`'s call span (not inside
`launch_stage_inner`); append `--auto` to the Code-stage prompt strings (`FixType::FullExecute`,
`FixType::GapsOnly`, and the plain `Stage::Code` prompt) so GSD's own sync-clear step does not
immediately undo DevFlow's write; and add the new preflight check to the existing
`generic_preflight_checks` framework in `preflight.rs`, gated by `state.mode` per D-08.

```
        │  (refuse loudly if --mode auto and a condition is not a definite pass)
        ▼

        ▼

        │
        ▼  (new process, own lifetime — THIS is where the RAII guard belongs)
[pipeline_launch::run_monitor]
        │  1. set workflow._auto_chain_active = true  in the WORKTREE's .planning/config.json
        │  2. run_pipe_owning_monitor(...) — owns the Claude child's stdin/stdout for the
        │     ENTIRE stage duration, delivers the prompt "/gsd-execute-phase {N} --auto"
        │        │
        │        ▼
        │     [Claude process, cwd = worktree] executes GSD's execute-phase.md skill
        │        │  Step: "sync chain flag with intent" —
        │        │    if $ARGUMENTS lacks --auto/--chain: clear _auto_chain_active
        │        │    (the --auto token in the prompt is what SKIPS this clear)
        │        │  ...waves run...
        │        │  Step: checkpoint_handling —
        │        │    AUTO_MODE = check auto-mode --pick active   (reads the SAME config.json)
        │        │    if a task returns gate="blocking": auto-approve (unless blocking-human)
        │        ▼
        │     Claude exits, prints DEVFLOW_RESULT: {...}
        │  3. RAII guard fires here (Ok or Err from run_pipe_owning_monitor) — sets flag false
        ▼
advance(project_root, phase)   — state machine transition, may loop back to Code with
                                  FixType::GapsOnly ⇒ same Stage::Code, prompt carries
                                  "--gaps-only --auto"
```

**Where the SIGKILL gap sits:** if `devflow __monitor` itself is SIGKILLed (or its host OS-killed),
the RAII guard never runs — the flag stays `true` in the worktree's `.planning/config.json`, which
is a *tracked* file. The next `devflow resume` for that phase (same worktree, same branch) is where
D-01's force-clear must run, before any config read.

### Pattern 1: RAII env/state guard, restore-on-drop

**What:** this codebase already has three instances of exactly the shape D-01 asks for — a struct
that mutates process/global state in `::set`, and unconditionally restores it in `impl Drop`, so a
normal return, an early `?`, or an unwinding panic all restore it identically.
**When to use:** exactly D-01's "RAII guard that fires on every in-process exit."
**Example (existing precedent, not hypothetical):**
```rust
// Source: crates/devflow-cli/src/pipeline_launch.rs:2679-2700 (test-only today,
// but the exact shape D-01 asks for — restore-on-Drop, no clear() call needed at
// the use site)
struct LegacyEnvOverride(Option<std::ffi::OsString>);

impl LegacyEnvOverride {
    fn set(value: &str) -> Self {
        let prior = std::env::var_os("DEVFLOW_CLAUDE_LEGACY_LAUNCH");
        unsafe { std::env::set_var("DEVFLOW_CLAUDE_LEGACY_LAUNCH", value) };
        Self(prior)
    }
}

impl Drop for LegacyEnvOverride {
    fn drop(&mut self) {
        unsafe {
            match self.0.take() {
                Some(prior) => std::env::set_var("DEVFLOW_CLAUDE_LEGACY_LAUNCH", prior),
                None => std::env::remove_var("DEVFLOW_CLAUDE_LEGACY_LAUNCH"),
            }
        }
    }
}
```
`[VERIFIED: crates/devflow-cli/src/pipeline_launch.rs:2679-2700]` — read this session, quoted
verbatim above. Note: Rust runs `Drop` on an unwinding panic by default (this workspace sets no
`panic = "abort"` in any `Cargo.toml` checked this session), so a guard of this shape does cover
D-01's "error, panic-unwind" cases; it cannot and does not cover SIGKILL, which is why D-01 also
requires the independent force-clear.

### Pattern 2: Atomic file write (temp + rename)

**What:** write to a sibling `.tmp` path, then `rename()` — the rename is atomic on the same
filesystem, so a reader never observes a partially-written file, and a process killed mid-write
leaves the original file untouched (the new content is lost, not the old content corrupted).
**When to use:** every write to `.planning/config.json` — this file is read by whatever GSD skill
step runs next inside the live Claude process, so a torn write is a real risk during the run.
**Example (existing precedent to extend, not copy verbatim — the new code writes into a JSON file
GSD itself also writes to, so it must preserve every other key, not construct a fresh `State`):**
```rust
// Source: crates/devflow-core/src/workflow.rs:174-193
pub fn save_state(state: &State) -> Result<(), WorkflowError> {
    let path = state_path(&state.project_root, state.phase);
    let contents = serde_json::to_string_pretty(state)?;
    write_state_atomic(&path, &contents)?;
    Ok(())
}

fn write_state_atomic(path: &Path, contents: &str) -> Result<(), WorkflowError> {
    if let Some(parent) = path.parent() {
        ensure_devflow_dir(parent)?;
    }
    let tmp = path.with_extension("tmp");
    std::fs::write(&tmp, contents)?;
    std::fs::rename(&tmp, path)?;
    Ok(())
}
```
`[VERIFIED: crates/devflow-core/src/workflow.rs:174-193]` — read this session, quoted verbatim.
The new `.planning/config.json` writer should follow the same `tmp` + `rename` shape but parse the
existing file into `serde_json::Value` first (so unrelated keys survive byte-for-byte structurally),
mutate only `workflow._auto_chain_active`, and re-serialize — see Don't Hand-Roll for the ordering
pitfall this introduces.

### Anti-Patterns to Avoid

- **Scoping the RAII guard to `launch_stage_inner`/`spawn_agent_and_record`:** these functions
  return as soon as the detached monitor is spawned — before the agent has run at all. A guard here
  clears the flag almost immediately. (See Pitfall 2.)
- **Setting the flag without changing the prompt string:** `execute-phase.md`'s sync-clear step
  fires whenever `$ARGUMENTS` lacks `--auto`/`--chain`, independent of what's in config.json when
  the step runs. (See Pitfall 1.)
- **Widening the stage-set constant "for completeness" to include `Stage::Plan`:** this is the
  exact defect D-04 spent an adversarial-review round establishing is unimplementable — setting the
  flag for Plan makes `plan-phase.md` chain into `execute-phase.md` (`plan-phase.md:1564`), because
  GSD has only one flag for both "bypass checkpoint" and "chain to next stage." D-05's own required
  doc comment exists specifically to stop a future contributor from doing this.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Edit one nested key in a JSON file while leaving every other key's value AND relative order untouched | A custom regex/string patch on the raw file text | `serde_json::Value` parse → mutate → re-serialize, with the crate's `preserve_order` Cargo feature enabled | Without `preserve_order`, `serde_json::Map` is backed by a `BTreeMap` and serializes keys alphabetically — confirmed this session: `Cargo.lock` pins `serde_json 1.0.150` with dependencies `itoa, memchr, ...` and no `indexmap`, i.e. the feature is currently OFF workspace-wide `[VERIFIED: Cargo.lock:431-437]`. A round-trip today would silently re-sort `.planning/config.json`'s top-level keys (`commit_docs, workflow, git, intel, review, model_overrides, mempalace` → alphabetical) on every single DevFlow-driven run, producing a large diff on a tracked, committed file every time. A hand-rolled string patch avoids the reorder but re-implements JSON-adjacent parsing for a problem the ecosystem already solved with one Cargo feature flag. |
| Detecting "did the process crash mid-write" for a file also written to by an independent tool (GSD) | A custom lockfile / mtime-heuristic around `.planning/config.json` | The existing atomic temp+rename idiom (`write_state_atomic`) | Already proven in this codebase for exactly this failure mode (`.devflow/state-{NN}.json`); GSD's own `config-set` presumably does something similar on its own writes, so DevFlow's write should be equally torn-write-safe without inventing new coordination |
| A 3-state (holds / does-not-hold / could-not-determine) precondition report that also needs to gate one mode and merely report in another | A parallel, bespoke gate mechanism next to `preflight.rs` | Extend `generic_preflight_checks`/`run_preflight`'s existing `Result<(), String>` aggregation shape, with the new check internally deciding Ok/Err based on `state.mode` (D-08) | The framework already solves "refuse loudly, aggregate every reason, dispatch through the same never-silent gate+notify path" for three other checks (`preflight_major_bump_check`, `preflight_interactivity_check`, `preflight_gh_auth_check`) at `crates/devflow-cli/src/preflight.rs:610-886` `[VERIFIED: crates/devflow-cli/src/preflight.rs:610-886]` (see Code Examples) — a parallel mechanism would duplicate the retry-ceiling handling, the `Advance`-skips-re-check reasoning, and the `truncate_reason` sanitization already proven correct there |

**Key insight:** every piece of machinery this phase needs already has a same-file precedent in
this codebase (RAII guard, atomic write, aggregating preflight check) — the work is composition and
correct placement, not new mechanism design. The one place a genuinely new library feature is
needed (`preserve_order`) is a one-line Cargo.toml change, not new code.

## Common Pitfalls

### Pitfall 1: Setting the config flag without adding `--auto` to the prompt undoes itself
**What goes wrong:** DevFlow writes `workflow._auto_chain_active: true`, spawns the Claude agent
with the unmodified prompt `"/gsd-execute-phase {N}"`, and the checkpoint still stalls.
**Why it happens:** `execute-phase.md` runs this exact bash block near the top of every invocation,
before any checkpoint is ever reached:
```bash
# REQUIRED: prevents stale auto-chain from previous --auto runs
if [[ ! "$ARGUMENTS" =~ --auto ]]; then
  gsd_run query config-set workflow._auto_chain_active false || true
fi
```
`[VERIFIED: ~/.claude/gsd-core/workflows/execute-phase.md:161-165]` — read this session, quoted
verbatim. `$ARGUMENTS` here is GSD's name for the text after `/gsd-execute-phase {N}` in the prompt
DevFlow constructs. DevFlow's current prompt templates for the Code stage carry no such flag —
confirmed this session at `crates/devflow-core/src/prompt.rs:299-304`
(`FixType::GapsOnly => format!("/gsd-execute-phase {phase} --gaps-only")`,
`FixType::FullExecute => format!("/gsd-execute-phase {phase}")`) and at
`crates/devflow-core/src/stage.rs:60-68` (`Stage::Code => "/gsd-execute-phase {N}"`)
`[VERIFIED: crates/devflow-core/src/prompt.rs:299-304, crates/devflow-core/src/stage.rs:60-68]`.
**How to avoid:** the Code-stage prompt(s) DevFlow builds — the plain stage prompt AND both
`fix_prompt` arms that route through Code (`FullExecute`, `GapsOnly`) — must include `--auto` in the
command string, e.g. `"/gsd-execute-phase {N} --auto"` / `"/gsd-execute-phase {N} --gaps-only --auto"`.
Flag order does not matter — GSD's phase-argument parsing extracts any `--`-prefixed token from
`$ARGUMENTS` independent of position `[CITED: ~/.claude/gsd-core/references/phase-argument-parsing.md]`.
The Plan-stage prompt (`idempotent_stage_prompt`) must NOT receive this change — that is exactly
what D-04 forbids.
**Warning signs:** a live drill (criterion 5) where the checkpoint still stalls even though
`.planning/config.json` shows `_auto_chain_active: true` was written moments before launch — check
`.devflow/` capture logs for whether the sync-clear step ran and flipped it back to `false` before
`checkpoint_handling`.

### Pitfall 2: The RAII guard's scope must match the detached monitor's lifetime, not the CLI call's
**What goes wrong:** a guard placed around the code that calls `monitor::spawn_monitor` clears the
flag right after the detached process is forked — while the actual agent (and the checkpoint it
might hit) is still minutes or hours from running.
**Why it happens:** `spawn_monitor`/`spawn_agent_and_record` return as soon as the detached
`devflow __monitor` (or, on the Legacy arm, a detached `sh` script) is forked; the calling
`devflow start`/`resume` process then prints `"...monitor will auto-advance"` and exits
`[VERIFIED: crates/devflow-cli/src/commands.rs:472-476, crates/devflow-cli/src/pipeline_launch.rs:696-723]`.
The Claude subprocess that actually evaluates the checkpoint runs under the DETACHED monitor's
supervision (`run_pipe_owning_monitor`, `crates/devflow-cli/src/pipeline_launch.rs:594-627`), a
separate OS process spawned via `.arg("__monitor")`
`[VERIFIED: crates/devflow-core/src/monitor.rs:385, crates/devflow-cli/src/main.rs:134-135,561-568]`.
**How to avoid:** place the set/clear pair inside `run_monitor`
(`crates/devflow-cli/src/pipeline_launch.rs:594-627`), wrapping the call to
`monitor::run_pipe_owning_monitor`, so the guard's `Drop` fires only when that call returns — Ok or
Err — which is genuinely the end of the Code-stage agent's run.
**Warning signs:** a test that asserts the flag is `true` immediately after `devflow start` returns
would pass even with the bug present — the bug only shows up if the assertion checks the flag
*while the agent is still running* or the checkpoint fixture actually blocks despite the flag having
been "set."

### Pitfall 3: The `dirty` field on `workflow_started` is unrelated to the working-tree dirtiness this decision worries about
**What goes wrong:** treating D-01's "`workflow_started` records a `dirty` field... a self-inflicted
dirty tree may interact with DevFlow's staleness checks" as meaning an uncommitted
`.planning/config.json` edit could trip DevFlow's own build-staleness gate.
**Why it's not what it looks like:** the `dirty` field in that event payload is
`env!("DEVFLOW_BUILD_DIRTY")` — a **compile-time** value baked in by `build.rs`, recording whether
the *devflow binary itself* was built from a dirty source tree, not the live runtime working tree
`[VERIFIED: crates/devflow-cli/src/commands.rs:488-503, crates/devflow-cli/build.rs:18,69]`. The
actual runtime dirty-tree check that could theoretically interact is
`enforce_build_staleness`/`tree_has_modified_build_inputs`, and it only inspects `git status
--porcelain` for paths matching a fixed, narrow list:
```rust
// Source: crates/devflow-cli/src/staleness.rs:183-194
fn affects_compiled_binary(rel_path: &str) -> bool {
    const BUILD_AFFECTING_FILES: [&str; 4] = [
        "Cargo.toml",
        "Cargo.lock",
        "build.rs",
        "rust-toolchain.toml",
    ];
    rel_path.ends_with(".rs")
        || BUILD_AFFECTING_FILES
            .iter()
            .any(|name| rel_path == *name || rel_path.ends_with(&format!("/{name}")))
}
```
`[VERIFIED: crates/devflow-cli/src/staleness.rs:183-194]` — read this session, quoted verbatim.
`.planning/config.json` matches none of these patterns, so a dirty `.planning/config.json` alone
will never trip this gate, on any run — this repo or any other.
**How to avoid:** don't spend plan effort defending against a staleness-gate interaction that
source shows cannot occur. The REAL risks CONTEXT.md's own D-01 "Scope note" already narrows this
to remain live: a sweeping `git add -A`/`git add .` catching the leaked `true` (this repo has
already had exactly that incident, per `CLAUDE.md`), and `git reset --hard` restoring an
already-committed `true`. Design the force-clear and RAII guard against those two, not against
`enforce_build_staleness`.
**Warning signs:** none directly observable — this is a design-time correction, not a runtime
symptom to detect.

### Pitfall 4: The Legacy monitor launch arm has no Rust process to hang an RAII guard on
**What goes wrong:** the RAII-guard design (Pattern 1) assumes a Rust process supervises the agent
for the flag's true-window. That's accurate for Claude at the Code stage today (Code is in
`STREAM_JSON_STAGES`, so `claude_stream_launch_enabled` selects `MonitorLaunch::PipeOwning`
`[VERIFIED: crates/devflow-cli/src/pipeline_launch.rs:541-547,579-581]`), but the codebase also has
a `MonitorLaunch::Legacy` arm — "the pre-31 detached `sh` script: stdin is `/dev/null`... the script
waits on the agent then runs `devflow advance`. Every non-Claude adapter, every stage not yet
widened... and the checkpoint-resume relaunch all run through here"
`[VERIFIED: crates/devflow-core/src/monitor.rs:244-249]`, and it is still reachable for Code via
`DEVFLOW_CLAUDE_LEGACY_LAUNCH`/`--legacy-claude-launch` or a non-Claude agent.
**Why it happens:** a `Drop` guard can only exist inside a Rust process's stack frame; a detached
shell script has no equivalent unless the generated script text itself sets/traps the flag (e.g. a
`trap ... EXIT` clause), which is far more fragile than Rust `Drop` and does not survive SIGKILL any
better than the Rust guard does.
**How to avoid:** D-10's own fixture is explicitly "launched against a real Claude agent," and this
phase's canonical scope (per CONTEXT.md) is the Claude/PipeOwning path. The planner should either
(a) explicitly scope D-01's guard to the PipeOwning arm and document the Legacy arm as an accepted
gap (the force-clear on `start`/`resume` still repairs a Legacy-arm leak, just later), or (b)
extend the Legacy arm's generated shell command to set/clear the flag too. Either is legitimate; not
deciding is the failure mode — silently assuming the guard "just works" for both arms would leave
`--legacy-claude-launch` (already a documented, loudly-logged escape hatch this project keeps
alive) as an unattended-mode-breaking combination nobody tested.
**Warning signs:** a live drill run with `DEVFLOW_CLAUDE_LEGACY_LAUNCH` set, or with a non-Claude
agent, still stalls at a checkpoint despite the feature otherwise working for Claude.

### Pitfall 5: Gaps-only and full-execute are the same `Stage`, not two stages
**What goes wrong:** building D-05's "named stage-set constant" as a lookup table keyed by
something richer than `Stage` (e.g. `(Stage, FixType)` pairs) in anticipation of gaps-only needing
separate treatment.
**Why it's unnecessary:** the Validate→Code loop-back function is literally named
`loop_back_to_code`, and `select_loop_back_fix` returns a `FixType` (`GapsOnly` or `FullExecute`)
that only changes the PROMPT TEXT dispatched at the SAME `state.stage == Stage::Code`
`[VERIFIED: crates/devflow-cli/src/pipeline_outcomes.rs:317-395]` (`fn select_loop_back_fix(...)
-> FixType`, function body sets `state.last_verification_fingerprint`/`...mtime_nanos` and returns
`FixType::GapsOnly` or `FixType::FullExecute` — no `Stage` value is touched). `stage.rs`'s `Stage`
enum has exactly five variants (`Define, Plan, Code, Validate, Ship`) and no gaps-only variant
`[VERIFIED: crates/devflow-core/src/stage.rs:14-27]`.
**How to avoid:** confirm at plan time whether the stage-set constant genuinely needs to be a list
(future-proofing for a stage this decision explicitly forbids adding) or can be a single
`Stage::Code` check — either is defensible, but building elaborate structure around a
single-element set is over-engineering the "named constant" D-05 actually asked for.
**Warning signs:** none at runtime — this is a design-review-time check on the diff's shape.

1. **Does the chain-flag mechanism need to be conditioned on `state.mode == Mode::Auto`?**
   - **RESOLVED — yes.** `35.1-01-PLAN.md` § F-1: the chain flag is engaged only when
     `state.mode == Mode::Auto`, following `preflight_interactivity_check`'s existing precedent. The
     `--auto` prompt token is deliberately NOT mode-gated (§ F-2) — it cannot enable bypass on its
     own, since `check auto-mode` reads only `.planning/config.json`.

     phase's stated goal ("`devflow start --mode auto` can actually complete... with no human

     auto` runs specifically.
   - What's unclear: CONTEXT.md's D-01–D-06 never states this gating condition in so many words —
     they describe *when in the run* (Code stage, gaps-only loop) but not *which DevFlow `--mode`*.
   - Recommendation: raise with the operator before planning proceeds; this changes where the
     `state.mode` check sits in the new code (inside `run_monitor`'s guard-entry condition, most
     likely) and is exactly the kind of ambiguity CONTEXT.md's own decisions did not resolve.
