## Planner decision record

CONTEXT.md left the fixture prompt text and n to the planner. These are resolved here; the tasks
implement them.

### P-01 — One drill, two prompt variants, separate attribution (resolves "exact prompt text")

A single combined prompt that asks for both a sub-agent AND a backgrounded shell in one run makes
attribution ambiguous — an emitted `task_started` could belong to either mechanism. Instead the
drill carries **two prompt variants**, one per path, so each capture's events are attributable by
construction:

- **Variant A (sub-agent dispatch):** the prompt instructs the agent to delegate a small,
  concrete piece of work to a sub-agent (Task/Agent tool) and report the result. Expected
  families if 47ea511's capture generalises: `task_started` → `task_progress`* →
  `task_notification`/`task_updated` (terminal), and **no** `background_tasks_changed`.
- **Variant B (backgrounded shell):** the prompt instructs the agent to launch a long-running
  shell command **in the background** (`run_in_background: true`) and continue. Expected outcome
  is *unknown by construction* — this is the phase's open question. The capture must record
  whether any tool event actually carries `run_in_background: true`, and what families (if any)
  follow.

Each variant runs at **n=2** (D-01's "aim n≥2 per path where run cost permits"; two runs is the
minimum that lets a count be called "repeated", and this phase's honesty bar accepts n=2 as the
stated sample size — criterion 4 requires stating it, not inflating it).

### P-02 — The positive control is `task_started` on Variant A (resolves "real zero vs broken probe")

Variant A is known-good territory: 47ea511's capture and 34-evidence both show a sub-agent
dispatch emits `task_started`. So Variant A's own `task_started` count is the positive control —
if a Variant A capture shows zero `task_started`, the probe is broken (prompt not honored, wrong
argv), not the world. Variant B has no known-good family; its zeros are only interpretable because
Variant A in the same drill run demonstrates the counting path works.

### P-03 — What this plan does NOT establish

- It establishes the **synthetic** event-family mapping. Whether that mapping matches production
  is plan 35.3-02's question (D-01's caveat is load-bearing).
- It does not answer criterion 2 ("does the gate see real concurrency") — that answer needs the
  real capture and the analysis in 35.3-03.
- If Variant B cannot be forced (the CLI refuses `run_in_background: true` under a synthetic
  prompt), that is recorded honestly as a scope limitation, not papered over.
