<objective>
Make `{N}-VERIFICATION.md` go stale, so a forced re-run stops inheriting the previous run's verdict.

Purpose: nothing deletes, dates or invalidates the artifact, and a `--force` re-run of the same
phase checks out a branch that still carries the previous run's committed copy. That re-run is
mid-arc by construction, so its first Validate failure finds the stale artifact, reads it as a
verdict, and dispatches a gaps-only pass against zero matching plans — gating unresolvably. That is
the same unattended-stall class DOGFOOD-01 exists to prevent, reached from a new direction, and it
is a regression path the Phase 33 fix opened.

Output: a run-scoped content fingerprint recorded once the evidence root is known, a freshness
comparison inside the single loop-back selector, and the two-direction test that is the only thing
distinguishing this fix from a rule that disables gaps-only forever.
</objective>

**This departs from the 999.79 backlog entry's stated fix direction, and CONTEXT.md flags that
departure as overrulable on sight.** The entry proposes comparing a recorded plan count against the
phase's current plan set. That detects "the plan set changed" and false-negatives whenever a replan
happens to produce the same count. The run-scoped content fingerprint is exact instead of
indicative. ROADMAP criterion 3 permits it explicitly by saying "or equivalent".

**A-05's correction is load-bearing for where the capture goes.** The tempting justification — that
`start()` always constructs fresh state, so a run-start baseline is available — is true but does not
establish what it is used for. The artifact lives under the **evidence root**, which in worktree mode
is created by `ensure_phase_worktree` at `crates/devflow-cli/src/commands.rs:239` with the result
assigned at `:244`, well after state construction. At construction time the file does not exist on
any reachable path, so capturing there would record "absent" for every worktree run and make every
first check read as fresh. Capture **after the worktree fork has completed**, where
`state.worktree_path` holds its final value for this run and both modes resolve a real evidence root.

**A-12's fork, and why branch (a) is taken.** On a forced re-run the stale artifact is already on
disk when the run starts. Recording its hash *before* the Validate agent runs makes the agent's
rewrite register as a change. The alternative — recording only when Validate finishes — makes the
first check see no baseline and dispatch a full execute, and then every later check compares an
unchanged stale hash and dispatches a full execute forever. That is a silent permanent regression of
what Phase 33 built, and the two-direction test is what discriminates the two branches. It is
mandatory, not nice-to-have.

**Verified anchors.** `select_loop_back_fix` is at `crates/devflow-cli/src/pipeline_outcomes.rs:315`
with exactly three call sites, at `:389`, `:441` and `:454`. `phase_verification_exists` is at
`crates/devflow-core/src/agent_result.rs:2654` and its only caller in the workspace is
`pipeline_outcomes.rs:316`. Re-derive these before editing.

**F-10 — the ownership shape when `select_loop_back_fix` gains access to run state. Added after the
second cross-AI review pass, which predicted a borrow conflict here (C3); the prediction was checked
and does not hold, and saying so is more useful than a warning about an error that will not
occur.**

The structural facts the finding reports are correct: two of the three call sites (`:389` and `:441`)
sit inside `match run_gate(project_root, state, Stage::Validate, &context)? { … }` arms opened at
`:385` and `:437`. The inference that `state` is therefore still mutably borrowed for the duration of
the match is not. `run_gate` returns `Result<GateAction, CliError>` (`pipeline_gate.rs:262-267`) —
an owned value with no lifetime parameter — so the mutable reborrow ends when the call returns. The
direct evidence is already in the tree: both of those arms **today** call
`loop_back_to_code(project_root, state, fix)`, passing `state` mutably, and compile.

*What was actually checked, and its limits:* the shape was reproduced in a standalone program —
owned-return scrutinee, a `&mut State` argument appended after a `state.phase` read — and it
compiles; a negative control with a scrutinee that genuinely holds a live borrow fails with `E0499`,
so the check can distinguish the two cases. That establishes the shape, not this exact file; the
compiler is the authority at execution time.

**What WOULD produce the conflict, which is the thing worth guarding.** The `evidence_root` binding
at the top of `handle_validate_outcome` is deliberately an owned `PathBuf`, and its comment says why:
"Owned (`PathBuf`, not `&Path`) so it holds no borrow of `state` across the `&mut state` calls in
each arm." If that binding is changed to borrow from `state.worktree_path` while the new `&mut State`
argument is added, every arm produces `E0499`. Keep it owned. Append the state parameter last, after
the existing `evidence_root` and `phase` arguments, so the `phase` read completes before the mutable
borrow begins.

**F-11 — the crash window on the fingerprint write, corrected and accepted rather than closed.
Raised by the second review pass (H-2) at the reviewer's confidence; re-derived here.** The ordering
claim checks out: `save_state` at `pipeline_outcomes.rs:423` runs before the `:441` and `:454`
selector calls, so it does not carry their baseline update; the update is persisted by
`prepare_loop_back_to_code`'s own `save_state` at `pipeline_gate.rs:143`, reached through
`loop_back_to_code` immediately after each selector call.

Two corrections to how the finding framed it, both of which change what the plan should do:

1. **The window does not span the blocking gate wait.** At `:441` the sequence is: `run_gate` blocks
   → returns → selector mutates → `loop_back_to_code` → `prepare_loop_back_to_code` → `save_state`.
   The wait is *before* the mutation. The unpersisted interval is a handful of statements, and the
   only I/O in it is the gate cleanup.
2. **The failure direction is fail-OPEN, not fail-safe.** If the update is lost, a later same-run
   loop-back compares the artifact against the *older* baseline. An artifact that has not changed
   since still differs from that older value, so it reads **fresh** and dispatches gaps-only where it
   should have read stale and dispatched a full execute. That is the 999.79 direction — inheriting a
   verdict — not the over-execute direction the finding assumed. It matters because a fail-safe
   framing would justify leaving this alone, and it is not fail-safe.

**Decision: accept the window, and close the part that is actually testable.** No new write is added
— a second `save_state` in the selector would double the persistence cost of every loop-back to
defend a window with no blocking call in it. What IS required is proof that the update is persisted
*at all* on the normal path, which is a real risk (a selector that mutates a local copy, or an arm
that returns before `loop_back_to_code`, would lose it every time, not only under a kill). Task 3's
acceptance requires observing the new baseline in the persisted state file after a completed
loop-back. The residual kill-window is recorded as a stated limitation, with its true direction, in
this plan's `must_haves`.

**Surface choice, made explicitly because D-08 asks for a complete enumeration.**
`phase_verification_exists` keeps its signature — no third breaking change from this plan. What is
added is one new `pub` function returning the fingerprint, plus one new `pub` field on `State`. Both
are additive.
