**Correction carried from the second cross-AI review pass (C1), and re-verified against source
during this revision.** An earlier draft of this list filed the two new `State` fields under
"Changed, breaking", with the rationale "breaking for anyone constructing the struct by literal".
That rationale is false. `crates/devflow-core/src/state.rs:33` carries `#[non_exhaustive]` on
`pub struct State`, so an external crate cannot use a struct literal at all; the attribute exists
precisely to make field additions non-breaking, and the comment two lines above it at `:30-31` says
so in as many words — *"Paying that cost once here makes every future field additive."* Both fields
are also `#[serde(default)]`, so existing state files deserialize unchanged.

Do not restore the old classification. A changelog that claims four breaks where two exist teaches a
reader that this project's break notices are approximate, which is worse than a missing line: the two
real breaks in this release are the ones a consumer must act on, and they must not be surrounded by
three that need no action.

Explicitly unchanged, and worth stating because CONTEXT.md anticipated otherwise:
- `devflow_core::agent_result::phase_verification_exists` — D-08 flagged that plan `35-05` might add
  a third breaking change here. It did not; the freshness work was built on an additive function and
  a private path resolver. Record the non-event so a reader does not have to infer whether it was
  overlooked.

Private removals, not public surface but recorded so the deletion reads as deliberate:
`git::inline_key_fingerprint` and the two tests deleted with it.

**Release mechanics are settled and are not this plan's job.** Version stays `v2.5.0`; the milestone
is not renamed; the version is set in two places at release time and `devflow-core` publishes before
`devflow-cli`. This plan writes the entry under the new version heading and does **not** edit the
workspace version — that belongs to the release cut's own version step. Plan the artifacts, not the
decision.
