<objective>
Build the guard that notices when the CLI behaviour this entire arc rests on has gone away.

Purpose: `task-notification` delivery is **undocumented CLI behaviour**, observed only on
`claude_code_version 2.1.220`. A CLI update can invalidate it silently, and if delivery is gone
then every multi-plan wave silently orphans work — the exact 999.64 shape this phase exists to
close. A version-string check would be a *proxy* for the behaviour rather than the behaviour, so
the guard plants a declared token and confirms it comes back.

Output: a once-per-run startup canary that declares its own success token, confirms the token
only inside a top-level `result` event, refuses to run when the behaviour is absent or
unverified, and records its outcome in the run's provenance.
</objective>

**Token.** `pub fn declare_token() -> String` returning a fixed-prefix nonce — the prefix
`DEVFLOW_DELIVERY_CANARY_` followed by a hex rendering of a value hashed with
`std::hash::DefaultHasher` over the current `SystemTime` nanos, `std::process::id()`, and a
monotonically incrementing counter, so two calls in one process differ. Do not add a new
dependency for this: per `31-RESEARCH.md`'s ASVS V6 row the token needs only to be unguessable
enough that an agent cannot produce it by chance inside its own generated text — a nonce, not a
cryptographic secret. State that in the doc comment so nobody later "upgrades" it into a security
control it is not.

**Outcome.** `pub enum CanaryOutcome { Confirmed, Absent, Unverified(String) }`, deriving
`Debug`, `Clone`, `PartialEq`, `serde::Serialize`, `serde::Deserialize`, with
`#[serde(rename_all = "snake_case")]` so its persisted form matches this codebase's existing
convention for multi-word wire values.

**Launcher seam.** `pub trait CanaryLauncher { fn run(&self, prompt: &str, capture: &Path) ->
Result<(), String>; }` and `pub struct ClaudeCanaryLauncher;` implementing it: build argv with
`ClaudeAgent::exec_command`, spawn with stdin and stdout piped, write
`monitor::user_turn_line(prompt)` plus a newline to stdin from a writer thread, tee stdout lines
to `capture`, and close stdin once the child emits a top-level `result` event. The seam exists so
the four matcher tests never spawn a real agent; every test in this task injects a launcher that
writes a canned capture.

**The check.** `pub fn run_delivery_canary<L: CanaryLauncher>(launcher: &L, capture_dir: &Path)
-> CanaryOutcome`. It declares a token, composes a throwaway prompt that instructs the agent to
dispatch one trivial background task and to end its final turn by emitting the token verbatim,
runs the launcher against a capture path inside `capture_dir`, and then delegates the match to
`agent_result::token_reported_in_capture(&capture_text, &token)`.

Two traps, both discovered in Phase 30, must be visible in the code and in its doc comments:

  1. **Prompt echo.** The stream echoes the prompt back, so the planted token *will* appear in the
     capture as an echo. It is therefore matched only inside a top-level `result` event, through
     the existing exported helper — never with a substring scan of the whole capture, and never
     through a second, locally-defined notion of which lines are trustworthy. `31-RESEARCH.md`
     records that `claude_stream_gate_shape` is no longer a live function name; the live gate
     predicate is `classify()` returning `CaptureKind::ClaudeStream`, and the provenance predicate
     is `is_top_level`. Cite those, not the retired name.
  2. **It proves delivery, not work.** The agent can see the token in its own prompt and could
     emit it without doing anything — that is 999.67's shape. The doc comment must state plainly
     that a `Confirmed` outcome means "the notification path works" and never "the work happened".
     Summaries and merges remain the evidence of work (D-16, and plan 31-05's acceptance run).

Write the five tests in `<behavior>` with injected launchers and canned captures derived from the
real archived event shapes.

the two occurred, what it means, and what the operator can do. D-15 rejects both alternatives
explicitly — warning-and-proceeding fails in unattended mode because the warning scrolls past, and

phase exists to eliminate. The refusal message for `Absent` must state that the multi-plan wave
guarantee is not currently backed by observed behaviour; the message for `Unverified` must state
that the guard could not run and name the reason, without claiming the behaviour is gone.

The refusal must not leave a half-launched stage behind: place the gate before any state mutation

at `pipeline_launch.rs:110-118` for `monitor_pid`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Canary child stdout → `CanaryOutcome` | An agent-authored stream decides whether the whole run is permitted to proceed |
| Declared token → capture text | A value DevFlow plants travels through the agent and comes back through untrusted output |
| `CanaryOutcome` in `.devflow/state-NN.json` → later launches | A persisted decision is trusted by every subsequent stage in the run |
| Canary event payload → `.devflow/events.jsonl` | Run provenance is written to a file committed evidence has already leaked from once |
