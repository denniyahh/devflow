## Summary

The implementation is small and correct for the stated requirement (BUDGET-01): `DEFAULT_RETRY_BUDGET_SECS = 120` is one of the offered values and `deadline_after` returns `start + budget`. I ran the suite with `python3 -m unittest discover -s tests`: 6 tests pass, exit 0. No security issues were found (no I/O, no input parsing, no secrets).

The problems are in the surrounding harness and edge-case behaviour, not in the arithmetic. The most important one is that the standard no-argument test command silently runs zero tests. I verified this: `python3 -m unittest discover` prints "NO TESTS RAN" and exits 5.

What this review does not establish: it did not exercise `deadline_after` against a real clock or real callers, because no caller exists in the scope. Nothing here shows the 120 s choice is right for the upstream. That is a policy decision recorded in the plan, and I did not re-derive it.

## Warnings

### WR-01: Default test discovery finds zero tests (no `tests/__init__.py`)

**File:** `tests/` (missing `tests/__init__.py`); affects `tests/test_budget.py`, `tests/test_budget_deadline.py`
**Issue:** `python3 -m unittest discover` run from the repo root exits 5 with "Ran 0 tests / NO TESTS RAN", because `tests/` is not an importable package. Only the exact form `discover -s tests` works. The variant `discover -s tests -t .` fails outright with "Start directory is not importable". Any CI job or developer using the common form gets a vacuous run, and a wrong exit code is the only signal. A harness that does not check for a non-zero exit would treat it as a pass.
**Fix:** Add an empty `tests/__init__.py`, so both `python3 -m unittest discover` and `python3 -m unittest discover -s tests -t .` collect the tests. Pin the canonical command in project docs or CI as well. Run it again afterwards and confirm the test count is 6, not 0.

### WR-02: `deadline_after` accepts any value and its time base is undocumented

**File:** `probe/budget.py:9-11`
**Issue:** The docstring does not say which clock `start_secs` must come from (`time.monotonic()` or `time.time()`). The function does no validation. `deadline_after(float("nan"))` returns NaN, and every later `now < deadline` comparison is then False, so the retry loop would give up immediately or never retry, depending on how the comparison is written. `float("inf")` yields a deadline that never expires. A `bool` or `str` start is not rejected, and a str raises a confusing `TypeError` from inside the function. A caller that mixes a wall-clock start with a monotonic "now" gets a wrong deadline with no diagnostic. Today there are no callers, but this is the one public function in the module.
**Fix:** State the clock in the docstring, and reject non-finite input:
```python
import math

def deadline_after(start_secs: float) -> float:
    """Return start_secs + the retry budget. start_secs must be a finite
    value from the same clock (e.g. time.monotonic()) used to test expiry."""
    if not math.isfinite(start_secs):
        raise ValueError(f"start_secs must be finite, got {start_secs!r}")
    return start_secs + DEFAULT_RETRY_BUDGET_SECS
```
Add a test for NaN and inf. If the project decides to allow them, document that choice.

### WR-03: Tool runtime state is left untracked and un-ignored

**File:** `.gitignore:1-4`
**Issue:** `.planning/milestone.lock` and `.planning/state.json` show as untracked in `git status`, and `.gsd/` holds a sentinel file. None of them is ignored. These look like per-run orchestration state (a lock file and a state snapshot). A blanket `git add .planning` or `git add -A` would commit a live lock and state into history. That can wedge other worktrees or runs that read it after merge. `.gitignore` covers `.devflow/`, `.worktrees/` and bytecode, but not these paths.
**Fix:** If these files are runtime-only, add them:
```
.planning/milestone.lock
.planning/state.json
.gsd/
```
First check whether the tooling expects `state.json` to be committed. `STATE.md` is tracked, so `state.json` may be intentional.

## Info

### IN-01: `devflow.toml` `capture_retention = 64` is undocumented and out of this phase's scope

**File:** `devflow.toml:2`
**Issue:** The phase is about the retry budget, but `devflow.toml` also sets `capture_retention = 64`. It has no unit (count, MB, days?) and no explanation. `base_branch = "integration"` is fine: the branch exists locally and on origin. `64` is a magic value that a future reader cannot interpret.
**Fix:** Add a comment giving the unit and the reason, or remove the key if it is not intended to be set here.

### IN-02: Derived constants in the budget comment can drift from the code

**File:** `probe/budget.py:3-6`
**Issue:** The rationale quotes 30, 300, 90 and 240 s in prose only. If the upstream failover window or pager threshold changes, nothing fails. The `OFFERED_BUDGETS` tuple in the test duplicates 30/120/300 too.
**Fix:** Optional. Name the upstream failover window and pager threshold as constants, with a test asserting `failover < budget < pager`. That ties the rationale to an enforced invariant.

### IN-03: Test redundancy and weak type assertion

**File:** `tests/test_budget.py:10`, `tests/test_budget_deadline.py:13-28`
**Issue:** `assertIsInstance(DEFAULT_RETRY_BUDGET_SECS, int)` also accepts `True`, which is an int, though `True` is not in `OFFERED_BUDGETS` and so is caught anyway. Three of the four tests in `test_budget_deadline.py` (start-plus-budget, distinctness, one-for-one shift) all re-state `start + budget` over the same inputs. Only the mock test checks something the others do not, namely that the constant is read at call time. `test_budget.py` also pins the budget to a historical menu of offered values, so changing the budget later fails a test that encodes a one-time decision, not a requirement.
**Fix:** Collapse the three overlapping tests into the first one. Keep the mock test. If the budget may legitimately change, assert an invariant (a positive int) instead of membership in the offered set.
