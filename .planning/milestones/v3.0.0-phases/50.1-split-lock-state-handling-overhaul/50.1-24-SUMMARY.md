# Phase 50.1 Plan 24: `stop` says what actually happened Summary

**`stop` now reports a safe-point stop, a pending stop and an orphaned agent as what they are, and the exit file records 143 after a safe-point stop. One finding remains: a `stopped` flag written to disk during a gate wait does not stop the run, and this plan does not cover it.**

## The two carry-overs

### D-19's stop half (from 50.1-03): met for the GONE window

D-19 says that when the supervisor is gone and the agent still runs, `stop` and `status` name the live pid and the manual kill, never "nothing is running" or a `resume` that would refuse, and that a dead-supervisor and live-agent fixture pins it. It also says an arm that ends the agent is backlog 999.170.

- **Met:** with the socket GONE, `stop` names the pid, `kill -TERM -- -{pid}` and 999.170, exits non-zero, signals nothing and writes nothing. The fixture uses a real supervisor, SIGKILLed, with its socket and sidecar then removed, and its dead-agent control takes today's path.
- **Limit:** a SIGKILLed supervisor that keeps its socket reads STALE, and `stop` then takes Phase 50's backstop, which does end the group or refuses and lists its members. That is the existing behaviour the plan names and this plan did not change. So "a `stop` arm that ends the agent is backlog" is true of the GONE window only.

### Stop during a gate wait, then an answer (from 50.1-10): partly covered

There are three different sequences. Each was run, not only read.

| Sequence | What happens | `stop`'s words | Exit file | Test |
|----------|--------------|----------------|-----------|------|
| Socket stop during the wait, answer afterwards | The wait ends at safe point 4 and the gate closes. The later answer fails and nothing transitions | "honoured at an advance safe point; nothing was signalled; exit code 143" | `143` | `a_stop_during_a_gate_wait_beats_a_later_answer_and_reports_the_safe_point` |
| Answer committed, then a socket stop while the run advances | One `transition` (Validate to Ship), then safe point 2, and nothing launches | Same line | `143` | `a_stop_after_a_gate_answer_stops_after_its_transition_and_reports_it` |
| `stop` itself answers: a live waiter gets the abort (arm 1) | `workflow_aborted`, and the state file is removed | "wrote a rejection…" | Keeps the agent's `0` | Temporary test, not committed. Not a safe-point stop, so D-16 does not name it |
| **`stopped` written to disk only, then the gate approved** | **The answer is applied and the stage launches again under a state reading `stopped`. No `advance_stopped`** | **Nothing: no stop reply exists** | Absent (archived by the launch) | Temporary test, not committed |

**This plan does not cover the last row.** Safe points read the stop token, not the state's `stopped` field. By reading, `devflow stop` does not produce it against a live waiter, because arm 1 answers with an abort and the socket and holder arms set the token or the holder's flag. A hand-written flag, or a later path, would. 50.1-10's "the next advance refuses" was not measured here. The entry is in `deferred-items.md`, and it needs a ruling on whether a safe point should also read the state.

## Decisions Made

- The `stopped` reply is written from a fact recorded at the signal, so `signal_group` returning false reads as not signalled.
- `AcceptedPending` keeps today's wording for owner `agent_running` too ("its next safe point"), to keep one line. For that owner the agent's group was already signalled, so the line is less exact there.
- A failed 143 write warns and emits an event and does not change the run's outcome, because the stop already happened.

**2. [Rule 1 - Bug] "Nothing was signalled" would have been false for a forwarded stop**
- **Found during:** Task 1

- **Committed in:** `2c96c88`

**3. [Rule 1 - Bug] `group_signalled` is recorded at the signal, not in `request_stop`**
- **Found during:** Task 1
- **Issue:** The plan sets it from the stop's action. `KillAgentGroup` with a refused pgid or an already observed exit sends nothing, so the line would claim a group ended.
- **Fix:** Set from `signal_group`'s result, with `a_refused_group_signal_is_not_reported_as_signalled`. A stop that does send a signal reads the same as the plan's rule.
- **Committed in:** `58a7b63`, `2c96c88`

**4. [Rule 1 - Bug] An accepted-pending stop would loop in `stop_pending_launch`**
- **Found during:** Task 3
- **Issue:** That loop re-probes after an ended stop. A supervisor still alive would get another request and another 22 s wait, without end.
- **Fix:** A distinct `ShutdownResult::AcceptedPending`: the pending arm records the launch and returns. **This branch has no test;** the recorded-socket path does.
- **Committed in:** `bd9de67`

**5. [Rule 2 - Correctness] Where 143 is and is not written**
- **Found during:** Task 2
- **Issue:** The plan names only the engaged advance. The promotion-wait stop also ends as a stop beside a completed agent, and a superseded or handed-off supervisor must not write, because the exit path is shared with whoever owns the phase now.
- **Fix:** One helper, called from both arms and skipped when handed off. `Err(NotOwner)` does not reach it.
- **Committed in:** `63f3b30`

**6. [Rule 2 - Correctness] Tests the plan did not name**
