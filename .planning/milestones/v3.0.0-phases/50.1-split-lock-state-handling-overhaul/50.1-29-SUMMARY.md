## Carry-overs

- **From 50.1-18, `stop` over a pending supervisor that never publishes:** this plan changes it only when a foreground process holds the phase. After the same 15 s wait, `stop` signals that launcher (+3 s release wait). If the launcher is still running, `stop` exits non-zero with the not-marked message, which says the launcher gives the reservation back itself. If it exits and the lock reads abandoned, `stop` clears the reservation and records `stopped`. With no holder, 50.1-18's non-zero "nothing was signalled or recorded" refusal is unchanged (`stop_waits_for_an_unpublished_pending_supervisor_then_reports_honestly` still passes). So a pending supervisor that has outlived its launcher and never publishes still ends in that refusal.
- **From 50.1-19, a hand-run `advance` beside a live supervisor:** now guarded. `advance_command` claims the holder, then refuses through `refuse_advance_over_a_live_supervisor`. `a_hand_run_advance_refuses_while_a_supervisor_of_the_phase_is_live` failed without the guard: `advance stage mismatch: expected define, state is plan`, meaning the call went past the live supervisor to the advance itself.

## Accomplishments

- `liveness`: `claim_phase_holder` (an exclusive flock, close-on-exec, never removed) and `install_holder_stop_handler` (an atomic store, `SA_RESTART`, an empty mask).

- `stop_via_holder` replaces the lock arm. `persist_stopped_state` waits for the holder's release and reports D-18's not-marked outcome. Over a missing state, a signalled holder that exited is no longer reported "already stopped".

## Limits found, not fixed

Logged in `deferred-items.md`:

- **`devflow parallel`:** the stop flag is process-wide and never cleared, and `parallel` runs `start` for each phase in one process. From reading the code, not from a run: a `devflow stop --phase N` that signals a `devflow parallel` would also stop every phase it launches after N.
- **The not-marked message reads its pid from the record after the wait.** If the signalled holder exits and a different foreground process claims within the 3 s wait, the message names the new pid as signalled. `signal_sent` is a bool by plan.
