## What this does not establish

- The flag is set inside `Merge` only, before every later hook boundary, so this shows no boundary check exists. No test drives a stop that arrives during `VersionBump`, `ChangelogAppend` or `BranchCleanup`. No code reads the flag there.
- The fixture repos have no remote, so no push ran in any of these tests.
- A stop landing after safe point 5, during the notify or the auto-answer, is honoured at safe point 6 by reading the code. `a_stop_before_finalization_is_honoured_before_the_merge` covers that safe point, but no test lands a stop inside that window.
- A stop that arrives after the pass started leaves no record if the pass succeeds, as the plan derives from D-18. `stop`'s non-zero message is the only trace.
- Strength of the runs: each new test ran a handful of times here, about 3 to 5 apiece, with one `check.sh all` and one `cargo test --workspace` beside the rest of the suite. That is a weak bound on flakiness. The D-18 tests take about 3 s, pinned by `stop`'s `TERMINATE_VERIFY_WAIT`, so that duration measures the wait and not the pass.
- The bound `at most 6 s` is computed from constants and source lines. No run measured a supervisor taking that long. The doc notes a poll interval on top of each wait.
