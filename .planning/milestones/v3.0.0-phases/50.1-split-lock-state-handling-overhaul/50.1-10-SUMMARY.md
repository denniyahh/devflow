# Phase 50.1 Plan 10: Gate-Wait and Launch Writes as Field Deltas Summary

**`pipeline_launch::commit` replaces every `save_state` in the two pipeline files, so a stop or a `yes_ship` revoke written during a multi-day gate wait is no longer overwritten when the wait ends.**

## What this does not establish

Read this before relying on the plan.

- **A stop that survives a gate wait is kept on disk, but nothing here acts on it.** If a gate is answered after a `stop` landed, `run_gate_with_timeout` returns the answer and its caller goes on to transition or finish, with the replaced copy holding `stopped = true`. The next `advance` then refuses. This comes from reading the code; no test exercises it. A grep of plans 11-29 found no plan that names this case, which is a weak search and not proof that none covers it.
- **The commit helper closes lost updates only at sites that use it.** `pipeline_outcomes.rs` (other than the ceiling reset), `preflight.rs` and `commands.rs` still save whole copies until 50.1-11.
- **V-12 is one waiter sampled three times over 200 ms.** Every gate wait goes through the one wait call, so this is good evidence, but it is a sample. The long per-phase lock is still held across gate waits until 50.1-16, -19 and -20.
- **V-12 passed at RED by design.** It guards a property today's code already had. Its discriminating power comes from its control, not from a RED run.
- **`record_supervisor_stop`'s pre-check and long lock are unchanged.** The new test proves ordering against a write in progress, not against every interleaving.
- **`scripts/check-in-container.sh` was not run.** The plan does not ask for it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The ceiling reset would have been reverted in production**
- **Found during:** Task 2
- **Issue:** `reset_phase_failures_at_ceiling` set `phase_validate_failures = 0` in memory and relied on the next save. After `transition` and the loop-back became field deltas, the replace reverted it, so the ceiling gate would have refired on every failure. The plan's site list and 50.1-11's do not name this.
- **Fix:** It commits its own reset and returns a `Result`. The reset now runs before `select_loop_back_fix` in the ceiling arm, because its replace would otherwise drop the observation.
- **Files modified:** `crates/devflow-cli/src/pipeline_outcomes.rs`, outside the plan's `files_modified`; 50.1-11 owns the rest of this file.
- **Verification:** The existing ceiling test failed before the fix and passes after. New `a_ceiling_loop_back_persists_the_reset_and_the_verification_observation`, with a control.
- **Committed in:** `aa9a7dc`, `b0ddc0f`

**2. [Rule 1 - Bug] The verification observation would have been lost**
- **Found during:** Task 2
- **Issue:** `select_loop_back_fix` records the observation in memory. F-11 documents that `prepare_loop_back_to_code`'s write persists it and forbids a second write. Committing only `stage` and `gate_pending`, as planned, would have reverted it, and the next cycle would have read an unchanged artifact as fresh (the 999.79 direction).
- **Fix:** `prepare_loop_back_to_code` also sets those two fields, from the caller's copy. No other writer touches them during an advance. They therefore go beyond the plan's delta, and on the Ship and other loop-backs that made no selection they re-write the loaded values.
- **Verification:** `a_loop_back_commits_its_fields_and_the_verification_observation`
- **Committed in:** `aa9a7dc`

**3. [Rule 1 - Bug] The publish save does not write `stopped` unconditionally**
- **Found during:** Task 2
- **Issue:** The plan says the production save commits `supervisor`, `stopped` and `stop_reason` from the passed state. That would set `stopped = false` over a stop landed during the launch, re-creating the lost update.
- **Fix:** `stopped` and `stop_reason` are written only when the passed state has a stop.
- **Verification:** `the_publish_save_commits_only_the_record_and_a_stop`
- **Committed in:** `aa9a7dc`

**4. [Rule 2 - Missing critical] `record_supervisor_stop` bounds its write-lock wait**
- **Found during:** Task 2
- **Issue:** The plan names `update_state_with`, which blocks with no limit. T-50-68 promises that a wedged holder cannot keep the supervisor from reaching `finish`.
- **Fix:** `update_state_with_within` with `SUPERVISOR_STOP_WAIT`. The failure message for a state that will not load at the second check now reads "the state was not updated" rather than "does not load"; the pre-check's message is unchanged.
- **Verification:** the two `record_supervisor_stop_*` tests. The timeout path itself is not tested.
- **Committed in:** `aa9a7dc`

**5. [Rule 3 - Blocking] `resume` split into `resume_loaded`**
- **Found during:** Task 3
- **Issue:** The test needs a writer between `resume`'s load and its commit, and `resume` has no seam there.
- **Fix:** `resume` keeps its lock, refusal and load, and calls `resume_loaded` with the loaded copy. No behaviour change. The test calls `resume_loaded` directly, so `resume`'s lock and refusal are not part of this test.
- **Committed in:** `85080f2`

**6. [Rule 2 - Missing critical] Added test-only `WAIT_ENTERED`, and two tests beyond the plan's list**
- **Found during:** Task 1 and the controls
- **Issue:** Waiting only for the gate file could let the control's first probe run before the waiter took the lock. The mutation control also showed that no test covered the Validate stamp reaching disk.
- **Fix:** `WAIT_ENTERED` signals once the waiter is at its wait, with the lock already taken in the control. Added `a_validate_launch_commits_its_dispatch_stamp` and `record_supervisor_stop_leaves_a_state_naming_another_launch_byte_identical`.
- **Committed in:** `a847b01`, `a9e6349`, `3ea40ac`
