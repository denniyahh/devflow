# Phase 50.1 Plan 08: Gate Waiter Registration and the Binding Wait Summary

**A gate's waiter now registers with a held flock before its gate file is published, and its wait moves no file, backs off to one read a minute, still cancels within about a second, and lets a stop beat an answer.**

## What This Does Not Yet Do

**No production code calls the new waiter API yet.** Nothing outside tests calls `open_registered`, `register_waiter` or `await_answer`, so a real gate still has no registration until 50.1-14 moves the wait over.

**One change is live now: the unkeyed polls' timing.** `poll_response_cancellable` used to read every second. It now reads at 0, 1, 3, 7, 15, 31, 63 s and then every 60 s, so a human's late answer can take up to 60 s to be picked up. The plan asks for this (D-13 item 4). A cancel now also beats a response already on disk, which reverses the old doc comment, and I rewrote that comment.

## Accomplishments

- A waiter holds a `flock` on `NN-{stage}.{gate_id}.waiter`. `waiter_status` reads only that lock, so a crashed waiter reads `Absent` although its file remains.
- `open_registered` registers, then publishes. A writer that sees the gate file finds the waiter registered, or registered and since dead.
- `await_answer` only reads its own slot. An unbound body comes back as `Unbound { reason }`, untouched, for the caller to move.
- `close` and the bridge's `cleanup` remove a `.waiter` only when it reads `Abandoned`. `phases_on_disk` ignores a `.hold-tmp`.
- A test-only pre-answer and answer-publish hook, each with a release-build no-op.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's loop would have lost an answer in its last backoff gap**
- **Found during:** Task 2
- **Issue:** The plan's loop reads only at backoff boundaries and returns `TimedOut` at the deadline. With a 30 s timeout the last read is at 15 s, so an answer at 16 s would time out with the answer on disk. The old polls read at the deadline, so this would have been a regression.
- **Fix:** The next boundary is capped at the timeout, so the deadline is itself a read. It adds at most one read per wait and does not change the 3-read test.
- **Files modified:** `crates/devflow-core/src/gates.rs`
- **Verification:** `gates::tests::await_answer_reads_once_more_at_its_deadline`, RED above
- **Committed in:** `029ad94`, test in `c585bab`
