# Phase 50.1 Plan 16: Record the Supervisor Before Spawn Summary

**`start` and `resume` now reserve at the top, with the live-run guard and the `pending_supervisor` write in one write-lock closure, and hold no long lock. A launcher SIGKILLed during its publish wait leaves a supervisor that a second launch refuses, naming only `devflow stop`.**

## Accomplishments

- D-01 for `start` and `resume`: the state names the launch before its supervisor exists, the supervisor publishes under that id, and the publish save promotes it.
- A second launcher cannot pass the guard while the first is between its guard and its write.
- A pending supervisor counts as live from its liveness lock alone, with no pid read. An unheld or missing lock is abandoned: the next launch replaces it, removes the file and prints `cleared an abandoned launch reservation <id>`.
- D-08: `start` and `resume` no longer call `lock::acquire`.
- A launch that fails, or returns without spawning, gives the reservation back.
- Both carry-overs from 50.1-07 are closed, not reported as open (see below).

## Deviations from Plan

**1. [Rule 1 - Bug] A fast agent's advance could race its launcher's publish**
- **Found during:** Task 1, from the doc comment on `wait_for_launch_record`, which said production ordering came from the lock `start` no longer holds.
- **Issue:** the plan drops the long lock here and 50.1-19 adds the promotion wait. Between them, a fast agent's advance could launch stage N+1 and the launcher's publish could then overwrite that record with stage N's.
- **Fix:** `wait_while_launch_is_pending`, called before the advance in `run_monitor`. It waits only while the state names this launch as pending, bounded by `LAUNCH_RECORD_WAIT`. 50.1-19 should replace it.
- **Verification:** three unit tests. No end-to-end test forces the race itself.
- **Committed in:** `5fa2e0f`

**2. [Rule 3 - Blocking] `Reservation::for_phase` added to core**
- **Issue:** `Reservation::new` needs a `State`, and `resume` reserves before it has one.
- **Fix:** an additive constructor; `new` delegates to it.
- **Committed in:** `5fa2e0f`

**3. [Rule 3 - Blocking] `resume` moved in Task 1, not Task 2; `launch_test_hold` defined in Task 1, not Task 3**
- **Issue:** merging the guard's wrappers into `reserve_launch` left `resume` with nothing to call, and Task 1's tests use the `reserved` hold.
- **Impact:** the commit split differs from the plan's task split. The content is what the plan names.

**4. [Rule 2 - Missing Critical] `recover --clean` refuses over a live pending supervisor**
- **Issue:** the pending half sits in `possibly_live_sockets`, which `recover --clean` shares. Keeping it out would let clean delete a live launch's state, now that no lock contends.
- **Verification:** not covered by a test of its own. It shares the code the V-01 tests exercise.

**5. [Rule 2 - Missing Critical] Removal of an abandoned liveness file is confined**
- **Issue:** the plan removes the recorded path, which comes from a state file, so a bad state could name any file.
- **Fix:** only the path the launch id derives to, and only while it probes abandoned.

**6. [Rule 2 - Missing Critical] A failed spawn and a stale held reservation discard their liveness file**
- **Issue:** the plan names `discard` for a refused guard and for `abandon_reservation`. A `spawn_monitor` failure, and a held reservation the state no longer names, would otherwise leave a file.
- **Risk:** if a failed spawn's supervisor somehow survived its teardown, its file would be gone. Its pending record is cleared on that path anyway.

**7. [Rule 2 - Missing Critical] Refusal wording under `resume`**
- **Issue:** the closing line and the agent paragraph both name `devflow resume`, which the plan's prohibition forbids while a pending lock is held.
- **Fix:** with a live pending supervisor, a refused `resume` closes with `devflow status --phase N` and omits the agent paragraph. `a_resume_refused_over_a_pending_supervisor_never_names_resume` pins this, with a recorded-supervisor control.

**8. [Additions] Tests and a hold point beyond the plan**
- `the_launcher_keeps_its_lock_until_the_publish_save` and `a_real_supervisor_holds_its_reserved_lock_after_its_launcher_exits` (the carry-overs), `a_fresh_run_is_refused_once_its_reservation_was_cleared`, and the hold point `before_publish_save`.
- `launch_test_hold` appends a line per arrival, not an empty file, so V-05's control can wait for exactly two launchers rather than rely on 300 ms.
- `go_waiting_claude_dir` moved to `test_support` so both test modules can use it.

**Total deviations:** 7 auto-fixed (1 bug, 2 blocking, 4 missing critical), plus the additions in item 8.
**Impact on plan:** the bridge in item 1 is the one behaviour the plan did not name, and it exists to keep a correct order until 50.1-19.

## Not Established

- **`devflow stop --phase N` does not yet end a pending supervisor with no socket.** The refusal names it, as the plan requires, and 50.1-18 makes it work. V-01 ends its supervisor through the socket after releasing the hold, not through `stop`. What `stop` does in that window today was not checked.
- **V-01 runs through the test harness's `__monitor` entry,** not the real binary. The real binary's lock is covered separately, after a normal start, and not in the killed-launcher window.
- **V-01 covers the window with the supervisor held before its agent spawn.** A launcher killed after the agent spawn and before the publish was not tested; there the pid file also refuses.
- **The fast-agent race in deviation 1 is not reproduced end to end.** The fake `exit 0` agents in `start_lock_e2e` pass, but they do not assert the ordering.
- **A refused `start` now creates `.devflow/` and the phase's state write-lock file,** which the old guard did not do when the old lock refused. State, gate and pid files stay byte-identical, as the tests assert, and no liveness file is left. The write-lock file was not compared.
- **One suite run is weak evidence for timing.** The negative controls show these tests can fail. They do not show the tests or the code are free of flakes.
