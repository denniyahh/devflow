## Decisions Made

- `finish()` removes the registration file before releasing the lock, so the "absent" reads find the file missing and never depend on a flock's release. Both tests assert immediately after `finish()` for that reason, which stays inside the test authoring rule on released locks.
- `phase_gate_waiter` returns the status and the gate together, so the two cannot describe different gates.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `gate_waiter` names the gate its status describes when several are open**
- **Found during:** Task 1
- **Issue:** The plan assumes one open gate per phase, but `PhaseFacts.waiter` is `Live` when any of the phase's open gates has a held registration, and several open gates is a real shape. Naming the first gate beside that status would report a gate with no waiter as `live`.
- **Fix:** `phase_gate_waiter` replaces `phase_waiter_status`, returning the gate with a live registration, else the first open gate.
- **Files modified:** `crates/devflow-cli/src/commands.rs`
- **Verification:** `doctor_json_names_the_live_gate_among_several_open_ones`, failing under the "always the first open gate" mutation above
- **Committed in:** `b8009b5`, test in `e626639`

**2. [Rule 2 - Missing Critical] A refused gate id reads `null` (threat T-50.1-156)**
- **Found during:** Task 1
- **Issue:** `OpenGate.gate_id` is the gate file's id, unchecked, and `Gates::list_open` lists a gate whose id `GateId::parse` refuses. A damaged file could put a path into JSON that operators paste, against the plan's "never a path" rule.
- **Fix:** `gate_waiter_json` emits the id only if `GateId::parse` accepts it. The plan's text for the open-gate case says `gate_id` is the gate's id; this is the one case where it reads `null` with a gate open.
- **Files modified:** `crates/devflow-cli/src/commands.rs`
- **Verification:** `doctor_json_gives_a_refused_gate_id_as_null`, and a path-valued fixture in the no-`/` scan, both failing under the "check removed" mutation above
- **Committed in:** `b8009b5`, tests in `e626639`

**3. [Rule 2 - Missing Critical] A test for the plan's "every entry" claim on a phase with several findings**
- **Found during:** Task 2
- **Issue:** The plan's tests can see a single entry per phase, which would pass whatever the renderer did on later entries.
- **Fix:** Added `doctor_json_repeats_the_gate_waiter_on_every_finding_of_a_phase`, which requires at least two entries. No temporary mutation of the renderer was run against it, so its failing direction is not shown.
- **Files modified:** `crates/devflow-cli/src/commands.rs`
- **Committed in:** `e626639`
