**Reviewed:** 2026-11-02

## Summary

Reviewed `tests/test_budget.py` with `probe/budget.py` as context. Both tests pass (`Ran 2 tests ... OK`). I also ran mutations in a scratch copy under `$HOME/.cache` (since removed): budget set to 30, 300 and 150 each failed the first test. A literal `120` in `deadline_after` with the constant at 121 failed both tests. A literal `120` with the constant at 120 passed.

What that establishes: the tests catch a wrong budget value and a wrong deadline formula. What it does not establish: that the budget value is correct (the 120 choice is unconfirmed by a human, per the disposition file), or any behavior of non-finite or non-float input.

No security issues or crashes. The defects are in the test design.

## Warnings

### WR-03: Budget test is self-contradictory and collapses to `== 120`

**File:** `tests/test_budget.py:5,11-13`
**Issue:** `OFFERED_BUDGETS = (30, 120, 300)` is asserted as the acceptable set. The range assertions then require `90 < value < 240`, which excludes 30 and 300. The intersection of the two is `{120}`, so the test is equivalent to `assertEqual(..., 120)` spelled as three assertions. Verified by mutation: 30 fails on `30 not greater than 90`, 300 fails on `300 not less than 240`, and 150 fails on `not found in (30, 120, 300)`.

This conflicts with `01-REVIEW-DISPOSITION.md` (WR-01), which says an operator "can override it by changing `probe/budget.py`". Overriding to any other offered value (30 or 300) turns the suite red, so the override needs a test edit too. The test name says "one of the offered values" but it enforces one specific value.

**Fix:** Decide what the test is meant to pin. Either pin the chosen value explicitly:
```python
CHOSEN_BUDGET_SECS = 120
self.assertEqual(DEFAULT_RETRY_BUDGET_SECS, CHOSEN_BUDGET_SECS)
```
or, if the contract is "an offered value that satisfies the failover and pager constraints", name the constraints and filter the offers by them:
```python
UPSTREAM_FAILOVER_SECS = 90
PAGER_ESCALATION_SECS = 240
self.assertIn(DEFAULT_RETRY_BUDGET_SECS, OFFERED_BUDGETS)
self.assertGreater(DEFAULT_RETRY_BUDGET_SECS, UPSTREAM_FAILOVER_SECS)
self.assertLess(DEFAULT_RETRY_BUDGET_SECS, PAGER_ESCALATION_SECS)
```
and drop or justify offered values the range can never accept.

### WR-04: Deadline test restates the implementation and cannot tell the constant from a literal

**File:** `tests/test_budget.py:16-18`
**Issue:** All three assertions compute the expected value as `start + DEFAULT_RETRY_BUDGET_SECS`, which is the implementation's own expression. The test shows `deadline_after` adds the constant. It does not show that it adds the constant rather than a hardcoded number: a literal `120` in `deadline_after` passes whenever the constant is also 120 (verified). The test also never checks an independent expected number, so its result depends on `DEFAULT_RETRY_BUDGET_SECS` being right, which is the other test's job. Three inputs (10.0, 0.0, -5.0) all exercise the same single code path.

**Fix:** Patch the constant so the test is independent of its real value:
```python
from unittest import mock

with mock.patch("probe.budget.DEFAULT_RETRY_BUDGET_SECS", 7):
    self.assertEqual(deadline_after(10.0), 17.0)
```
That fails if the function uses a literal or a stale copy of the budget.

## Info

### IN-03: Magic numbers 90 and 240 duplicate a comment in the source module

**File:** `tests/test_budget.py:12-13`
**Issue:** The bounds come from the comment in `probe/budget.py:3-4` (90-second failover, 240-second pager escalation). The comment's figures cannot be checked from this repo (see disposition IN-01). The test copies them as bare literals, so the source and the test can drift without any link between them.
**Fix:** Name the constants as in WR-03, or export them from `probe/budget.py` and import them in the test.

### IN-04: `assertIsInstance(..., int)` does not exclude `bool`, and no test covers input type or non-finite input

**File:** `tests/test_budget.py:10,15-18`
**Issue:** `bool` is a subclass of `int`, so the isinstance check is weaker than it looks. Here the `assertIn` that follows makes it harmless, because `True` is not in the offered set. `deadline_after` is untested for `int` input (returns `int`, not `float`), `nan` and `inf`. The disposition file defers this because no caller exists yet. I agree it is latent, not a defect today.
**Fix:** Add edge-case tests when the first retry loop calls `deadline_after`. Until then, leave this as is.
