## Warnings

### WR-01: Constraint stated as fact in code is unenforced; tests accept 30 and 300

**File:** `probe/budget.py:3-5`
**Issue:** The comment says the budget "must cover the upstream's 90-second failover and stay under the 240-second pager escalation". That is a hard invariant, but it exists only as prose. `tests/test_budget.py` asserts only membership in `(30, 120, 300)`. Editing the constant to 30 or 300, the two values the plan rejects for violating exactly this invariant, still leaves the suite green, so a one-character change would silently break the stated contract. The summary notes this gap itself (D2: "tests only check that the value is one of 30/120/300"). Test files are out of scope for this review except where they affect reliability, and this one does.
**Fix:** Name the two bounds as constants and assert them, either at import or in the test:
```python
UPSTREAM_FAILOVER_SECS: int = 90
PAGER_ESCALATION_SECS: int = 240
DEFAULT_RETRY_BUDGET_SECS: int = 120
assert UPSTREAM_FAILOVER_SECS <= DEFAULT_RETRY_BUDGET_SECS < PAGER_ESCALATION_SECS
```
Prefer putting the bounds assertion in `tests/test_budget.py` over a module-level `assert`, which `python -O` strips.

### WR-02: Unverified, agent-chosen value documented as settled

**File:** `probe/budget.py:3-5`
**Issue:** The source comment presents the 90 s and 240 s figures as established facts. The SUMMARY records that these came only from the plan's `<context>` and were not checked against any other source. It also records that Task 1 (`gate="blocking-human"`) was resolved by the orchestrator agent and not by a human. A later maintainer reading only the code would take the number as vetted. The value is reversible, but until a human confirms it, the code gives no hint that it is provisional.
**Fix:** Do not ship this as final until a human confirms or changes the value. Until then, make the status visible in the comment, for example "Provisional: 90 s/240 s figures from plan 01-01, unverified; pending human confirmation." Remove the note once confirmed.

## Info

### IN-01: `deadline_after` does not say which clock `start_secs` is on

**File:** `probe/budget.py:8-10`
**Issue:** The function returns `start + 120`, so the result is only meaningful against the same clock as the input. Nothing says whether that is `time.monotonic()` or `time.time()`. A caller mixing the two gets a silently wrong deadline. Wall-clock time is also vulnerable to NTP steps, which matters when the budget is chosen to fit within a 240 s window. There is no input validation, so NaN, negative or `bool` inputs pass through unchanged. That is acceptable for a helper this small, but the clock contract should be written down.
**Fix:** Extend the docstring: "`start_secs` and the return value must come from the same clock; use `time.monotonic()` for deadlines."

### IN-02: Docstring leaves open whether the deadline bounds an in-flight call

**File:** `probe/budget.py:9`
**Issue:** "the time at which retries stop" bounds when new retries stop, not when the last call returns. The comment's rationale is that the probe reports its own failure before the 240 s pager. A call started just before the deadline with no per-call timeout could run past 240 s and defeat that. No caller exists yet, so this is not a defect today. It is a contract gap for the first caller.
**Fix:** State in the docstring whether callers must cap each attempt at the remaining budget (`deadline - now`), or add a per-attempt timeout when the retry loop is written.
