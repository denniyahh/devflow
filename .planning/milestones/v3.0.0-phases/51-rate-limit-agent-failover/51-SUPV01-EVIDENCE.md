## Experiments: publish wait and cron-arm read

**Publish wait (read 1).**
- **Intervention.** The test-only seam `DEVFLOW_TEST_WITHHOLD_PUBLISH_PROBE=<agent>:<stage>` (`monitor.rs`, compiled out of release builds; pinned by `monitor::tests::the_publish_probe_seam_is_compiled_out_of_non_test_builds`) makes `spawn_monitor`'s one publish wait treat every probe as unanswered. That wait is pinned to one by `monitor::tests::non_test_code_waits_for_publish_exactly_once`. The seam is keyed by the launch being spawned, so the primary's `claude:code` launch publishes while the failover relaunch's `codex:code` launch does not.
- **Failover arm.** Tested by `pipeline_launch::tests::failover_with_the_publish_probe_withheld_ends_at_a_gate`. The fallback's relaunch publishes nothing. The run then emits `agent_handoff`, then `agent_handoff_relaunch_failed`, whose reason is the `NotReady` text, then the Code `gate_fired`. There are no cron instructions, no `rate_limit_resume_scheduled` and no Codex socket. The state shows agent Codex, fallback consumed and the gate pending. R2-13: the fallback stub's group had live members when it recorded itself (pid = pgid, so it leads its own group). After the gate, that group has no live member.
- **Healthy baseline.** `pipeline_launch::tests::a_rate_limit_with_a_fallback_hands_off_and_completes_the_same_stage`, the same rig with no intervention: the fallback publishes and completes Code.
- **Ordinary-launch control.** `pipeline_launch::tests::an_ordinary_transition_with_the_publish_probe_withheld_fails_the_same_way` withholds a Plan → Code transition's Code launch (`claude:code`). No Code successor is published. The run settles at stage Code with no supervisor record and no Code socket. No `stage_launched` for `code` is emitted, and the Code agent's group ends. The assertions cover only what the run leaves behind (R2-9).
- **Intervention removed.** The same transition with the seam unset, run once as a temporary test. Code published (`stage_launched` for `code`, recorded as the supervisor), completed, and the run stopped at its `--until code` cap. The outcome flips, so the failure above is the withheld read's, not the transition's.
- **Which end a test build reaches.** In a test build the successor's own promotion watch ends it, because its `PROMOTION_WAIT` (5 s under `cfg(test)`) expires before the launcher's 10 s `PUBLISH_WAIT`. The launcher then sees it "exited by itself before publishing". In a release build `PROMOTION_WAIT` is 15 s, so the launcher's `end_unpublished_child` ends it first ("did not publish within"). Neither test reaches that release path.
- **Answer for this read.** Failover depends on SUPV-01's publish wait exactly as every Code launch does: withheld, both fail to publish alike. Failover's failure is visible (an event plus a gate). The ordinary transition's is not (see below).

**Cron arm's recorded-socket read (read 5).**
- **Intervention.** The recorded supervisor's socket path has a regular file as its parent, so `supervisor::probe` fails with `ENOTDIR`. The test asserts this error before relying on it.
- **Cron arm.** Tested by `pipeline_launch::tests::a_cron_resume_and_an_ordinary_resume_refuse_alike_when_the_recorded_probe_cannot_answer`. `resume` of a rate-limit-paused Code run (cron instructions written, not stopped, one infra fault charged) recording that socket is refused. The refusal names the socket and `probe failed`, and the state file is unchanged byte for byte.
- **Ordinary-launch control.** In the same test, a `--until code`-stopped run recording the same socket is refused with the same text, phase number aside.
- **Healthy baseline.** In the same test, a paused run whose recorded socket is GONE resumes and records its own supervisor. In a temporary run, a stopped run with a GONE socket also resumed.
- **Mutation.** With `socket_live_socket`'s probe-error arm changed to return `None`, the test fails with `phase 5197: resume over an unprobeable record launched`.
- **Answer for this read.** The cron arm's `resume` reads the recorded socket exactly as every `resume` does, and fails closed on an unanswerable probe.

## Experiments: post-save probe and pending-record lock probe

All four in-supervisor runs withhold a Code launch (R-2), so each failover run and its ordinary control differ only in failover. Every planted path's probe error is asserted before it is relied on.

**Post-save probe (read 2; review B-2, R2-8).**
- **Intervention.** The test-only seam `DEVFLOW_TEST_WITHHOLD_SUCCESSOR_PROBE=<agent>:<stage>:<marker-path>` (`successor_probe_for`, `pipeline_launch.rs`, `#[cfg(test)]`; pinned by `pipeline_launch::tests::the_successor_probe_seam_is_compiled_out_of_non_test_builds`, which plants an ungated decoy call and an ungated decoy read). `successor_runs_on` takes its probe as a parameter. `publish_record` passes `devflow_core::supervisor::probe` in a release build, and the seam's closure in a test build. For the named launch, the closure writes the marker and answers `Gone` without probing, so `successor_runs_on`'s own `Gone` arm (crates/devflow-cli/src/pipeline_launch.rs:2578) decides. `Gone` is the answer that flips the run's shape. An error would not, see below.
- **Failover arm.** Tested by `pipeline_launch::tests::failover_with_the_post_save_probe_answering_gone_records_the_run_stopped` (`codex:code`). The Codex stub is held on `go-fallback`. While it is held, the state reads `stopped` with `NEXT_STOPPED_BEFORE_SAVE_REASON`. Its record names the successor, not stage N (saved before the probe). The agent is Codex and the fallback is consumed. There is one `agent_handoff` (`rate_limited`), and no `agent_handoff_relaunch_failed`, `gate_fired`, `rate_limit_resume_scheduled` or cron instruction. The seam's marker exists, and a successor socket other than stage N's is still in the cache dir.
- **Ordinary-launch control.** `pipeline_launch::tests::an_ordinary_transition_with_the_post_save_probe_answering_gone_records_the_run_stopped` (`claude:code`, Plan → Code, no fallback, Code stub held on `go2`). While the stub is held, the run is recorded stopped the same way, with the same reason, at stage Code. The record names the successor, the marker exists, and the successor's socket is there.
- **Healthy baseline.** `pipeline_launch::tests::a_rate_limit_with_a_fallback_hands_off_and_completes_the_same_stage` (no intervention): the fallback is handed off and completes Code.
- **Intervention removed.** Each rig was run once with the seam unset, as a temporary test. Failover: while Codex was held, the state read `stopped=false`, `stop_reason=None`, agent Codex, one handoff. The record named the successor and its socket probed Alive. No marker was written. On release, Code completed (`advance_evaluated` success, then `workflow_finished` `stopped_at`). Ordinary: while held, `stopped=false` at Code, the record named the successor and it probed Alive. On release, Code completed the same way. The outcome flips, so the stopped shape above is the read's.
- **After the release, with the seam set (observed, not asserted).** In both runs the successor's agent finished. Its own advance then emitted `advance_failed` with reason `stopped` and the stop reason above, and the successor's socket was gone within the 30 s poll. The state kept `stopped` and `NEXT_STOPPED_BEFORE_SAVE_REASON`, with the record still naming that successor. Failover and the ordinary run ended identically. The successor did not rewrite the state, and no supervisor outlived the drop.
- **The error arm (crates/devflow-cli/src/pipeline_launch.rs:2583-2588), by reading, not by a test.** A probe error makes `successor_runs_on` log "could not probe the next supervisor at … after its publish" and return `true`. That is the same value an Alive `agent_running` answer gives, so `publish_record` takes the healthy baseline's `HandedOff` branch (:2419-2420). Withholding the probe as an error could not have produced a different outcome from the baseline, so no test is offered for it (R2-8).
- **Answer for this read.** A `Gone` post-save answer records the run stopped, and failover and an ordinary Code launch dispose of it identically. An error answer keeps the handoff on both.

## Conclusion

Failover arm: failover makes no liveness read about the current run, and each read it makes about its successor is one an ordinary in-supervisor Code launch makes and disposes identically: withheld, the publish wait fails both (pipeline_launch::tests::failover_with_the_publish_probe_withheld_ends_at_a_gate, pipeline_launch::tests::an_ordinary_transition_with_the_publish_probe_withheld_fails_the_same_way); answered `Gone`, the post-save probe records both stopped while the successor runs (pipeline_launch::tests::failover_with_the_post_save_probe_answering_gone_records_the_run_stopped, pipeline_launch::tests::an_ordinary_transition_with_the_post_save_probe_answering_gone_records_the_run_stopped); unprobeable, the pending-record lock probe refuses both (pipeline_launch::tests::failover_over_an_unprobeable_pending_record_ends_at_a_gate, pipeline_launch::tests::an_ordinary_transition_over_an_unprobeable_pending_record_is_refused_the_same_way); the only difference in any of them is what follows a failed launch, where failover opens the never-silent gate and the ordinary transition is left ungated.
Cron arm: the cron arm's resume reads the recorded supervisor's socket and lock and the pending record's lock exactly as any resume does, refusing a rate-limit-paused run and an `--until`-stopped run with the same text when any of the three cannot be probed and resuming both baselines (pipeline_launch::tests::a_cron_resume_and_an_ordinary_resume_refuse_alike_when_the_recorded_probe_cannot_answer, pipeline_launch::tests::a_cron_resume_and_an_ordinary_resume_refuse_alike_when_the_recorded_lock_cannot_be_probed, pipeline_launch::tests::a_cron_resume_and_an_ordinary_resume_refuse_alike_when_the_pending_lock_cannot_be_probed).

"SUPV-02 depends on SUPV-01" therefore means this: both arms rely on SUPV-01's reads only as every ordinary launch or resume does, and no experiment found a read that failover or the cron arm disposes of differently.

## What this does not establish

- **Stub agents and the capture shape.** Every run uses shell stubs on the legacy capture launch, not a real `claude` or `codex`, and not the stream shape.
- **Substituted answers, not real faults.** A withheld publish probe, a substituted `Gone`, and planted unprobeable locks stand in for a crashed or hung supervisor and a corrupt lock. A `Gone` answer while the successor still runs is a substituted answer, not a successor that really ended. No real supervisor crashed or hung in any experiment.
- **One machine.** Linux (Fedora Kinoite), one run of each experiment test per gate, plus the reruns named in 51-10's and 51-13's SUMMARYs. That is a weak bound and does not size flakiness.
- **A planted pending record, not a racing launcher.** Read (3) was exercised by a record the test wrote while no supervisor was writing, not by a second real launcher racing this one.
- **Read (4) is untested.** It is a gap, for the reason in the coverage check.
- **The post-save probe's error arm is settled by reading, not by a test** (R2-8).
- **The release-build ordering of the publish wait** (51-10): a test build ends an unpublished successor through its own promotion expiry, not the launcher's `end_unpublished_child`.
- **The checker's reach.** `pipeline_launch::tests::the_supv01_evidence_is_complete` proves that every cited file, line and test exists, and that one cited file names each row's read. It does not prove that a cited line holds the read, or that a cited test exercises it. Those were re-read by hand at `5559cd2`, and every cited line was re-read again at `b94d356`.
