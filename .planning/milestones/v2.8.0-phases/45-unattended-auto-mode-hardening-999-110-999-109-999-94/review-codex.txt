# Adversarial Review

Purpose: get N independent models to *attack* a set of documents — find
contradictions, unstated assumptions, decisions that don't survive contact with
the code, scope leaks, and non-falsifiable criteria — rather than summarize or
praise them.

The skill fans out one headless CLI invocation per reviewer, collects the raw
responses, and writes a consolidated verdict. Model + effort are selected per
reviewer. Where a provider exposes a catalog command it is queried; otherwise the
provider's *current* model/effort is read from its config (read-only) and
overridden per-run via flags — never a stale hardcode, and never a global config
write (antigravity accepts `--model`/`--effort` per-run flags, so no config write is needed).

## Interface

```
adversarial-review \
  --targets <files...>                # required — documents to review
  --reviewers <cli:model:effort,...>  # default: claude, codex, antigravity
  --lens <name>                       # default: adversarial (see below)
  --out <dir>                         # default: ./reviews/ (use .planning/reviews/ in GSD projects)
  --no-query                          # skip catalog/config discovery; use explicit args only
```

`--reviewers` grammar: `cli[:model[:effort]]`. Omit `model` and/or `effort` to
discover from the provider (catalog or config) and default to `high` effort.
Example: `--reviewers claude:opus:high,codex::high,antigravity` — `codex::high`
keeps codex's current model at high effort; bare `antigravity` uses its config model.

## Per-provider reference

| CLI | headless | model selection | catalog | effort selection |
|---|---|---|---|---|
| `pi` | `pi -p "<prompt>"` | `--model <id>` | ✅ `pi --list-models` | `--thinking off\|minimal\|low\|medium\|high\|xhigh\|max` |
| `claude` | `claude -p --output-format json "<prompt>"` | `--model sonnet\|opus\|haiku\|fable` | ❌ fixed small set | `--settings '{"effortLevel":"high"}'` |
| `codex` | `codex exec "<prompt>"` | `-m <model>` or `-c model="..."` | ❌ | `-c model_reasoning_effort=low\|medium\|high` |
| `antigravity` | `antigravity -p "<prompt>"` | `--model <id>` | ✅ `antigravity models` | `--effort low\|medium\|high` |
| `opencode` | `opencode run "<prompt>"` | `-m provider/model` | ✅ `opencode models [provider]` | `--variant minimal\|high\|max` |

### Config files (read-only; learn the *current* value, never mutate by default)

- claude — `~/.claude/settings.json` keys `model`, `effortLevel`.
- codex — `~/.codex/config.toml` keys `model`, `model_reasoning_effort`.
- antigravity — `~/.gemini/antigravity-cli/settings.json` key `model` (e.g. `"Gemini 3.6 Flash (Low)"`).

These live in HOME, not the repo. The repo's `.claude/` and `.codex/` hold
permissions/hooks/skills, not the model catalog. Config stores only the
*current* model, not the full available list.

Normalized effort vocabulary: `low | medium | high | max`. Map per provider where
the vocab differs (`xhigh`≈`max` for pi; `minimal`≈`low`, `high`→`high`,
`max`→`max` for opencode; codex caps at `high`; antigravity takes `--effort low|medium|high`).

## Procedure

1. **Resolve reviewers.** Parse `--reviewers` (default: `claude,codex,antigravity`).
   Resolution per reviewer:
   - **Model**: explicit arg > provider catalog (pi/opencode) > config current
     value (claude/codex/antigravity) > omit-flag (CLI's own default).
   - **Effort**: explicit arg > `high` default. The provider's *configured*
     effort is read and reported but is **not** the default — adversarial
     review warrants deep reasoning, and a config `low` (e.g. codex) would
     defeat it. antigravity takes `--effort` (and `--model`) as per-run flags.

2. **Discover (skip with `--no-query`).**
   - Catalog where available: `pi --list-models`, `opencode models`.
   - Config (read-only) where not: read the three files above to learn the
     current model + effort. This is the "default" — grounded in what the
     operator has configured, not a hardcode.
   Present the discovered values if the operator wants to choose; otherwise
   proceed with the resolved defaults and say what was chosen.

3. **Build the review prompt.** Feed each reviewer the lens, the list of target files, **and the
   full planning context they would otherwise resolve themselves** (SPEC.md, CONTEXT.md,
   RESEARCH.md, the ROADMAP phase section, prior reviews) — all inlined. This makes doc reads
   CWD-independent, which matters because reviewers read the codebase themselves (the adversarial
   lens tells them to). Use the adversarial lens below unless `--lens` overrides it.

4. **Invoke in parallel, from the review root.** Resolve the directory that owns the target docs
   (a phase worktree `.worktrees/phase-N` if it exists, else the checkout) — this is the tree the
   reviewers must read. Launch each reviewer with its CWD set to that root: `cd <root>` in a
   subshell, plus the CLI's own flag where one exists (`codex exec --cd <root>`, `claude --add-dir
   <root>`, `antigravity --add-dir <root>`). **Why this is load-bearing:** the reviewer's own file
   reads resolve against its CWD, so a wrong CWD hands it a stale tree — this exact mistake
   produced a review that quoted the previous checkout's SPEC. Note `codex` anchors its project to
   `~/.codex/config.toml`'s trusted dir, not CWD — pass `--cd <root>` explicitly and still
   sanity-check its citations in step 5. One shell per reviewer, with a timeout (default 5m;
   antigravity's `--print-timeout` is 5m — raise it for long prompts). A reviewer whose CLI is
   absent or times out is recorded as `skipped`, never silently dropped.

5. **Collect, verify, consolidate.** Write `{out}/{cli}.md` per reviewer (raw response + the exact
   invocation + the review root used, so the result is reproducible). **Sanity-check before
   trusting a reviewer:** its citations must match the review root's current files — a reviewer
   quoting a different checkout's SPEC (or reporting a target file "not on disk") means its CWD was
   wrong; discard those specific citations and flag the reviewer. Dedupe a reviewer whose body
   repeats itself (antigravity and codex both emitted their findings twice in testing) — keep one
   copy. Then write `{out}/SUMMARY.md` synthesizing: which findings are agreed across reviewers,
   which conflict, and which are actionable — grouped by target file.

## Default adversarial lens

> You are an adversarial reviewer. Attack the following documents. Do not
> summarize or praise them. Find, with the exact file and the exact line/quoted
> text for each:
> 1. contradictions between the documents,
> 2. unstated assumptions that would break under real use,
> 3. decisions that do not survive contact with the actual codebase or tool,
> 4. scope leaks (work that belongs in another phase/item),
> 5. acceptance criteria that are not falsifiable or have no negative control,
> 6. missing edge cases or failure modes.
> Be specific and hostile. Prefer 5 sharp findings to 20 vague ones. Where a
> finding is speculation, label it as such.

//! Stage-transition hooks.
//!
//! Branching, docs, changelog, and version bumps are no longer workflow stages
//! (as they were in v0.x). They are *hooks* that fire at specific stage
//! transitions. [`hooks_for_transition`] maps a `(from, to)` stage move to the
//! hooks that should run, and [`Hook::run`] executes one.

use crate::config::GitFlowConfig;
use crate::git::GitFlow;
use crate::phase_id::PhaseId;
use crate::stage::Stage;
use crate::version;
use std::path::{Path, PathBuf};
use std::process::Command;
use tracing::{info, warn};

/// A side-effecting action that fires at a stage transition.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Hook {
    /// Create the `feature/phase-NN` branch from develop.
    BranchCreate,
    /// Delete the merged feature branch after Ship.
    BranchCleanup,
    /// Regenerate and commit docs.
    DocsUpdate,
    /// Merge the phase feature branch into develop before release bookkeeping.
    Merge,
    /// Append a CHANGELOG entry.
    ChangelogAppend,
    /// Compute and write the next version, then tag it.
    VersionBump,
}

/// Context passed to every hook.
#[derive(Debug, Clone)]
pub struct HookContext {
    /// Phase the workflow is on.
    pub phase: PhaseId,
    /// Project root.
    pub project_root: PathBuf,
    /// Stage the workflow is entering.
    pub stage: Stage,
    /// Git-flow branch model.
    pub git_flow: GitFlowConfig,
    /// The version `VersionBump` actually tagged, set once it runs (GAP-7).
    /// `ChangelogAppend` reads this instead of re-deriving the version from
    /// disk, so the changelog heading and the git tag never desync — in
    /// particular when there is no version file and `version::read_version`
    /// would otherwise error and fall back to the `unreleased` literal.
    pub shipped_version: Option<String>,
    /// The Keep-a-Changelog-grouped body `VersionBump` computed, set once it
    /// runs (D-12, T-26-11). `ChangelogAppend` reads this instead of
    /// re-deriving it from live git state, for the same reason
    /// `shipped_version` must be handed forward rather than re-derived:
    /// once `VersionBump` has created the release tag, the range this body
    /// was computed over collapses to empty (the tag is now the baseline),
    /// so a re-derivation after the fact would silently produce an empty
    /// changelog entry.
    pub shipped_changelog_body: Option<String>,
}

/// Errors produced by hooks.
#[derive(Debug, thiserror::Error)]
pub enum HookError {
    /// A git-flow operation failed.
    #[error(transparent)]
    Git(#[from] crate::git::GitError),
    /// A version operation failed.
    #[error(transparent)]
    Version(#[from] version::VersionError),
    /// Filesystem operation failed.
    #[error("hook I/O failed: {0}")]
    Io(#[from] std::io::Error),
}

impl Hook {
    /// Run this hook against the given context.
    pub fn run(&self, ctx: &mut HookContext) -> Result<(), HookError> {
        match self {
            Hook::BranchCreate => branch_create(ctx),
            Hook::BranchCleanup => branch_cleanup(ctx),
            Hook::DocsUpdate => docs_update(ctx),
            Hook::Merge => merge_feature(ctx),
            Hook::ChangelogAppend => changelog_append(ctx),
            Hook::VersionBump => version_bump(ctx),
        }
    }
}

/// Which hooks fire when moving `from` → `to`.
///
/// - Validate → Ship: docs are finalized before shipping.
/// - Ship → (done): merge + version bump + changelog + branch cleanup.
/// - everything else: none.
///
/// `ChangelogAppend` deliberately does NOT run here (WR-04, 17-12): a
/// changelog heading naming a release is only true once `VersionBump` has
/// actually cut the tag, and `VersionBump` runs in [`hooks_after_ship`],
/// strictly after this transition.
pub fn hooks_for_transition(from: Stage, to: Stage) -> Vec<Hook> {
    match (from, to) {
        (Stage::Validate, Stage::Ship) => vec![Hook::DocsUpdate],
        _ => Vec::new(),
    }
}

/// Hooks that fire after Ship completes (the workflow's terminal transition).
///
/// `ChangelogAppend` runs strictly after `VersionBump` (WR-04, 17-12) — the
/// entry must describe the version `VersionBump` actually wrote and tagged,
/// never a version computed independently of it. It runs before
/// `BranchCleanup` so a changelog failure still stops short of deleting the
/// feature branch (`run_checkout_hooks`' terminal-batch fail-fast breaks on
/// the first error in this batch).
pub fn hooks_after_ship() -> Vec<Hook> {
    vec![
        Hook::Merge,
        Hook::VersionBump,
        Hook::ChangelogAppend,
        Hook::BranchCleanup,
    ]
}

fn branch_create(ctx: &HookContext) -> Result<(), HookError> {
    let git = GitFlow::new(&ctx.project_root);
    let branch = git.feature_start(ctx.phase)?;
    info!("BranchCreate: created {branch}");
    Ok(())
}

fn branch_cleanup(ctx: &HookContext) -> Result<(), HookError> {
    let git = GitFlow::new(&ctx.project_root);
    let branch = format!(
        "{}phase-{}",
        ctx.git_flow.feature_prefix,
        ctx.phase.padded()
    );
    if git.branch_exists(&branch) {
        // Non-force cleanup is intentional: never discard unmerged work.
        match git.delete_branch(&branch, false) {
            Ok(()) => info!("BranchCleanup: deleted {branch}"),
            Err(err) => {
                let message = err.to_string();
                if message.contains("not fully merged") || message.contains("not yet merged") {
                    warn!(
                        "BranchCleanup: feature branch {branch} is not merged yet — left in place"
                    );
                } else {
                    warn!("BranchCleanup: could not delete {branch}: {err}");
                }
            }
        }
    }
    Ok(())
}

/// Merge the phase's feature branch into develop, then re-assert ancestry
/// (23-06 / T-23-62) before reporting success.
///
/// **The post-merge ancestry re-check runs here — immediately after
/// `merge_feature_into_develop` returns `Ok`, while the feature branch still
/// exists — because this is the only place in `hooks_after_ship` where the
/// assertion is both meaningful and safe.** `BranchCleanup` runs later in the
/// same batch and deletes the branch; after that, an ancestry check fails
/// closed on an absent branch (`git.rs:89-92`: "an absent branch is not proof
/// of a merge") and would report `false` for every successfully shipped
/// phase, so this check can never be moved after the batch without inverting
/// its meaning.
///
/// **No-rollback policy, stated here because it must not be re-derived
/// later:** on the ancestry re-check's failure path below, `merge_feature`
/// does NOT undo the merge. `git merge --no-ff` has already committed on
/// `develop` by the time the re-check runs, and automatically resetting a
/// shared integration branch is a far more dangerous operation than the
/// inconsistency it would be papering over. Instead, this returns `Err`; the
/// containing `run_checkout_hooks` batch fails; `finish_workflow_with_gate_timeout`
/// reopens an actionable Ship gate whose context tells a human to resolve the
/// git error, and the operator decides. Plan 23-10's recovery-path artifact
/// must know this exact state.
fn merge_feature(ctx: &HookContext) -> Result<(), HookError> {
    let git = GitFlow::new(&ctx.project_root);
    let branch = format!(
        "{}phase-{}",
        ctx.git_flow.feature_prefix,
        ctx.phase.padded()
    );
    if !git.branch_exists(&branch) {
        return Err(crate::git::GitError::Command(format!(
            "feature branch `{branch}` is missing; refusing to report an unproven merge"
        ))
        .into());
    }
    if git.is_merged_into_develop(ctx.phase) {
        info!("Merge: {branch} is already merged; nothing to merge");
        crate::events::emit(
            &ctx.project_root,
            ctx.phase,
            "merge_result",
            serde_json::json!({"merged": false, "branch": branch}),
        );
        return Ok(());
    }

    git.merge_feature_into_develop(ctx.phase)?;

    if !git.is_merged_into_develop(ctx.phase) {
        crate::events::emit(
            &ctx.project_root,
            ctx.phase,
            "merge_result",
            serde_json::json!({"merged": false, "branch": branch}),
        );
        return Err(crate::git::GitError::Command(format!(
            "merge of `{branch}` reported success but the branch is still not an ancestor of \
             develop; refusing to report an unproven merge"
        ))
        .into());
    }

    info!("Merge: merged {branch} into develop");
}

/// The Code stage's dedicated prompt.
///
/// The Code arm ONLY carries [`AUTO_CHAIN_PRESERVING_FLAG`] (D-04/D-05, 35.1-01
/// Pitfall 1): `execute-phase.md` wipes `workflow._auto_chain_active` at the top
/// of every invocation whose `$ARGUMENTS` lacks this token, which would clear
/// the flag DevFlow just set before `checkpoint_handling` ever reads it.
fn code_stage_prompt(phase: PhaseId) -> String {
    let command = format!(
        "{} {AUTO_CHAIN_PRESERVING_FLAG}",
        gsd_command_for(Stage::Code, phase)
    );
    format!(
        "Run the GSD workflow command for this stage:\n\n    {command}\n\n\
        ## Advisory incremental self-review\n\
        \n\
        After each plan or wave lands, perform a quick, shallow self-check \
        for doc accuracy, leaked data, CI/build correctness, and \
        external-state claims. Record any drift in the working output and \
        continue execution; the authoritative review happens during Ship. \
        This check must not pause execution or request human input.\n\
        \n\
        {COMPLETION_PROTOCOL}"
    )
}

/// Render a [`StageIntent`] as the legacy Claude/OpenCode slash-command text.
///
/// This is the byte-identical renderer: Claude and OpenCode produce exactly
/// what `stage_prompt` produced before the migration (CONTEXT D-01 zero
/// regression). It lives here — not in the adapters — so the two agents cannot
/// drift apart, and the per-stage snapshot tests pin it.
pub fn render_claude_style(intent: &StageIntent) -> String {
    match intent {
        StageIntent::Define { phase } => define_stage_prompt(*phase),
        StageIntent::Plan { phase } => idempotent_stage_prompt(*phase),
        StageIntent::Code { phase, fix: None } => code_stage_prompt(*phase),
        StageIntent::Code {
            phase,
            fix: Some(fix),
        } => fix_prompt(*fix, *phase),
        StageIntent::Validate { phase } => validate_stage_prompt(*phase),
        StageIntent::Ship {
            phase,
            review_angles,
        } => ship_stage_prompt(*phase, review_angles),
    }
}

/// Whether the `ancestor` ref is an ancestor of the `descendant` ref, against
/// ALREADY-FETCHED local refs — issues NO `git fetch`. Generalises
/// [`origin_main_ancestor_status`] to an arbitrary ref pair (used by
/// `release --verify`'s post-cut checks: is the release tag on `main`, and
/// has the `main`→`develop` sync run). Distinguishes "not an ancestor"
/// (exit 1) from "a ref is absent" (exit 128) so the caller can degrade to
/// an actionable `git fetch` message instead of reporting a false
/// divergence.
pub fn ref_is_ancestor(project_root: &Path, ancestor: &str, descendant: &str) -> AncestorStatus {
    let both_exist = [ancestor, descendant].iter().all(|r| {
        git_command(project_root)
            .args(["rev-parse", "--verify", "--quiet", r])
            .output()
            .map(|out| out.status.success())
            .unwrap_or(false)
    });
    if !both_exist {
        return AncestorStatus::RefAbsent;
    }
    let is_ancestor = git_command(project_root)
        .args(["merge-base", "--is-ancestor", ancestor, descendant])
        .output()
        .map(|out| out.status.success())
        .unwrap_or(false);
    if is_ancestor {
        AncestorStatus::Ancestor
    } else {
        AncestorStatus::Diverged
    }
}

## Summary verdict

**REJECTED as currently specified; APPROVED WITH CONCERNS after mandatory replanning.**

The three decisions identify real failure modes, but D-01 and D-03 are underspecified enough that implementing them literally could produce a system that launches from one branch and ships into another, while still silently making the same checkpoint decision. D-02 is directionally sound but its proposed path rule is narrower than “Cargo workspace members.”

## Critical findings / risks

### D-01 — base-branch configuration is not propagated through the lifecycle

The current GitFlow implementation is structurally hardcoded to `develop`:

- `feature_start()` checks out `self.config.develop`.
- `merge_feature_into_develop()` checks out and merges into `self.config.develop`.
- `is_merged_into_develop()` tests ancestry against `self.config.develop`.
- `cleanup_merged()` uses `git branch --merged <develop>`.
- `hooks_after_ship()` invokes merge and cleanup without a separate target-baseline concept.

Therefore, changing only worktree creation or preflight resolution is unsafe. A phase could be created from `workspace/denniyahh`, then Ship would merge it into `develop`, or cleanup would evaluate merge status against `develop`. This can cause:

- false “not merged” results;
- feature branches retained or deleted incorrectly;
- phase commits landing on an unintended integration branch;
- release/version hooks operating on a branch that does not contain the planning changes;
- divergence between local configured branches and their remote tracking branches.

D-01 also conflates at least three concepts that should be modeled separately:

1. worktree start point;
2. feature-branch integration target;
3. release synchronization target.

A configured planning branch may be suitable for bootstrapping `.planning/` but not intended as the merge destination.

The context says “base branch resolution,” while the implementation question includes merge and cleanup. The plan must explicitly define whether the configured branch replaces `develop` globally or only serves as a worktree start point.

`origin/<branch>` currency is also unresolved. Existing ancestry helpers operate on already-fetched local refs and return `RefAbsent` when the remote ref is unavailable; they do not fetch. A config such as `workspace/denniyahh` needs explicit behavior for:

- no local branch;
- no `origin/<configured-branch>`;
- stale remote-tracking ref;
- branch existing locally but not remotely;
- configured branch diverging from `develop`.

### D-02 — `crates/*` is not equivalent to Cargo workspace membership

The proposed predicate excludes valid layouts:

- root-package source under `src/`;
- workspace members in `components/*`, `packages/*`, or arbitrary paths;
- workspace members declared explicitly or through glob patterns in `[workspace].members`;
- excluded members and nested workspaces;
- generated/build inputs referenced by `build.rs` outside the listed root files.

Conversely, a simple `starts_with("crates/")` may include paths that are not workspace members.

Path handling needs a defined canonical representation. Git status and diff output can contain:

- `./` prefixes;
- quoted or escaped paths;
- rename pairs;
- deleted paths;
- paths with spaces;
- platform-specific separators;
- directory names such as `crates-old/` that must not match `crates/`.

The rule must be tested against positive and negative controls, including `.planning/spikes/.../Cargo.toml`, `crates-old/foo.rs`, root `src/main.rs`, renamed files, and workspace members outside `crates/`.

### D-03 — prompt text cannot override hardcoded workflow behavior

The repository already contains dedicated checkpoint auto-decision machinery (`checkpoint_auto_decide_prompt`, `workflow._auto_chain_active`, and `execute-phase` auto-mode handling). If `execute-phase` selects the first option in code or shell logic, adding prose to `code_stage_prompt` cannot reliably change that behavior.

Potential outcomes include:

- the prompt is never consulted by the internal decision loop;
- the agent follows the instruction but the executor still records the first option;
- the instruction applies only to Code-stage invocation, while auto-resume occurs in another process or prompt;
- rationale is generated in free text but not persisted in the gate/audit ledger;
- recommended-option markings are treated as mandatory despite the stated “on merits” requirement.

This decision requires an explicit distinction between:

- policy supplied to the LLM;
- deterministic executor behavior;
- checkpoint parser/selector;
- persisted decision evidence.

If the hardcoded “first option” behavior belongs to GSD’s scripts rather than DevFlow, DevFlow cannot claim to fix it through `prompt.rs` alone. The plan must identify the actual authority and add an integration test proving that option order changes the selected decision.

## Recommendations for planning

1. **Split D-01 into separate configuration fields or explicitly constrain scope.** Define `worktree_start_ref`, `integration_target`, and any release target semantics. Update feature creation, merge, ancestry checks, cleanup, preflight, and release hooks consistently. Add tests for configured branch, default fallback, missing refs, stale `origin/*`, and divergence.

2. **Resolve the configured branch against both local and remote refs deliberately.** Specify whether DevFlow fetches, requires a prior fetch, or degrades with an actionable error. Test `RefAbsent`, stale remote tracking, and local-only branches.

3. **Implement D-02 from Cargo metadata rather than a directory prefix.** Prefer `cargo metadata --no-deps` or equivalent workspace parsing, cache the member roots, normalize Git paths, and define treatment of root packages, nested workspaces, excluded members, renames, and build-script inputs. If the intended scope really is only `crates/*`, rename the decision accordingly and document the deliberate limitation.

4. **Trace D-03 to the real decision authority before coding.** Locate the exact GSD loop that chooses the first option. If it is deterministic DevFlow code, change the selector and persist structured rationale. If it is external GSD behavior, treat prompt text as advisory only and add a verification gate that rejects an unreasoned or inconsistent decision.

5. **Add negative-control acceptance tests.**

   - D-01: start from configured planning branch, then verify Ship merges/checks/cleans against the intended target; repeat with default `develop`.
   - D-02: `.planning/spikes/.../Cargo.toml` must be false while a real workspace member change must be true; include root-package and outside-`crates` cases.
   - D-03: present two decisions in reversed order and assert the selected option follows merits, not position, with rationale persisted.

6. **Add an explicit compatibility and migration rule.** Existing configs must continue using `develop`; conflicting `git.base_branch` and `git.planning_branch` values must fail clearly rather than silently choosing one.
