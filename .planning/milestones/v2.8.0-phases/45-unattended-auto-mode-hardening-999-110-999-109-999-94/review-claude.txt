## Adversarial Review — Phase 45: Unattended Auto-Mode Hardening

**Summary verdict: APPROVED WITH CONCERNS**

The problem diagnoses are correct and each decision addresses its stated symptom. But I traced all three against the actual code (`config.rs`, `git.rs`, `staleness.rs`, `prompt.rs`, `preflight.rs`, `commands.rs`) rather than the CONTEXT.md's abstractions, and each decision has a scope gap that will surface as a real bug, not a theoretical one.

---

### D-01 (base branch resolution) — the concern is real and already provable in code

`git.base_branch` is being proposed as *the* fix, but "which branch is the trunk" is not one setting in this codebase — it's at least three independent, already-configurable surfaces that currently all default to the literal string `"develop"` and have no relationship to each other:

1. **`GitFlowConfig.develop`** (`crates/devflow-core/src/config.rs:55`, already user-overridable via `devflow.toml` since Phase 16) — drives `GitFlow::is_merged_into_develop` and `GitFlow::divergence_from_develop` (`git.rs:170,392`). These are the Ship-stage/status functions that decide whether a feature branch has landed and whether local trunk is behind origin.
2. **The bare string literal `"develop"`** in `commands::phase_artifact_on_develop` (`commands.rs:90-97`) — used by preflight to check CONTEXT.md/PLAN.md existence before allowing a headless run. Not routed through `GitFlowConfig` at all today.
3. **The already-generic `base: &str` parameter** threaded through `phase_reachability_on_base`, `ensure_phase_reachable_on_base`, `base_ref_currency`, `ensure_base_ref_current` (`preflight.rs:146,286,368,537`) and `tag_exists_and_reachable` (`commands.rs:3458`) — these already accept a configurable base, but nothing currently *feeds* them anything other than `"develop"`.

If D-01 introduces `git.base_branch` and only threads it into worktree creation + the preflight functions that already accept `base: &str`, **`GitFlowConfig.develop` is untouched** — because it's a separate struct with its own default. Concretely: an operator sets `git.base_branch = workspace/denniyahh` to fix the AUTO-01 symptom (worktree missing `.planning/config.json`). The phase worktree now forks correctly. But at Ship time, `GitFlow::is_merged_into_develop` still asks "is this ancestor of `develop`?" — never true, since the branch's parent lineage is `workspace/denniyahh`. Ship status/merge-completion logic silently misreports every phase as unmerged, or the merge-back step (wherever it targets `GitFlowConfig.develop`, i.e. `develop`) pulls in `workspace/denniyahh`'s full unrelated history as a side effect of the merge. This isn't speculative — it's two independently-defaulted config surfaces in the code today, and D-01 as scoped ("configuration fields and worktree creation call sites … and preflight") doesn't visibly claim the Ship-side ones.

Also unaddressed: `base_ref_currency` fetches `origin/{base}` and fails closed if diverged from local. Personal branches like `workspace/denniyahh` are frequently *not pushed* to `origin` (per this session's own git status: branch is ahead, and a memory record flags this exact branch going 20 commits unpushed for days). If `git.base_branch` points at an unpushed local branch, `ensure_base_ref_current` will either warn-and-proceed (fail-open path) or, worse, treat a branch with no `origin/*` ref as `Undeterminable` — need to confirm which, because "fail-open" here means auto-mode silently skips a currency check it was designed to enforce, on every single run, not just this one.

### D-02 (workspace-scoped staleness) — right idea, one under-specified predicate

Verified against the actual workspace: `Cargo.toml` lists only `crates/devflow-core` and `crates/devflow-cli` (no root `src/`), and `crates/devflow-cli/build.rs` is a **per-crate** build script, not a root one. `rust-toolchain.toml` is root-only. So the concrete file layout matches D-02's assumption — good.

The gap is in the CONTEXT.md's own wording, not the underlying reality: it says scope to "`crates/*`… **plus root build files**." Taken literally, that phrase could be implemented as an *exact* top-level match for `Cargo.toml`/`Cargo.lock`/`build.rs`/`rust-toolchain.toml`, which would silently stop matching `crates/devflow-cli/build.rs` — except it wouldn't, because that path is already inside `crates/*` and gets caught by the prefix rule regardless. That's a lucky coincidence of the current layout, not a property the spec establishes. If a third crate is ever added with its own `build.rs`, or if `.cargo/config.toml` (workspace-level rustflags/linker config — currently not in `BUILD_AFFECTING_FILES` at all, pre-existing gap, not introduced by D-02) starts mattering, the predicate needs the planner to write it as "starts-with `crates/` OR exact-match one of these root filenames," not "root files, more narrowly scoped than before." Worth being explicit in the plan rather than trusting the CONTEXT.md prose.

Minor: `rust-toolchain` (no `.toml` extension) is also a rustup-recognized filename; this repo only uses the `.toml` variant today, so it's not a live bug, just a thing the planner shouldn't assume is out of scope if anyone ever adds the bare file.

### D-03 (decision-checkpoint policy prompt) — likely redundant, possibly inert, wrong control surface

This is the weakest of the three decisions, for a reason the CONTEXT.md doesn't surface: **`checkpoint_auto_decide_prompt` already exists** (`prompt.rs:515-527`, itself labeled D-03 from an earlier phase, 28-CONTEXT.md) and already does almost exactly what DECN-01 proposes — "resolve the checkpoint yourself, using your own best judgment… record your reasoning… auditable." So either:

- DECN-01 is describing the *same* mechanism and the phase is largely already shipped (in which case Phase 45 should verify and close, not re-implement), or
- DECN-01 is about a genuinely different mechanism — GSD's own internal `checkpoint:decision` type inside `execute-phase`'s skill logic, which (per this project's own memory record on `checkpoint:decision`) has **no resume path at all** under DevFlow's one-shot `claude -p` launch model, and where "take the first option" may be a scripted/procedural step in GSD's skill file that runs *before* the agent ever reasons about the prompt DevFlow hands it.

I grepped `gates.rs` and `pipeline_gate.rs` for any "first option" / checkpoint-kind dispatch logic and found none — confirming the blind-first-option behavior described in the phase's own problem statement is **not DevFlow's code**, it's GSD-core's (`@opengsd/gsd-core`, an external package this repo doesn't own). That directly answers the reviewer question: injecting instruction text into `code_stage_prompt` cannot override a hardcoded script step in an external tool's workflow. If GSD's `execute-phase.md` resolves `decision` checkpoints procedurally (not via LLM judgment) when unattended, no amount of prompt-layer instruction changes that behavior — the fix belongs upstream in GSD-core, and D-03 would ship a prompt nobody's inference path ever reads for the specific failure mode DECN-01 describes. If GSD instead *does* delegate to the agent's judgment already but the agent defaults to "just pick first to keep moving," then D-03 is plausible but is competing with whatever instructions the `/gsd-execute-phase` slash command itself injects — precedence between DevFlow's wrapper text and GSD's own skill instructions is unverified and needs to be checked before writing the plan, not after.

---

### Recommendations for planning

1. **D-01**: Before planning worktree/preflight call sites, decide explicitly whether `git.base_branch` *replaces* `GitFlowConfig.develop` for merge/divergence purposes or is a second, independent knob. If independent, the plan must state — and a test must enforce — that Ship-stage merge target, `is_merged_into_develop`, and `divergence_from_develop` all read the same resolved value `devflow start` used to fork the worktree. Add a currency-check test where `base_branch` names a branch with no `origin/*` counterpart (the realistic case for personal branches) and assert the actual fail-open/fail-closed behavior, not the assumed one.
2. **D-02**: Write the predicate as "path starts with `crates/` OR path exactly equals one of the four root filenames," and add a regression test for a hypothetical `crates/*/build.rs` to lock in that the prefix rule — not a hardcoded root-only list — is what's carrying it.
3. **D-03**: Before writing a plan, get a straight answer from the GSD-core skill source (or a maintainer) on whether `decision`-checkpoint resolution under `--auto`/unattended is a scripted step or an LLM-judgment step. If scripted, redirect DECN-01 to a GSD-core issue instead of a DevFlow prompt change, and note in CONTEXT.md that Phase 28's existing `checkpoint_auto_decide_prompt` is a distinct, already-shipped mechanism for a different checkpoint kind (`blocking-human` gates) so the two aren't conflated during review.
4. General: none of the three decisions currently name a test that exercises the *unhappy* path (base branch unpushed to origin; a spike crate added outside `crates/`; a GSD decision checkpoint hit under `--mode auto` end-to-end) — add one negative-control test per decision before calling any of them done, per this repo's own standing rule about proxy measurement.
