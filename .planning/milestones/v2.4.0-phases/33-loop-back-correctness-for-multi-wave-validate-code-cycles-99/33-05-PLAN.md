## The fix — transcribe the shape, do not re-derive it

### The one-line correction, and why it must repeat three times

`select_loop_back_fix`'s first parameter is renamed to `evidence_root`, and each of the three call
sites inside `handle_validate_outcome` resolves it with the codebase's existing fallback expression
`state.worktree_path.as_deref().unwrap_or(project_root)`.

It cannot be hoisted to a single binding at the top of `handle_validate_outcome`. That would be a
shared borrow of `state` living across the whole function, while `state` is passed as `&mut` to
`run_gate`, `transition`, `abort` and `loop_back_to_code` throughout it. The three-site repetition is
forced by the borrow checker, not a style choice — and it matches the fix shape `33-REVIEW.md`
records. Do **not** introduce a new helper function to deduplicate it: the prescribed change adds no
new symbol beyond the renamed parameter, and a helper would have the same borrow profile anyway.

### The two adjacent reads must stay on different roots

This is the single most important property of the change, and the easiest to destroy while "tidying
up" the neighbourhood:

| Read | Correct root | Why |
|---|---|---|
| `phase_verification_exists` (`:244`, via the helper) | the **worktree** | `.planning/` is tracked; the agent authors the artifact in its own cwd, and it is committed to the feature branch, invisible from the main checkout until merge |
| `phase_commit_count` (`:301-302`) | the **main checkout** | git refs and the object database are shared across worktrees, so the main checkout can already see the worktree's commits — and `33-REVIEW.md`'s own negative control observed exactly that, reading `1` from the main checkout in the same probe where the `.planning/` artifact read as absent |

Two adjacent lines, two opposite correct answers. The prohibition against retargeting the second one
is in `must_haves.prohibitions` and is checked mechanically in Task 1's acceptance criteria.

### Borrow-checker decision rule

Prefer binding the returned `FixType` to a local immediately before the `loop_back_to_code` call, so
the shared borrow of `state` ends before the mutable one begins. If an inline form compiles, that is
fine too. Reach for a `.to_path_buf()` allocation **only** if the borrow checker actually demands it,
and if it does, say so in the SUMMARY rather than leaving the allocation unexplained.

**The control relationship, stated explicitly rather than left implicit.** Scenario A is the mirrored
negative control the verification prescribes: same worktree setup as the positive test, opposite
precondition, opposite required outcome. Without it the new suite cannot tell the real fix apart from
a no-op that returns `GapsOnly` whenever a worktree happens to be configured. The two preserved
tests are the third leg — they are what proves the `unwrap_or` fallback still works, so a fix that
reads the worktree *unconditionally* fails them rather than shipping.

**Scenario B is a planner addition beyond the verification's `missing:` list, and is flagged as such
rather than folded in silently.** Its cost is roughly twenty lines inside a test function that
already exists for scenario A; what it buys is discrimination the prescribed pair cannot supply. An
implementation that checks *both* roots — a plausible and superficially safer misreading of the fix —
passes the positive test, passes scenario A, and passes both preserved tests. Scenario B is the only
case that fails it. It is also the case that most directly encodes why the OR is wrong: an artifact
visible from the main checkout while a phase is in flight in a worktree is a stale artifact from a
different run, and treating it as this phase's evidence is CR-01 with the sign flipped. If the
executor judges scenario B genuinely infeasible, report that as a finding — do not drop it quietly.
