## Root cause, in one paragraph

33-03 changed `handle_validate_outcome` so `consecutive_failures` resets to 1 when
`mode::consecutive_failures_made_progress(state.last_validate_failure_commit_count, current)` is
true, and `consecutive_failures_made_progress(None, _)` is `true` by construction (33-02's design:
"no prior record" reads as progress). Any test that seeds `consecutive_failures` directly — rather
than driving it there through repeated real failures — therefore has a `None` baseline, and its
pre-seeded streak is silently reset to 1 on the first `handle_validate_outcome` call. 33-03's Rule 1
deviation fixed three such sites in `pipeline_outcomes.rs`. It missed two more.

### Why these three discriminators and not others

| | abort path (what the abort test intends) | loop-back path (the bug) |
|---|---|---|
| `state.stage` after the call | stays `Validate` — `abort()` takes `&State` and cannot mutate it | set to `Code` by `prepare_loop_back_to_code` |
| `state.consecutive_failures` | accumulated to `>= MAX_CONSECUTIVE_FAILURES` | reset to 1 by the progress branch |
| `loop_back` event payload | never emitted | emitted, carrying `consecutive_failures` |

The gated-arm test reads the **event payload**, not post-call state, deliberately:
`prepare_loop_back_to_code` interpolates the counter into the event at the moment the arm is taken
(pipeline_gate.rs:150), which is the fact under test. Asserting `should_gate(...)` on post-call
state instead would be probing a value adjacent to the question rather than the question itself.
