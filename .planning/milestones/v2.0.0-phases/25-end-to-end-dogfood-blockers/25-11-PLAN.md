`25-CONTEXT.md` **D-02** states 999.47's production risk is already closed, because
`looks_like_devflow_process` has *no production callers* — `stop` moved to
`lock::holder_identity`'s recorded `(pid, starttime)` pair. **That was accurate on
2026-07-27, about `stop`.** It was then invalidated by this phase's own 25d work
(**D-17**): plans 25-02 and 25-07 introduced `agent::discover_stray_devflow_processes`, a
**new** `/proc`-cmdline-derived inference, in production, with two live consumers —
`commands::gate_sweep`'s `--reap-strays` pass (`commands.rs:1149-1151`) and `doctor`'s
`collect_stray_process_findings` (`commands.rs:2998-2999`). D-13's own reasoning applies to
it verbatim: *"Any `/proc`-derived inference races exec."*

The reachable production hazard is the **false-positive** direction, and it is destructive:

1. `monitor::spawn_monitor_inner` (`monitor.rs:134-160`) spawns `sh -c <script>` where the
   script contains `MONITOR_WRAPPER_MARKER` verbatim.
2. That wrapper shell forks for the agent (`"$@" ... &`) and again for the trailing
   `devflow advance`. `agent.rs`'s own doc comment (`:175-187`) states the rule: between
   `fork()` and `execve()` *"the child is a copy of its parent: `/proc/<pid>/cmdline`
   reports the PARENT's argv."*
3. So each of those transient children, mid-window, presents `sh`, `-c`, and a script
   containing the marker — exactly `classify_stray_layer`'s Layer 1 test
   (`agent.rs:373-380`). It is classified `MonitorWrapper`. Symmetrically, a child forked by
   `devflow advance` presents argv[0] basename `devflow` and argv[1] `advance` — Layer 2.
4. `reap_stray_candidates` (`commands.rs:1273-1314`) re-confirms `is_same_process`. That
   guard **passes**: it is genuinely the same process with the same start time. The guard
   defends against pid *recycling*, not against fork-inheritance.
5. `terminate_and_verify` then sends `SIGTERM`, escalating to `SIGKILL`.

Net: `devflow gate sweep --reap-strays` can kill a healthy, just-launched agent or monitor.
The test at `commands.rs:3663-3667` states outright that this command is expected to run
while *"this machine's live process table legitimately contains other, unrelated devflow
activity (concurrent phases in sibling worktrees)"* — so the co-occurrence this needs is not
hypothetical, it is the documented operating condition.

The **false-negative** direction (the test-side shape: a census miss during the window) is
NOT a production concern — a process created microseconds ago is by construction not a
stray, and `gate_sweep` re-runs discovery after each pass. So the production mitigation
targets the false-positive direction only, and it lives in plan 25-12, not here.

**This plan is scoped to (a), the test-side barrier.** It is what unblocks the push.
</scope_decision>
