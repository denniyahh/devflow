<why_this_does_not_block_the_code_fixes>
This plan sits in wave 2 and depends on 25-08 and 25-09 — it is BLOCKED BY them, and blocks
neither. That shape is deliberate and load-bearing for two reasons:

1. **Evidence validity.** `ci.yml` sets `concurrency: group: ${{ github.workflow }}-${{ github.ref }}`
   with `cancel-in-progress: true`. If this plan ran in parallel with 25-08/25-09, their
   merges would push new commits to the same ref and CANCEL any trial in flight, silently
   destroying the observation. Trials are only meaningful on a settled branch head.
2. **Attributability.** The tree that ships is the tree with both fixes in it. Observing CI
   on a pre-fix tree would produce evidence about code that is about to change.

Its own verification is latency-bound (it waits on real CI, roughly 5–15 minutes per
trial, up to five trials plus a human sign-off). Nothing else in this gap-closure run waits
on it.
</why_this_does_not_block_the_code_fixes>

<trial_design>
**N = 5 consecutive green trials.** 999.47's historically observed reproduction rate was
roughly 50% per CI run (`ROADMAP.md`: "cost two retries on 2026-07-27 alone (~50% failure
rate)"). Five consecutive greens bound the residual probability that the flake is still
live at 0.5^5 = 1/32 ≈ 3.1%. Fewer than five is not sufficient evidence; this number is not
negotiable downward inside the plan.

**Why reruns of one run are valid trials.** `ci.yml` has NO `actions/cache` step, so every
job is a cold checkout, cold `cargo build`, cold `cargo test`. Each attempt runs in a fresh
`mcr.microsoft.com/devcontainers/rust:2.0.13-1-bookworm` container, on the same pinned
image `scripts/assert-image-parity.sh` enforces. Holding the head SHA fixed across trials
is a feature, not a shortcut: it makes all five observations attributable to exactly the
tree that ships, which distinct pushes would not.

**Serialization is mandatory.** Because of `cancel-in-progress: true`, trial *k+1* must not
be started until trial *k* reports `status: completed`. A run whose conclusion is
`cancelled` is NOT a trial: record it as discarded and re-run it.
</trial_design>
