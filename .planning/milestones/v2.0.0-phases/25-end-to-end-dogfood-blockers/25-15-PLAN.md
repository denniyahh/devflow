<objective>
Stop `devflow doctor` from telling an operator that live, registered DevFlow processes are orphans,
and stop `devflow gate sweep --reap-strays` from SIGKILLing them.

The `/proc` census is purely structural by design — argv shape plus euid, no orphan test of any
kind — and `agent.rs` documents that plainly, placing the obligation on the caller. Neither caller
discharges it. `doctor` asserts orphan-ness it never checked and names a destructive repair; the
sweep acts on the same unfiltered list behind a 2-second age floor that bounds the fork/exec
cmdline-inheritance race and has no bearing on whether a process is owned. A monitor wrapper minutes
old sails past that floor. SIGKILL is uncatchable, so the wrapper's `trap cleanup TERM INT` never
fires and its backgrounded child is orphaned — manufacturing exactly the orphan class 999.44 exists
to eliminate.

Purpose: unit 25d's primitives are sound (`25-VERIFICATION.md` truth 6, verified). The defect is
entirely in what gets handed to them. This plan interposes one filter, shared by both surfaces, and
corrects the three operator-facing strings that describe semantics the code did not have.

Output: a registry-reachability filter, an explicit ruling on `--root`, corrected `doctor` and
`--reap-strays` wording, a corrected census doc comment, and a regression test in which a live
registered pid and a genuine orphan appear in the same discovery pass.
</objective>

<why_this_does_not_violate_d17>
**D-17 requires 25d's discovery to be registry-INDEPENDENT. This plan adds a registry-based filter.
The two are compatible, and the argument must be checked rather than assumed — it is the one way
this fix could silently undo the unit it is repairing.**

`agent::discover_stray_devflow_processes` is not touched (except for its doc comment). Discovery
remains a `/proc` census with no registry input, no lock-file input, no state-file input, and no
parentage test. What changes is that the two CALLERS subtract a set before acting.

The question that matters: can that subtraction hide 999.44's originating case — a live process
whose project root was deleted out from under it?

No, and the mechanism is stated in `25-RESEARCH.md`:441, independently of `25-REVIEW.md`'s own
claim: once the root directory is gone, `.devflow/lock-{phase:02}` and `.devflow/state-{phase:02}.json`
under that root are gone with it, so `lock::holder_identity` and `workflow::list_states` both return
nothing for it *even while the OS process is still alive*. A deleted root therefore contributes
ZERO pids to the reachable set. Subtracting the empty set changes nothing. `registry::prune_missing`
removes such entries entirely, which only makes the set smaller still.

The filter can only ever remove pids that a live, on-disk state file or lock file names — which is
exactly the population `doctor` currently misreports and the sweep currently destroys.

This argument is not left as prose: Task 1's `a_deleted_root_contributes_nothing_to_the_reachable_set`
asserts it against a real spawned process with a real deleted root, and the pre-existing
`reap_strays_e2e.rs` deleted-root tests remain green unmodified.
</why_this_does_not_violate_d17>

<resolved_decision>
## `--root` cannot narrow the safety set — ruling, with the reason the suggested alternative is refused

`25-VERIFICATION.md`'s `gaps[1].missing` offers: *"Honour `--root` in the stray pass (scope the
reachable-pid filter to the given root), or document loudly at the call site why it cannot be
scoped."* `25-REVIEW.md`'s CR-01 makes the same offer.

**Ruling: the parenthetical is refused. Scoping the reachable-pid filter to `--root` would make the
command MORE dangerous, not less.**

The reachable-pid set is a SAFETY set — a subtraction. Narrowing it does not narrow what gets
reaped; it narrows what gets PROTECTED. `devflow gate sweep --root /project-a --reap-strays` would,
under the parenthetical, compute the reachable set from `/project-a` alone, and then reap the whole
machine's census — including `/project-b`'s live monitor, which is now unprotected because
`/project-b` was excluded from the safety set. That is a strictly larger blast radius than the
status quo, delivered under a flag whose help text promises restriction.

**What gets built instead, in three parts:**

1. **The reachable set is always machine-wide.** It is computed from `registry::load_roots()`
   regardless of `--root`, and the explicit `--root` is UNIONED IN (not substituted), so a root the
   registry has not recorded — the plausible reason an operator passes `--root` at all — is also
   protected.
2. **The reaping scope genuinely cannot be narrowed, and that is documented at the call site.** A
   stray by definition has no project root for any registry entry, lock file, or state file to name;
   there is no root-valued attribute on a `StrayProcess` to filter by. The existing comment at
   `commands.rs:1143-1148` already says this and is correct — it is retained and extended with the
   safety-set half, which is the half it does not currently address.
3. **The operator is told, at the terminal, not only in a comment.** When `--root` and
   `--reap-strays` are combined, the sweep prints a warning line before the pass. The `--root` help
   text in `main.rs` says the same. A flag that silently means something different from its help
   text is how CR-01 reached an operator in the first place.

**Consequence for the discretionary sweep behaviour:** `--reap-strays` is opt-in, was introduced by
25-07 within this same phase, and has never been released. Changing what it reaps is therefore not
a compatibility break on any shipped surface — the rating on both tasks is `reversible` rather than
`costly`, and no `checkpoint:decision` is warranted under this run's reversibility gate.
</resolved_decision>
