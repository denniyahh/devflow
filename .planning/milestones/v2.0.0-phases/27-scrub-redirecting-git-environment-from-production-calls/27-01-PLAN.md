## Shared recipe: the hostile-`GIT_DIR` harness

Every verification in this phase that needs a hostile environment uses this exact
shape. `HOSTILE` is a throwaway repository unrelated to the workspace; setting
`GIT_DIR` for only the `cargo` invocation is deliberate — process-global
`std::env::set_var` is `unsafe` in Rust 2024 and unsound here (Phase 25 D-14).

```
HOSTILE=$(mktemp -d) && git init -q "$HOSTILE"
GIT_DIR="$HOSTILE/.git" cargo test <scope>
```

A `test result:` line must actually print. A timeout, or a `0 passed` line (which
means the filter matched nothing — see the `--exact` false-green trap), is a
FAILURE, not a pass.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| parent process env -> `devflow` process | An operator shell, a git hook, `rebase --exec`, `bisect run`, or `submodule foreach` may export `GIT_DIR` / `GIT_WORK_TREE` into DevFlow. DevFlow does not control what is on the other side of this boundary. |
| `devflow` process -> spawned `git` child | The only boundary this phase can control. Everything the child sees is chosen here; the scrub happens on this edge. |
| spawned `git` child -> on-disk repository | Resolved by the `git` binary itself from `--git-dir` > `GIT_DIR` > `.git` discovery from cwd. Out of DevFlow's reach; the environment is the only lever. |
