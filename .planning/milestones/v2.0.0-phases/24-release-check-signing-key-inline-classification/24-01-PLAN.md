<objective>
Make `check_ssh_signing_viability` classify an inline (literal) `user.signingkey`
value the way git itself does, instead of assuming every value is a filesystem
path.

Today the function does `Path::new(&signingkey)` then `key_path.exists()`, and on
a miss returns `NotViable { reason: "…the key file does not exist" }`.
`check_signing` maps `NotViable` → `"fail"`, and `release_check` turns any
`"fail"` into a non-zero exit. So an operator with a legitimately viable inline
signing key gets `devflow release --check` failing, with a factually wrong
reason. This is a false hard-fail on a correct configuration, not a wording nit.

Purpose: predict what git will actually do at `git tag -s` time. Git classifies
`user.signingkey` by prefix and never stats it (D-01), so any rule that diverges
from git's is wrong by construction — including the "safer-looking" try-the-path-
first ordering that D-02 explicitly rejects.

Scope: the `gpg.format=ssh` branch only. One pure classifier, one sibling
fingerprint helper, one rewired arm, and the unit tests that prove them (D-11).
`check_gpg_signing_viability`, the other three preflight checks, and every CLI
mapping are untouched.

Output: `crates/devflow-core/src/git.rs` with `inline_signing_key_blob` and
`inline_key_fingerprint` added, `check_ssh_signing_viability` rewired, and five
new tests in its existing `mod tests` block.
</objective>

**Step 3 — the stdin fingerprint helper (D-05, D-09).** Add a private
`fn inline_key_fingerprint(key_blob: &str) -> Option<String>` directly below
`public_key_fingerprint`, mirroring its `Option<String>` return, its `.ok()?`
fail-soft chain, its `if !output.status.success() { return None; }` guard, and its
identical `String::from_utf8_lossy(&output.stdout).split_whitespace().nth(1).map(str::to_string)`
parse — `ssh-keygen -l`'s output shape is the same whether the key arrived by
path or by stdin, so do not write a second parser. What differs: build
`Command::new("ssh-keygen")` with `args(["-lf", "-"])`, set `Stdio::piped()` on
stdin, stdout and stderr, `.spawn().ok()?`, then `child.stdin.take()?`,
`write_all(key_blob.as_bytes()).ok()?`, explicitly `drop` the stdin handle, and
finish with `child.wait_with_output().ok()?`. The `.take()` + `drop` is
mandatory, not stylistic: borrowing via `as_mut()` happens to work on this host
but does not positively close the pipe, and a differently-shaped input could hang
(RESEARCH Pitfall 1). Add the two missing imports — `std::io::Write` and
`Stdio` alongside the existing `Command` — in the house import order.

The blob is written to stdin and to nothing else: never an argv element, never a
temp file (D-09). Argv is world-readable through `/proc/<pid>/cmdline`, and this
project already holds the no-interpolation-of-sensitive-data line from Phase 12.
State that constraint in the doc comment so a later refactor that passes the blob
as an argument is recognisable as a security regression rather than a cleanup.
Also record the D-06 discretion call in that doc comment: a value of exactly
`key::` yields an empty blob, `ssh-keygen` then exits non-zero, and this function
returns `None` — which the caller routes to `Unknown`. That is the intended
outcome and needs no special-case branch.

**Step 4 — rewire the classification arm (D-02, D-07, D-12).** In

do not retype them. When it is `Some(_)`, perform no path construction and no
