## The registry's storage shape changed in this revision, and why

**Cross-AI review BLOCKER 4, orchestrator-verified.** The previous revision
stored the whole registry in one `roots.json` and registered by
load-modify-write. Its concurrent acceptance criterion accordingly asked only
that the file afterwards contain **"at least one"** of two concurrent entries,
and its threat model conceded a concurrent registration **"can lose an entry"**
— while this plan's own success criteria claimed *"a running phase cannot be
missing from the registry."* Those cannot both be true. A lost entry makes
`gate list --all-roots`, plan 23-04's sweep, and plan 23-05's stop blind to an
active gated run, which is precisely the failure this plan exists to prevent,
and `devflow parallel` can launch several phases within milliseconds of each
other on the launch path that registers.

**Resolution: one file per `(project_root, phase)`**, in a `roots/` directory,
enumerated with `read_dir`. Registration writes only its own file, so there is
no read-modify-write window and therefore no lost-update race to mitigate —
both concurrent registrations survive, and the acceptance criterion now requires
exactly that. This also strictly improves corruption tolerance: one torn file
costs one entry instead of the entire registry, so a truncated write can no
longer blind enumeration to every other root on the machine.

Rejected alternative: keeping one file and serializing writes with an advisory
lock (the `File::create_new` spin `lock.rs:75-110` already implements). It works,
but it adds a contended lock on a hot launch path in order to defend a data
structure that did not need to be shared in the first place, and a crashed
holder then needs its own stale-lock recovery — `lock.rs` carries roughly forty
lines of exactly that, for exactly that reason. A directory of independent files
has no such failure mode.
