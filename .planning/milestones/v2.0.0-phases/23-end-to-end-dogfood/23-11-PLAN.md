## Two outcomes, not one: RUN RECORD and ACCEPTANCE VERDICT

**Cross-AI review MEDIUM (Codex), adopted.** The previous revision conflated
"this artifact is a valid run record" with "the phase's acceptance criterion was
met": Task 1's automated verification required a workflow-finished event in the
artifact, while the same plan correctly insisted that an incomplete run should
still be documented accurately. Those requirements pull against each other, and
in the direction that matters — an honest failure record could not satisfy its
own verification, which is exactly the pressure that produces a rewritten record
rather than a truthful one. This phase exists because of a document that scored
a stage it had not run.

**Resolution.** The artifact opens with a machine-readable declaration, on its
first content line, of the form `outcome: acceptance-passed` **or**
`outcome: run-incomplete`, and the two are verified separately:

- **RUN RECORD VALID** — checked by Task 1. Requires the structural evidence
  contract: the verbatim launch command, event excerpts, the absent-events list,
  the poll series, the staleness finding, the manual-intervention assertion, and
  an `outcome:` declaration that matches what the evidence shows. **A
  `run-incomplete` record can and should pass this.** It requires, additionally,
  the exact stop cause and the cleanup state.
- **ACCEPTANCE PASSED** — checked by Task 2, and only claimable when
  `devflow evidence --phase <target> --require-shipped` exits zero on the
  post-run tree. Nothing else may be substituted for it: not the event excerpt,
  not the git log, not the record's own prose.

A run that stops short and says so precisely is a successful execution of this
plan and a failed acceptance run. Task 3's human checkpoint judges both, in that
order.
