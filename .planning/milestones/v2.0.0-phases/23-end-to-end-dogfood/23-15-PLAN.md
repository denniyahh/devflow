## Two outcomes, not one: RUN RECORD and ACCEPTANCE VERDICT

Retained verbatim in intent from `23-11-PLAN.md`, because the pressure it
defuses is real and this plan is under more of it than the last one was — a
second consecutive failed acceptance is exactly the situation in which a record
gets quietly improved.

The artifact opens with a machine-readable declaration on its first content
line: `outcome: acceptance-passed` **or** `outcome: run-incomplete`. The two
outcomes are verified separately:

- **RUN RECORD VALID** — checked by Task 1. Requires the structural evidence
  contract: the verbatim launch command, event excerpts, the absent-events list,
  the poll series, the guard-at-launch record, the staleness finding, and the
  manual-intervention assertion, with an `outcome:` declaration matching what
  the evidence shows. **A `run-incomplete` record can and should pass this.**
- **ACCEPTANCE PASSED** — checked by Task 2, and claimable only when
  `devflow evidence --phase 24 --require-shipped` exits 0 on the post-run tree
  **and** a `workflow_shipped` event for phase 24 exists in `.devflow/events.jsonl`.
  Nothing may be substituted: not `workflow_finished`, not the git log, not the
  record's own prose. `workflow_finished` is emitted at two sites — real Ship
  finalization and `transition`'s `--until` clean-stop branch — which is
  precisely the false green 23-06 was built to eliminate.

A run that stops short and says so precisely is a successful execution of this
plan and a failed acceptance run. Task 3 judges both, in that order.

## Operational hazards, named so they are not discovered

**This plan runs in the primary checkout, sequentially.** The acceptance run is
detached and outlives any single agent turn. An executor operating inside a
linked worktree does not own that run — it orphans it. Task 1's precondition
asserts this before launching.

**Do not stop the run to fit a turn.** If the observation window exceeds the
executing agent's budget, record the poll series so far, mark observation as
ongoing, and hand the polling command back to the operator. `devflow stop` is a
sanctioned abort, not a scheduling tool: using it to end an otherwise-healthy
run converts a possible pass into a certain failure.

**Do not repeat the probe's instrument defect.** `23-PROBE-FINDINGS.md` records
a polling loop that substring-matched only the last line of the event stream for
a gate marker, and missed a pending gate because the true last line was the
notify event that follows it. Test the whole recent tail, and test for events by
name.

**The one-way gate for Task 1 lives in 23-14, not in this file.** Task 1 carries
a `one-way` reversibility rating; its decision checkpoint is **23-14 Task 3**, a
blocking `checkpoint:decision` in the immediately preceding wave that this plan
depends on. A structural validator scanning one plan at a time will flag Task 1
as ungated — that flag is a tooling limitation, and the gate is real. If 23-14
Task 3 selected `hold` or `retarget`, this plan does not start as written.
