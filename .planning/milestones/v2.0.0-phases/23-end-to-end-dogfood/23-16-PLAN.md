**This plan supersedes the previously-recorded next action.** `23-ACCEPTANCE-RUN-2.md` §15 and `23-VERIFICATION.md` both recorded the agreed next step as "retry with a develop-built binary" — build `devflow` from a `develop` checkout instead of `feature/phase-23`, because any binary built from the working branch has an embedded commit that is, by construction, not an ancestor of `develop`'s tip. **The operator has since rejected that plan as a workaround**, not a fix: building only from `develop` would permanently prevent dogfooding any change from the branch that contains it — a feature-branch fix could never be validated by actually running it. This plan replaces that workaround with the real fix: the staleness *check itself* is defective on genuinely divergent lineages, and closing that defect removes the need to special-case which branch the binary is built from.

**The defect, source-verified (re-verify every claim below yourself before trusting it):**

`crates/devflow-cli/src/staleness.rs`'s `embedded_commit_is_stale` (line ~45) is not coupled to `develop` — it compares the binary's embedded commit against `execution_root`'s `HEAD` (line ~50), whatever tree that happens to be. The apparent develop-coupling comes from elsewhere: `devflow start` forks the phase worktree from `develop`, so when `enforce_build_staleness` evaluates the worktree's `HEAD` (18c), that HEAD happens to be develop's tip.

The function has four ancestry outcomes, and the content-aware exemption `ancestry_range_affects_build` (line ~94, the 21d/999.29 fix — reused verbatim per D-07, never forked) guards only ONE of them:

| Topology | Result | Content check? |
|---|---|---|
| embedded == HEAD | Fresh | n/a |
| embedded strict ancestor of HEAD | Stale or Fresh | YES (line ~57) |
| HEAD strict ancestor of embedded | Ahead (warn) | n/a |
| divergent / mutually non-ancestor | **Stale** | **NO** |

Line ~76, `Ok(Some(1)) => Staleness::Stale` inside the reverse-probe match, is a bare return that never consults the exemption. That arm is what killed the 23-15 acceptance run: the running binary's embedded commit (`0c9dcfe`) and the phase-24 worktree's fork point (`0dad20d`) are mutually non-ancestors (`git merge-base --is-ancestor` exits 1 both directions — reconfirmed independently three times across `23-ACCEPTANCE-RUN-2.md` §10/§15 and `23-VERIFICATION.md`), and the only commit that made them diverge (`0c9dcfe` itself) touched nothing but `23-GUARD-SHIP-RECORD.md`.

**The fix is small because `ancestry_range_affects_build` needs no changes.** It runs `git diff --name-only <embedded> HEAD` (line ~97) — a two-dot diff that compares TREES, not history, so it is already correct across divergence. Only its call site is gated behind the wrong condition: it must also run in the divergent-lineage arm, not only the strict-ancestor arm.

**Empirical proof the fix unblocks the real case, independently reproducible:** `git diff --name-only 0c9dcfe 0dad20d` returns exactly one file (`.planning/phases/23-end-to-end-dogfood/23-GUARD-SHIP-RECORD.md`), which `affects_compiled_binary` classifies as non-build-affecting.
