<objective>
Run the phase's tracer: **one real, unattended `devflow start` in the scratch
repo, driven end to end, and record exactly where it dies.**

This is the leading vertical slice by construction, not by ceremony.
CONTEXT.md is explicit: *"23a leading is load-bearing, not ceremonial: it is the
only unit permitted to invalidate the rest of the scope."* Every downstream plan
(23-03..23-11) is gated on this plan's verdict. The run touches every layer the
phase will later modify — CLI entry, preflight, staleness, monitor spawn, agent
capture, stage transition, gate — on a single path, with a real agent, and its
`<verify>` is a real end-to-end observation rather than a per-layer unit test.

Grounding (`.devflow/events.jsonl`, ROADMAP.md's run-record table): **no phase
has ever completed a full five-stage devflow-driven run.** Phase 17 reached
Ship and died to two silent monitor deaths. Phase 21 stopped after Define.
Phase 22 stopped dead at a Plan relaunch with no `advance_evaluated`. The
hypothesis this phase is built on is that the `sh -c` monitor is the blocker.
This plan tests that hypothesis instead of assuming it.

Purpose: scope 23b/23c/23d from evidence (D-03), and give the phase a chance to
discover something cheaper that bites first.
Output: `23-PROBE-FINDINGS.md` — a recorded artifact with verbatim evidence —
and an explicit, human-confirmed scope verdict.

  <action>
Re-run `scripts/scratch-dogfood-repo.sh` into a **fresh** destination (do not
reuse the one plan 23-01 dry-ran against — a dry run may have left state), then
launch one unattended run and observe it to termination.

Launch, exactly: `devflow start --phase 1 --agent claude --mode auto <dest>`.
Note `--mode auto` deliberately: per `crates/devflow-core/src/mode.rs:82-94`,
Auto suppresses Validate gates but Ship **always** gates in both modes, so a run
that reaches Ship and parks is the expected, informative outcome — that parking
is itself the evidence for D-04 and must be recorded as such, not treated as a
failure.

Observation protocol, per 23-VALIDATION.md:
- Poll `devflow status <dest>` and `tail` the scratch repo's
  `.devflow/events.jsonl` every **30-60 seconds**. Short enough to catch a stage
  transition, long enough not to interfere.
- **Do not** run `devflow advance` manually. **Do not** inspect or signal
  processes with `ps`/`kill` to nudge the run forward. The whole point is to
  observe what an unattended operator would see. If you need process facts for
  the finding, capture them read-only and record that you did.
- Terminate observation when one of: `workflow_finished` is written; the run
  parks at a gate with no further events for >10 minutes; or no event has been
  appended for >30 minutes while `devflow status` reports something other than a
  healthy in-progress stage. Record which termination condition fired.

Evidence to capture into `23-PROBE-FINDINGS.md` — this is D-03's requirement and
it is not optional:
- Verbatim `events.jsonl` lines for every stage transition observed, at minimum
  the `transition`, `stage_launched`, `advance_evaluated`, `gate_fired`,
  `gate_resolved` and `workflow_finished` events that did appear, and an explicit
  list of which of those **did not** appear.
- The `.devflow/phase-01-*` capture files (`stdout`, `stderr.log`, `exit`,
  `agent-pid`) for at least the stage where the run succeeded or first failed —
  copy them into the findings document (truncate long stdout, but keep the head
  and tail and say how much was elided).
- The final `devflow status` and `devflow doctor` output.
- A timeline: wall-clock timestamps against stage transitions.

Then write the analysis section. It must answer, in these words:
- **Where it stopped** — which stage, which event was last, and what the
  `.devflow/phase-01-exit` file did or did not contain.
- **Why** — attribute the stop to a specific mechanism. If the monitor died,
  say which of the `sh -c` script's steps it died in and what proves it. If it
  was something else entirely (staleness, preflight, gate timeout, rate limit,
  a GSD command failing inside Claude), say so plainly — a finding that
  contradicts the phase's hypothesis is the highest-value outcome this task can
  produce.
- **Scope verdict** — one line each for 23b, 23c, 23d and `--yes-ship`, stating
  CONFIRMED / INVALIDATED / UNTOUCHED with the evidence that supports it.

If the run instead reaches a **completed** Ship stage, record that: it would
mean the phase's acceptance criterion is already reachable in a scratch repo,
which does not by itself close the phase (D-02's self-hosted run exercises the
staleness `Block` path that is structurally unreachable here), but it does
change what 23b is buying and must be stated as such.

Do not modify any Rust source in this task. Do not fix anything you find. The
deliverable is the finding.
