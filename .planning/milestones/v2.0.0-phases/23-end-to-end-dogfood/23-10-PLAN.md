## Is the acceptance criterion reachable once plans 23-03 through 23-09 land? Yes — with four named preconditions.

The orchestrator asked for this judgment explicitly. It is **reachable**, and
the evidence says so more strongly than at any prior point in this project's
history: two independent runs reached Ship within one hour on this machine
(`23-ORPHAN-FORENSICS.md`), with `infra_failures: 0` and eleven correct stage
launches on the one that was observed end to end (`23-PROBE-FINDINGS.md`). The
pipeline mechanism is not what stops it. Four things must hold:

1. **The Ship gate must be answerable without a human.** `Mode::should_gate`
   returns true for Ship in both modes, so an unattended run parks there by
   construction. Closed by plan 23-09.
2. **The target phase must produce a security artifact before Ship.** The probe
   at `/tmp/devflow-probe-02-...` reached Ship and was blocked at `/gsd-ship`
   preflight with "security ship gate active and blocking with
   `workflow.security_enforcement=true` and no SECURITY.md in the phase dir."
   `23-RESEARCH.md` verified this repository's `.planning/config.json` carries no
   `security_enforcement` override either, so the default applies here exactly as
   it did in the scratch repo — **the self-hosted run is not structurally exempt
   from that wall.** It is very likely a non-issue in practice, since every
   recent phase in this repository produced a security artifact through its
   ordinary workflow, but `23-RESEARCH.md` logs that as Assumption A1, explicitly
   unverified because no phase has yet completed an unattended run here. Task 3
   converts the assumption into a check.
3. **The target phase must not attest to its own Ship at Validate.** The other
   probe reached Ship and was rejected because `01-VERIFICATION.md` scored
   "Define→Plan→Execute→Ship carried end-to-end" as verified while Ship had not
   run. That catch was a non-deterministic prompt-side review, not an enforced
   invariant. Task 3 checks the target phase's own acceptance criteria for the
   same shape before the run starts, using plan 23-06's oracle as the arbiter.
4. **An abandoned run must be endable without `kill(1)`.** If the acceptance run
   parks at an unanswerable gate, the pre-23-04 outcome was a process pair
   resident for up to seven days. Closed by plans 23-04 and 23-05, and Task 2
   proves both answer on this repository before the run rather than during it.

## Task order changed in this revision: the authorization now comes last

**Cross-AI review BLOCKER 2, orchestrator-verified.** The previous revision put
the one-way authorization checkpoint first, and its `<resume-signal>` asked the
operator to confirm *"(d) that Task 2's recovery-point rehearsal has completed
successfully"* — while Task 2 began after it. The operator was being asked to
attest to a rehearsal that could not have happened yet. For a one-way unattended
merge into `develop` that is not a cosmetic ordering slip; it is the checkpoint
failing to be a gate at all, because the only fact that would justify saying
"proceed" is unavailable at the moment the question is asked.

**Resolution: split the checkpoint into its two genuinely different decisions
and put them on either side of the evidence.**

1. **Task 1 — target selection.** Reversible. Naming a candidate phase commits
   nothing and mutates nothing, and it must come first because Task 3's content
   preconditions are checks *about that specific phase's plan set* and cannot be
   run against an unnamed target.
2. **Task 2 — rebuild, seven behavioural checks, recovery ref, local restore
   rehearsal, remote restore path.**
3. **Task 3 — the two content preconditions**, against the phase named in Task 1.
4. **Task 4 — the one-way authorization.** Blocking. Asked only once the
   rehearsal has actually run, the remote's branch-protection answer is known,
   and both preconditions carry a recorded disposition. Every fact the operator
   is asked to weigh now exists on disk before the question is put.

This plan therefore carries four tasks rather than the usual two or three. That
is deliberate and is not a context-budget problem: Tasks 1 and 4 are blocking
checkpoints that consume essentially no executor context, and Tasks 2 and 3 both
write into one document rather than touching source. Splitting them across two
plans would produce a plan whose entire content is a checkpoint, and would
reintroduce the ordering hazard across a plan boundary where it is harder to see.

**Reversibility ratings for this plan's decisions:** Task 1 `reversible` — a
candidate target can be changed at Task 4 at zero cost. Task 4 `one-way` — it
authorizes a real merge, version bump, and changelog commit on the primary
repository, performed with no human watching.
