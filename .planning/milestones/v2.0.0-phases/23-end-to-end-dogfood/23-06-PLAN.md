<objective>
Close the false-green attestation class: make "did this phase actually ship?"
a question with one deterministic answer that a Ship-stage or Validate-stage
attestation cannot get wrong by accident.

This is a **new cross-cutting unit added by this replan**, carrying the new
requirement token **`23e`**. It did not exist in the original 23a/23b/23c/23d
breakdown. Stated explicitly, as required, because it is a scope addition.

Purpose: two independent runs on the operator's machine reached Ship within one
hour, and **both were stopped by content/config gates, not process failures**
(`23-ORPHAN-FORENSICS.md`). One of them was stopped because
`01-VERIFICATION.md` scored the truth "Define→Plan→Execute→Ship carried
end-to-end" as verified, with frontmatter `status: passed` and `score: 3/3`,
while Ship had demonstrably not run — no merges, no tags, no remotes. DevFlow
caught a false-green in an attestation document and refused to ship. That is
correct behaviour. The problem is **how** it was caught: verified this session
by reading the full evaluation pipeline, `devflow-core` never reads
`VERIFICATION.md`. `evaluate_agent_result_inner` (`agent_result.rs:846-869`)
consumes only Layer 0's declared probes, the agent's own `DEVFLOW_RESULT`
payload, exit codes, and commit evidence. The catch happened inside the agent's
own GSD review prompt and was reported back through the normal result contract.
**That is non-deterministic prompt behaviour, not a code-enforced invariant.**
Nothing would have caught the same defect had the review missed it.

Output: a read-only structural oracle, a CLI verb exposing it, and one enforced
post-condition.

## Two RESEARCH.md recommendations are disproven by source. Recorded, not silently overridden.

`23-RESEARCH.md` Question C and Pattern 3 recommend a default-on structural
check placed **"before `handle_ship_outcome` accepts an `AgentStatus::Success`
at `Stage::Ship`"**, confirming "a new merge commit exists on the target branch
since `started_at`, or a new tag was created, or the remote was pushed to."
That placement is **wrong**, and Assumption A2 in the same document flagged
exactly this risk ("an overly strict check could block a legitimate Ship; the
planner should verify the exact evidence signal before landing it"). Verified
this session:

1. `hooks::hooks_after_ship()` returns `[Merge, VersionBump, ChangelogAppend, BranchCleanup]`
   (`crates/devflow-core/src/hooks.rs:105-112`).
2. That batch runs inside `finish_workflow_with_gate_timeout`
   (`crates/devflow-cli/src/pipeline_gate.rs:188`), which is only reached from
   `handle_ship_outcome`'s `GateAction::Advance` arm
   (`crates/devflow-cli/src/pipeline_outcomes.rs:275-286`) — that is, **after**
   the Ship gate has already been approved.

So at the moment RESEARCH.md proposes checking, no merge, tag, or push can
exist yet, by design. The check would fail for every legitimate Ship and block
the phase's own acceptance criterion. It is not landed.

Second correction, subtler and equally load-bearing:
`GitFlow::is_merged_into_develop` fails closed when the feature branch is
absent — *"An absent branch is not proof of a merge"* (`git.rs:89-97`). But
`BranchCleanup` runs **after** `Merge` in the same batch and deletes that
branch. So an ancestry check performed after `hooks_after_ship` completes
returns false for every successfully shipped phase. Any merge post-condition
must run inside `merge_feature`, while the branch still exists.

**What is actually missing, having established what is not.** DevFlow's own
enforcement of the Ship path is structurally sound already: `run_checkout_hooks`
returns `all_succeeded` (`pipeline_outcomes.rs:477-495`), `finish_workflow`
loops and reopens the Ship gate on any hook failure, and `merge_feature`
already refuses a missing branch. The gap is not in DevFlow's enforcement — it
is that **this authoritative fact is not exposed anywhere a reviewer or an
automated probe can read it**, so the attestation layer reconstructs it by hand,
differently every time, and got it wrong. This plan exposes it, and makes the
exposure usable as a Layer 0 probe, which is a code-enforced path: *"A failed
probe outranks every agent-controlled signal"* (`agent_result.rs:704-711`).

**Visible skip, recorded per protocol:** spec-less probe fallback skipped —
phase has no requirement IDs to probe (visible skip). `must_haves.truths` are
derived from the ROADMAP phase goal and the probe/forensics evidence.

## The predicate this plan originally chose was itself a false green. Corrected here.

**Cross-AI review BLOCKER 1, orchestrator-verified, and re-verified against
live source while writing this revision.** The previous revision of this plan
defined `ShipEvidence::shipped` as "whether `workflow_finished` has been emitted
for this phase", asserted three separate times that it is the only site emitting
that event, and instructed the executor to write that claim into source as "the
load-bearing comment of the whole plan." **The claim is false.**
`workflow_finished` is emitted at **two** sites:

- `crates/devflow-cli/src/pipeline_gate.rs:221` — real Ship finalization, guarded
  by the entire `hooks_after_ship` batch succeeding. Payload:
  `serde_json::Value::Null` (no `reason` key).
- `crates/devflow-cli/src/pipeline_gate.rs:79` — the `devflow start --until
  <stage>` clean-stop branch inside `transition()`, payload
  `{"reason": "stopped_at", "stage": …}`, which `return`s **before** the
  checkout hooks, before `state.stage = to`, before the `transition` event, and
  before `launch_stage`. Nothing resembling a Ship has run.

Consequence had it shipped: `devflow evidence --require-shipped` would report
**shipped** for any phase halted with `devflow start --until plan`. The oracle
built to eliminate false greens would have shipped one, in the exact predicate
the phase depends on. The ROADMAP's own run record already names this shape —
Phase 21 is logged as "`workflow_finished` after one stage."

**Correction adopted (Codex's first option, the structural one).** Emit a
**distinct, terminal-only `workflow_shipped` event** from
`finish_workflow_with_gate_timeout` and make *that* the predicate. Rejected
alternative: keeping `workflow_finished` and filtering on
`reason != "stopped_at"`. That is a payload-discipline convention, not a
structural guarantee — any future third emission of `workflow_finished` without
a `reason` key silently re-opens the same hole, and the finalization payload is
literally `Null` today, so "absence of a reason field" is exactly the
fingerprint a careless new emitter would also have. A dedicated event name has
one emission site and its meaning cannot drift.

**Backward compatibility, stated so it is not mistaken for a defect.** Phases
that finalized before this plan lands have no `workflow_shipped` line, so the
oracle reports them NOT shipped. That is the **fail-closed** direction and is
accepted deliberately: an oracle that under-claims is safe, one that
over-claims is the defect this plan exists to remove. The corroborating
`workflow_finished_seen` and `finished_reason` fields make the distinction
legible in the oracle's own output rather than hiding it.

**Assumption A2 resolved.** The strict shipped predicate is the terminal-only
`workflow_shipped` event in DevFlow's own append-only event log, **not** git
ancestry — deliberately, so the predicate is immune to merge shape. Git facts
are reported alongside as corroboration and are never the gate. Checked against
this repository's real history this session: `develop` carries both `Merge pull
request #N` commits (protected-branch PR merges) and local `--no-ff` `merge:`
commits, tags `v1.8.0`/`v1.8.1` exist, and remote `origin` is configured — an
ancestry-based predicate would have been shape-sensitive across exactly that mix.
