## CONFIRMED

- [severity: BLOCKER] **Per-phase socket keying deadlocks stage transitions under in-process advance and takeover safety** — evidence: `50-CONTEXT.md:50-52` (D-02), `50-CONTEXT.md:158-161` (Claude's Discretion), `crates/devflow-cli/src/pipeline_launch.rs:992,1735-1738`, `crates/devflow-cli/src/pipeline_gate.rs:52,111`, `.planning/audits/2026-07-24-socket-supervisor-spike.md:38,209-211`, and `.planning/spikes/socket-supervisor/main.rs:70-74`.
  - *Why it breaks:* Under D-02, the stage-N monitor executes `advance` in-process. `advance` transitions the state machine and calls `launch_stage()`, which calls `spawn_monitor()` to launch the stage-(N+1) monitor *before* the stage-N monitor process ever returns or exits. If sockets are keyed per-phase as suggested (`ab12cd34-22.sock`), the stage-N monitor is still alive and listening on that exact socket. When the stage-(N+1) monitor starts, the spike's mandatory takeover safety rule ("probe socket first; refuse if ALIVE with exit code 3") fires: stage-(N+1) connects to stage-N, sees `ALIVE`, and aborts. The pipeline wedges permanently at every stage boundary. Conversely, if stage-N unbinds/unlinks its socket *before* running `advance`, then during the entire execution of `advance` (which takes the per-phase lock, evaluates git diffs, runs hooks, or waits up to 60 s for lock contention), probing the socket returns `GONE`. This contradicts `50-CONTEXT.md:165` ("`BetweenStages` likely folds into ALIVE; GONE while state says a stage is running is a finding, not a normal state") and prevents `devflow stop` from reaching the monitor via socket.
  - *Suggested correction:* Sockets must be keyed per-launch (e.g. `<root_hash>-<phase>-<launch_id>.sock`), not per-phase, and stage-(N+1) launch must register the new socket before stage-N unbinds its own, OR `50-CONTEXT.md` must specify an atomic socket-handover protocol between stage monitors.

- [severity: BLOCKER] **Socket `shutdown` and SIGTERM abort in-process `advance` mid-flight, corrupting state and orphaning locks and gates** — evidence: `50-CONTEXT.md:60-66` (D-04), `50-CONTEXT.md:78-82` (D-05), `crates/devflow-cli/src/pipeline_launch.rs:1629,1830`, `crates/devflow-cli/src/pipeline_gate.rs:352`, and `.planning/spikes/socket-supervisor/main.rs:135-156`.
  - *Why it breaks:* In the spike, "advance" was an artificial 2-line test mock that wrote a string to a temporary file (`main.rs:118`). In DevFlow, `advance` is a long-running, lock-holding, state-mutating operation: it acquires the per-phase lock `.devflow/lock-NN`, evaluates results, runs checkout hooks, mutates `state.json`, and can block on `run_gate_with_timeout` for hours or days. If `devflow stop` sends `shutdown` over the socket (or if the monitor receives SIGTERM/SIGINT) while `advance` is running (i.e. after the agent process has already exited):
    1. The agent is already dead, so `killpg` on the agent group is a no-op.
    2. "Suppresses advance" cannot suppress an advance that is already executing on another thread.
    3. The shutdown handler in the spike calls `std::process::exit(0)`. In Rust, `process::exit` immediately aborts the process without running destructors: `.devflow/lock-NN` remains locked on disk; temporary `.state-NN.json.*.tmp` files are leaked; open gate files (`gate-NN-*.json`) are left with no live waiter; and `state.stopped = true` is never written. Furthermore, the monitor's exit handler overwrites `exit_file` with `143`, turning a successful agent completion into an apparent failure.
  - *Suggested correction:* The supervisor must track internal lifecycle states (`SupervisingAgent`, `Advancing`, `WaitingGate`). If `shutdown` or SIGTERM arrives while `Advancing` or `WaitingGate`, the monitor cannot call `process::exit(0)`; it must coordinate cancellation through the existing gate abort and lock release paths, ensuring the phase lock is dropped cleanly and `state.stopped` is set.

- [severity: BLOCKER] **STALE backstop start-time validation fails closed when the process group leader has exited, leaving orphaned trees uncollectible** — evidence: `50-CONTEXT.md:67-70` (D-04), `crates/devflow-core/src/agent.rs:214-230` (`process_start_time`, `is_same_process`), and `.planning/audits/2026-07-24-socket-supervisor-spike.md:59-97` (C3, C5).
  - *Why it breaks:* In Unix, when the agent is spawned with `.process_group(0)`, the agent process is the leader of the process group (`agent_pgid == agent_pid`). If the agent process exits or is killed while child processes (background tools, severed-ppid orphans) survive, the process group remains non-empty under POSIX. However, because the group leader (`pid == pgid`) has exited and been reaped, `/proc/{agent_pgid}/stat` no longer exists on disk. Calling `agent::is_same_process(agent_pgid, recorded_start)` returns `false` (`None`). Under D-04 ("only if the group is non-empty **and** the recorded start time and boot id still validate"), the validation check fails closed. The backstop will REFUSE to kill any orphaned process group whose leader has died — the exact failure mode C3 and C5 were created to solve.
  - *Suggested correction:* Clarify the STALE backstop specification: start-time validation against `/proc/{pgid}/stat` only applies if the process group leader is still alive. If the leader has exited, POSIX non-emptiness enumeration plus `boot_id` validation is the sole authorization required to invoke `killpg(-pgid)`.

- [severity: MAJOR] **Circular dependency: sweep cannot map sockets to project root/phase when state will not load, disabling D-06 and D-09** — evidence: `50-CONTEXT.md:44-46` (D-01), `50-CONTEXT.md:83-86` (D-06), `50-CONTEXT.md:98-103` (D-09), and `50-CONTEXT.md:158-161` (Claude's Discretion).
  - *Why it breaks:*
    1. Sockets cannot live in the project tree due to the 104/108-byte `sun_path` bound (spike C6).
    2. Sockets are placed in `~/.cache/devflow/` keyed by a hash of `(project_root, phase)` (e.g. `ab12cd34-22.sock`). A cryptographic/truncated hash is one-way and cannot be inverted back to a project path.
    3. D-09 requires that when a state file exists but will not load, `start`'s guard consults the sweep for that root and phase. But if the state file does not load, the state cannot tell the caller where the socket is. And if `doctor` sweeps `~/.cache/devflow/*.sock` without loadable state (D-06), it cannot determine which repository owns the socket.
    4. Furthermore, because D-04 persists `agent_pgid`, `start_time`, and `boot_id` inside `state.json`, when state will not load, those fields are unavailable. The STALE backstop cannot execute because it has no recorded PGID or timestamps.
  - *Suggested correction:* The supervisor must persist its identity metadata (project root, phase, pgid, start_time, boot_id) into a small sidecar file in `~/.cache/devflow/<key>.meta` alongside the socket at spawn time, decoupled from `state.json`. Alternatively, D-01 must permit `start` to derive the socket path deterministically from `(project_root, phase)` at probe time.

- [severity: MAJOR] **2.x upgrade verb's PID check reproduces the 999.143 permanent refusal on recycled PIDs with no work-preserving recovery** — evidence: `50-CONTEXT.md:123-127` (D-15), `50-CONTEXT.md:110-111` (D-12), `crates/devflow-core/src/state.rs:288`, and `.planning/ROADMAP.md:928-941` (Phase 999.143).
  - *Why it breaks:* A 2.x `state.json` records a bare `monitor_pid: Option<u32>` and `.devflow/phase-NN-agent.pid` records a bare `agent_pid` — neither records a start time. D-15 states that the upgrade verb "refuses while the 2.x state's recorded monitor or agent pid is alive." If an unrelated system process recycles either PID on the host, `agent::agent_running(pid)` returns `true`. The upgrade verb will permanently refuse to upgrade the state. Because D-14 mandates that every other verb (`start`, `resume`, `stop`) refuses 2.x state, and D-12 parked 999.143's work-preserving recovery, the operator has no way to clear the stale PID without destroying the branch and worktree (`start --force`).
  - *Suggested correction:* The upgrade verb must provide an explicit override flag (e.g. `devflow recover --upgrade-state --phase N --force-recycled-pid`) or check `/proc/<pid>/cmdline` to prevent unrelated recycled PIDs from permanently locking out the upgrade.

- [severity: MAJOR] **`resume`'s live-run guard omitted from D-09, permitting duplicate concurrent agent execution** — evidence: `50-CONTEXT.md:98-103` (D-09), `crates/devflow-cli/src/commands.rs:2457-2462,2470-2492` (`refuse_resume_over_a_live_run`), and `50-CONTEXT.md:159-160`.
  - *Why it breaks:* D-09 explicitly updates `refuse_start_over_a_live_run` to check socket liveness and consult the sweep. It completely omits `refuse_resume_over_a_live_run` (added in Phase 48-20 / backlog 999.140). Under the rule that "a new monitor never steals a live socket; only a STALE one may be reclaimed", if a monitor dies leaving a STALE socket while the agent group is still alive, running `devflow resume` would reclaim the STALE socket and spawn a second agent concurrently in the same worktree over the running orphaned agent.
  - *Suggested correction:* D-09 must mandate updating the shared `refuse_launch_over_a_live_run` helper (which gates both `start` and `resume`) so that `resume` also refuses if the socket is ALIVE or STALE with a live agent group.

- [severity: MAJOR] **Removing `monitor_pid` from `State` breaks D-15 and causes an unmanaged breaking API change in `devflow-core`** — evidence: `50-CONTEXT.md:24,110` (Phase 50 removes monitor-pid half), `50-CONTEXT.md:123-125` (D-15), `crates/devflow-core/src/state.rs:34,288`, and `crates/devflow-core/src/monitor.rs:308`.
  - *Why it breaks:*
    1. If `monitor_pid` is deleted from the `State` struct, `serde` will ignore `monitor_pid` when deserializing a 2.x `state.json`. D-15's upgrade verb will not be able to read `state.monitor_pid` to check if the 2.x monitor is still running.
    2. In `devflow-core`, `pub monitor_pid: Option<u32>` is a public field on a struct exported by a published library crate (`crates/devflow-core`). Deleting it is a breaking change.
    3. `pub fn spawn_monitor(...) -> Result<u32, MonitorError>` in `devflow-core` returns `u32` (the monitor PID). Changing this to return a socket path breaks the public crate API. `50-CONTEXT.md` discusses the state-file format break at length but fails to address or specify the semver break on the `devflow-core` crate API.
  - *Suggested correction:* Retain `pub monitor_pid: Option<u32>` on `State` marked `#[deprecated]` (or read raw JSON in D-15 before deserialization), and explicitly declare the breaking API changes in `devflow-core` (`spawn_monitor`, `MonitorLaunch`).

- [severity: MINOR] **Reboot handling leaves orphaned STALE sockets uncollectible** — evidence: `50-CONTEXT.md:44` (D-01), `50-CONTEXT.md:67-69` (D-04), and `50-CONTEXT.md:83-86` (D-06).

When `recover --clean` runs, D-04 specifies that the STALE backstop only executes if `boot_id` validates. Because the host rebooted, `boot_id` does not validate.   - *Suggested correction:* Explicitly specify: if a STALE socket's recorded `boot_id` does not match the current kernel boot ID, all processes from that run are guaranteed dead; the socket may be safely unlinked immediately.

## SUSPECTED

- [severity: MAJOR] **Signal forwarding in Rust supervisor lacks async-signal-safety specification** — evidence: `50-CONTEXT.md:78-82` (D-05: "SIGTERM / SIGINT to the supervisor behaves exactly like a socket shutdown... Kill the agent group, record 143, suppress advance, remove the socket, exit").
  - *Why it breaks:* [SPECULATION: dependent on implementation strategy] In a POSIX signal handler, allocating heap memory, locking standard mutexes, writing formatted strings to files, and calling `thread::sleep` are not async-signal-safe. If the executor implements D-05 by registering a signal handler with `libc::sigaction` or `signal_hook` that directly invokes the spike's shutdown routine, the supervisor will be vulnerable to deadlocks and undefined behavior. D-05 must specify that signal handling is routed via a self-pipe or dedicated signal-handling thread.

- [severity: MINOR] **`sun_path` length limit risk on macOS tempdirs during E2E tests** — evidence: `50-CONTEXT.md:47,90` (D-01, D-07) and `.planning/audits/2026-07-24-socket-supervisor-spike.md:100-114` (C6).
  - *Why it breaks:* [SPECULATION: untested on macOS host] On macOS, default `TMPDIR` paths under `/var/folders/.../T/` are ~49 bytes long. If D-07 points `HOME` and `XDG_CACHE_HOME` to a nested `tempdir` inside `TMPDIR`, the path to `~/.cache/devflow/` can exceed 75 bytes. If the socket filename exceeds 28 bytes (e.g. including a full hash or timestamp), the total path exceeds the 104-byte macOS `sun_path` limit, causing tests to fail on socket bind.
