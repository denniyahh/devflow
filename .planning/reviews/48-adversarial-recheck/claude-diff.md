## Needs my awareness

**1. CONFIRMED — `persist_stopped_state`'s holder re-read neuters the check it guards, and has zero coverage.**
The hunk swaps the observed `holder` for a fresh `lock::holder_status(project_root, phase)`. That re-read is taken *after* the abort was written and after the real waiter may have released. The `Live { pid } if pid.to_string() == contending_pid` arm then compares two values pulled from the same lock file moments apart — near-tautological for any genuinely contended lock. Waiter W aborts and exits; a queued `advance` (pid A) takes the lock; `stop` prints *"pid A is waiting on the gate and will clear phase state as it aborts"* and returns success, while A is not waiting, the gate is already consumed, and state is never marked stopped. That is the exact unevidenced-success claim T-48-16-02/03 exist to forbid — and the function's own header in this diff says the observed holder is the only admissible input.
The guard test `answered_gate_contention_claims_a_waiter_only_for_the_observed_live_holder` calls the message builder **directly** with a hand-supplied holder, so it never touches the changed call site. The two tests that do reach it use a lock that never changes hands. **The only behavioural change in this hunk is entirely untested, sitting beside a green test asserting the opposite property.**

**2. CONFIRMED — the Ship D-05 carve-out was silently subordinated to `gate_pending`, and the covering tests were mutated instead of extended.**
`gate_is_current` runs *before* the `gate.stage != Stage::Ship` check, so Ship is no longer exempt. Proof is in the patch's own edits: `stop_is_idempotent_against_an_already_answered_gate` asserts the response file exists and previously passed with a plain `State::new(...)`; it now requires two added lines (`stage = Ship`, `gate_pending = true`) to pass. Four fixtures were amended the same way. No test was added for the case the amendment deleted — a Ship gate with cleared or non-matching state is now an untested silent no-op.

**3. CONFIRMED — the Supervise test never verifies the "records" half of its own name, and the patch weakened its one state assertion.**
`assert!(state.to_string().contains("state file"))` was deleted with no justification in the diff; any error now satisfies `expect_err`, including a corrupt file. And because the test aborts at the second gate — which clears state — it structurally cannot observe `checkpoint_approval`. The R-8 durability claim the whole Supervise branch rests on is verified for Auto only. Its gate count is also loose: it filters `stage == "code"` and counts to 2, which any other Code-stage gate satisfies.

**4. CONFIRMED — the new Supervise `reason` is a dead write at `Stage::Validate`.** The fall-through dispatch routes Validate to `handle_validate_outcome`, which takes no `reason`. The "Supervise mode requires a human decision…" string is computed and dropped, producing exactly the generic-stage-failure reading T-28-16 forbids two arms below. (Reachability of Validate with `checkpoint_confirmed` is SUSPECTED — I couldn't read the two verify predicates.)

**Also confirmed, lower severity:** the stale-gate branch prints `devflow resume --phase N` on what phase 112 asserts is a *successful* stop (7); the `checkpoint_auto_decided` event now claims `"Auto-only"` enforcement that `relaunch_checkpoint_session` does not perform locally (10); the rejection test's justifying comment "the route under test has no mode check (D-07)" is false after this patch (11).
