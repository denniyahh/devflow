<objective>
Run the phase's acceptance criterion.

**Acceptance here is behavioural, not code-shaped.** CONTEXT.md says it
directly: *"The phase is done when one phase has actually been driven
start-to-finish by devflow, unattended, reaching a completed Ship stage — not
when the supervisor compiles and its unit tests pass."* Everything `cargo test`
can prove is already proven by plans 23-05 through 23-10. What no test can prove
is this: a real Claude Code invocation, consuming real GSD slash commands, over
real wall-clock time, driven by the supervisor, through all five stages, with
nobody watching.

The record to beat, from `.devflow/events.jsonl` and ROADMAP.md's run table:
**no phase has ever completed a full five-stage devflow-driven run.** Phase 17
reached Ship, looped back to Code, and died to two silent monitor deaths (~4h
lost). Phase 21 stopped after Define. Phase 22 stopped dead at a Plan relaunch
with no `advance_evaluated`. Two of the three were blocked at least once by the
self-dogfood staleness guard.

Purpose: prove the loop, or record precisely where it still breaks.
Output: `23-ACCEPTANCE.md`, and a human verdict on whether this phase met its
own criterion.

Launch one unattended run against the phase chosen at plan 23-11's checkpoint,
on **this** repository, and observe it to termination without intervening.

Launch, exactly:
`devflow start --phase <N> --agent claude --mode auto --yes-ship`
where `<N>` is the phase named in `23-ACCEPTANCE-SETUP.md`.

**Observation protocol** — the same one 23-VALIDATION.md prescribes and plan
23-02's probe used, so the two runs are comparable:
- Poll `devflow status` and `tail` `.devflow/events.jsonl` every **30-60
  seconds**. Short enough to catch a stage transition, long enough not to
  interfere.
- **Do not** run `devflow advance`. **Do not** answer a gate. **Do not** use
  `ps` or `kill` to inspect or nudge anything. The whole claim being tested is
  that none of that is necessary any more; using any of them invalidates the
  run. If you need process facts for the record, get them from `devflow status`
  and `devflow doctor` — which is the point.
- Record, at each poll, what `devflow status` reported: the socket state, the
  derived liveness, and the current stage. This series is the direct evidence
  for the "a stall is distinguishable from a pause" claim, and it is what
  Finding 1 says was impossible before.
- **If the run stalls**, do not rescue it by hand. Use `devflow stop --phase N`
  — the verb plan 23-10 built — and record that you did.

  **If `devflow stop` itself cannot resolve the run, `kill` is the sanctioned
  last resort (review finding — OpenCode, LOW).** The case is concrete: a
  supervisor that accepts the socket connection but never processes `shutdown`
  will make `stop`'s `Alive` branch hang or return without effect, and because
  the socket is `Alive` rather than `Stale` the `reap_stale_group` backstop
  deliberately refuses to fire. There is then nothing left inside DevFlow to
  try. So: after `devflow stop` has been given one bounded attempt, get the
  supervisor's pid from `devflow status` / `devflow doctor` — never from `ps`,
  which the protocol forbids as an *observation* tool — and `kill` the process
  group, escalating to `kill -9` only if a plain TERM does not land.

  Needing `kill` is itself a **finding about `devflow stop`**, not a footnote:
  record the exact sequence, what `stop` reported before it, and which socket
  state was observed, and carry it into the verdict section as a named gap.
  The whole premise of the phase is that `ps` and `kill` are no longer
  necessary; an instance where they were is evidence against that premise and
  must be recorded as such rather than tidied away.
- **If the run does something destructive or clearly wrong**, stop it with
  `devflow stop`, restore `develop` using the literal command recorded in
  `23-ACCEPTANCE-SETUP.md`, and record the whole sequence. Restoring is not a
  failure of this plan; failing to record it would be.

- The final `git log --oneline` on `develop` showing exactly what the run
  merged, and the diff of the version and changelog commits it made.
- Whether the phase's worktree was removed by `Hook::WorktreeRemove` (plan
  23-10) — this run is the first ever to reach that path on *success*. Note

**Re-run the full gates after the run, before judging it
(review finding — Codex, MEDIUM).** The run merges a real phase into `develop`,
bumps the version and commits a changelog entry — it changes the tree. Plan
23-11 established that the tree was green *before* the run precisely so any
failure during it would be attributable to the pipeline; that attribution only
holds if the tree is checked *after* it too. Re-run CI's own three gates —
`cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`
and `cargo fmt --check` — capture their results into `23-ACCEPTANCE.md`, and
treat a post-run failure as part of the verdict rather than as separate
housekeeping: a run that reached Ship while leaving the tree broken has not met
the phase's criterion, however clean its event log looks.

**Redact before committing, against a checklist — not just `$HOME`
(review finding — Codex, MEDIUM).** The captures contain raw agent output, which
on this project has previously carried absolute home paths and OS usernames into
committed artifacts (999.10 / WR-02, three prior instances). A `$HOME`-only scan
misses most of the class, because agent output shortens, splits and re-forms
paths. Walk every one of these before committing, and record in the document
that each was checked:

1. **The absolute home path** — `$HOME` verbatim.
2. **The OS username on its own** — `$(id -un)`. It appears inside paths the
   `$HOME` grep will not match, in git author/committer strings, and in agent
   prose.
3. **The home directory's basename** — `$(basename "$HOME")`. On this host that
   differs from the `/var/home/...` prefix, so a prefix grep misses it.
4. **Absolute `/var/home/...` and `/home/...` paths** — including any that the
   agent rendered with a different prefix than `$HOME` resolves to.
5. **`/tmp/...` and `$TMPDIR/...` probe paths** — the scratch repository and any
   fixture directories from plans 23-01/23-02, which encode both the username
   and the machine's layout.
6. **Remote URLs and tokens** — `git remote -v` output, `https://…@github.com/…`
   forms, and anything resembling a credential in an agent transcript.
7. **The socket path** — `~/.cache/devflow/<hash>-<phase>.sock`. The file name
   alone is fine and is what the code emits; a full path in a pasted excerpt is
   not.

Replace each with a stable placeholder (`<HOME>`, `<USER>`, `<TMP>`,
`<REMOTE>`) rather than deleting the line, so the excerpt stays readable as
evidence. Redact **after** capturing verbatim and before committing — never edit
the underlying `.devflow/` captures themselves, which are the primary record.
