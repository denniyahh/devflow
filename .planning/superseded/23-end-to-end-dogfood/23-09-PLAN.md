<objective>
Make "unattended" actually reachable.

`Mode::Auto` does **not** make a run hands-off.
`crates/devflow-core/src/mode.rs:82-94` documents the rule in its own words:
**"Ship always gates (both modes)."** Auto suppresses Validate gates only. So a
Define→Ship run in Auto parks at the Ship gate and waits for a human — which
means this phase's goal, *one phase driven Define→Ship unattended*, is
unreachable by construction without a pre-authorization. That is why D-04
exists, and why this plan is a precondition for the acceptance run in plan
23-11.

**Auto-answer, not bypass (D-06).** The gate still fires, still notifies, and
still records a resolution. The audit trail must show a decision that was made
in advance, never a checkpoint that quietly did not happen. RESEARCH verified
the mechanism already exists and needs nothing new: `Gates::write_gate`,
`Gates::respond` and `Gates::poll_response` together produce exactly the event
shape a human approval produces, differing only in the responder field.

**The trap this plan exists to avoid.** Two distinct gates carry the
`Stage::Ship` tag: the routine pre-merge approval at `handle_ship_outcome`, and
a **separate finalization-retry gate** inside `finish_workflow_with_gate_timeout`,
fired only when the terminal hooks — Merge, VersionBump, ChangelogAppend,
BranchCleanup — fail *after* the first approval. A naive
`if stage == Stage::Ship && state.yes_ship` check anywhere in the generic gate
runner would silently pre-approve both, including the one that exists precisely
because a git or version operation already went wrong mid-finalization. The
wrapper shape below makes "only the routine approval is ever auto-answered" true
**by construction** — the retry gate's call site simply never invokes the
wrapper — rather than true by a convention someone could later widen.

**On D-07.** `--yes-ship` is deliberately **not** refused on the self-dogfood
workspace. That is a recorded, accepted risk (D-07), and the operator explicitly
declined a refusal guard this phase. Do not add one here. Its two
operator-specified mitigations — drive a low-stakes phase, and establish a
recovery point before starting — are encoded as tasks in plan 23-11, where the
irreversible run happens.

Purpose: make the acceptance run possible without making unattended merging a
default.
Output: a per-run flag, persisted per run, that auto-answers exactly one gate.
</objective>

**`commands.rs`** — in `start`, set `state.yes_ship` from the parameter

**Why persisted at all, since D-05 says "per-run only".** These are different
things and the distinction belongs in a comment at the assignment site. D-05
forbids a *standing default* — a `devflow.toml` key or environment variable
that makes unattended auto-merge the silent behaviour of every future run. It
does not forbid this run's own `state.json` remembering the flag this run was
given. Persistence is required because the Ship gate can fire in a process
invocation that happens long after the original command line is gone: a
supervisor restart, a `devflow resume`, or the in-process advance tail from
plan 23-06. A value held only in the original process's memory would be missing
at exactly the moment it is needed.

belongs where an operator will read it.

  <action>
Add `pipeline_gate::run_gate_auto_approved(project_root, state, stage, context)`
— a wrapper that fires a gate and, when `state.yes_ship` is set, immediately
writes an approving response to it, then falls through to the normal
`run_gate_with_timeout` polling so the resolution is picked up through the
ordinary path.

Sequence, and the ordering matters — verify it against `run_gate_with_timeout`'s
own body before writing it, because a naive prelude would double-write the gate
file:
1. If `state.yes_ship` is false, delegate straight to the existing `run_gate`
   and change nothing. A run without the flag must behave byte-identically to
   today.
2. If it is set, ensure the gate is written exactly once — either by letting
   `run_gate_with_timeout` write it and injecting the response between its
   `Gates::write_gate` and its `Gates::poll_response`, or by writing it here and
   calling a variant that does not re-write. **Read `run_gate_with_timeout`
   first and pick whichever avoids a double `write_gate`**; `Gates::respond`
   errors if no open gate exists, so the order is load-bearing rather than
   stylistic.
3. The `GateResponse` is `approved: true`, with a `note` recording that this was
   pre-authorized at launch and a `responded_by` value naming the flag. Both
   fields are the audit trail D-06 requires: an auditor reading the gate ledger
   must be able to distinguish a pre-authorized approval from a human one
   without inference.
4. Emit a `ship_gate_pre_authorized` event before returning, so the decision is
   in `events.jsonl` as well as the ledger. Events are append-only and never
   silent; an unattended run's most consequential decision must not be visible
   only in a file an operator would have to know to look for.

**Call it from exactly one place: `handle_ship_outcome`.** Replace its
`run_gate(...)` call with `run_gate_auto_approved(...)`, leaving the three
`GateAction` arms unchanged.

**Do not** add a `stage == Stage::Ship && state.yes_ship` check inside
`run_gate`, `run_gate_with_timeout`, or anywhere else generic. The
finalization-retry gate in `finish_workflow_with_gate_timeout` carries the same
`Stage::Ship` tag and fires only after a terminal hook has already failed —
Merge, VersionBump, ChangelogAppend or BranchCleanup. Auto-approving *that* one
would mean an unattended run silently retrying past a git or version failure,
which is the opposite of what a pre-authorization should buy. Its call site must
continue to use the non-auto-approving path.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI flag → merge, version-bump and changelog authority | A single flag authorizes irreversible git operations on the operator's repository |
| `devflow.toml` / environment → run behaviour | Config is ambient and shared; a standing auto-merge setting would be invisible at invocation time |
| gate ledger and `events.jsonl` → audit | These are the only record that a decision was made; a missing entry is indistinguishable from a skipped checkpoint |
| terminal-hook failure → retry gate | This gate exists because something already went wrong; approving it unattended compounds a failure |
