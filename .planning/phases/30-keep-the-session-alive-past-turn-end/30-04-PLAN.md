<objective>
Close review finding M1: re-measure the post-stdin-close exit timing across
several trials and archive it as evidence, and — for the first time — observe
what the CLI actually does when stdin is closed while background tasks are
still pending.

Purpose: the 0.38s exit figure that the ROADMAP and `30a-evidence/README.md`
both cite exists only in a harness's console output from a session that is gone.
It is unarchived and unreproducible, and it is a single sample. Separately,
review constraint 4 requires Phase 31's monitor to close stdin only on marker
AND drained task set, and states plainly that close-with-pending-tasks
"is untested and must be treated as undefined". Building a close rule around an
undefined behavior without ever observing it is the kind of assumption this
phase exists to remove.

Output: a re-measurement harness, archived per-trial evidence, and
`30d-MEASUREMENTS.md`.
</objective>

  <action>
    Write `30d-exit-timing-harness.py` supporting two trial modes, selected by a
    command-line argument, both built on `run_experiment_v3.py`'s experiment core.

    **Mode A — drained close (the M1 re-measurement).** Run the two-child
    experiment to completion, wait until `background_tasks_changed` reports an
    empty task array and the final `result` event has arrived, then close stdin
    and measure the interval from the close syscall returning to child process
    exit. This is the 0.38s figure, re-measured. Support an `--iterations N`
    argument and default it to 5, so the output is a distribution rather than
    the single sample the current figure is.

    **Mode B — close with pending tasks (the undefined case).** Run the same
    experiment but close stdin deliberately EARLY: after the first `result`
    event has arrived while `background_tasks_changed` still lists at least one
    outstanding `local_agent` task. Then record what actually happens, with a
    bounded observation window — do not block indefinitely. Capture, at minimum:
    whether the process exits and with what code, how long it took, whether any
    further `result` event arrived after the close, whether the pending child's
    signal file ever appeared on disk, and whether anything was written to
    stderr. Any of hang, immediate exit, truncated final result, or silently
    vanished child work is a legitimate finding — this mode has no expected
    outcome, which is the entire point of running it.

    Timestamp with a monotonic clock, not wall-clock time, for every interval
    measurement. Wall-clock is subject to NTP adjustment mid-measurement, and
    sub-second intervals are exactly where that shows up.

    Gate only on `local_agent`-typed entries in `background_tasks_changed.tasks`
    when deciding whether tasks are drained. RESEARCH.md's Pitfall 6 records an
    additional `local_bash`-typed `task_started`/`task_notification` pair per
    child that never appears in `background_tasks_changed` at all — confirmed at
    planning time against the v3 capture, where the empty-array event at line 44
    and the non-empty ones at lines 8, 13 and 29 list only `local_agent`
    entries. Assumption A2 in RESEARCH.md's log is that the `local_bash` pair is
    informational. This harness should RECORD every `local_bash` event it sees
    into the trial log rather than filtering them out, so the assumption gets
    evidence instead of another restatement.

    Write per-trial raw JSONL and a machine-readable timings file into
    `30d-evidence/`, one subdirectory or filename prefix per trial so trials are
    individually inspectable. Apply the same redaction as 30c before any write.

    As with 30c, the harness records observations and does not print a verdict.
  </action>
