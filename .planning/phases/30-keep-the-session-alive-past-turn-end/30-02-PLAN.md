<objective>
Run the v3 background-task experiment once inside a faithful replica of
`spawn_monitor`'s production process environment, and record a binary answer to
the one question that gates Phase 31: **does the Claude CLI still deliver
`task-notification`-origin `result` events when it is not running inside an
interactive Claude Code session?**

Purpose: all three archived 30a captures ran inside an interactive session —
inherited environment, merged stderr, no worktree. Review finding M4 flags that
as the deciding untested variable. If delivery does not survive the production
environment, Phase 31's monitor rewrite rests on a premise that does not hold,
and the locked decision is that Phase 31 is **cancelled before it is planned**
rather than paid for. This experiment is deliberately sequenced ahead of the
expensive work.

Output: a standalone harness, its raw evidence, and `30c-VERDICT.md` carrying a
machine-readable `delivery: confirmed | refuted` field.
</objective>

<why_a_replica_and_not_spawn_monitor_itself>
The ROADMAP phrases this unit as "run the v3 harness once *through `spawn_monitor`
itself*". Taken literally that is impossible, and the reason is worth stating so
nobody re-litigates it mid-execution: `spawn_monitor` configures the child with
`.stdin(Stdio::null())` (`monitor.rs:171`). The entire experiment depends on
holding stdin OPEN past the first `result` event — that is what keeps the
session alive. A harness run through an unmodified `spawn_monitor` would have
its stdin closed at launch and could not perform the measurement at all, and
modifying `spawn_monitor` to allow it is explicitly forbidden.

So the experiment isolates the ENVIRONMENT variable instead: replicate every
process characteristic `spawn_monitor` imposes except the one under test. That
is a stronger experiment than the literal reading anyway — it changes one
variable rather than conflating environment with pipe ownership, which is
Phase 31's separate question.
</why_a_replica_and_not_spawn_monitor_itself>

    Replicate these five characteristics, each a real difference between an
    interactive session and production:

    1. **Launch via `sh -c`**, not a direct `claude` exec — production builds
       `hermetic_command("sh", workdir)` then `.arg("-c").arg(&script)`.
    2. **Scrubbed environment.** Parse the two const string arrays out of
       `crates/devflow-core/src/git.rs` at harness runtime (read the file,

       under `ALSO_REDIRECTING_GIT_VARS`) and remove every named variable from

       the harness silently tests an environment production does not impose. If
       parsing yields zero variables from either const, abort with a clear error
       rather than proceeding: an empty scrub is the failure mode that looks
       like success.
    3. **Detached process** — `start_new_session=True`, so the child sits in its
       own process group with no controlling terminal.
    4. **No TTY** on any stream.
    5. **stderr redirected to its own separate file**, never merged into stdout.
       Production separates them via the `sh` script's own redirection, and
       merged stderr is one of the three environment caveats
       `30a-evidence/README.md` names as untested.

    The single deliberate deviation, which must be commented as such in the
    source: the harness owns and holds open the child's **stdin** pipe. That is
    the variable under test.

    Land the child's stdout in `30c-evidence/raw_output.jsonl` and stderr in
    `30c-evidence/stderr.log`. Read the JSONL by tailing that file, so the
    capture path also matches production, where the `sh` script's redirection
    writes the file and DevFlow reads it back afterwards.

    Emit a run log recording at minimum: the resolved `claude --version`, the
    variables actually removed from the child environment, wall-clock timestamps
    for launch / first `result` event / each later `result` event / stdin close /
    process exit, and the `origin` field of every `result` event observed.

    **Redact before writing anything into `30c-evidence/`.** Replace the
    operator's home directory with a tilde and the OS username with a
    placeholder in every recorded path. This repository has a standing leak
    class — backlog 999.10, and finding WR-02 in the Phase 18 review, both about
    absolute home paths and usernames reaching committed artifacts. This
    evidence directory is committed.

    Do not have the harness print its own verdict. 30a's README records that the
    harness-printed verdict was wrong in v1 and unreliable in v2, and that the
    raw JSONL is the evidence of record. The harness reports observations;
    Task 2 interprets them.
  </action>
