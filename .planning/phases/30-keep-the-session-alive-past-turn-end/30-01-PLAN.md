thinnest end-to-end path that takes a real archived `stream-json` JSONL capture

<assumption_delta_decision>
Detector `assumption-delta scan 30` returned `detected: true` (pluralization
signals). The architectural question it raises: `agent_result.rs` gains a SECOND
adapter event-stream parser alongside the existing Codex one.

**Noun now primary:** adapter event-stream parser (was singular/Codex-only, now
two).

**Decision: `add-alongside`.** The dispatch seam stays two parallel gate
functions — `is_codex_event_stream` and `is_claude_event_stream` — each called
by its own parser, each slotted independently into `evaluate_layer1`'s
`.or_else()` chain. It does NOT promote to a general adapter-stream dispatch
table.

**Rationale:** there are exactly two adapters and the two gates are mutually
exclusive by construction (Codex keys on `thread.started`/`turn.*`, Claude on
`system`/`init`; neither shape can satisfy the other). A dispatch abstraction
would add indirection with exactly one implementation behind each arm and no
caller that benefits. The `.or_else()` chain already IS the dispatch, and it is
readable.

**Accepted debt:** a third adapter is the trigger to revisit. At three parsers
the chain's ordering constraints (which gate must be tried before which) stop
being self-evident from reading it top to bottom, and a table with explicit
precedence earns its keep.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| coding agent → DevFlow | The agent writes arbitrary, attacker-influenceable text to `.devflow/phase-NN-stdout`; DevFlow parses it to decide whether a stage succeeded. |
| CLI process → DevFlow | The `claude` CLI itself emits the stream envelope fields (`type`, `origin`, `session_id`) that DevFlow trusts as authoritative. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-01 | Spoofing | `parse_claude_event_result` / `last_top_level_result` | high | mitigate | Last-result selection operates only on TOP-LEVEL objects produced by parsing one JSONL line into one `serde_json::Value`. An `origin`- or `result`-shaped structure the agent writes inside its own `result` text is inert string content there and structurally unreachable — same protection class as the existing D-04/T-28-04 `session_id` mitigation. Never route event selection through `json_scan`/`json_find_key`. |
