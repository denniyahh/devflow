<objective>
Close the false-positive surface review constraint 3 identifies: under a
stream-json capture, the raw stdout contains the operator's full prompt echoed
back as a `user` event, so any prompt that merely *documents* a checkpoint gate
rendering reads as a live gate declaration to a substring scan that does not
know which event it is inside.

Purpose: `blocking_human_checkpoint_reported` scans raw, unbounded stdout. That
is correct today, because under the single-document envelope the only place gate
text can appear is inside the one `result` field the agent authored. Stream-json
breaks that invariant — echoed input becomes textually indistinguishable from
agent-authored output. The review calls this the one existing reader that
"survives by accident", and the failure mode is silent: a checkpoint auto-decide
fires, or the resume ceiling is consumed, on a stage whose prompt merely
discussed checkpoints.

This is the highest-value regression in unit 30b, and DevFlow's own planning
documents are exactly the kind of prompt content that triggers it.

Output: `claude_stream_reports_human_gate` and a gated stream branch in
`blocking_human_checkpoint_reported`, with the prompt-echo regression cluster.
</objective>

<review_incorporation>
Cross-AI review (`30-REVIEWS.md`, codex/gpt-5.6-sol, 2026-08-02) raised two
findings against this plan. Both were re-verified against the archived capture
during replanning. One is ACCEPTED in full, one PARTIALLY accepted with the
rejected half reasoned below.

**MEDIUM — all top-level assistant narration becomes trusted gate text.
ACCEPTED, the `assistant` filter is removed entirely.** The previous action kept
both `assistant` and `result` events. Re-parsing `raw_output_v3.jsonl` confirms
the reviewer's mechanism and adds the decisive detail: every top-level
`assistant` event carrying turn-FINAL text is duplicated verbatim into the
`result` event that follows it (line 17 → 19, line 36 → 37, line 53 → 54), so
admitting `assistant` events buys no detection capability that `result` events
do not already give. What it does buy is a new false-positive surface, and the
capture shows exactly that shape: line 6's top-level assistant text — "I'll
spawn both subagents in the background now." — is mid-turn narration that
appears in NO result event. An agent narrating "next I'll handle the task whose
`**Gate:** `blocking-human`` line the plan declares" would have recreated the
very false positive this plan exists to close, one layer inward. Scanning only
the `result` text of top-level `result` events removes it at zero cost.

**LOW — repeated full-stream parsing and concatenation is avoidable. ACCEPTED.**
`checkpoint_reported_in_capture` runs on every `devflow advance`, over a capture
that grows for the whole stage. The function now returns `bool` and
short-circuits on the first match rather than building one large `String`; it is
renamed accordingly (`claude_stream_gate_text` →
`claude_stream_reports_human_gate`), because a function that no longer returns
text should not be named as if it does.

**PARTIALLY REJECTED — "ideally under the same last-result semantics as verdict
parsing."** The narrowing to `result` events is accepted; the further narrowing
to the LAST result event is not, and the reason is this phase's own architecture.
Plan 30-01 established last-result-wins for the VERDICT, because a verdict is a
single final answer. Checkpoint detection is not a final answer — it asks
whether a human-blocking gate was reported anywhere in this stage's output, and
today's implementation scans the whole capture. Under stream-json a checkpoint
can be declared in turn N's result and be followed by task-notification turns
N+1, N+2 (v3 archives exactly that turn shape, three results in one process).
Last-result-only would silently drop that declaration and fall through to the
generic gate — the opposite-direction harm T-30-24 exists to prevent, and a
silent loss of a human authorization request is worse than the false positive
being fixed. All top-level `result` events are scanned; the difference from
today is which EVENTS are eligible, not how many of the eligible ones are read.
</review_incorporation>
