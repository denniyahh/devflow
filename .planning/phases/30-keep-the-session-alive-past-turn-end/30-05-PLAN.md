<objective>
Close the false-positive surface review constraint 3 identifies: under a
stream-json capture, the raw stdout contains the operator's full prompt echoed
back as a `user` event, so any prompt that merely *documents* a checkpoint gate
rendering reads as a live gate declaration to a substring scan that does not
know which event it is inside.

Purpose: `blocking_human_checkpoint_reported` scans raw, unbounded stdout. That
is correct today, because under the single-document envelope the only place gate
text can appear is inside the one `result` field the agent authored. Stream-json
breaks that invariant — echoed input becomes textually indistinguishable from
agent-authored output. The review calls this the one existing reader that
"survives by accident", and the failure mode is silent: a checkpoint auto-decide
fires, or the resume ceiling is consumed, on a stage whose prompt merely
discussed checkpoints.

This is the highest-value regression in unit 30b, and DevFlow's own planning
documents are exactly the kind of prompt content that triggers it.

Output: `claude_stream_gate_text` and a gated stream branch in
`blocking_human_checkpoint_reported`, with the prompt-echo regression cluster.
</objective>

  <action>
    Add `claude_stream_gate_text(events: &[serde_json::Value]) -> String`,
    placed with the other stream functions. It walks the events in order and
    concatenates, separated by newlines, the text of only those events that pass
    BOTH filters:

    First filter, event type: keep `assistant` and `result` events. Exclude
    `user` events entirely. A `user` event in this stream is always either the
    operator's original prompt echoed back, or a `task_notification` summary
    re-injected as user-role content — in neither case is it the agent declaring
    a gate. Also exclude every `system` event; `init` carries the tool and agent
    inventory, which is inert text that has no business in a gate scan.

    Second filter, provenance: keep only top-level events. An event is top-level
    when its `parent_tool_use_id` is JSON null OR the key is absent entirely.
    The absent case matters and must not be treated as non-top-level: `result`
    events carry no such key at all, confirmed across all three archived
    captures, so a naive presence check would drop exactly the events that
    matter most. This discrimination is the pitfall that invalidated the v1
    experiment outright — its heuristic mistook subagent-forwarded narration for
    orchestrator resumption, and the whole capture was discarded.

    For text extraction: from an `assistant` event take the text of each `text`
    block in `message.content`; from a `result` event take the `result` string
    field. Read these with direct `.get()` chains. Do not use `json_scan` or
    `json_find_key` — a recursive traversal would reach right back into the
    nested content both filters just excluded, silently undoing the fix.

    Then modify `blocking_human_checkpoint_reported` — and only its body, not
    its signature — to branch: build the event vector with `claude_stream_events`;
    if `is_claude_event_stream` returns true, run `text_reports_human_gate` on
    `claude_stream_gate_text`'s output ALONE and return that; otherwise fall
    through to the existing two-target logic completely unchanged.

    The `else` branch must be the existing code, untouched. The stream branch
    returns without consulting raw stdout at all — scanning both would reinstate
    the false positive this task exists to remove, since the echoed prompt is in
    the raw stdout by definition.

    Extend the function's doc comment to record the new branch and why the
    stream path deliberately does not also scan raw stdout. Point at review
    constraint 3 by name so the reason survives.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator prompt → DevFlow control flow | Under stream-json the prompt is echoed back into the same capture DevFlow scans for control signals, so operator-authored text crosses into a decision path it never touched before. |
| subagent → orchestrator relay | Subagent narration is forwarded into the top-level stream tagged with `parent_tool_use_id`, and can carry text that reads as an orchestrator declaration. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-21 | Tampering | `blocking_human_checkpoint_reported` under stream capture | high | mitigate | Exclude `user` and `system` events from the gate scan; the stream branch never scans raw stdout. Closes the prompt-echo false positive named in review constraint 3. Asserted by the echoed-prompt regression test, not by inspection. |
| T-30-22 | Spoofing | subagent-forwarded events | high | mitigate | Keep only events whose `parent_tool_use_id` is null or absent. Subagent-forwarded content cannot present as an orchestrator declaration. Absent-key is treated as top-level because `result` events carry no such key — confirmed across all three archived captures. |
| T-30-23 | Tampering | text extraction path | medium | mitigate | Extract event text with direct `.get()` chains only. A `json_scan`-family traversal would descend back into the nested content both filters exclude, silently undoing the mitigation while the tests on the outer shape still pass. |

All ten pre-existing checkpoint tests must pass unedited — editing one to accommodate a behavior change is a rejected pattern under this repository's own acceptance rules. |
