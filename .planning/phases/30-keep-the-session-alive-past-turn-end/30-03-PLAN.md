<objective>
Restore the three Layer-1 signals that die under a JSONL capture but survive
today under the single-document envelope: rate-limit classification, envelope
failure (`is_error`), and `session_id`.

Purpose: review constraint 3 states these explicitly. `claude_session_id` in
particular breaks the Phase 28 checkpoint-resume path — that phase's whole
delivery was reconstructing a session via `claude --resume`, which needs a
`session_id` DevFlow can read. A stream capture returns `None` from every one of
these three readers today, so flipping the adapter in Phase 31 would silently
regress rate-limit resume, failure attribution, and checkpoint resume all at once.

Output: `detect_claude_stream_rate_limit`, `claude_stream_session_id`, a stream
envelope-failure branch in `parse_claude_event_result`, and the wiring that makes
each reachable from the existing entry points.
</objective>

Cross-AI review (`30-REVIEWS.md`, codex/gpt-5.6-sol, 2026-08-02) rated this plan
**HIGH risk** and named it the first of three cross-plan blockers: "fix Plan
30-03's rate-limit semantics before any Rust implementation." Four findings.
Three ACCEPTED and fixed below; one REJECTED with rationale.

**HIGH — every healthy v3 stream would classify as `RateLimited`. ACCEPTED,
Task 1 rewritten.** Re-verified by reading the capture directly:
`raw_output_v3.jsonl` line 15 is
`{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","resetsAt":1785645600,"rateLimitType":"five_hour","overageStatus":"rejected",…}}`.
That event is present in a stream that then completed three turns successfully.
The previous plan classified the mere PRESENCE of a `rate_limit_event` as
rate-limited and mandated that exact line as the POSITIVE fixture — it would have
codified a false positive, and `outcome_policy.rs:41` maps
`AgentStatus::RateLimited` to `Action::AutoResume`, so every healthy Claude
stream stage would have been routed into the rate-limit resume path. Note the
second trap in the same object: `overageStatus:"rejected"` sits one level down
from `status:"allowed"`, so any nested search for the token `rejected` also
false-positives. The classifier must read `rate_limit_info.status` by direct
`.get()` and nothing else.

**HIGH — historical rate events outrank the final outcome. ACCEPTED, Task 1
rewritten.** The previous detector searched the whole event history before
examining the last result. In v3 the rate event (15) precedes all three results
(19, 37, 54), so an informational event from the first turn would have decided a
stream that finished cleanly forty seconds later. Rate-limit interpretation is
now scoped to the final turn interval.

**MEDIUM — the exact session-ID verification could fail without failing the
task. ACCEPTED, fixed in Task 2's verify.** The two commands were joined with
`;`, which discards the first command's status. Now `&&`.

**LOW — `pub` on `claude_stream_session_id` is broader than needed. REJECTED,
with rationale.** The suggestion is to prefer `pub(crate)` absent a concrete
cross-crate caller. Checked at replanning time: its sibling `claude_session_id`
is itself `pub` with no caller outside `agent_result.rs` — the cross-crate
consumer is the `session_id_from_capture` wrapper
(`pipeline_launch.rs:443`) — so `pub(crate)` here would make the two session
readers asymmetric for no behavioural gain, and the ROADMAP's 30b unit
description states the parsing layer is "public API in `devflow-core`". The
reviewer's underlying concern (a `pub` symbol with no caller becomes drift) is
already answered by the wiring requirement in this task: the function is
consumed by `session_id_from_capture` in the same commit, so it is never an
unreferenced export. Keeping `pub`.
</review_incorporation>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| coding agent → DevFlow | The agent authors `DEVFLOW_RESULT` marker JSON that DevFlow deserializes, and controls the text inside `result` fields. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-11 | Spoofing | `claude_stream_session_id` | high | mitigate | Read the top-level `session_id` of an `init` event via a direct `.get()`; never `json_scan`/`json_find_key`. Preserves the D-04/T-28-04 guarantee by construction: an agent cannot redirect the session DevFlow resumes into by planting a `session_id` inside its own marker JSON. Enforced by a runtime regression test asserting the planted value is not returned. |
| T-30-12 | Spoofing | `detect_claude_stream_rate_limit` | medium | mitigate | Read `rate_limit_info` and its `status` with direct `.get()` on the top-level `rate_limit_event` object. A nested traversal would let agent-authored text supply a fabricated retry hint (which drives the resume cron's scheduling) and would additionally reach the archived event's own nested `overageStatus:"rejected"`, misclassifying a healthy stream. |
| T-30-13 | Tampering | rate-limit vs failure precedence | high | mitigate | Rate-limit detection runs before both the marker and envelope-failure paths inside `parse_claude_event_result`, mirroring `evaluate_layer1`'s documented single-document ordering. Misclassifying a rate-limited run as generic `Failed` disables the only automated recovery path for it. Asserted by a dedicated precedence test. The precedence is deliberately narrow: the detector only fires on a final-turn explicit denial, so it cannot shadow the outcome of a stream that completed. |
| T-30-26 | Denial of Service | false-positive rate-limit classification | high | mitigate | Two independent guards, both required, neither a substitute for the other: (1) positional — only `rate_limit_event` entries after the second-to-last `result` event are eligible, so history cannot outrank the final turn; (2) semantic — only an explicitly enumerated denial `status` classifies, and every unrecognised value defers. Without them, `outcome_policy.rs:41` routes `RateLimited` to `Action::AutoResume`, so every healthy Claude stream stage — each of which carries a routine `status:"allowed"` telemetry event — would be auto-resumed against a fabricated retry time instead of advancing. Enforced by the mandatory negative regression built from the real archived event. |
| T-30-14 | Elevation of Privilege | `AgentResult` field surface | high | mitigate | No `session_id` field is added to `AgentResult`. `parse_marker_lines` deserializes agent-authored JSON directly into that struct, so any added field is agent-settable — the rejected design is recorded at `agent_result.rs:256-265` and stays rejected. |
| T-30-15 | Tampering | envelope-over-marker precedence | medium | mitigate | `is_error: true` on the last `result` event overrides a success marker, matching `detect_claude_envelope_failure`'s existing rule that the envelope is authoritative for errors and a stale or echoed success marker must not win. |
