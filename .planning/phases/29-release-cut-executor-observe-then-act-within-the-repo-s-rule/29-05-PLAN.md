<design_notes>
RD-N decision references are defined in `29-01-PLAN.md` § design_notes.

**Why one action serves two steps.** CONTRIBUTING.md § "Cutting a Release"
step 1 puts the version bump and the changelog section in the same commit set,
and step 2 lands them through one pull request into `develop`. Mapping both
`VersionBumped` and `ChangelogWritten` to the same idempotent action keeps the
code honest about that: the two observations are distinct facts with distinct
oracles, but one action produces both. The action re-derives everything from the
version string on each run, so calling it a second time after a partial failure
completes what is missing rather than duplicating what exists.

**Why a scratch worktree.** The operator may be on any branch with any working
state when a release is cut. `worktree::add` gives the release branch its own
checkout, so the operator's checkout is never moved, stashed, or dirtied. This
also removes the class of failure `scripts/sync-main-to-develop.sh` guards
against by refusing to run unless the tree is clean and the branch is `develop`
— the executor does not need that guard because it never operates in the
operator's checkout at all.
</design_notes>

`pub fn release_branch_name(version: &str) -> String` — returns
`release/bump-v<version>`. `pr_refs` must return this same string as the head
for steps 1 and 2; add a test asserting the two agree so they cannot drift.

`fn prepare_bump_branch(project_root: &Path, version: &str) -> Result<PreparedBranch, String>`
where `PreparedBranch` is a small public struct carrying the branch name, the
number of commits created, and whether the branch already carried them.

The sequence:

1. Fetch `develop` from `origin` through `git::git_command(project_root)` so
   the start point is current. This is an action step, so a fetch is correct
   here — unlike the observer in `29-02`, which must not mutate.
2. Create a scratch worktree with `worktree::add(project_root, &scratch_path,
   &branch, "origin/develop", true)`. Place the scratch path under the
   directory `worktree::worktrees_dir` already uses, with a name derived from
   the version so a concurrent run on a different version cannot collide. If
   `add` returns `WorktreeError::Exists`, remove the stale path with
   `worktree::remove(project_root, &scratch_path, true)` and retry once; a
   second failure is an `Err` carrying git's own message.
3. Inside the scratch worktree, parse the operator-supplied version string into
   a `version::Version` and call `version::write_version(&scratch_path,
   &version)`. That single call performs the two-place bump. Do not write
   either location by hand and do not call `version::compute_version` — the
   operator's positional is the only version source in this phase, and a second
   source is a second implementation that can drift while driving irreversible
   steps.
4. Run `cargo build` in the scratch worktree via
   `git::hermetic_command("cargo", &scratch_path)` so `Cargo.lock` picks up the
   new version, as CONTRIBUTING.md step 1 requires. Use `hermetic_command`
   rather than a bare `Command`: cargo's git-invoking build scripts are the
   documented motivating case for the Phase 27 scrub (threat T-29-05).
5. Commit `Cargo.toml` and `Cargo.lock` with `GitFlow::commit_path`, using a
   conventional-commit subject in the repository's own style naming the version.
6. Compute the changelog body with the existing chain in the order
   `hooks.rs`'s `version_bump` already uses:
   `version::reachable_semver_baseline`, then `version::release_range_start`,
   then `version::changelog_sections`, then `version::render_changelog_body`.
   Compose the file with `ship::prepend_changelog(&existing, version, &today,
   &body)`. Write and commit `CHANGELOG.md` with `commit_path`. Do not write new
   formatting logic: this content chain shipped in Phase 25 and is the one piece
   Phase 26 built cleanly.
7. Push the branch to `origin`.
8. Remove the scratch worktree on **every** exit path, success and failure
   alike, so a failed run leaves no orphaned registration. Structure this so the
   removal cannot be skipped by an early return — a guard value whose `Drop`
   performs the removal, or a single inner function whose result is captured
   before an unconditional cleanup call.

If the branch already exists on `origin` and already carries both changes,
return a `PreparedBranch` marked already-prepared and make no new commit.

Add `#[cfg(test)] mod tests` cases for every `<behavior>` bullet against real

Add the pull-request half of the action and wire it into the walk.

`fn pr_argv(head: &str, base: &str, title: &str, body_file: &Path) -> Vec<String>`
and `fn merge_argv(number: u64, method: MergeMethod) -> Vec<String>` — pure
argument-vector builders, returned as owned strings so they can be asserted in
tests without executing anything. `merge_argv` always includes
`method.flag()`; because `MergeMethod` has no unspecified variant, an
argument vector with no method flag is unrepresentable. This is the executable
form of this phase's promoted merge-intent model: every merge passes an
explicit method that came out of resolution against a discovered set.

`pub fn open_and_arm_pr(project_root: &Path, head: &str, base: &str, title: &str,
body: &str, intent: MergeIntent) -> Result<u64, String>` — the shared helper
every pull-request-backed step uses.

1. Call `release_policy::discover_allowed_merge_methods(project_root, base)`,
   then `release_policy::resolve_merge_method(intent, &allowed)`. Do this
   **before** creating anything: discovering that the required method is
   unavailable after a pull request already exists would leave an armed PR that
   cannot be merged correctly. On `Err`, return it as the refusal text
   unchanged — it already names the intent, the required method, and the
   discovered set (RD-9's "refuse loudly rather than silently substituting").
2. Create the pull request with `gh pr create`, passing the head, base, title,
   and a body supplied via a temporary file rather than an inline argument, so
   no changelog or version text ever crosses a shell. Every argument is a
   discrete `Command::args` element and `.current_dir(project_root)` is pinned.
   Read back the created number with `gh pr view --json number --jq .number`
   rather than parsing `gh pr create`'s human-readable stdout.
3. Arm auto-merge with `gh pr merge --auto` plus the resolved method flag.
   Never issue a bare `--auto`: this repository already lost the sync-back
   ancestry once, on 2026-07-27, to exactly that omission, and needed a repair
   pull request. Do not build a polling loop of your own — GitHub's own
   auto-merge is the thing that waits for the required checks, and re-running
   the walk is how DevFlow learns whether it landed.
4. On any `gh` failure, return `Err` with a failure-class description and the
   exit status, never with `gh`'s raw stdout or stderr (T-29-03).

`fn bump_and_changelog_pr(project_root: &Path, version: &str) -> Result<String, String>` —
calls `prepare_bump_branch`, then `open_and_arm_pr` with
`MergeIntent::VersionBump`, head `release_branch_name(version)`, base
`develop`, and a title in the repository's conventional-commit style naming the
version. Returns a detail naming the branch, the pull-request number, and the
resolved method.

Wire it in: `action_for(ReleaseStep::VersionBumped)` and
`action_for(ReleaseStep::ChangelogWritten)` both return this action. Leave the
remaining four arms as they are; `29-06` and `29-07` fill them.

Add unit tests in `release_execute.rs` for the argument-vector builders and the
resolution-refusal path, using fixture allowed-method arrays and never calling
`gh`. Add a CLI-level test in `crates/devflow-cli/tests/release_cut.rs` named
`cut_stops_with_a_real_reason_when_the_remote_is_unreachable`, asserting the
step stops with a message that quotes the real tool failure rather than an
invented one. Add `merge_argv_always_carries_a_method_flag`, iterating every
`MergeIntent` variant against every allowed set that resolves successfully and
asserting each built vector contains one of the two flags — this is the
invariant this phase's `<assumption_delta_decision>` names, and it goes red the
moment a future change reintroduces a hardcoded or omitted method.

<threat_model>
ASVS level **1**; blocking threshold **high**.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator -> DevFlow CLI | the version string reaches file writes, commit messages, branch names, and pull-request titles |
| DevFlow -> `origin` | a branch is pushed; the push crosses `scripts/hooks/pre-push`, which enforces repository policy |
| DevFlow -> GitHub REST API (via `gh`) | pull-request creation and auto-merge arming, driven by a discovered allowed-method set |
| DevFlow -> the operator's own checkout | must remain untouched; the scratch worktree is the isolation boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-29-01 | Tampering | version string reaching branch names, titles, and `gh` argv | high | mitigate | every argument a discrete `Command::args` element; the pull-request body is passed by file, never inline; no shell is invoked, asserted by a source-level check for `sh -c` |
| T-29-08 | Tampering | an auto-merge with no method flag silently squashing | high | mitigate | `merge_argv` always includes `MergeMethod::flag()`; `MergeMethod` has no unspecified variant; `merge_argv_always_carries_a_method_flag` asserts it across every intent and allowed set |
| T-29-18 | Tampering | the executor moving or dirtying the operator's checkout | high | mitigate | all writes and commits happen in a scratch worktree created by `worktree::add`; a test asserts the project root's HEAD, branch, and porcelain status are unchanged |
| T-29-19 | Denial of Service | an orphaned scratch worktree blocking every later run | medium | mitigate | removal on every exit path including failures, plus a remove-and-retry-once path when `worktree::add` reports the path already exists; a forced-failure test asserts `git worktree list` is clean |
| T-29-05 | Tampering | inherited `GIT_DIR` redirecting `cargo build` in the scratch worktree | medium | mitigate | `hermetic_command("cargo", &scratch_path)`, the documented motivating case for the Phase 27 scrub |
| T-29-03 | Information Disclosure | `gh` stdout/stderr on the create and merge calls | high | mitigate | failure-class descriptions and exit status only; raw `gh` output never logged, printed, or embedded in an error (T-17-13) |
| T-29-16 | Tampering | a duplicate pull request from a re-run | medium | mitigate | `open_pr` runs before the action in `cut`'s walk, and the branch name is a deterministic function of the version so a re-run finds the same head |
| T-29-SC | Tampering | npm/pip/cargo installs | high | mitigate | this plan adds zero new dependencies; `cargo build` in the scratch worktree resolves only already-pinned dependencies. Any new dependency requires the Package Legitimacy Gate and a blocking human checkpoint first |
</threat_model>
