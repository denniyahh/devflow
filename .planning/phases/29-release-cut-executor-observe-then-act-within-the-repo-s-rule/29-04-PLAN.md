<objective>
Build the walker that turns unit 29a's observations into unit 29b's actions:
`devflow release cut <version>`, which observes each of the six release steps
in order, performs the first one that is not done, and stops at the first hard
gate with an accurate report of where it stopped and why.

This plan builds the walk, the CLI, the report, the in-flight pull-request
observation, and the tests that prove the executor carries no
operator-presence requirement. It deliberately builds **no step actions yet** —
those land in `29-05`, `29-06`, and `29-07`, one reversibility tier at a time.

Purpose: the design rule (RD-2) is a control-flow shape, not a slogan. This
plan is that shape, isolated, with the two properties that are easiest to lose
later — refusing on unreachable, and never requiring a human — pinned by test
before any irreversible code exists to distract from them.

Output: `crates/devflow-core/src/release_execute.rs` (new), the
`devflow release cut` subcommand, and `crates/devflow-cli/tests/release_cut.rs`.

## Why this build carries no step actions, and why that is not a scope reduction

The operator's locked unit split (ROADMAP.md § "Units — split by reversibility,
not by step count, and each independently shippable") requires that 29a, 29b,
and 29c each ship on their own, and that a stall in 29c still leave 29a and 29b
delivered. That is only true if the walk exists independently of the actions it
drives. Phase 26 produced 74 commits and delivered nothing usable precisely
because everything was one indivisible blob.

So this build walks all six steps and carries an action for none of them yet.
`29-05` supplies steps 1 and 2, `29-06` supplies steps 3 and 5, and `29-07`
supplies steps 4 and 6. Every one of the six is planned; none is deferred,
reduced, or left to a later phase.

**The report for a step with no action in this build is not a prediction and
not a self-imposed gate.** It is a fact about the binary that is running,
stated plainly, and it is exactly the shape RD-2 prescribes: advance as far as
you can, stop, and say accurately where you stopped and why.

## The walk, in one paragraph

For each step in `ReleaseStep::ALL` order: observe it. `Unreachable` stops the
walk and refuses — an oracle that could not be reached must never lead to an
action, because acting on it risks redoing an already-completed irreversible
step. `Present` records the step done and moves on. `Absent` triggers the
in-flight check for pull-request-backed steps: an open PR for the same head and
base means the step is under way and the walk stops with the PR number rather
than opening a second one. Otherwise the step's action runs, the step is
re-observed, and the walk stops with an accurate account — because GitHub's
auto-merge is asynchronous, the honest post-action state is almost always
"armed, not yet landed", and the correct response is to stop and let a later
run re-observe. Re-running *is* resuming; nothing is carried between runs.
</design_notes>

  <action>
Create `crates/devflow-core/src/release_execute.rs` and declare it in `lib.rs`
as `pub mod release_execute;`, alongside the other release modules.

Define:

`StepOutcome` — a public enum with variants `AlreadyDone { detail: String }`,
`InFlight { detail: String }`, `Performed { detail: String }`,
`Stopped { reason: String }`, and `NoActionInThisBuild { unit: &'static str }`.
Derive `Debug`, `Clone`, `PartialEq`, `Eq`. Add `pub fn is_terminal(&self) ->
bool`, true for `InFlight`, `Performed`, `Stopped`, and
`NoActionInThisBuild` — the walk stops on all four, and only `AlreadyDone`
continues it. `Performed` is terminal on purpose: an action that was just taken
has an asynchronous outcome, and continuing past it would mean predicting that
outcome, which RD-2's third layer forbids.

`CutReport` — a public struct with `pub steps: Vec<(ReleaseStep, StepOutcome)>`
and `pub authorized: bool`, plus `pub fn stopped_at(&self) -> Option<(ReleaseStep,
&StepOutcome)>` returning the first non-`AlreadyDone` entry, and
`pub fn all_done(&self) -> bool`.

`StepAction` — a type alias or small trait object for a step's action, taking
the project root and the version and returning `Result<String, String>` where
`Ok` carries a human detail and `Err` carries the real failure text. Provide
`fn action_for(step: ReleaseStep) -> Option<StepAction>` returning `None` for
every step in this build. `29-05`, `29-06`, and `29-07` each replace specific
`None` arms with real actions; the `match` is exhaustive over all six variants
with no wildcard arm, so a new step cannot be silently skipped.

`fn unit_for(step: ReleaseStep) -> &'static str` — maps each step to the unit
identifier that supplies its action: steps 1, 2, 3, and 5 to `29b`, steps 4 and
6 to `29c`. Used only to make the `NoActionInThisBuild` report say which unit
is missing.

`pub fn cut(project_root: &Path, version: &str, authorized: bool) -> CutReport` —
the walk. If `authorized` is false, return immediately with a single
`Stopped` outcome whose reason states that a release requires the mandate and
names all three ways to grant it (`--yes-release`, `yes_release = true` in
`devflow.toml`, `DEVFLOW_YES_RELEASE`). Do not observe anything first: an
unauthorized run must not even touch the network. Otherwise iterate
`ReleaseStep::ALL` in order, calling `release_observe::observe`:

- `Observation::Present` records `AlreadyDone` and continues.
- `Observation::Unreachable { reason }` records `Stopped` carrying that exact
  reason text and ends the walk. Do not retry, do not degrade, do not proceed.
  Acting on an unreachable oracle is how an already-completed irreversible step
  gets redone.
- `Observation::Absent` first calls `open_pr` for the step's head and base when
  the step is pull-request-backed. `PrPresence::Open { number }` records
  `InFlight` naming the number and ends the walk — the step is under way and a
  second pull request would be a duplicate. `PrPresence::Unreachable { reason }`
  records `Stopped`. `PrPresence::None` looks up `action_for(step)`: `None`
  records `NoActionInThisBuild { unit: unit_for(step) }` and ends the walk;
  `Some(action)` runs it, records `Performed` on `Ok` or `Stopped` on `Err`,
  and ends the walk either way.

`cut` performs no writes to `.devflow/`, to `devflow.toml`, or to any other
DevFlow-owned file, and holds no state across invocations. Re-running is
re-observing.

`pub enum PrPresence { Open { number: u64 }, None, Unreachable { reason: String } }` —
three-valued like every other observation in this phase.

`pub fn open_pr(project_root: &Path, head: &str, base: &str) -> PrPresence` —
runs `gh pr list --state open --head <head> --base <base> --json number --jq
'.[0].number'` with `Command::new("gh")`, `.current_dir(project_root)` pinned,
and discrete `Command::args` elements. Empty stdout is `None`; a parseable
number is `Open`; a spawn failure, non-zero exit, or unparseable stdout is
`Unreachable` with a failure-class reason that never embeds `gh`'s raw output
(T-29-03). Also define `pub fn pr_refs(step: ReleaseStep, version: &str) ->
Option<(String, String)>` returning the head and base branch names for the
pull-request-backed steps and `None` for steps 4 and 6, which are not
pull-request-backed. The head branch names must be deterministic functions of
the version so a re-run finds the same branch: use `release/bump-v<version>`
for steps 1 and 2, `develop` for step 3, and `sync/main-to-develop-v<version>`
for step 5.

In `main.rs`: add `Cut { version: String, #[arg(default_value = ".")] project:
PathBuf, #[arg(long)] yes_release: bool }` to the `ReleaseAction` enum, and a
dispatch arm calling `release_cut(&project_root(project)?, &version, yes_release)`.
The version stays a required positional and is never re-derived from
`compute_version` — a second version source is a second implementation that can
drift, which is the bug class RD-5 exists to prevent, and here it would drive
irreversible steps.

In `commands.rs`: add `pub(crate) fn release_cut(project_root: &Path, version:
&str, yes_release_flag: bool) -> Result<(), CliError>`. Combine the flag with
`devflow_core::config::yes_release(project_root)` using logical OR, exactly as
`commands::start` combines `--yes-ship` with its config value — the flag has no
negative form, so passing it always wins. Before the walk, run the same
`gh auth status` check `preflight.rs` already performs before any other `gh`
call, and on failure stop with that as the reason rather than letting six
oracles each fail separately. Then call `cut`, print one row per reported step
using `release_status`'s existing icon-printing loop shape, print the stop
reason prominently as the last line, and return `CliError::Message` when the
report is not `all_done`.

Add `#[cfg(test)] mod tests` in `release_execute.rs` covering every
`<behavior>` bullet. Structure `cut` so the observation source can be
substituted in tests — take the observer as a function parameter on an inner
`cut_with` and have the public `cut` pass `release_observe::observe` — so the
walk's control flow is tested against injected `Observation` sequences with no
network. Assert on the returned `CutReport`, never by re-deriving the walk
inside the test body.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator -> DevFlow CLI | the mandate and the version string cross here and gate every subsequent action |
| DevFlow -> GitHub REST API (via `gh`) | open-pull-request state is untrusted external input that decides whether an action is attempted |
| DevFlow -> local filesystem | the executor must record nothing; any write to `.devflow/` is a boundary violation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-29-07 | Repudiation | an action taken with no operator mandate | high | mitigate | `cut` returns immediately on `authorized = false` and observes nothing; three CLI tests cover the flag, environment, and config-file grant paths and the refusal path |
| T-29-11 | Tampering | acting on an unreachable oracle and redoing a completed step | high | mitigate | `Observation::Unreachable` ends the walk before any action is looked up; an injected-unreachable unit test asserts the report length is exactly one |
| T-29-16 | Tampering | a duplicate pull request created because an in-flight one was not seen | medium | mitigate | `open_pr` runs before any pull-request-backed action; `PrPresence::Unreachable` stops rather than proceeding, so an unanswerable in-flight check never leads to a second PR |
| T-29-14 | Tampering | the executor accumulating a progress record | high | mitigate | `cut` performs no DevFlow-owned writes and holds nothing across invocations; `cut_writes_no_devflow_state` and `cut_is_idempotent_across_runs` assert both halves |
| T-29-03 | Information Disclosure | `gh` stdout/stderr in `open_pr` and the auth gate | high | mitigate | failure-class descriptions only; raw `gh` output never logged, printed, or embedded in a reason (T-17-13) |

| T-29-17 | Denial of Service | the executor blocking forever waiting for input that never arrives | high | mitigate | no stdin read exists on any release path; `cut_runs_unattended_with_stdin_closed` spawns with a null stdin and a bounded wait and fails rather than hanging |
