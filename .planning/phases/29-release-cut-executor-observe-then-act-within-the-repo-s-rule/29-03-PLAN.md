## OPEN QUESTION 1, RESOLVED: the authorization-record boundary

`.planning/ROADMAP.md:2149-2152` states that operator authorization is the one
thing that cannot be observed, that "a minimal persisted record may survive —
for authorization only, never for progress", and that pinning the boundary was
a discuss-phase task. No discuss-phase ran. **This plan pins it.**

**The boundary: DevFlow reads the authorization record. DevFlow never writes
it.**

That single asymmetry is what makes the exception safe, and it is not a
convention — it is structural. A progress ledger requires the executor to
*write* what it has done. An executor that performs zero writes to any
DevFlow-owned state file cannot have a ledger, whatever anyone later intends.
Phase 26's CR-05 (an in-flight ledger permanently bricks the release path) and
CR-02 (the ledger says Complete while nothing is published) both require a
write that this design makes impossible.

Concretely, authorization lives in exactly the three places the shipped
`yes_ship` precedent (Phase 28, D-12) already established, and nowhere else:

| Source | Written by | Read by | Precedent |
|---|---|---|---|
| `--yes-release` CLI flag | the operator, per invocation | `commands::release_cut` | `--yes-ship` on `devflow start` |
| `yes_release = true` in `devflow.toml` | the operator, by hand | `config::yes_release` | `yes_ship` in `DevflowConfig` |
| `DEVFLOW_YES_RELEASE` | the operator's environment | `config::yes_release` | `DEVFLOW_YES_SHIP` |

Four properties make this a mandate rather than a ledger, and each is asserted
by a test in this plan:

1. **Read-only.** No DevFlow code path writes `devflow.toml` or any file under
   `.devflow/` for release purposes.
2. **Not consumed.** Reading authorization does not clear or decrement it. It
   is a standing grant, so re-running is free — which is the same property
   derived state gives every other step.
3. **Carries no progress.** The record is a single boolean. It cannot express
   "step 3 done", so it cannot drift into meaning that.
4. **Defaults to false.** An absent file, or one that omits the key, never
   authorizes.

**Scope: one mandate covers the whole sequence.** RD-4 says the operator
"grants intent once (a flag) ... thereafter the executor proceeds as far as the
repo's rules and the environment permit." Adding a *second*, narrower flag for
the irreversible steps would be a self-imposed gate that no repository rule
imposes — precisely what RD-2 forbids by construction. One flag, whole
sequence. 29-RESEARCH.md § Open Questions 1 flagged this as undecided because
Phase 26's D-03 predates the unit split; RD-4's wording settles it, and it is
settled here rather than left to the executor.

**This is not an operator-presence requirement.** RD-3 is explicit: the shipped
executor must not require a human at the keyboard and must not refuse to run
unattended. A mandate is checked once, from configuration; it never waits for
input, never reads stdin, and never blocks. `29-04-PLAN.md` carries the test
that proves it.

<assumption_delta_decision>
**Detector fired** on this phase with one substantive signal.

**Signal (`kind: chosen`, substantive):** *"apply a fixed internal policy to
**choose** among them"* — the merge method moves from a derived or compiled-in
constant to a value chosen against a discovered set. A configuration decision
is becoming a modeling decision.

**Also fired, and dismissed with reasons rather than silently:** three
`pluralization` signals on the roadmap's words "second implementation",
"another", and "also". All three are argumentation artifacts of the roadmap's
prose — it argues *against* second implementations — not evidence of a real
identity becoming plural. No modeling change follows from them.

**The noun that is now primary:** not "the merge command" and not "the merge
method", but **a merge *intent*, resolved against a discovered allowed-method
set**. The intent (`VersionBump`, `ReleaseCut`, `SyncBack`) is the durable
concept; the concrete method is the output of resolving it against facts
discovered at runtime, and may legitimately differ per repository, per branch,
and over time.

**Decision: `promote`.** `MergeIntent` plus `resolve_merge_method(intent,
allowed)` becomes the primary representation. The old specific form — "squash
on `main`, merge on `develop`" — is demoted to a detail of one variant: it is
the *preference* each intent expresses, and it is never a branch-name lookup
and never a constant that reaches a `gh` invocation without passing through
resolution. Rationale: this is a generalization, and the correct move on a
generalization is to promote the general representation and demote the specific
one, not to keep both. Keeping the branch-name form alongside would leave two
sources of truth for one decision, which is the exact drift class RD-9 names.

**Invariant test encoding the generalized intent** (implemented in Task 2 and
re-asserted at every call site in `29-05-PLAN.md` and `29-06-PLAN.md`): *every
merge this executor performs passes an explicit method that was present in the
discovered allowed set.* It goes red the instant a future change reintroduces a
hardcoded method or a bare auto-merge with no method flag.
</assumption_delta_decision>

Create `crates/devflow-core/src/release_policy.rs` and declare it in `lib.rs`
as `pub mod release_policy;`, placed alphabetically between `recover` and
`registry` alongside the other new release modules.

Define:

`MergeIntent` — a public `Copy` enum with variants `VersionBump`,
`ReleaseCut`, `SyncBack`. This is the promoted primary noun per this plan's
`<assumption_delta_decision>`: pull requests are classified by what they are
*for*, never by which branch they target. Two different PRs into `develop`
(the version bump and the sync-back) require different methods, which is
precisely why a branch-name lookup is insufficient and why the roadmap forbids
copying "squash on main, merge on develop".

`MergeMethod` — a public `Copy` enum with variants `Merge` and `Squash`, plus
`pub fn flag(self) -> &'static str` returning the literal `gh pr merge` flag
and `pub fn api_name(self) -> &'static str` returning the lowercase name as it
appears in GitHub's allowed-method lists. There is no third variant and no
"unspecified" variant: a merge with no method is unrepresentable in this type
system, which is what makes Pitfall 3 impossible to reintroduce by accident.

`MergePolicyError` — a public enum with `NotAllowed { intent: MergeIntent,
required: MergeMethod, allowed: Vec<String> }` and `AllowedSetUnknown { reason:
String }`, implementing `std::fmt::Display` (or `thiserror::Error`, matching
`GitError`'s existing style) so the CLI can print an actionable refusal.

`pub fn required_method(intent: MergeIntent) -> MergeMethod` — the fixed
internal policy, and the only place a per-intent preference is written down.
`VersionBump` and `ReleaseCut` require `Squash`; `SyncBack` requires `Merge`.
Document the `SyncBack` arm with the incident: CONTRIBUTING.md step 6 records
that a squashed sync collapses the two parents, discards the ancestry link the
step exists to create, and did so on 2026-07-27, needing a repair PR. That
requirement is a hard constraint of the operation, not a repository setting,
so it is expressed in the policy and not discovered.

`pub fn resolve_merge_method(intent: MergeIntent, allowed: &[String]) -> Result<MergeMethod, MergePolicyError>` —
pure, no I/O. Returns `AllowedSetUnknown` when `allowed` is empty. Otherwise
compares `required_method(intent).api_name()` against the allowed entries,
trimmed and compared case-insensitively. Returns `Ok` on a hit and `NotAllowed`
on a miss. It must never return the other method on a miss: refusing loudly is
the required behavior (RD-9), because a silent substitution is exactly how the
documented incident happened.

`pub fn intersect_allowed(repo_level: &[String], branch_level: &[String]) -> Vec<String>` —
pure. The effective allowed set is the intersection of what the repository's
merge settings permit and what the branch's ruleset permits; either one can
forbid a method independently.

`pub fn discover_allowed_merge_methods(project_root: &Path, branch: &str) -> Result<Vec<String>, String>` —
the discovery I/O. Query the repository's own merge settings with
`gh api repos/{owner}/{repo}` reading `allow_merge_commit` and
`allow_squash_merge`, and the branch's effective rules with
`gh api repos/{owner}/{repo}/rules/branches/<branch>` reading the
`pull_request` rule's `allowed_merge_methods`. Combine with
`intersect_allowed`. If the branch-rules endpoint returns no `pull_request`
rule, the branch imposes no additional restriction and the repository-level set
stands alone. Use `Command::new("gh")` with `.current_dir(project_root)` pinned
and discrete `Command::args` elements. Every failure returns `Err` with a
failure-class description that never embeds `gh`'s raw output (T-29-03).

Never cache the discovered set to disk and never compile a copy of it into the
source. The measured live values in `.planning/ROADMAP.md:2079-2089` are a
snapshot for humans reading the plan, not a value for the code to carry — the
repository's owner can change them without a code change, which is the whole
reason discovery exists.

Add `#[cfg(test)] mod tests` covering every `<behavior>` bullet. Every
resolution case uses fixture arrays passed directly to `resolve_merge_method`;
no test calls `gh`. Include the two live-measured configurations as named
fixtures (`develop` allowing merge and squash, `main` allowing squash only) and
at least one hypothetical configuration that is not this repository's, so the
suite proves the policy is general rather than tuned to today's settings.
  </action>
