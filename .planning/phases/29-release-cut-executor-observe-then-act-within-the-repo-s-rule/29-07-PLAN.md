## The two checkpoints in this plan are build-time gates, not runtime behavior

This plan contains a `checkpoint:decision` and a `checkpoint:human-verify`.
Both gate **how DevFlow gets built** — whether this code is written at all, and
whether the resulting diff is fit to merge. Neither becomes a requirement
inside the shipped executor.

RD-3 is explicit and non-negotiable: the shipped executor must not carry a rule
requiring a human at the keyboard and must not refuse to run unattended.
`29-04-PLAN.md`'s `cut_runs_unattended_with_stdin_closed` asserts that property
and must stay green through this plan. A build-time review gate and a runtime
presence requirement are different things, and conflating them is precisely the
mistake the operator caught and reversed in an earlier draft of the roadmap
entry.

## D-10, carried unchanged and stated once more because this is the step it is about

No signing-viability predictor. Not here, not anywhere. The tag step constructs
the command CONTRIBUTING.md documents, runs it, and reports git's own exit code
and stderr. This project has twice deleted signing predictors outright (999.50,
999.54) rather than fix them, because a predictor is a second implementation of
git's behavior that must stay in sync with it forever. `git.rs` still contains
a viability helper for `release --check`'s preflight; it is reference only and
no code in this plan calls it.

The same reasoning governs the missing-key case. `scripts/hooks/pre-push` makes
enforcement **opt-in**: an unset `devflow.releaseSigningKey` means no
enforcement, so a contributor who never cuts a release needs no setup. The
executor must be no stricter than the repository's own rule (RD-2), so an unset
key is not a refusal — it degrades to the same command the documented shell form
degrades to, the push is attempted, and the hook is the authority on whether the
result is acceptable. DevFlow surfaces the hook's own message and stops.

## Why the crates.io JSON API and not the sparse index

`cargo publish` itself waits on the sparse index, which is CDN-cached and can
lag a completed publish — that lag is the literal mechanism behind the
"waiting for devflow-core 2.2.0 to be available" line this repository already
observed during the real v2.2.0 cut. DevFlow's own re-observation uses the
database-backed JSON endpoint instead, which has no such layer. The two waits
are answering the same question against different sources, so DevFlow's bound
does not need to match cargo's.

`pub enum TagPlan` with variants `CreateNew`, `ReplaceLocal { existing: String }`,
`LeaveAlone { existing: String }`, and `Refuse { reason: String }`. Derive
`Debug`, `Clone`, `PartialEq`, `Eq`.

`pub fn plan_local_tag(project_root: &Path, tag: &str, target_commit: &str) -> TagPlan` —
observes the local tag namespace before anything is created. The phase-Ship
hook at `hooks.rs:278-337` creates a local, lightweight, unsigned tag of exactly
this name on every ordinary Ship, unconditionally, so on any machine where a
phase has ever shipped the name is already taken. The tag verb refuses to
overwrite an existing name without the force flag, so this is not a rare edge
case — it is the common case.

The four branches:
- no tag of that name: `CreateNew`.
- a tag at the target commit that is lightweight or annotated-but-unsigned:
  `ReplaceLocal`. Forcing over it is correct — it is the hook's artifact, and
  the release needs a signed tag at the same commit.
- a tag at the target commit that is annotated and carries a signature block:
  `LeaveAlone`. Never force over a tag that already correctly names the release
  commit and is signed; re-creating it would replace a possibly-correct
  signature with whatever key is ambient.
- a tag of that name at any **other** commit: `Refuse`, with a reason naming
  both commits. Forcing here would silently retarget a release name, which is
  the one outcome worse than stopping.

Determine annotated-versus-lightweight from the object type of the ref, and
signature presence by inspecting the tag object's body for a signature block —
not by cryptographic verification. Verification needs the signer's public key
resolvable in whatever environment this runs in, and its absence is a local
tooling gap rather than evidence about the tag. Presence is answerable
everywhere; whose signature it is, is the pre-push hook's question, and it
already answers it by fingerprint.

`pub fn tag_argv(release_key: Option<&str>, tag: &str, commit: &str, force: bool) -> Vec<String>` —

`pub fn publish_plan(project_root: &Path) -> Result<Vec<String>, String>` —
calls `git::publish_order(project_root)` and returns its result unchanged.
Error on an empty result. Do not sort, filter, reverse, or otherwise adjust the
sequence, and do not write any crate name as a literal anywhere in this module:
the order is computed from the workspace's own members and dependency graph and
is already tested, and a second implementation is a second thing that can drift
from the first. CONTRIBUTING.md states plainly that the ordering is a hard
requirement rather than a convention, because the dependent crate resolves
against the published registry version once packaged and fails to build if the
dependency is not live.

`pub fn publish_all(project_root: &Path, version: &str) -> Result<Vec<String>, String>` —
iterates `publish_plan`'s result in order. For each member:

1. Observe its publish state at the target version using the crates.io JSON
   oracle already built in `release_observe`. Published means skip and record;
   not published means proceed; unreachable means stop the whole run and return
   the reason. An unreachable registry must never be read as "not published",
   because acting on that reading is how a completed irreversible step gets
   redone.
2. Publish with `git::hermetic_command("cargo", project_root)` and the package
   selector for that member. `hermetic_command` rather than a bare command:
   cargo's build scripts invoke git and inherit the redirecting variables all
   the way down the process tree, and cargo is the documented motivating case
   for the Phase 27 scrub (threat T-29-05).
3. On failure, return an error containing cargo's own stderr and stop. Do not
   attempt to undo the crates already published: RD-6 is fail-fast with no
   automatic rollback, which is safe here precisely because every step is
   independently re-runnable — a later run re-observes and continues from
   wherever the world actually is. Note also that cargo's own duplicate-version
   rejection is the authoritative final gate: the pre-check in step 1 is a
   skip-what-is-done optimization, never the sole thing standing between the
   run and a duplicate attempt.
4. On success, re-observe availability against the crates.io JSON endpoint with
   a bounded wait — a small number of attempts over roughly thirty seconds, not
   an open-ended loop — before moving to the next member. Exhausting the bound
   returns an error naming the member and the bound rather than proceeding: the
   next crate resolves against the registry and will fail to build if the
   dependency is not yet live. Use the JSON endpoint and not the sparse index;
   the index is CDN-cached and its lag is the mechanism behind the wait message
   cargo itself printed during the real v2.2.0 publish, which would manufacture
   exactly the ambiguity this phase exists to remove.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator -> DevFlow CLI | the version string reaches tag names, tag messages, and package selectors |
| DevFlow -> local signing key material | the release key is selected by an explicit config value; its value and path must never be logged |
| DevFlow -> `origin` (tag push) | crosses `scripts/hooks/pre-push`, which is the authority on whether the tag carries the right key |
| DevFlow -> crates.io (publish) | the single most irreversible boundary in the project |
| crates.io HTTPS API -> DevFlow's decision to publish | a wrong answer here can cause a duplicate publish attempt |
