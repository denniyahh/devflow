  <action>
    Planner/orchestrator decision, 2026-11-18 (not an operator decision): an agent waiting in a `devflow_ask` call can be silent on its stream, and every agent's monitor gives it a 120 s idle window (`idle_timeout_setting_for`). Claude's MCP client emits `tool_progress` heartbeats while a call is held (53-MCP-SPIKE.md:74), but codex's output during a hold is unmeasured, so the monitor must not count the silence while the stage's question is open, and must stop holding once the question outlives its bound (an unbounded hold is the immortal-run failure this project already knows).

    Write the three tests first and see the first one fail (before the change its 3 s silence is recorded as an idle timeout). Add `pub question_wait: Option<Duration>` to `StageSpec` (additive: the struct is `#[non_exhaustive]`; `StageSpec::new` sets None), documented as the longest an open question gate for `stage` may hold the idle window. In `run_stage`, build a probe from `spec.project_root`, `spec.phase`, `spec.stage` and `spec.question_wait`, and pass it to `drive_stream_io`. The probe returns the open question's gate id and age only when `stage` and `question_wait` are both Some, the stage's gate file at `Gates::gate_path` parses as a `GateFile`, its `gate_kind` is `Some(GateKind::Question)`, and its age (now minus its `timestamp`, in seconds) is below the bound; an unparsable file, a gate of another kind, or a missing file holds nothing and the existing behaviour stands. In the idle arm of `drive_stream_io`, consult the probe before the background-task check: while it returns Some, log at info that the idle window is held for question gate <id> (<age>s of <bound>s) and continue, without consuming `idle_extensions`; once the age reaches the bound, warn that the question gate is still open past its bound and fall through to the existing checks, so `on_idle_timeout` fires as before. In `runner_stage_spec` set `spec.question_wait = Some(Duration::from_secs(gate_timeout_secs() + devflow_core::agents::ASK_CLIENT_TIMEOUT_MARGIN_SECS))`, the bound 53-08 Task 1 gives the client timeouts, so the server's typed timeout result reaches the agent before the monitor would act. In OPERATIONS.md add one sentence to the `DEVFLOW_CLAUDE_IDLE_TIMEOUT_SECS` row and the per-agent rows that share its semantics: while the stage's question gate is open its silence does not count toward the idle timeout, for at most the gate timeout plus 60 s from when the question opened. No new env var.
