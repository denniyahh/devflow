# Phase 35.1: Unattended-Launch Prerequisites - Context

**Gathered:** 2026-08-07
**Status:** Ready for planning

<domain>
## Phase Boundary

`devflow start --mode auto` can complete a phase with no human present: ordinary GSD
`gate="blocking"` checkpoints resolve instead of stalling the run, and a preflight refuses the
launch — loudly and before it starts — when the conditions that make that true do not hold.

This phase is about *whether an unattended run can proceed at all*. It is not about how an
unattended agent decides. The first-option `decision` checkpoint behaviour is 999.94 and stays
out of scope.

</domain>

<decisions>
## Implementation Decisions

### Chain-flag lifetime and leak repair

- **D-01:** `_auto_chain_active` is cleared by **two independent mechanisms**: an RAII guard that
  fires on every in-process exit (normal, error, panic-unwind), and a force-clear on every
  `devflow start` / `devflow resume` before launching. A SIGKILL between them is repaired by the
  next run rather than carried forward. The guard alone was rejected: it cannot survive SIGKILL,
  and a leaked `true` is exactly the committed-and-fires-next-phase failure criterion 2 names.
- **D-02:** The regression tests must exercise **both** failure paths as separate cases — one that
  SIGKILLs the process mid-stage and asserts the next start clears the stale flag, one that forces
  an in-stage error and asserts the guard cleared it. Kept separate so a regression in either
  mechanism is attributable instead of masked by the other. A single combined test was rejected
  for that reason.
- **D-03:** A repaired stale flag is **not silent**: emit an event to `.devflow/events.jsonl` and
  print a notice on stdout. A stale flag is evidence a prior run was killed; repairing it quietly
  discards that signal, and this project logs repairs and escape hatches loudly rather than
  applying them quietly.

### Auto-mode stage set

- **D-04:** Checkpoint auto-approval covers **Plan, Code, and the `--gaps-only` fix loop** — not
  Code and the fix loop alone. Rationale: DevFlow's Define stage is a deliberate no-op (D-14), so
  **Plan is the first stage at which an unattended run can stall**. Covering only Code would leave
  the earliest stall unfixed while claiming unattended runs work.
  **Note for the roadmap:** this is broader than criterion 1's literal wording, which names the
  Code stage and the fix loop. The widening is deliberate and operator-approved.
- **D-05:** The stage set is expressed as a **named constant** consulted by the launch path,
  following the existing `STREAM_JSON_STAGES` precedent (`crates/devflow-cli/src/pipeline_launch.rs:541`,
  widened by Phase 34). One greppable place to read and change it. An inline per-stage match was
  rejected — implicit policy in control flow is how the `{phase:02}` glob hazard stayed hidden.
  Config-driven was rejected as speculative configurability that also adds a way to silently
  disable the whole fix.
- **D-06:** This is checkpoint approval **only**. `workflow.auto_advance` is still NOT set
  persistently (criterion 3, upstream G-01) — stage-chaining stays banned and is a separate flag.

### Preflight refusal policy

- **D-07:** The preflight reports three distinct per-condition states — holds / does not hold /
  could not determine — and **refuses on anything that is not a definite pass**. Fail closed.
  This applies the 999.86 lesson from one phase earlier (a predictor that guessed rather than
  probed false-negatived twice) and the roadmap's existing "unreachable ≠ absent" rule.
  Warn-and-proceed was rejected in the criterion's own words: a warning is read by nobody in an
  unattended run.
- **D-08:** The preflight **gates `--mode auto` and reports on `--mode supervise`**. One code
  path, two consequences: refusal only where the prerequisites actually matter, but the
  per-condition report still prints in supervise so an operator can rehearse viability before
  committing to an unattended run. Gating every launch was rejected — it would block supervise
  runs that are fine with a human answering checkpoints.
- **D-09:** **No override.** No `--force-unattended` flag, no environment variable. A refusal is
  final; fix the condition or launch in supervise. — **Reversibility:** costly — adding an
  override later is easy, but removing one after operators build habits around it is not, and
  the standing principle is that DevFlow advances as far as the rules permit and stops at the
  first hard gate rather than routing around one. The `--legacy-claude-launch` precedent for a
  loudly-logged escape hatch was considered and explicitly declined here.

### The simulated unattended run

- **D-10:** Criterion 5's run drives a **throwaway fixture project with one trivial plan carrying
  one real GSD `blocking` checkpoint, launched against a real Claude agent**. Cheapest workload
  that still crosses every seam under test, and repeatable. Driving Phase 35.2 for real was
  rejected — a failed drill damages real planning artifacts and cannot be re-run identically. A
  fully mocked agent was rejected because a mock cannot demonstrate that GSD actually
  auto-approves a real checkpoint, which criterion 1 requires be established by driving one.
- **D-11:** The fixture is **pre-baked through CONTEXT.md**; Plan and Code run live. Criterion 5
  names Plan → Code as the seam, so those stages must be real. Pre-baking the plans was rejected
  because it would skip Plan, which D-04 just established as the first place an unattended run
  can stall. Running from Define was rejected as a Claude launch that exercises nothing new.

### Claude's Discretion

The operator did not choose to discuss these; they are open for the planner unless it finds a
reason to escalate:

- Where criterion 6's per-phase Validate-failure observation gets recorded.
- The concrete condition list the preflight checks, and how the required NOT-viable negative
  control fixture is constructed.
- Whether `--yes-ship` interacts with auto-mode at all.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- **`crates/devflow-cli/src/preflight.rs` (2910 lines) already implements exactly the shape
  criterion 4 asks for.** Stage-scoped checks that return `Result<(), String>` and refuse a
  launch: `preflight_interactivity_check` (:610), `preflight_gh_auth_check` (:643),
  `preflight_major_bump_check` (:733), dispatched by `generic_preflight_checks` (:870), with
  `*_applies(stage)` predicates gating per-stage applicability. **Criterion 4 needs a new check
  inside this framework, not a new mechanism.**
- **`devflow_core::events::emit`** — the append-only event log D-03's notice writes to.
- **`State::preflight_retries`** (`crates/devflow-core/src/state.rs:72`) — an existing persisted
  counter for preflight outcomes; check whether a refusal should touch it before adding anything new.

### Established Patterns

- **Named stage-set constants.** `STREAM_JSON_STAGES` (`pipeline_launch.rs:541`) currently lists
  all five stages; Phase 34 widened it deliberately. D-05 follows this shape.
- **Loudly-logged escape hatches.** `--legacy-claude-launch` logs to stdout, the monitor log, and
  an event. D-09 declines to add another one, but this is the shape if that is ever revisited.
- **Fail-closed preflights.** 999.86 replaced a *predictor* with a real probe after two live
  false negatives. D-07 generalizes that stance.

### Integration Points

- **`.planning/config.json` — DevFlow does not currently touch it at all.** Verified 2026-08-07 by
  grep across `crates/`: there are no reads, no writes, and no `gsd-tools config-set` invocations.
  **The entire chain-flag mechanism is new surface**, including deciding whether DevFlow shells out
  to `gsd-tools query config-set` or edits the JSON directly. This is the single largest unknown
  in the phase and the planner should treat it as such.
- **The file is tracked and `commit_docs` is `true`** (`.planning/config.json:2,6`), and it already
  carries `"_auto_chain_active": false` (:8). Confirmed live: `gsd-tools query check auto-mode`
  currently returns `{active: false, source: "none", auto_chain_active: false, auto_advance: false}`.
  This is precisely why a leaked `true` gets committed and fires on the next phase.
- **The launch path** in `pipeline_launch.rs` is where the stage-set const is consulted and where
  the RAII guard's scope is decided.

</code_context>

<specifics>
## Specific Ideas

- The operator's framing throughout was **fail closed and stay loud**: every one of D-01, D-03,
  D-07, and D-09 chose the option that refuses or reports over the option that proceeds or stays
  quiet. Downstream agents should resolve ambiguity in that direction rather than toward
  convenience.
- **Criterion 4's negative control is not optional.** "A preflight that cannot fail is the defect
  it exists to prevent." The NOT-viable fixture must be demonstrated failing, not assumed.
- Likewise for D-02: the tests must **print a failure** in the failing direction, not merely
  not-pass. A wedged harness and a failed assertion are different observations and only one is
  evidence (the 35-02 lesson).

</specifics>
