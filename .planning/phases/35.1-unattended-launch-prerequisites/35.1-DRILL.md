## What actually happened — post-run forensic analysis

### DevFlow's chain-flag mechanism: working correctly

Evidence confirmed from the Arm A worktree's capture files:

1. **`AutoChainGuard::engage` set the flag.** The working tree showed `modified: .planning/config.json`
   with the diff `"_auto_chain_active": false` → `"_auto_chain_active": true`.
2. **GSD read the flag as `true`.** The Code stage agent ran `gsd_run query config-get
   workflow._auto_chain_active` and received `true`.
3. **The `--auto` token was in the prompt.** The Code stage prompt carried
   `/gsd-execute-phase 1 --auto`, preventing GSD's sync-clear step from wiping the flag.
4. **The config.json was touched during the run and restored after.** Arm A's config mtime
   (20:38:49) is 180s after the gate fired (20:35:49) — exactly the gate timeout, which is when
   `AutoChainGuard::Drop` clears the flag back to `false`. Arm B's config was never touched.

### Why auto-approval didn't happen: GSD orchestrator injects conflicting instructions

The `execute-phase.md` orchestrator (the parent Code stage agent) constructs the executor subagent
prompt. For plans containing `checkpoint:human-verify` + `gate="blocking"`, it dynamically generates
a `<critical_gate>` block:

> *"You MUST NOT auto-approve it … gate=\"blocking\" checkpoints of type checkpoint:human-verify
> require a real human's explicit response and must never be auto-resolved by an agent."*

This contradicts GSD's own gate semantics, where `gate="blocking"` (as opposed to
`gate="blocking-human"`) IS auto-approvable per the gate table, the `checkpoint_handling` step, and
the executor's own `<checkpoint_protocol>`. The executor subagent followed the `<critical_gate>`
instruction over its own protocol, stopped at the checkpoint, and returned a checkpoint report.
The parent orchestrator then followed `<critical_gate>` over its own `checkpoint_handling` step
and surfaced the gate.

The root cause is an LLM behavioral issue in the orchestrator's prompt construction: it conflates
`gate="blocking"` (the default, auto-approvable case) with `gate="blocking-human"` (the exception).
Filed upstream as [open-gsd/gsd-core#3370](https://github.com/open-gsd/gsd-core/issues/3370).

### Practical impact: narrow

GSD's default `human_verify_mode = end-of-phase` (#3309) suppresses `checkpoint:human-verify` tasks
from generated plans entirely. A normal unattended run never encounters this bug because those tasks
don't exist in plans. The drill fixture only hits it because D-1 is a **locked decision** demanding
the checkpoint exist — an edge case by design.
