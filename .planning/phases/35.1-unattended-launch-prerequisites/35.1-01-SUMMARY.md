### 5. `AUTO_CHAIN_ELIGIBLE_STAGES` doc comment, verbatim

```rust
/// The stages whose launch may set GSD's `workflow._auto_chain_active` flag
/// (D-05, `35.1-CONTEXT.md`). One element, deliberately.
///
/// **[`STREAM_JSON_STAGES`] above is the shape precedent and an IMPERFECT
/// analogy.** That constant lists all five stages because its effect is purely
/// a DevFlow-internal transport choice with no upstream consequence: whichever
/// stage it names, the only thing that changes is how DevFlow talks to the
/// child. This flag is not like that. It has *different upstream effects per
/// stage*:
///
/// - At `Stage::Code` it is harmless. `execute-phase.md` reads the flag only to
///   decide whether to auto-approve an ordinary `gate="blocking"` checkpoint;
///   it never chains from it.
/// - At `Stage::Plan` it CHAINS. `plan-phase.md:1564` launches
///   `gsd-execute-phase` when the flag is set, which double-executes the Code
///   stage and misattributes its commits.
///
/// **So "completing" this list toward `Stage::Plan` is a defect, not a
/// finished job.** D-04 spent an adversarial-review round ruling exactly that
/// out, and ROADMAP criterion 3 forbids it. The flag GSD uses for "approve this
/// checkpoint" and the flag it uses for "chain to the next workflow step" are
/// the same boolean upstream; the fix is a gsd-core change splitting them in
/// two — tracked as **G-01** — not a widening of this list. If you arrived here
/// intending to add a stage, that ticket is what you actually want.
///
/// **Why one element and not a `(Stage, FixType)` table (F-6):** the
/// Validate→Code loop-back changes only the prompt text, at the same
/// `state.stage == Stage::Code`. `select_loop_back_fix` returns a `FixType` and
/// never touches `Stage`, and `Stage` has no gaps-only variant — so gaps-only
/// and full-execute are already covered by this single entry, and a keyed table
/// would encode a distinction the source does not have.
const AUTO_CHAIN_ELIGIBLE_STAGES: &[Stage] = &[Stage::Code];
```

It names D-04, D-05, `plan-phase.md`'s chaining behaviour, and G-01 as required.

### 6. F-1 and F-2 as PLANNER decisions, with their alternatives

These are distinct from CONTEXT.md's locked D-01…D-06. They were resolved during planning and are recorded here so a later reader can tell them apart.

**F-1 — the chain flag is engaged only when `state.mode == Mode::Auto`.**
CONTEXT.md's decisions describe *when in the run* (Code stage, gaps-only loop) but never name a DevFlow `--mode`. Implemented as the first half of `auto_chain_flag_eligible`.
- *Alternative considered and rejected:* engage on every mode. Rejected because auto-approving checkpoints on a run the operator explicitly chose to SUPERVISE is a silent behaviour change to an already-shipped mode that nobody asked for. `preflight_interactivity_check` (`preflight.rs:610-623`) is the file's existing precedent for exactly this condition.
- *Reversibility:* `reversible` — one boolean condition in one predicate.

**F-2 — the prompt token is UNCONDITIONAL; only the config write is mode-gated.**
The asymmetry is deliberate. `--auto` in `$ARGUMENTS` cannot by itself enable checkpoint bypass: `check auto-mode` reads `.planning/config.json` and nothing else, and within `execute-phase.md` the token's only effect is to skip the sync-clear block.
- *Alternative considered and rejected:* thread `mode` into `prompt::stage_prompt_for_project` so the token is mode-gated too. Rejected because that is a signature change to a `pub` function of the published `devflow-core` crate — the exact class of break Phase 35 had to enumerate in a changelog — bought to obtain a property the config gate already provides.
- *What it gives up, and how it is paid for:* GSD's sync-clear is a safety net that wipes a stale `true` left by a previously-interrupted run; sending the token on every Code launch disables it. It is replaced by DevFlow's own force-clear (plan `35.1-02`, D-01), which is strictly stronger, AND closed inside this plan by the guard's symmetry: a leaked `true` that survives to a supervise Code launch is overwritten by DevFlow before the agent starts.

## Decisions Made

Beyond F-1/F-2 above, three decisions were made inside the executor's own remit:

- **`GsdConfigError` carries a third variant, `Missing(PathBuf)`.** The plan named `Io` and `Json`. A bare `Io(NotFound)` would not say which path was absent, and `WorkflowError::MissingState` is the house precedent. Callers that need to distinguish "no GSD config in this project" from "unreadable" now can.
- **A non-object JSON root is an `Err`, not a wholesale replacement.** `[1,2,3]` parses fine but has nowhere for the key to live; overwriting the operator's file was the only alternative. Covered by `a_non_object_config_root_is_an_error_not_a_replacement`.
- **The temp file is `config.json.devflow-tmp`, not `config.tmp`.** `Path::with_extension("tmp")` would produce `config.tmp`, which reads like a config file of its own. The new name is unmistakably DevFlow's and is asserted to be cleaned up by `the_atomic_write_leaves_no_temp_file_behind`.
