Close verification gap B (criterion 2). The operator ruled it a gap on 2026-09-22 (Gap B). Today `start` takes
the per-phase lock, clears every gate file for the phase, overwrites `state-NN.json` and launches, without
checking for a live run. The lock is not held while an agent works. So a second `devflow start` for a running
phase silently wipes that run's gates, overwrites its state and launches a second agent.

Add a refusal guard to `start`, test first. Under the lock, and before any gate cleanup or state write, `start`
refuses if the phase has state whose run is live. It writes nothing and names `devflow stop --phase N` and
`devflow recover --clean --phase N`. The control: a dead or leftover state is still replaced exactly as today.

## Known limits (recorded, not fixed here)

- **999.136, operator-deferred.** The window between agent exit and the monitor's `advance` taking lock-NN stays
  lock-free. This plan does not make the lock span it. This is reasoned, not tested: the Legacy monitor stays alive
  across that window, so a recorded, live `monitor_pid` should make `start` refuse there too. Other writers in that
  window, such as the recover sweep, remain 999.136's scope.
- **Pid liveness, not identity. The operator accepted this with Option A on 2026-09-22.** A recycled pid makes a
  dead run look live, which gives a fail-closed false refusal. The refusal tells the operator to check each pid with
  `ps -p <pid>` before signalling it, so an unrelated process is not killed. Once `ps -p` shows a named pid is not
  this phase's DevFlow process, `devflow recover --clean --phase N` removes the state and the next `start` proceeds.
  This is the same class as D-03's "Lock reclaim tests pid liveness only" and the deferred "Lock reclaim by pid
  plus start time" (Phase 50).
- **No-state carve-out: an operator-approved narrowing (explicit operator ruling, 2026-09-22).** The guard applies
  only when the phase has a state file. `start` does not refuse when the phase has no state file, even if the agent
  pid file names a live process.
  - Reason: `recover --clean` removes the state but not the agent pid file, and no DevFlow verb removes that file.
    Without the carve-out, a leftover pid file whose pid is later reused by an unrelated long-lived process would
    block `start` with no DevFlow repair.
  - Cost: if `recover --clean` has already cleared state while the agent was still alive, `start` launches a second
    agent beside it. Two things guard against that. recover's own "cleared anyway" warning, and the refusal
    message, which allows `recover --clean` only after the named processes have exited.
  - Test `start_proceeds_when_no_state_exists_even_if_the_agent_pid_file_names_a_live_process` pins the carve-out.
- **Pre-existing: `stop` does not end a lock-free run. Found while wording the refusal; not fixed here.** In the
  window the guard targets, `devflow stop --phase N` marks the state stopped and signals nothing, and
  `advance_for_stage` never reads that mark (see the context facts). So the run continues through its next stage.
  The refusal message says so instead of offering `stop` as the way to end the run. This is filed as backlog
  999.138 in ROADMAP.md.
- A state file that exists but cannot be loaded (corrupt or legacy) is checked on the agent pid file only, since no
  monitor pid can be read. The tests do not exercise this branch.
