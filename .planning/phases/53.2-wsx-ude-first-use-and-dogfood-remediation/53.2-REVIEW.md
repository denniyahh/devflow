## Warnings

### WR-01: OPERATIONS.md contradicts the code on `stop` and the phase holder

**File:** `OPERATIONS.md:865` (also `:48`, `:49`, `:256-262`)

**Issue:** The `.holder-NN` row changed in this diff says "`stop` refuses while it is held and no runner is live". The code refuses whether or not a runner is live:

- With no live runner, `stop_report` refuses on `live_holder` (`commands.rs:4441-4449`).
- With a live runner, it refuses when `claim_phase_holder` returns `Held` (`commands.rs:4460-4469`).

Line 48 already says "live runner or not", so the two rows contradict each other.

D-12 also creates two cases the docs do not describe:

1. **A second `devflow stop` during the first one's wait.** It is refused, naming the first stop's pid and saying "run devflow stop --phase N again once it returns". Line 48 lists only `start`, `resume`, `discard` or `cleanup` as verbs that can hold the phase, and the doc comment on `stop_report` (`commands.rs:4414-4417`) does the same.
2. **`devflow cleanup` during a stop.**
   - What the code does: cleanup claims the holder, gets `Held`, and keeps the phase with "another DevFlow verb holds phase N (pid P) and is in progress; run this again once it returns" (`commands.rs:1749-1752`). It goes on to the next phase and exits non-zero.
   - What the docs say: the cleanup row (`:49`) and the Run liveness bullet (`:256-262`) describe only a held runner lock or an unreadable answer, and both name `devflow stop --phase N`. A stop's wait now holds the phase for 10 s or more, so this case is no longer a narrow race.

**Fix:**
- **Line 865:** replace "`stop` refuses while it is held and no runner is live" with "`stop` refuses while another verb holds it, live runner or not".
- **Line 48:** change the verb list to "(`start`, `resume`, `discard`, `cleanup`, or another `stop`)".
- **Cleanup row and the Run liveness cleanup bullet:** add "a phase another DevFlow verb holds (including a `devflow stop` still waiting for its unit) is kept, naming that verb's pid; run cleanup again once it returns".

### WR-02: The straggler's `trap` is synchronised by a fixed 500 ms sleep, now shared by two tests

**File:** `crates/devflow-cli/tests/service_e2e.rs:1091-1092`, `:1112`

**Issue:** `start_a_run_with_a_straggler` waits for the agent's argv log and then sleeps 500 ms. That sleep is the only thing ensuring the `setsid sh -c 'trap "" TERM; ...'` child has installed its trap before the test sends SIGTERM.

If the host is loaded (nextest runs the service suite in parallel), the SIGTERM can arrive before the trap is set. The straggler then dies and the unit goes straight to inactive. Both tests then sit in `wait_until(... == "deactivating")` for the full 60 s (`UNIT_FINISH_WAIT`) and fail with "the unit never read deactivating". That points at the unit, not at the setup race.

The sleep existed before this diff. Extracting it into a shared helper doubles the number of tests that depend on it.

**Fix:** Have the straggler signal readiness once its trap is set, and wait on that file instead of sleeping:

```rust
// STRAGGLER_TAIL becomes a format! over a ready path the fixture owns:
"setsid sh -c 'trap \"\" TERM; : > \"{ready}\"; exec sleep 60' </dev/null >/dev/null 2>&1 &\nsleep 120"
// start_a_run_with_a_straggler:
wait_until(|| ready.is_file(), &guard.unit, "the straggler never set its TERM trap");
```

## Info

### IN-01: Spawned `devflow` children are not killed when a test fails

**File:** `crates/devflow-cli/tests/service_e2e.rs:1118-1129`, `:1145-1197`, `:1241-1275`

**Issue:** `std::process::Child` neither kills nor reaps on drop. The children can be left running in these cases:

- **Test 1:** any assertion between spawning `stop` (`:1145`) and `wait_for_child` (`:1197`) panics with `devflow stop` still running. `UnitGuard` and the `TempDir`s then tear the project down underneath it.
- **Test 2:** the same applies to `discard` inside the loop at `:1250-1269`.
- **`wait_for_child`:** it panics on timeout without killing the child, so a hung `devflow` outlives the test.

This only happens on a failing run. It goes against the project's rule to clean up every PID a test starts.

**Fix:** In `wait_for_child`, call `let _ = child.kill(); let _ = child.wait();` before the timeout assertion. Also hold each spawned child in a small guard that kills and reaps it on drop.
