## Summary

I reviewed the changes in `9435f8c..HEAD` to the four files in scope. I also checked them against the code they call or replace: `service::notify_ready`, `run_runner`'s lock-then-READY order, `commit`/`update_state`, `resume_loaded`, `until_cap_fired`, `agent_running`, `HermeticHome::new`, and every test target's `mod common;`.

Nothing blocking was found. One warning stands: two older fake-launcher tests now pass for a reason other than the one they name.

The rest of the changes held up when traced:

- **Notify listener (#337).** All 28 test targets declare `mod common;` at the crate root, so `--exact common::fake_notify_listener_entry` resolves in every binary that writes the fake.
  - The socket path stays under `/tmp/dfh*/service-bin/`, well inside `sun_path`.
  - `.launched` is read only once its trailing newline has been written.
  - A `READY=1` sent just before the process exits is drained before the listener reports `exited`.
  - `agent_running` treats a zombie as gone.
  - The listener's stdio goes to `.log` and `/dev/null`, so it does not hold the caller's output pipe.
  - `run_runner` takes the runner lock before `notify_ready` (`pipeline_launch.rs:1247-1261`), so for the real runner, `READY=1` still implies the lock is held.
- **The new fast-runner test.** It is a real regression proof: a fake that went back to polling the lock would see the runner exit and print `FAKE_START_FAILED`.
- **WR-01 of the prior round (resume `--reviews` snapshot).** It is closed.
  - Nothing writes the state between `resume_loaded`'s last commit and the failed-launch commit: the preflight checks, `archive_prior_capture` and `launch_runner_unit` only emit events or run tools.
  - A runner that ran and stopped is caught first by `if s.stopped`.
  - A runner that ran, wrote the state and died leaves a state that differs from the snapshot, so it is kept with `reviews_pass` set. A plain `resume` does not clear `reviews_pass`, and `until_cap_fired` is false on the `resume launch failed` reason, so a plain resume reruns the reviews Plan, as the comment says.
  - The new test and the existing retry test cover the changed-state and unchanged-state directions.
- **WR-02 of the prior round (`--no-index`, untrack advice).** It is closed. The new test covers a tracked file that is also ignored, and the existing test asserts there is no untrack advice when nothing is tracked.

## Warnings

### WR-01: The two D-14 (#296) fake-launcher tests no longer test what they name

**File:** `crates/devflow-cli/tests/run_liveness_e2e.rs:1284-1333` (and `assert_no_proc_read_error`, `:1274-1282`)

**Issue:** Plan 18 removed the fake `systemd-run`'s lock reading: the `held()` loop over `/proc/PID/fd` and `fdinfo`. The fake now reports a launch as started only when it receives `READY=1` (`common/mod.rs:181-212`).

The two tests still claim to cover the old reading:

- `the_fake_launcher_does_not_take_an_unheld_runner_record_as_ready` writes an unheld `.runner-07` record.
- `the_fake_launcher_does_not_take_another_phases_held_runner_lock_as_ready` holds `.runner-01`.

Neither child sends `READY=1`. Both now fail the launch only because the child exits without notifying. The fake would print `FAKE_START_FAILED` with any `.runner-*` contents, or with none, so neither test can fail for the reason in its name or doc comment.

`assert_no_proc_read_error` guards against errors from `/proc` descriptor reads the fake no longer makes. The two tests also now check the same case, a child that exits without `READY=1`, and each spends `LAUNCHED_CHILD_LIFETIME` (2 s) doing it.

The project rule (a control must fail for the right reason) is what makes this a defect and not a style point: a reader would take these tests as proof that lock-based readiness is still enforced.

**Fix:** Replace both tests with one test whose name matches what it now checks, keeping it as the negative control for the fast-runner test:

```rust
/// #337: a launched command that exits without sending `READY=1` is a failed start,
/// as systemd reads a `Type=notify` unit whose main process exits before READY.
#[test]
fn the_fake_launcher_reads_a_command_that_exited_without_ready_as_failed() {
    let home = common::HermeticHome::new();
    let project = project_with_devflow_dir();
    let out = run_fake_launcher(&home, project.path(), "exit 0", &[]);
    let stderr = String::from_utf8_lossy(&out.stderr);
    assert!(
        !out.status.success() && stderr.contains(common::FAKE_START_FAILED),
        "the fake launcher read a command that never sent READY=1 as started: status {}, stderr {stderr}",
        out.status
    );
}
```

Then delete `other_phase_runner_lock_holder_entry`, its two env constants and `assert_no_proc_read_error`. If lock-before-READY should stay pinned now that the fake no longer enforces it, pin it on `run_runner` directly, not through the fake.

## Info

### IN-01: The failed-launch snapshot is re-read from disk, and a failed read gives a false "state changed" error

**File:** `crates/devflow-cli/src/pipeline_launch.rs:2228-2230`, `:2313-2327`
**Category:** necessity

**Issue:** `resume_loaded` ends with `commit(&mut state, ..)`, and `commit` sets `*state = committed` (`:992-998`). Nothing touches `state` after that, so the returned copy is already the committed state. The second `workflow::load_state` gives nothing that `serde_json::to_value(&state)` would not.

It does add a failure mode. If that read fails, `written` is `None`, `untouched` is false, and `kept` becomes true. A failed launch of either kind then reports "its run state changed after resume wrote it, so it was kept", which is false. A `resume --reviews` launch also stops restoring the `--until plan` halt. The outcome is fail-safe (state kept, reviews pass kept), but the message misstates what happened.

**Fix:** `let written = serde_json::to_value(&state).ok();`. The in-memory copy is the committed state, so no extra I/O is needed and there is no `None` case short of a serialisation failure.

### IN-02: `ls-files` probe errors are listed under the "not ignored, add these lines" header (extends prior IN-02)

**File:** `crates/devflow-cli/src/commands.rs:529-536`, `:543-555`

**Issue:** A `git ls-files --error-unmatch` failure other than exit 1 is pushed into `unchecked`. `unchecked` prints under "GSD writes derived files that git does not ignore here; add these lines to .gitignore:". In a repository whose `.gitignore` covers every path, a broken index then produces a warning claiming the files are not ignored, followed only by "could not check whether git tracks ...". The prior round's IN-02 noted the same header problem for `check-ignore` errors; this change routes a second kind of error into it.

**Fix:** Give probe errors their own block, for example `warning: could not check GSD derived files here:`, and print the "add these lines" header only when `to_add` is non-empty.

### IN-03: The listener's variable names and libtest name are hard-coded in the fake, apart from their constants

**File:** `crates/devflow-cli/tests/common/mod.rs:181`, `:248`, `:253`

**Issue:** The script spells out `FAKE_NOTIFY_SOCKET=`, `FAKE_NOTIFY_FILES=` and `common::fake_notify_listener_entry` as literals, while `FAKE_NOTIFY_SOCKET_ENV` and `FAKE_NOTIFY_FILES_ENV` name the same strings in Rust. A rename on one side is caught, but only at run time and in every e2e launch at once: the listener does nothing and the fake prints "the notify listener did not start".

**Fix:** Substitute them the way `@TESTEXE@` is substituted, for example `@NOTIFY_SOCKET_ENV@` and `@NOTIFY_FILES_ENV@` filled from the constants in `fake_systemd_run_calls`, so the two sides cannot drift.
