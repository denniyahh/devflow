## Summary

I reviewed the changes from `9801a39..HEAD`, focusing on the priority areas. Nothing blocking was found. Two warnings stand:

- A failed or timed-out `resume --reviews` launch can make a reviews Plan that crashed partway look like a finished `--until plan` halt.
- The #285 ignore warning gives a false result for GSD files that are tracked.

The other priority areas held up when traced against the source:

- **Stop holder (#297).** The holder is claimed after the liveness read and kept until the reload. `?` drops it on every early return. The runner never takes the phase holder: the only claimers are start, resume, discard and cleanup (`claim_foreground_holder` callers).
- **Reviews flag lifecycle.** The flag is set by `start` and by `resume --reviews`, read by `default_stage_prompt`, and cleared both in `enter_stage` and in the `--until` halt in `transition`.
- **Halt target (#281).** The halt records the target and `enter_stage` clears it. Old states fall back to `Stage::next`.
- **`localtime_r` call.** It is sound on Linux x86_64.
- **Discuss-before-plan prompt branches.** They match on both renderers.

The pure-logic settle-read tests in `service_e2e.rs` are `#[ignore]`d. CI still runs them through `scripts/check.sh service` (ci.yml:285), so this is not a coverage gap.

## Warnings

### WR-01: A failed `resume --reviews` launch can fake a completed Plan halt over a reviews pass that crashed

**File:** `crates/devflow-cli/src/pipeline_launch.rs:2288-2298` (reached from the `TimedOutLaunch::NotLive` arm at `:2259-2261`)

**Issue:** `re_mark_stopped_after_failed_launch` uses `s.stopped` as its only test of whether the runner ran.

- **Runner recorded a stop:** the stop is kept. This is correct.
- **Runner ran but recorded no stop:** this is the #258 case where systemd-run timed out, the unit was accepted, the runner launched the reviews Plan and then died before recording anything. The reviews branch then writes `stop_reason = until_halt_reason(Plan)` and `reviews_pass = false`.

The state now satisfies `until_cap_fired`: `stop_until == Plan`, `stage == Plan` and the reason matches. A later plain `devflow resume` therefore advances past Plan, through `resume_advance` and the stale `until_halt_target` from the original halt, into Code. By then the replan may be half-written and the reviews pass is lost.

`start`'s twin of this path (`not_live_after_timed_out_launch`, commands.rs:552-570) guards against the same race by comparing the on-disk state with the state it wrote. `resume` has no such check.

**Fix:** Snapshot the state after `resume_loaded`'s final commit, the same way `start` keeps `written`. Restore the halt only when the on-disk state still equals that snapshot. Otherwise keep the state, leave `reviews_pass` set so a plain resume reruns the reviews Plan, and name `status`/`discard`:
```rust
let written = serde_json::to_value(&state).ok();
// ... in re_mark_stopped_after_failed_launch(state, phase, why, reviews, written):
let _ = commit(state, |s| {
    if s.stopped { return; }
    s.stopped = true;
    let untouched = written.as_ref() == serde_json::to_value(&*s).ok().as_ref();
    if reviews && untouched {
        s.stop_reason = Some(until_halt_reason(Stage::Plan));
        s.reviews_pass = false;
    } else {
        s.stop_reason = Some(format!("resume launch failed: {err}"));
    }
});
```
Add a test that runs `service::double::run_during_launch` to change the state (for example, set `session_id`) under `LaunchEnd::TimedOutLeaving(inactive)`. It should assert that `until_cap_fired` is false and `reviews_pass` is still true.

### WR-02: The #285 ignore warning is wrong for GSD derived files that are tracked

**File:** `crates/devflow-cli/src/commands.rs:505-515`

**Issue:** `git check-ignore -q <path>` does not apply exclude rules to tracked files and exits 1 for them. I checked this in a scratch repo: a tracked `.planning/state.json` that `.gitignore` also lists gives exit 1, and the `--no-index` control gives exit 0.

A project that committed `.planning/state.json` therefore gets the warning "add these lines to .gitignore" on every `start` and `--dry-run`. The warning keeps firing after the line is added, and it never names the real fix, which is to untrack the file.

**Fix:** Probe with `--no-index` to decide whether a line is missing. Separately run `git ls-files --error-unmatch -- <probe>` and, when the file is tracked, print `untrack it: git rm --cached <probe>` instead of the `.gitignore` line:
```rust
.args(["check-ignore", "-q", "--no-index", probe])
```

## Info

### IN-01: The `start --reviews` file check is looser than its refusal text and than `resume`'s check

**File:** `crates/devflow-cli/src/commands.rs:883` (via `phase_artifact_on_base`, `:87-90`)

**Issue:** `phase_artifact_on_base(.., "-REVIEWS.md", ..)` accepts any path under `.planning/phases/{padded}-*/`, at any depth, that ends in `-REVIEWS.md`. For example, `53.2-x/archive/53.1-REVIEWS.md` passes. It also fails open when `git ls-tree` errors (`:83-86`).

The refusal text names `{padded}-*/{padded}-REVIEWS.md`, and `resume`'s `require_reviews_file_in_checkout` (pipeline_launch.rs:2743-2755) checks that exact name. So the two verbs disagree about the same file.

**Fix:** For REVIEWS.md, match `rest` as `<dir>/{padded}-REVIEWS.md` with no further `/`, and refuse rather than fail open on a `ls-tree` error.

### IN-02: The #285 warning prints before later refusals, contradicting its comment; its header misleads when only probe errors are listed

**File:** `crates/devflow-cli/src/commands.rs:400-404`, `:519-528`

**Issue:** The comment says the warning comes "after every refusal above so a refused start prints none". However, the user-manager, guard, base-currency, reachability, CONTEXT.md and REVIEWS.md refusals all come later, so a refused start still prints it.

Separately, when only probe errors occur (`to_add` is empty), the header still says "git does not ignore here; add these lines to .gitignore:" and lists no lines.

**Fix:** Reword the comment to "after the fallback refusals". Use a separate header for the could-not-check lines.

### IN-03: The #285 probe reads the primary checkout, not the run's tree

**File:** `crates/devflow-cli/src/commands.rs:493-507`

**Issue:** With a worktree, GSD writes into a tree forked from `base`, and that tree's `.gitignore` is the base's. The probe runs against `project_root`'s checked-out branch, which can differ from the base.

**Fix:** Run the probe after the base resolves, against `git check-ignore --no-index` with `base`'s `.gitignore`, or state in the warning which tree it read.

### IN-04: The `localtime_r` offset compiles only where `c_long` is 64-bit

**File:** `crates/devflow-cli/src/commands.rs:3025-3036`

**Issue:** `tm.tm_gmtoff` is a `c_long`, and the function returns `Option<i64>`. On a 32-bit Linux target this is a type error. `secs as libc::time_t` would also truncate silently there.

**Fix:** Use `i64::from(tm.tm_gmtoff)` and `libc::time_t::try_from(secs).ok()?`.

### IN-05: An unresolvable project base now hides the names of open branches

**File:** `crates/devflow-cli/src/commands.rs:5023-5028`

**Issue:** When `flow.develop` is not a local branch, every branch that no run owns is collapsed into one "could not be compared" line, and the branch names are no longer listed. The old output still listed them.

**Fix:** List the names with no counts, for example `  feature/phase-07 (not compared: develop is not a local branch)`.

### IN-06: `stop`'s holder pre-read repeats the claim's refusal when the run is still stopping

**File:** `crates/devflow-cli/src/commands.rs:4401-4418`
**Category:** necessity

**Issue:** For `RunnerLiveness::Stopping`, the pre-read refuses a held holder. The claim at `:4427-4437` then refuses the same held holder with the same `stop_refused_while_held` text. Only the `NotLive` arm needs the pre-read, because it returns without claiming. This is a judgment call: the pre-read still gives a different message when the holder file cannot be read.

**Fix:** Do the pre-read only for `NotLive`, and let the claim decide for `Stopping`.
