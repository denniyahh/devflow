Two design facts dominate planning. Step 6's "Add more / View / Replan" question is reachable through DevFlow only on the `--gaps` route (no short-circuit) and is not reached on `--reviews` (plan-phase.md:600 exempts `--reviews`).

**Primary recommendation:** Plan 01 = the prompt branch for #246 plus its live proof as a `checkpoint:human-verify`; land the #296/#276 harness plan before any e2e test that relies on the fakes; resolve the `StageIntent` semver question before planning #250's Rust shape.

### Pattern 1: Plan prompt filesystem probes (#246)

**What:** The existing Plan prompt asks the agent to `ls` for the deliverable before running GSD (prompt.rs:442-465, `idempotent_stage_prompt`; workflow-style twin `workflow_plan_prompt` :607-624). Add a second probe in the "does NOT exist" arm:

```text
- If it does NOT exist, check whether the phase has a discussion context:
      ls .planning/phases/{padded}-*/{padded}-*CONTEXT.md 2>/dev/null
  - If no CONTEXT.md exists: run /gsd-discuss-phase {N} (interactive; no --auto, --chain or --power).
    Every question it asks goes through devflow_ask with kind `discuss`, including a free-text
    "Other" follow-up; never wait for a next user message. When it has written CONTEXT.md, run
        /gsd-plan-phase {N}
  - If CONTEXT.md exists: run
        /gsd-plan-phase {N}
```

**When:** both renderers (claude style and workflow style), so codex/pi get the same branch. `PlanGaps` and the reviews route keep no discuss branch (plans exist there).
**Why prompt-only:** `StageIntent::Plan` is unchanged, so no semver impact. [VERIFIED: prompt.rs:442-465 read this session; quote: `ls .planning/phases/{padded}-*/{padded}-*{artifact} 2>/dev/null` with `let artifact = "PLAN.md";`]

### Pattern 2: Persisted pass flag selects the Plan intent (#250)

**What:** `default_stage_prompt` (pipeline_launch.rs:64-93) picks `PlanGaps` from a persisted `State` flag: `Stage::Plan if state.gap_closure_pass => prompt::StageIntent::PlanGaps { phase: state.phase, relaunch_note: state.relaunch_note.clone() }` [VERIFIED: pipeline_launch.rs:68-71]. Mirror it: `devflow start --reviews` sets a new `State` bool (additive, `State` is `#[non_exhaustive]` [VERIFIED: state.rs:33-34 `#[derive(Debug, Clone, Serialize, Deserialize)]` / `#[non_exhaustive]`]); the arm renders a reviews Plan intent with **no PLAN.md short-circuit** (like `gaps_plan_prompt`, prompt.rs:471-477). Because the flag is persisted and the prompt is re-rendered from state at every launch, resume keeps the route with no resume flag, which answers D-04's "if resume re-renders Plan" (it does: `default_stage_prompt` is "The only place a default stage prompt is rendered", pipeline_launch.rs:60-63). Clear the flag when the run leaves Plan (in `transition`'s commit), so a later gap-closure Plan is not a reviews pass.

**Refusal:** `start --reviews` checks `.planning/phases/{padded}-*/{padded}-REVIEWS.md` exists, else refuses naming the expected path. GSD's convention is `NN-REVIEWS.md` [VERIFIED: `.planning/phases/53.1-phase-53-remediation/53.1-REVIEWS.md` exists]. Dry run: `print_dry_run` (pipeline_gate.rs:1044-1110) builds the Plan line from `s.gsd_command()`; append ` --reviews` on the Plan line when the flag is set.

**Semver:** the intent itself is the problem. `pub enum StageIntent` (prompt.rs:161-196) carries no `#[non_exhaustive]` (rg finds the attribute only at prompt.rs:345, on `FixType`). Adding `PlanReviews { phase, relaunch_note }` or a field on `Plan` is a major change by semver-checks' rules [ASSUMED: lint `enum_variant_added` / struct-variant field added is major for an exhaustive enum; the planner's semver gate proves or refutes it]. See Open Question 1.

### Pattern 3: Run-recorded base for git comparisons (#248)

`discard_base` already does it: "the base the run recorded when its state loads and records one, else the project's" — `let recorded = match existing { workflow::Existing::Loaded(state) => state.base_branch.clone(), ... }; let base = recorded.unwrap_or_else(|| flow.develop.clone()); let git = GitFlow::with_config(project_root, config::GitFlowConfig { develop: base.clone(), ..flow });` [VERIFIED: commands.rs:2181-2196]. `print_open_branches` (commands.rs:4719-4741) instead uses `config::git_flow_for_project(project_root).develop` for every branch. `list_feature_branches` computes `ahead`/`behind` against `self.config.develop` and skips a branch equal to it [VERIFIED: git.rs:412-445].

**Recommended shape (no core API change):** `status` already has `rows: Vec<(PhaseId, workflow::Existing, RunStatus)>` (commands.rs:3047). Map each loaded row's expected branch name (`format!("{}phase-{}", feature_prefix, phase.padded())`, the `feature_start` format [VERIFIED: git.rs:163]) to its `base_branch`. Call `GitFlow::with_config(.., develop: base).list_feature_branches()` once per distinct base and take each run's branch from the list for its base; branches with no run use the config list. Print the base on every line (D-07: "Status names the base it compared against"), e.g. `feature/phase-07 — 0 ahead of workspace/denniyahh (run base)`. Make the selection a pure function over `(rows, lists)` so a unit test needs no git.

### Pattern 4: Question-gate banner (#247)

`banner_answer_lines` (commands.rs:3233-3256) prints approve/reject on `Ok(WaiterStatus::Live)` with no kind check. `Gates::read_question(project_root, phase, stage) -> Result<Option<QuestionSpec>, GateError>` [VERIFIED: gates.rs:813-822] returns the question; `QuestionSpec.options: Vec<QuestionOption>` with `pub id: String` [VERIFIED: question.rs:72-80, :102-103]. In the `Live` arm: `Ok(Some(q))` → `  answer:  devflow gate answer {phase} --gate-id {gate.gate_id} (--option <{ids joined by |}> | --text <answer>)`; `Ok(None)` → approve/reject as today; `Err` → the existing "could not be read" style line, no answer offered (consistent with D-09a's fail-closed rule in the doc comment at :3201-3205). The status-row "answer:" line uses `open_question_gate_id` (commands.rs:3163); reuse its read, do not add a second parser.

### Pattern 5: `--until` halt target (#281)

Halt commit (pipeline_gate.rs:93-110) sets `stopped`, `stop_reason = until_halt_reason(from)`, clears `gate_pending`, `code_fix*`, `relaunch_note`; `to` is in scope (`transition(project_root, state, to: Stage)`) but not recorded [VERIFIED: pipeline_gate.rs:71-110]. `resume_advance` (pipeline_launch.rs:2627-2632): `if !crate::pipeline_gate::until_cap_fired(state) { return None; } state.stage.next().map(|to| (state.stage, to))` [VERIFIED]. The only non-`next()` transition the cap can halt is `Step::ValidateAgain` at a non-Validate stage → `transition(project_root, state, Stage::Validate)` [VERIFIED: pipeline_outcomes.rs:2059-2066]; Validate itself never halts (`from != Stage::Validate`, pipeline_gate.rs:93).

**Shape:** new `#[serde(default)] pub until_halt_target: Option<Stage>` (name is discretion), written `Some(to)` in the halt commit; `resume_advance` returns `(state.stage, state.until_halt_target.or_else(|| state.stage.next())?)`; the resume commit (pipeline_launch.rs:2601-2606, which clears `stop_until` when `until_cap_fired`) also clears the new field. `resume_advance` must read the field **before** that commit clears it — check the call order in `resume_loaded` (:2509).

### Pattern 6: Holder across stop (#297)

`stop_report` (commands.rs:4185-4226) probes `liveness::live_holder` only when the runner is not Live, then `stop_unit` and `stop_outcome(phase, workflow::load_state(..))` with no hold. `discard` claims `let _holder = claim_foreground_holder(project_root, phase)?;` first (commands.rs:1891). Holder claimants today: start (commands.rs:407), resume (pipeline_launch.rs:2179), cleanup (commands.rs:1588), discard (:1891) [VERIFIED by rg this session]. `claim_foreground_holder` also runs `update_state_with_within(.., |_| Ok(..))` (commands.rs:4306-4311), which discard already calls on a phase with missing state, so it tolerates `MissingState`.

### Anti-Patterns to Avoid
- **Detecting REVIEWS.md to choose `--reviews`:** rejected by D-04 (deferred).
- **A `Stage::Discuss` variant:** deferred; also semver-major (`Stage` is exhaustive, stage.rs:13-23).
- **A probe that takes the lock it checks** (fake `systemd-run` using `flock`): it reproduces the #277 race inside the harness.
- **Fixing a flake by lengthening a sleep:** D-15/D-16 require condition waits and counted reproductions.
- **Process-hunting teardown for #178:** the issue warns that Validate runs `cargo test` inside a DevFlow run; a broad reaper can kill the observing run.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Writing an exec'd stub in a test | `fs::write` + `set_permissions(0o755)` | `devflow_core::test_support::write_executable` | Writes through a short-lived shell, so no test-process write fd exists for a sibling fork to inherit (ETXTBSY) |
| Polling a condition | `for _ in 0..N { sleep }` | `test_support::wait_until(timeout, what, pred)` | Panics naming what it waited for and the budget |
| Re-reading a run's base | new resolver | `discard_base` shape (commands.rs:2181) | One rule for "recorded base else config" |
| Local time zone math | manual offset tables | `libc::localtime_r` → `tm_gmtoff` | Reads `/etc/localtime`/`TZ` like every libc client |
| Question gate reading | parse the gate JSON | `Gates::read_question` | Shared wire format (53-01 flatten wrappers) |
| Child-process test isolation | `std::env::set_var` | `in_child_test` + env on the child `Command` | Repo rule: no process-global env mutation |

## Common Pitfalls

### Pitfall 1: discuss-phase ends the one-shot turn on free text
**What goes wrong:** GSD discuss-phase says, for "Other" with empty text, "output `\"What would you like to discuss?\"`, STOP generating, wait for the user's next message" [VERIFIED: ~/.claude/gsd-core/workflows/discuss-phase.md:104]. Under DevFlow's one-shot launch there is no next message: the turn ends and the stage finishes with no CONTEXT.md.
**How to avoid:** the prompt branch says every question, including free-text follow-ups, goes through `devflow_ask` (free text is answerable: `gate answer --text`, main.rs:348), and never ends the turn to wait. Do not use `--text` mode: it also says "Wait for the user's reply at the normal prompt" (modes/text.md).
**Warning signs:** a Plan stage that succeeds with no `*-CONTEXT.md` and no PLAN.md.

### Pitfall 2: discuss-phase auto-chains into plan-phase
**What goes wrong:** with `workflow.auto_advance` or `--chain`, discuss-phase itself starts plan-phase; the prompt then runs plan-phase a second time.
**How to avoid:** instruct "no `--auto`, `--chain`, `--power`"; after discuss, re-run the PLAN.md probe and only run `/gsd-plan-phase N` if no plan exists. [ASSUMED: other projects may set `auto_advance: true`; this repo has `"auto_advance": false` in .planning/config.json]

### Pitfall 3: the live proof (D-03) costs a real agent run and needs an answerer
**What goes wrong:** D-03 needs a real `claude` Plan launch on a scratch GSD project and someone answering discuss gates with `devflow gate answer`. A Code-stage executor cannot both be the run's agent and the operator answering it.
**How to avoid:** make it a `checkpoint:human-verify` task run from the orchestrating session after Code, with a minimal scratch project (one-phase ROADMAP, no CONTEXT.md, GSD derived files ignored), `--until plan`, and a script of the answers. Negative control: same project with a CONTEXT.md committed → zero `discuss` gates in `.devflow/events.jsonl`. Reinstall the binary first (dogfood rule). Open Question 2.

### Pitfall 4: the reviews pass hits the PLAN.md short-circuit
**What goes wrong:** rendering `--reviews` through `idempotent_stage_prompt` returns success immediately because plans exist.
**How to avoid:** a dedicated prompt with no probe, like `gaps_plan_prompt` (prompt.rs:466-477). Test: a reviews prompt does not contain `First check whether this stage's deliverable already exists`.

### Pitfall 5: `git check-ignore` reports a tracked file as not ignored, and a missing dir as not matching
**Verified this session (scratch repo, `.gitignore` = `.gsd/` + `.planning/state.json`):** `.gsd -> 1`, `.gsd/x/sentinel.json -> 0`, `.planning/state.json -> 0`, `.planning/milestone.lock -> 1` (control: not listed), tracked `state.json -> 1`, tracked with `--no-index -> 0`.
**How to avoid:** probe `.planning/state.json`, `.planning/milestone.lock` and a child path under `.gsd/` (e.g. `.gsd/dispatch-isolation-sentinel.json`), without `--no-index` (a tracked derived file is exactly the defect). Exit 0 = ignored, 1 = warn, 128 = git error (print it, do not treat as "not ignored"). Run in the project root, with `GIT_*` scrubbed in tests. GSD derived paths this repo ignores, with its reasons: `.gsd/`, `.planning/milestone.lock`, `.planning/state.json` [VERIFIED: .gitignore:33-45, quote: "`.planning/milestone.lock` holds `{phase, session, pid, updated_at}` ... `.planning/state.json` is a best-effort derived projection republished at every step boundary"].

### Pitfall 6: #297's holder claim changes stop during start's launch window
**What goes wrong:** start and resume hold the phase holder until `systemd-run` returns, which is after the runner holds its lock. With D-12, a `stop` in that window refuses ("another DevFlow verb holds phase N … run this again once it returns") where today it stops a Live runner.
**How to avoid:** state this in the plan; keep `run_liveness_e2e::stop_of_a_unit_stopped_before_the_runner_recorded_anything_says_stopped_during_launch` (no holder held there) and the holder-held refusal test just above it (run_liveness_e2e.rs ~:930-947) green. Keep the existing refusal wording, which that test asserts on (`pid {std::process::id()}`).

### Pitfall 7: changing the fake systemctl to `active` changes other tests
**What goes wrong:** `runner_liveness` treats any unit state other than `inactive`/`failed` as `Stopping` when the lock is free (commands.rs:2301-2304), and `discard`/start guards then wait `UNIT_STOP_WAIT` for inactive. A fake that reads `active` while the runner pid lives makes every lock-free-but-alive window a wait.
**How to avoid:** land #296 first (D-18), run the full CLI e2e suite before and after, and make `active` reflect the pid's life only (the fake's existing `alive()` helper in the stop branch reads `/proc/$pid/stat`, mod.rs:79-84).

### Pitfall 8: readiness probe for the fake systemd-run
`/proc/PID/fdinfo/FD` shows a held flock as `lock:	1: FLOCK  ADVISORY  WRITE ...` and no `lock:` line on an unlocked fd [VERIFIED: probed this session on Linux 7.2 with a scratch file; control fd showed no lock line]. So: for the launched pid, find the fd whose `readlink` is `$wd/.devflow/.runner-{padded}` (phase from the `--phase` argv the fake receives: service.rs:665-668 pushes `__runner` then `--phase`) and require a `lock:` line. This needs no lock of its own. [ASSUMED: the runner lock is an flock: liveness uses std `File::try_lock` (liveness.rs:336 `try_lock_past_probes`), which std documents as `flock` on Unix]

### Pitfall 9: #258 "unchanged" has no equality to compare with
`State` derives `Debug, Clone, Serialize, Deserialize` only (state.rs:33), no `PartialEq`. Compare `serde_json::to_value` of the state `start_reserved` committed against a reload on the NotLive arm; any difference (stage, history, canary, session) keeps the state. Adding `PartialEq` to `State` is additive but drags `PartialEq` onto every field type; the JSON compare needs no core change. `run_never_prepared` (`!state.verification_baseline_captured`, commands.rs:934-936) is a weaker check and not what D-11 says.

### Pitfall 10: the resume NotLive arm has a sibling of #258 (candidate defect, not in scope)
`resume`'s NotLive arm calls `re_mark_stopped_after_failed_launch`, which overwrites `stop_reason` with "resume launch failed: …" (pipeline_launch.rs:2247-2253). If the runner ran and halted at `--until` inside the launch bound, that overwrite makes `until_cap_fired` false (it matches `stop_reason` exactly, pipeline_gate.rs:50-54), so the next resume reruns the halted stage. Inferred from reading, not reproduced. The orchestrator should decide whether to file it as an issue (project rule) or fold it into the #258 plan.
