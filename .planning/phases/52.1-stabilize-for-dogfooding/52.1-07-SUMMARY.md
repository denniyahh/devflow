# Phase 52.1 Plan 07: `devflow discard` Summary

**`devflow discard --phase N` now exists: it lists the phase's worktree, state file and branch, then removes exactly
those, and it refuses, removing nothing, in 19 tested states (a run that is live or may be, an unmerged branch nobody
named, anything at the phase path it cannot account for).**

## Read this first

- **One decision is open, and I took the narrow side of it.** The plan says discard removes the worktree "only when
  git lists it" at `.worktrees/phase-NN`. It does not say what happens when that worktree is not on
  `feature/phase-NN`. A worktree on a detached HEAD can hold commits that no branch keeps, and the listing (path,
  uncommitted changes, state, branch) would not show them. I made discard **refuse** that state and remove nothing
  (`discard_worktree`). Widening it to "remove it anyway" is the operator's call, not mine.
- **The liveness test has two holes that the plan's design leaves, and I did not close them.** Both are source reads,
  neither is reproduced:
  1. With a state that is missing or does not load, `phase_run_liveness` sweeps the socket directory. A supervisor
     that has **not published its socket yet** is in no sweep; only its held liveness lock shows
     (`refuse_stateless_launch_beside_a_live_lock`'s comment says so, and `start` checks that lock through
     `recover::unrecorded_live_launches`). Discard does not check it.
  2. With a state that **loads**, only the supervisor that state names is probed. A socket of this phase that the
     state does not name (an orphan of an earlier launch) is not looked for.
  The plan fixes the function's shape (three building blocks, an exact enum, reused by 52.1-11), so adding a fourth
  check was not mine to do. No backlog entry was filed: this is the behaviour this plan exists to get right, so it
  goes to the operator, not to a 999.x.
- **The first two commits leave an unsafe verb in history.** `be11929` (tracer) removes without any refusal and
  `2fd5de2` has no live-run refusal. That is the plan's task order. Only the head, `0da924a`, is the verb.
- **The verb was never run by hand.** Every run was a test's child process against a `tempfile::TempDir`
  repository. The only hand runs of the built binary were `devflow --help`.

## What this does not establish

- **Other hosts.** Everything ran on this host (kernel 7.2.11, git 2.56.1). Nothing ran in the pinned container or
  in GitHub CI.
- **The holder across the removal.** A held holder refuses (tested, and the mutation that drops the claim fails the
  test). That the holder stays held until the last removal is a source read: `_holder` is bound for the whole of
  `discard`. No test starts a second verb in the middle of a removal.
- **Three of the four `Live` causes.** `discard_refuses_a_live_run` uses a running agent. An ALIVE supervisor, a
  pending launch and a held liveness lock with no socket reach the same arm through `probe_phase`, which other
  suites test; no discard test builds them.
- **A removal that fails.** The `warning:` line and the non-zero exit after a failed `git worktree remove`, state
  removal or `git branch -D` have no test. After the refusals above I know of no state that reaches them without an
  outside change between the read and the removal.
- **A change between the read and the removal.** A commit made on the branch by hand after the count and before
  `git branch -D` is deleted with it. The holder excludes DevFlow's own foreground verbs, and the liveness test a
  running agent; nothing excludes a person.
- **What else is under `.devflow/`.** Discard removes `state-NN.json` and its orphaned write temps and nothing else.
  Gate files, the agent pid file, logs, events, `.holder-NN` and `.state-NN.lock` stay (discard itself creates the
  last two). `recover --clean --phase N` is still what clears those.
- **`git worktree list` naming the primary checkout first.** The primary-checkout refusal relies on it. The test
  passes on git 2.56.1; I did not check other versions.

### `phase_run_liveness`, as committed

```rust
fn phase_run_liveness(
    project_root: &Path,
    phase: PhaseId,
    existing: &workflow::Existing,
    cache_dir: Option<&Path>,
) -> PhaseRunLiveness {
    let agent_alive = agent_pid_from_file(project_root, phase).is_some_and(agent::agent_running);
    let supervisor = match existing {
        workflow::Existing::Loaded(state) => probe_phase(state),
        workflow::Existing::Missing | workflow::Existing::Unloadable(_) => {
            PhaseLiveness::NotLaunched
        }
    };
    if agent_alive
        || matches!(
            supervisor,
            PhaseLiveness::Alive { .. }
                | PhaseLiveness::LaunchPending { .. }
                | PhaseLiveness::HeldNoSocket { .. }
        )
    {
        return PhaseRunLiveness::Live {
            agent_alive,
            supervisor,
        };
    }
    if matches!(
        supervisor,
        PhaseLiveness::Stale | PhaseLiveness::ProbeFailed(_)
    ) {
        return PhaseRunLiveness::Orphaned(supervisor);
    }
    if matches!(existing, workflow::Existing::Loaded(_)) {
        return PhaseRunLiveness::NotLive;
    }
    match possibly_live_sockets(project_root, phase, None, cache_dir) {
        Ok(sockets) if sockets.is_empty() => PhaseRunLiveness::NotLive,
        Ok(sockets) => PhaseRunLiveness::Swept(
            sockets
                .iter()
                .map(|socket| socket.repair_line(phase))
                .collect(),
        ),
        Err((dir, why)) => PhaseRunLiveness::SocketDirUnlistable { dir, why },
    }
}
```

`phase_run_liveness(` occurs twice in `commands.rs`: its definition and one call, in `discard`.
`possibly_live_sockets` is reached only after the `Loaded` return, so only for a missing or unloadable state.
