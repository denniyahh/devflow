# Phase 52.1 Plan 02: Truthful Launch Notices Summary

**GSD's first `_auto_chain_active: false` is committed as what it is, with no killed-run notice or repair event, and
an invalid `DEVFLOW_EXTERNAL_VERIFY_ENABLED` prints a foreground `warning:` at `start` and `resume` (999.219, 999.229).**

## Read this first

- **`cargo semver-checks check-release -p devflow-core` exited 0. It ran no checks.** Its last lines:
  `Checking devflow-core v3.0.0 -> v4.0.0-alpha.1 (major change)`, `Checked [0.000s] 0 checks: 0 pass, 260 skip`,
  `Summary no semver update required`. For a major bump the tool skips every lint, so exit 0 says the version bump
  permits breaking changes. It says nothing about the `ClearOutcome` field addition. Plan 52.1-13's exit-code gate on
  this command will pass for the same reason.
- **The benign-row e2e drives `devflow resume`, not `devflow start`** (deviation 1). The plan expected `start`.
  `start`'s call site has no e2e for this row.

## What this does not establish

- **`start` end to end.** `start` and `resume` both call `repair_leaked_auto_chain_flag`. The e2e covers `resume`. For
  `start` there is the unit test, which calls the helper with entry point `start` on the benign row, and the source
  read. No spawned `devflow start --no-worktree` ran over GSD's first false.
- **The three refusal branches of the recording commit** (the commit fails, the re-probe still differs, the re-probe
  cannot run) have no test. When the re-probe cannot run, the reason embeds `probe_head`'s own text, which says "the
  branch-tip repair was deferred": no leak is claimed, but the word "repair" is in it.
- **A refused recording commit still emits `auto_chain_flag_repaired`**, with `commit_refused` set. The plan's
  acceptance allows it ("only on the killed-run path or a refused commit"). The event name is inaccurate for that case.
- **One non-leak row has no test of its own:** HEAD holds `false` and the working copy has no key at all, in the same
  layout. By the source it is left uncommitted (the working copy holds no flag). Before this plan it was committed
  under the repair message. Under D-46 an uncommitted `.planning/config.json` stops Validate recording a PASS. The
  plan specifies this outcome; it is a behaviour change worth knowing.
- **The warning covers `start` and `resume` only.** `advance` and the detached supervisor, where the value is
  actually read, still report an invalid value through `tracing::warn!` only, as the plan says.
- **"First on stderr" is asserted for `start --dry-run` only**, and it holds because tracing is off by default. A
  test run with `RUST_LOG` exported could put a tracing line first. For `resume` the assertion is "before the
  refusal". `start` has no refusal test here (52.1-10 adds that refusal).
- **Each new test passed in one targeted run and once in the workspace run.** Two passes are a weak bound on
  flakiness. The e2e tests spawn the real binary.

## Accomplishments

- `force_clear_auto_chain` reads two facts before it strips the flag: whether HEAD held `true`, and whether the
  working copy holds an explicit `false`. A leak is `working_tree_repaired || head_flag_was_true`, and only a leak
  reaches the repair commit.
- A working copy holding `false` over a committed copy with no `true` flag (key absent, or layout only) is committed
  under `chore(gsd): record GSD's workflow._auto_chain_active: false`, re-probed at HEAD, and reported as
  `recorded_gsd_false`.
- A layout difference with no flag in either copy is left alone: no commit, nothing reported.
- The launch repair prints `note: devflow {entry} recorded GSD's workflow._auto_chain_active: false for phase {N} in
  a commit (the committed config held no true flag; nothing was leaked)` and writes no `auto_chain_flag_repaired`
  event for that case.
- `start` (before the dry-run return) and `resume_with_fallback` (before the holder claim) print
  `warning: DEVFLOW_EXTERNAL_VERIFY_ENABLED="yes" is not true or false; using devflow.toml or the default`.
- `OPERATIONS.md` says what the variable accepts and where the warning prints.

**1. [Rule 3 - Plan defect] The benign-row e2e drives `resume`, because the fixture the plan names does**
- **Found during:** Task 2
- **Issue:** The plan says to build the e2e from `a_leak_that_reached_the_branch_tip_is_repaired_in_the_commit_too`'s
  fixture "for the spawned-start shape" and to assert on "the spawned `devflow start` output". That fixture spawns

  `feature/phase-78` branch.

  A `start` e2e would need a different harness and a real launch; I did not add one. The plan's own output note is
  therefore reversed: the e2e drives `resume`, and `start` is covered by the shared helper, not by its own e2e.
- **Not established:** see "What this does not establish".
- **Files modified:** `crates/devflow-cli/tests/auto_chain_leak_repair_e2e.rs`
- **Committed in:** `8e6fa1f`

**2. [Rule 2 - Missing check] Assertions beyond the plan's wording**

  pass if `resume` printed nothing at all. It checks stdout and stderr together.
