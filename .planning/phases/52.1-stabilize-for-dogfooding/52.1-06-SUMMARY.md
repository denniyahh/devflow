# Phase 52.1 Plan 06: Released Write Lock Wait Summary

**`status_and_doctor_name_a_held_state_write_lock` now waits up to 2 s for a shared `write_lock_status` read to say
`Free` before its three post-release reads, and a fork parked before exec reproduces the 999.221 false `Held` on
demand (the old one-shot read fails on it, the wait passes).**

## Read this first

- **No test fails if the wait call is removed from the fixed test.** The reproduction is a separate test that calls
  the same helper and makes the same three reads. That `status_and_doctor_name_a_held_state_write_lock` calls
  `wait_for_released_write_lock` before its first post-release read (`commands.rs:19067`) is a source read. Under
  nextest that test passes with or without the call, because no other test's fork shares its process.
- **Two in-process passes do not show the flake is gone.** The CLI unit-test binary passed 2 of 2 in-process runs at
  `f48b851`. At `6962f1f`, before the fix, the same binary passed 1 of 2. The evidence for the fix is the
  reproduction, not the pass count. Repeated runs are plan 52.1-13's (D-08).
- **The note on `write_lock_status` is not the plan's sentence.** The plan says a *reader* in a multi-threaded process
  can see `Held`. By the lock's mechanism the process that matters is the *holder's*: a child it forks while the lock
  is held keeps the lock. I wrote that, and left out the plan's claim that `status` and `doctor` are single-threaded,
  which I did not check (deviation 3).

## What this does not establish

- **The natural timing.** The reproduction recreates the kernel state: a child that has not exec'd holds a duplicate
  of the holder's lock descriptor after the holder released. It does not recreate another test's fork landing inside
  the hold. The state it reads, `Held { pid: None }`, is the one the natural failures printed as `held by an unknown
  holder`.
- **A rate.** Nobody measured one. Natural occurrences known: one on 2026-11-10 (the 999.221 entry) and one on
  2026-11-15 at `6962f1f`, in the orchestrator's in-process `scripts/check.sh test`
  (`commands::tests::status_and_doctor_name_a_held_state_write_lock`, `commands.rs:19067`, `control: released`, left
  `Some("  state write lock: held by an unknown holder …")`, right `None`; 52.1-CONTEXT, "Execution-time notes").
  The second is one occurrence in two in-process runs at that head. It is not a rate.
- **A fork slower than the bound.** A sibling's child that takes more than 2 s to reach its `exec` still fails the
  test, now with the wait's timeout text. That is the intended reading of a leak.
- **That later reads stay free.** After the wait, the three reads rely on nothing taking the lock exclusively. I
  checked that `status_supervisor_lines` and `build_phase_facts` call `write_lock_status` (the shared read). I did not
  trace every function the three reads call (`probe_phase`, for one) for an exclusive lock on the state lock file.
- **Production.** No run has shown `status` or `doctor` printing a held lock after a release. Whether any production
  holder's process forks from another thread while it holds the lock was not looked at. An external reader was not
  run against a parked fork; that it would also read `Held` follows from `flock` semantics (the lock belongs to the
  open file description), not from a test here.
- **Other hosts.** Everything ran on this host only (kernel 7.2.11). Nothing ran in the pinned container or in
  GitHub CI.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The never-released control runs in a child process, not in the shared test process**
- **Found during:** Task 2
- **Issue:** The plan has the control hold a parked fork, unreleased, for the whole 2 s wait. A parked fork holds a
  copy of every descriptor of the process it is forked from. In an in-process `cargo test` run that is every sibling
  test's lock files, stub write descriptors and pipe ends for 2 s, which is how this phase's flakes happen. 52.1-01
  met the same problem (its deviation 1) and wrote the rule into `ForkHeldBeforeExec`'s doc comment after this plan
  was written. Not observed here; it follows from what the helper does.
- **Fix:** The test re-runs itself with `devflow_core::test_support::run_test_in_child` and holds the fork only in
  the child, which runs that one test. The `catch_unwind` and the text assertion are the plan's, inside the child.
- **Files modified:** `crates/devflow-cli/src/commands.rs`
- **Verification:** passes (2.015 s to 2.023 s in four runs); the four mutations above fail it through the child's
  output
- **Committed in:** `64e8680`

**2. [Rule 2 - Missing check] The control also asserts the wait lasted its bound**
- Without `waited_for >= RELEASED_WRITE_LOCK_WAIT`, a wait that gave up on the first held reading with the right text
  would pass the control, and that wait would not outlast a slow fork. The last mutation above is that case. The
  assertion is a lower bound, so load cannot make it fail.
- **Committed in:** `64e8680`

**3. [Rule 1 - Plan defect] The note on `write_lock_status` names the holder's process**
- **Found during:** Task 2
- **Issue:** The plan's note says a reader in a multi-threaded process can see `Held`, and that production readers
  are short-lived single-threaded processes. The lock is an `flock` on the holder's open file description
  (`WriteLock` releases it by closing the file, with no explicit unlock). What keeps it held is a child forked by the
  *holder's* process during the hold. The reader's threads do not enter into it; in the test process the holder, the
  forking thread and the reader happen to be one process. I did not check whether `status` and `doctor` are
  single-threaded.
- **Fix:** The note says: one reading can say `Held` for a moment after the release; why (the holder's process
  forks from another thread during the hold); that it has been seen only in the multi-threaded test process;
  that `status` and `doctor` take one reading in a short-lived process and print how to judge it; and that a caller
  needing the released state polls with a bound. The plan's must-have (a note about the fork-before-exec window, no
  production change) is met.
- **Files modified:** `crates/devflow-core/src/workflow.rs`
- **Committed in:** `f7f2c3e`
