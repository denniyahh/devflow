## Phase Boundary

Make DevFlow stable enough to resume dogfooding at Phase 53: a supervised run drives a phase from Plan to a finished
Validate with no hand-run stage and no hand-edited `.devflow/` state. The phase fixes known defects and flakes that
block or erode that, and closes by proving it with one live supervised run.

Not dogfooded itself (operator, 2026-11-11, ROADMAP.md). It runs as GSD commands in an agent session, the same way
Phase 52 did (52-CONTEXT D-18).

Out of scope: new capabilities (the question channel is Phase 53), and anything that does not block or erode an
unattended Plan→Validate run or the by-hand close-out after it.

### Flake fixes (999.221, 999.222, 999.223, 999.232)
*Revised 2026-11-11 after the adversarial review (`52.1-context-review/`): the first version's D-05 checked the wrong
boundary, its stub fix did not fix the error it named, and its evidence step had no runner that could reproduce the
race.*
- **D-05 [auto]:** Reproduce each failure on demand before fixing it. The suspected race happens between fork and
  exec, and `O_CLOEXEC` does not close it: a close-on-exec descriptor is still inherited until the child's `exec`. So
  an audit for descriptors missing `O_CLOEXEC` proves nothing. Instead, each fix gets a test helper that holds a
  forked child between fork and exec (a `pre_exec` that waits) while the test runs its check. With that child the old
  code must fail and the fixed code must pass. That is the negative control.
  The causes are not all the same:
  - **999.221, 999.222: another test's fork.** The code already accepts this cause: `workflow.rs`
    `wait_for_free_write_lock` and its comment, and `liveness.rs` `in_own_process`.
  - **999.223:** it failed under nextest, where each test runs in its own process, so no other test's fork can
    explain it. Suspect first the test's own ordering: it asserts the liveness file is `Missing` before it waits for
    its own launcher to exit (agy finding 10, speculation).
  - **999.232:** a killed `sleep` descendant that is not gone yet, not a descriptor.
- **D-06 [auto]:** The fixes:
  - **999.221:** wait for the release, with the existing 2 s `wait_for_free_write_lock` pattern, before **all three**
    post-release reads in the test, not one.
  - **999.222:** retry the stub's spawn on `ETXTBSY` (bounded, test builds only). The temp-file-and-`rename` shape in
    the backlog entry does not work: `rename` keeps the same inode, so a forked child that still holds the write
    descriptor still makes `exec` fail. The planner may keep the rename as well, but not as the fix.
  - **999.223:** fix the order in the test (wait for the launcher, or a bounded poll for `Missing`) once the research
    step reads why the probe said `Live`. If a production `stop` can report a live run after it returns, that is a
    defect to file, not something to poll around.
  - **999.232:** a bounded wait (at most 2 s) for the descendant to be gone, using the zombie-aware liveness check
    (GitHub job containers do not reap zombies; see `test_support::live_group_members`).
  - If a production caller (`status`, `doctor`, `stop`) can show the same brief false state in a multi-threaded
    process, add a note beside the function. Do not change production code for it unless a misreport is shown.
- **D-07 [auto]:** Every poll and retry gets a control where the state never arrives (the lock stays held, the
  descendant stays alive, the write descriptor stays open). It must fail with the poll's own timeout message, not
  hang and not pass.
- **D-08 [auto]:** Evidence for each flake:
  1. The D-05 reproduction: old code fails, new code passes. This is the main evidence.
  2. Repeated runs under the runner that failed. In-process `cargo test` for 999.221, 999.222 and 999.232; their
     races cannot happen under nextest, where each test has its own process. nextest for 999.223.
  `scripts/check-in-container.sh` cannot run a single test, so the repeated runs need a small harness that the plan
  names. The report states the count and says what it does not prove: N passes is a weak bound on a rate nobody
  measured.

### `--force` redesign (999.224)
- **D-09 [auto, item 1 operator]:** Adopt the entry's fix shape, with these meanings made explicit:
  1. **Each verb does one thing (operator, 2026-11-11).** The operator: "start should only be for new phases. resume
     should only work on an incomplete phase. nothing should restart a finished phase."
     - **`start`** works only on a phase with no run state, no phase worktree and no phase branch. Otherwise it
       refuses, and the refusal says what it found:
       - an incomplete run: it names `resume`;
       - a finished run: it says the phase is finished and names the close-out or `discard`;
       - a leftover worktree or branch with no state: it names `discard`.
     - **`resume`** works only on a run that has not finished. It already refuses a finished run.
     - **Nothing re-runs a finished phase.** This amends 52-CONTEXT D-35's bullet "a new `start` on the phase says it
       replaces the finished state": `start` now refuses instead.
     - `advance`, `status` and every refusal name only the verb that applies.
  2. **`devflow discard --phase N`:**
     - Before removing anything, it lists what it will remove: the worktree, its uncommitted changes, the state, and
       the branch.
     - It refuses while a run is live, with the same liveness refusal `cleanup` uses. It holds the phase's foreground
       holder across its check and the removal, so a concurrent `start` cannot slip in between (codex finding 5).
     - It refuses an unmerged branch unless the operator passes the branch's name, and the name must match the
       phase's recorded branch.
     - In `--no-worktree` mode, when the branch is checked out in the main checkout, it refuses and says which branch
       to switch to first. It does not switch branches itself.
  3. **A stale or unprobeable supervisor** goes through `devflow stop`, and `cleanup` stops offering `--force` for it.
     Add tests that `stop` ends both a `Stale` and a `ProbeFailed` run, because this removes the only other way out
     for them.
  4. **The ">50 commits ahead" refusal** gets an override named for what it overrides.
  5. **`cleanup`** removes a finished or stopped run's worktree **and its state** only when the branch is merged, the
     worktree is clean and no run is live. Otherwise it keeps them and names `discard`. Today it keeps every stopped
     run's worktree before it looks at the branch at all.

  Every message that names `--force` as the way on is rewritten: `restart_verb`, `kept_stopped_worktree_line`, the
  `phase_worktree.rs` "use --force to recreate it" and "refusing --force" messages, the `resume` refusal for a
  finished run, and the `advance` hint. None of them may name a raw `git worktree remove --force && git branch -D` as
  the routine way out. They name `discard`.
  — **Reversibility:** one-way — the CLI is the published `devflow` binary crate (`cut-release.sh` publishes
  `devflow-core`, then `devflow`). Removing a flag or verb after 4.0.0 ships breaks scripts that call it. The version
  is `4.0.0-alpha.1` and unpublished, so doing it now rides the same major bump. `cargo semver-checks` applies only if
  a `devflow-core` `pub` item changes.
- **D-10 [auto]:** The Phase 52 invariant (3f0714f: no `--force` deletes an unmerged phase branch) becomes: **no path
  deletes an unmerged branch implicitly.** The one exception is `discard` with the branch named as in D-09.2.
  - Each path gets a refusal test: `start` worktree, `start --no-worktree`, `cleanup`, `discard` without the name, and
    `discard` with a wrong name.
  - Add a test with a non-default base; nothing tests one today.
- **D-11 (operator, 2026-11-11):** `--force` is removed from `start` and `cleanup` outright. There is no hidden flag,
  no migration and no deprecation period (operator, 2026-10-12: no users). Typing it gets clap's own "unexpected
  argument '--force'" error. Update the tests that assert the old text (for example the
  `refused.contains("use --force")` assertion in `commands.rs`).

### Planning-time decisions (2026-11-11, after 52.1-RESEARCH.md)
The researcher found three questions the decisions above left open. Provenance is per item.
- **D-20 (operator, 2026-11-11):** Two run states D-09.1 did not cover:
  - A state left only by a killed `start`'s reservation (no recorded supervisor, no worktree, no branch) counts as
    **no run**: `start` proceeds. Today's refusal telling the operator to run `start` again goes away.
  - A state file that does not load makes `start` **refuse and name `discard`**. `start` no longer replaces it and
    keeps a copy.
- **D-21 (operator, 2026-11-11; amends the existing R-6 behaviour, confirms D-09.3 as written):** `devflow stop` ends
  a `ProbeFailed` run through the identity-checked backstop, the same as a `Stale` one.
  - Operator's reasoning: a supervisor whose socket cannot be probed cannot be recovered, so it is in effect gone.
    Checked against source before the decision was recorded: the backstop (`supervisor/backstop.rs`,
    `BackstopDecision`) validates the group's identity itself (recorded leader present with its start time, same
    boot, own uid; otherwise `LeaderRecycled`/`EmptyGroup`/`PreviousBoot`/`Refuse*` signal nothing). The probe was
    never what stopped a wrong-process kill.
  - The run's state survives, so `resume` continues the phase afterwards.
  - The existing test `stop_reports_a_probe_error_and_never_runs_the_backstop` (`stop_e2e.rs`) is rewritten to assert
    the backstop runs. Its negative controls stay: a recycled leader or empty group is still not signalled.
  - The residue stays a refusal: with no usable sidecar nothing can validate the group, so `stop` still refuses and
    signals nothing. That refusal names the manual kill (D-09: every refusal names the way on), never `--force`.
- **D-22 (agent, delegated by the operator 2026-11-11: "if you can decide this based on your understanding, do so"):**
  999.219's open fix. When HEAD lacks `workflow._auto_chain_active` and the working copy holds `false` (GSD's first
  `config-set` in a project whose committed config never had the key, e.g. a fresh project or the default scratch
  dogfood fixture), DevFlow **commits it under an accurate message** ("record GSD's `_auto_chain_active: false`"),
  emits no killed-run notice and no `auto_chain_flag_repaired` event. The killed-run repair, message and notice fire
  only when HEAD or the working tree actually held `true`. Leaving the write uncommitted was rejected: the dirty tree
  stops Validate recording a PASS, which defeats this phase's goal. Fixture row: HEAD without the key, working tree
  `false` → accurate commit, no killed-run notice.
- **D-23 (operator, 2026-11-11; answers plan 52.1-07's flag-naming sign-off):** `discard`'s confirmation flag is
  `--delete-unmerged-branch <BRANCH>`: `devflow discard --phase N [PROJECT] [--delete-unmerged-branch <BRANCH>]`. The
  value must equal the phase's derived branch (D-09.2). The sign-off is answered, so plan 52.1-07 needs no
  `checkpoint:decision` for it.
- **D-24 (operator, 2026-11-11; supersedes D-09.4):** the `start --no-worktree` ">50 commits ahead" refusal and the
  ">10" warning beside it are **removed**, not given a renamed override. No `--allow-stale-base` flag exists.
  - Why (checked in source before the decision): `divergence_from_develop` measures the branch the main checkout
    happens to be on, but `feature_start` then runs `git checkout <base>` and `git checkout -b feature/phase-NN`, so
    the phase branch is always cut fresh from the base. The check guards nothing, and its message ("your branch is too
    far behind") is false. It also compares local refs only, so it never said whether the base is current with origin.
  - Test: `start --no-worktree` from a current branch more than 50 commits behind the base succeeds, and the new phase
    branch's tip equals the base's tip.
- **D-25 (operator, 2026-11-11; refines D-21's residue):** a supervisor that is alive but never answers its socket
  (`NoReply`) and still holds its launch's liveness file: `stop` ends the validated agent group through the backstop,
  never signals the supervisor pid (the liveness file's pid cannot be validated: a forked child can inherit the lock),
  exits non-zero, and names `kill <pid>` followed by `devflow resume --phase N`. `resume` refuses until that process
  exits. The operator accepted the planned behaviour as recommended.
- **D-26 (operator, 2026-11-12; simplifies how D-09.1/D-20 are built, and widens `start --dry-run`):**
  - **One place for the rules.** `start`'s refusals over an existing run (finished → close-out or `discard`;
    incomplete → `resume` or `discard`; state that does not load → `discard`) are one new guard that runs **after**
    the three existing guards in `reserve_launch` (live run, finished-run resume, and the
    launch-not-yet-published lock guard `refuse_stateless_launch_beside_a_live_lock`), at the point where today an
    unloadable state is backed up and replaced (`keep_unloadable_state`, which goes). The existing guards, their
    order and their tests stay as they are. In particular, `a_start_refuses_an_unloadable_state_beside_an_unpublished_supervisors_lock`
    keeps asserting the live launch id. There is no separate early copy of the checks at the top of `start`.
  - **Reservation-only (refines D-20):** `run_never_prepared(state) && state.supervisor.is_none()` counts as no run.
    A leftover worktree or branch is then caught by 52.1-09's refusals (which name `discard`). Nothing under the
    state write lock spawns `git` (the D-08 rule on `reserve_launch`).
  - **`start --dry-run` reports every refusal a real `start` would hit**, read-only: the guards above in the same order,
    then 52.1-09's leftover worktree/branch refusals, then the preview. To keep the order in one place, the guard
    sequence is a single function that both `reserve_launch`'s closure and dry-run call, with dry-run passing no own
    launch id. Dry-run takes no reservation, no holder and no write lock, and writes nothing. Dry-run before this
    phase returned before every guard (`commands.rs` `if dry_run` before `claim_foreground_holder`), so this is a new
    behaviour.
  - Why (agent analysis, checked in source, accepted by the operator): plan 10's earlier design added an early copy
    of the checks. The copy skipped the unpublished-launch guard and would have named `discard` over a live launch.
    Its reservation-only test also needed a git spawn under the lock.
  - **Clarification (agent, 2026-11-12; D-26's own wording):** "the existing guards stay as they are" means their
    logic and order, not their message text. D-09.1 governs the text. The start live-run refusal's "run `devflow start`
    again" / "then `devflow start`" lines name, after `devflow stop`, the verb that will act on what stop leaves:
    `devflow resume --phase N` over a loaded incomplete run. `start_lock_e2e`'s `assert_start_refuses_live_run`
    fragment is updated with it.
- **D-27 (operator, 2026-11-12; extends D-26's dry-run):** `start --dry-run` also runs, read-only, the two purely local
  checks from `start_reserved`: the agent binary is on PATH (`ensure_agent_binary`), and the base branch resolves
  (`config::base_branch`, plus `ensure_base_is_a_local_branch` for a configured base). It does **not** run
  base currency (`ensure_base_ref_current` fetches and can fast-forward the base) or phase reachability on the base
  (meaningful only once the base is current). The dry run prints one line naming every `start_reserved` check it
  skipped (base currency, phase reachability, the CONTEXT.md/PLAN.md checks on the base). Agent refinement,
  2026-11-12: the dry run checks in the same order as a real start, so both print the same first refusal.
