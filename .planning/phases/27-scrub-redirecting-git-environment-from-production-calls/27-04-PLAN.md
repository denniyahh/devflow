## Recorded decision: RESEARCH Open Question #1 — IN SCOPE

`27-RESEARCH.md` § Open Questions #1 and § Pitfall 1 raise a genuine indirect
git-invoking site that is **not** among the 41 counted call sites and **not** in
`27-CONTEXT.md`'s seven-file list: `commands.rs::test_cmd` (base-commit line
1956) runs `sh -c "cargo test"`, `sh -c "cargo clippy …"`, and
`sh -c "cargo fmt --check"`. That child `cargo` compiles `devflow-cli`, which runs
`build.rs::run_git` at compile time to embed `DEVFLOW_BUILD_COMMIT`. A hostile
`GIT_DIR` inherited by `devflow test` therefore reaches `git` two processes down.

**Decision: IN SCOPE for this phase.** Scrub the `sh` invocation via
`hermetic_command("sh", project_root)`. Rationale, recorded here rather than left
implicit:

1. **D-02's boundary is preserved exactly, not stretched.** D-02 excludes
   `build.rs`'s source and `build.rs`'s own compile-time invocation, on the
   grounds that its actor is *whoever compiles the binary* and its moment is
   *build time*. Nothing here edits `build.rs`, and
   `git diff --stat -- crates/devflow-cli/build.rs` must stay empty. What is
   scrubbed is DevFlow's own spawn edge in a shipped runtime command — a
   different actor (an **operator** running `devflow test`) at a different moment
   (**runtime**) from the one D-02 excused.
2. **D-01's framing covers it directly.** There is no legitimate reason a
   DevFlow-issued command would want to silently redirect via an inherited
   variable. `devflow test` is a DevFlow-issued command.
3. **`27-CONTEXT.md` anticipated it under Claude's Discretion.** Discretion item
   #2 names this case verbatim: "a scrub that only wraps `Command::new(\"git\")`
   calls would miss a production call that shells out to `cargo` in a way that
   itself invokes git." And `hermetic_command`'s own doc comment names `cargo`,
   "whose build scripts invoke `git`", as its motivating case. The general-form
   constructor exists for exactly this.
4. **None of the three legitimate reasons to defer applies.** Not a context-cost
   problem (one construction swap), not missing information (the site and its
   mechanism are fully characterised), not a dependency conflict.
5. **Nothing legitimate breaks.** The scrub makes the child behave as if launched
   from a clean shell, which is what an operator running `devflow test` expects.

**Explicitly NOT in scope, and not an oversight:** the seven other
`Command::new("sh")` sites in `commands.rs` all sit below the
`#[cfg(test)] mod tests` boundary (base-commit line 3226). They are test fixtures,
which already have their own containment layer via `test_support`. This phase
scrubs production spawn edges.

## Shared recipe: the hostile-`GIT_DIR` harness

```
HOSTILE=$(mktemp -d) && git init -q "$HOSTILE"
GIT_DIR="$HOSTILE/.git" cargo test <scope>
```

A `test result:` line must actually print. A timeout, or a `0 passed` line
(meaning the filter matched nothing), is a FAILURE, not a pass. Never use a bare
`cargo test --workspace` under a hostile `GIT_DIR` — it does not terminate
(`27-RESEARCH.md` Pitfall 2). For `devflow-cli`, always append
`-- --skip pipeline_gate --skip pipeline_outcomes` when running the whole binary
target under a hostile `GIT_DIR`.
