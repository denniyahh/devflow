## The agent's environment and authentication (measured, not assumed)

A `systemd-run --user` unit does not inherit the calling shell's environment, so no `CLAUDE*` variable of a Claude Code
session reaches the nested agent (RESEARCH Pattern 2). It is not a clean environment either: the unit inherits the user
manager's environment, and the three `--setenv` values only add or override `PATH`, `HOME` and the hook command.
Measured by variable name only on 2026-09-29 (checker, re-confirmed by the orchestrator and the planner; no value was
printed or recorded): 98 names, including `ANTHROPIC_API_KEY`, `ANTHROPIC_TOKEN`, `DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR`, and
no `CLAUDE*`, no `DEVFLOW_*` and no `ANTHROPIC_BASE_URL` (a Claude Code shell does set that one; per the checker, to a
non-local host).
DevFlow hands the agent that environment minus git's redirecting variables (`crates/devflow-core/src/git.rs:87-93`,
`crates/devflow-core/src/monitor.rs:431-444`; reasoned). Claude Code in `-p` mode always uses `ANTHROPIC_API_KEY` when
it is present (code.claude.com/docs/en/troubleshoot-install) and reports the source it used as `apiKeySource` on the
stream-json `system`/`init` event (code.claude.com/docs/en/agent-sdk/typescript, `ApiKeySource`). Whether that key works
without the base URL the operator's sessions use is unknown, and a failure would surface only after the Define approval,
spending one of the three attempts (D-11).

The unit environment is not the only input that decides the agent's credential. Claude Code's authentication
precedence (code.claude.com/docs/en/authentication, read 2026-09-29) is: cloud-provider credentials when
`CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` or `CLAUDE_CODE_USE_FOUNDRY` is set; `ANTHROPIC_AUTH_TOKEN`;
`ANTHROPIC_API_KEY`; the `apiKeyHelper` setting; `CLAUDE_CODE_OAUTH_TOKEN`; Anthropic profiles (`ANTHROPIC_PROFILE`, the
federation variables, `~/.config/anthropic`); and last the `/login` credential in `.credentials.json` under the
configuration directory (`$HOME/.claude`, or `CLAUDE_CONFIG_DIR` when set). Those variables reach `claude` from the unit
environment or from the `env` block of any Claude Code settings file that applies to the launch (the docs say to remove
a credential variable "wherever it's set: your shell environment or the `env` block of a settings file",
code.claude.com/docs/en/remote-control): user settings `$HOME/.claude/settings.json` for the unit's `HOME`, managed
settings `/etc/claude-code/managed-settings.json`, and `.claude/settings.json` and `.claude/settings.local.json` in the
directory `claude` runs in (the scaffold writes no project `.claude/`, per the header of
`scripts/scratch-dogfood-repo.sh`). Checked by key name and existence only on 2026-09-29, no value read:
`~/.claude/settings.json` has an `env` block whose keys are `ANTHROPIC_API_KEY` and `CLAUDE_CODE_SHELL`, and no
`apiKeyHelper` key; `/etc/claude-code/` and `~/.config/anthropic` do not exist; `~/.claude/.credentials.json` exists.
So `ANTHROPIC_API_KEY` reaches the agent from two sources, the user manager's environment and the user settings' `env`
block. Which of the two values Claude Code uses when both set it is unverified. `agent-env-names.txt` shows only the
first source, and `auth_source` names the mechanism (`ANTHROPIC_API_KEY`), not which source supplied its value. The
probe reads the same settings as the run (same `HOME`, no `--bare` or `--settings`); its working directory differs from
the agent's, which matters only if a project `.claude/` exists.

The tool therefore measures and probes instead of clearing the environment. An `env -i` launch would also drop
`DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR`, which `notify-send` and possibly gh's credential store need (reasoned,
not verified), and would change which credential the agent uses; choosing that credential is the operator's decision,
not this tool's. `probe-auth` records variable names with `compgen -e` inside the unit and never reads, prints or
records a value; the probe's raw output stays in a scratch directory that is deleted, and only derived fields are
recorded. The prompt is `Reply with exactly P49_AUTH_OK and nothing else.`; the probe creates no repository and pushes
nothing. What a passing probe establishes: the `claude` on this `PATH` authenticated and answered in this environment
at launch time. What it does not: that authentication holds for the whole run, or which account or bill the credential
belongs to (`auth_source` names only the mechanism).

The selftest simulates the operator's repository step with a LOCAL bare repository: it adds it as `origin` of the
scaffolded project and fills it with `git -C <bare> fetch <project> main:main integration:integration`, so no command in
the tool or its selftest sends anything to a remote. Fake `gh` answers `repo view` with
`{"nameWithOwner":"tester/p49-live-attempt-1","visibility":"PRIVATE"}` and `auth status` with a `Logged in to github.com
account tester` line and a `Token scopes: 'gist', 'read:org', 'repo'` line. The `--fake-cmds` directory of every
selftest case holds a fake `claude`, so no selftest reaches the real one; by default it prints a stream-json `system`/`init`
line carrying `"apiKeySource":"ANTHROPIC_API_KEY"` and a `result` line with `"is_error":false` and
`"result":"P49_AUTH_OK"`, and exits 0. The fake `systemd-run` runs a `--wait` unit in the foreground and returns its
exit status, and passes the caller's environment through plus the `--setenv` values, as a unit inherits the user
manager's environment.
