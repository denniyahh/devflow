- `pipeline_launch::tests::auto_rescan_rejection_parks_for_supervised_repair` failed once under a full `scripts/check.sh all` run (found during 50-13 verification)
  status: resolved
  **Resolved by `96b457b`:** the defect was in the test, not in production code. The writer read the state, then checked the response file. `park_auto_rescan_repair` saves `stopped` and only then removes the response, so a writer descheduled between its two reads could miss the whole park: it saw "not stopped", then "response gone", and wrote an abort no gate had asked for. The writer now checks the response first and reads the state second, so a response the park removed is always seen with `stopped` set. A response the pre-fix loop-back removed (state not stopped) still triggers it. A temporary probe in the writer (not committed) confirmed the order in 4 of 4 loaded failures: the first read saw `stopped: false`; by the time the writer wrote, the state was stopped and the gate file was gone. In every failure the one-Code-gate assertion just before it passed, so no extra gate fired. Production code answers a gate only through `Gates::respond`, which refuses when no gate file is open, so it cannot leave a response behind the way the test's writer did. Both full-suite failures reported this phase had the same signature; neither was instrumented.
  **Stress evidence:** the recipe runs the test binary directly in N parallel loops under `stress-ng --cpu C` on a 4-core host. At HEAD `2697ea2`: 3/800 failed with N=8, C=8; 9/2600 with N=16, C=12; 1/600 with each loop pinned to one CPU. Every failure was at the same assertion (`pipeline_launch.rs:6132`) and its child-wrapper companion. With the fix, in alternating batches against HEAD: 0/600 (N=8, C=8) and 0/2000 (N=16, C=12). A 20 ms sleep injected between the writer's two reads (not committed) made the old order fail 50/50 and the new order pass 50/50, unloaded. The negative control still bites: a mutant that routes the Auto rejection through the pre-fix loop-back fails 45/45 (5 unloaded, 40 loaded) with the new writer, after three Code gates, at "Auto rejection must park the phase instead of aborting it", with the third gate answered by the writer's abort. Zero failures in 2600 loaded runs bound the remaining rate under this recipe below about 0.12% at 95% confidence. They do not prove the window is closed for every load shape. The writer's separate 2 s "the re-scan response was not consumed" deadline was not hit in any loaded run and was not changed.
  **What:** the test's negative-control writer thread loads the state, sees it not stopped, then sees the response file gone and writes a third-gate response, so the final `third_gate_response_written` assertion fails. Between the writer's `load_state` and its `exists()` check, `park_auto_rescan_repair` can both save `stopped` and run `Gates::cleanup`. It is a check-then-act race in the test's writer, polled every 5 ms.
  **Evidence:** it failed once at 50-13's HEAD under the loaded full run and passed 6 of 6 runs alone. The advance it drives calls `advance_for_stage` in the test process with no supervisor stop token engaged, so its gate poll is the unchanged `Gates::poll_response` path; 50-13 did not change that test or `park_auto_rescan_repair`. Whether it also fails at the plan's base under load was not checked.
  **Fix options (not taken, out of 50-13's scope):** have the writer re-read `stopped` after it sees the response gone and before it writes, or signal the park through a file the test owns.
- Two socket-probe tests failed once under a loaded `scripts/check.sh all` run and passed alone (found during 50-13 verification)
  status: resolved
  **Resolved by `6d46008` (fix), failing tests first in `9481671`:** the defect was in production code, `supervisor::probe`. When a listener was being released at the moment of a probe, the connect landed in its backlog and the ping then read a reset or hit a broken pipe; `probe` reported that as `NoReply`, although a fresh connect would be refused (`Stale`). The e2e test hit it because a SIGKILLed supervisor is multi-threaded: its leader reads as a zombie (`agent_running` is false) while another thread still holds the fd table. A `/proc/<pid>/task` snapshot taken at probe time showed the leader in `Z` and 1 or 2 threads in `R` in every failure, and no task directory in every pass. The backstop test hit it because `cargo test` runs tests as threads of one process: a child forked by another test thread keeps a copy of the fixture's dropped listener until it execs. The same recipe with `--test-threads=1` failed 0/30, and the backstop module under nextest (one process per test) failed 0/30 where `cargo test` failed 2/20 to 3/30, always inside the shared `stale_socket` fixture. `probe` now connects once more after a reset or broken pipe. `Stale` still comes only from a refused connect, and a listener that stays up but closes every connection stays `NoReply` after exactly one more connect (control test `probe_never_reads_a_live_listener_that_closes_connections_as_stale`).
  **Stress evidence:** e2e under `stress-ng --cpu 8`, one `cargo test --exact` run per iteration: 5/60 failed before the fix (3/30 at `80cd108`, 2/30 with the fix reverted), 0/100 after (60 with a temporary re-probe log that recorded 3 re-probes, 40 at the committed `6d46008`). The backstop test run beside a temporary in-process spawner test (3 threads spawning `true` for 3 s, `--test-threads=4`, not committed): 6/60 failed before (4/30 at `80cd108`, 2/30 reverted), 0/120 after, with the re-probe taken in 7 of the 60 logged runs. Zero failures in 100 and 120 runs bound the remaining rate below about 3% at 95% confidence; they do not prove the window closed. `request_shutdown` maps a reset to `NoReply` the same way and was not changed.
  **What:** `supervisor_e2e::status_reports_each_liveness_state_with_its_repair_verb` failed at `probe the orphaned socket: NoReply("no ping reply: Connection reset by peer (os error 104)")` right after it SIGKILLed a supervisor and saw the pid gone, where it expects `Stale`. In the same run, `devflow-core` `supervisor::backstop::tests::pidfd_group_signal_is_used_when_the_kernel_supports_it` failed at `the fixture socket must probe STALE`. Both probe a socket whose owner has just died.
  **Evidence:** each passed 8 of 8 runs alone, and both passed in the full run before. 50-13 does not touch either test, `probe` or the backstop; a SIGKILLed supervisor never runs 50-13's code. One reading, not checked: a connect that lands in the dying listener's backlog before the kernel closes it reads as a reset, not a refusal.
  **Fix options (not taken, out of 50-13's scope):** retry a probe that reads `NoReply` from a reset a few times before asserting `Stale`, or have `probe` treat a reset on connect like a refusal.

- The backstop's leader-gone refusal tells the operator to inspect the group with `ps -o pid,pgid,sid,lstart,args -g <pgid>`, which on procps-ng selects a session, not a process group (found during 50-18)
  status: open
  **What:** `supervisor/backstop.rs` (`RefuseLeaderGone`, about line 211) prints that command, `doc_check.rs:709` pins the string, `backstop.rs` tests at about lines 1164 and 1365 assert it, and OPERATIONS.md's `devflow stop` row quotes it. On procps-ng, `ps -g <list>` means "select by session OR by effective group name". An agent group's session is not its pgid (the 50-18 fault arm saw an agent in pgid 561461 with sid 561361), so the hint lists no member of a group that still has members.
  **Evidence:** `man ps` on this host (`-g grplist: Select by session OR by effective group name`); `ps -o pid,pgid,sid,lstart,args -g <agent pgid>` printed only its header against a live fake-agent group whose members `/proc/<pid>/stat` field 5 listed. The refusal text itself also lists the members it found, so the operator is not left blind; only the suggested command is wrong. The refusal path was not run live by 50-18 (its cases end a group whose leader is present).
  **Impact:** an operator who runs the suggested command sees no member and may conclude the group is empty when it is not. Fix options (not taken, out of 50-18's scope, crates/ change): `ps -o pid,pgid,sid,lstart,args --pid "$(pgrep -g <pgid> | paste -sd,)"`, or `pgrep -g <pgid> -a`, updating the doc_check pin, the two tests and the OPERATIONS.md row together.
