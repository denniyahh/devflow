<objective>
Give every launch failure path a defined end state (checker revision 2026-10-14). 50-11 made a launch record
`state.supervisor`, and 50-13 made the handoff publish N+1 before N exits; neither says what the record holds when a
launch is refused or fails, when the save that publishes N+1 fails, or when N+1 is stopped before that save lands. This
plan closes those three: a failed or refused launch clears the record (WR-04's rationale, moved from the monitor pid to
the socket record), a failed publish save shuts the unrecorded successor down, and a stop that reached the successor
first is recorded as a stop.

Purpose: `status` and `doctor` (50-12) never send the operator to `devflow resume` after a launch that did not happen,
and no supervisor is left running that the state does not name.
Output: `record_failed_launch`, `publish_record` and the `refuse_launch` clear in `pipeline_launch.rs`, with tests.
</objective>

`refuse_launch` (:582-586) does the same for a canary refusal; its tests are
`launch_stage_inner_clears_monitor_pid_on_early_failure` (:3057) and `absent_canary_refuses_to_launch` (:3741). RESEARCH
Finding 2 (:460-479) gives the handoff order and two rules this plan implements: "If step 3 times out or step 4 fails,
N sends `shutdown` to N+1's path and records `stopped` with a reason. Do not leave an unpublished agent running", and
"keep N's record until step 4 replaces it in one save, and clear it only on the failure path". After 50-11 the
timeout half is inside `spawn_monitor` (it calls 50-24's `wait_for_publish`, which ends a not-ready supervisor and its
agent group and returns `NotReady`);
after 50-12, `phase_liveness` maps no record to `NotLaunched` and a GONE record with `stopped` false to
`GoneWhileActive` (`devflow resume`). After 50-13, the launcher's order is: `spawn_monitor` returns `Published` →
`test_hold("before_publish")` and safe point 3 → the one save that records N+1 → `HandedOff` → `finish` after
`advance_with` returns; a supervisor whose `AgentOutcome::Stopped` arrives while the state does not name its launch id
writes nothing (the lock-skip rule) — this plan does not change that rule. In-crate tests run monitors through the
50-10 harness entries (`DEVFLOW_TEST_MONITOR_FULL=1` for a run that advances).
