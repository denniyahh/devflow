### Locked Decisions

**D-01 — Run-owned marker shape.** The run-owned marker is a `verification_run_nonce: Option<u64>`
field on `State`, written before the Validate stage is launched and read after it completes. A
nonce that differs from what was written means Validate did not run (the agent did not author the
artifact). A matching nonce means it did. This shape was chosen over a separate marker file (adds
lifecycle management for no benefit) or an evidence-root marker (lives in the same tree a checkout
replaces, defeating its purpose). State is already the home of the fingerprint/mtime fields and
their observation site; the nonce joins them there. Reversibility: reversible — the field is local
to `State`; removing it restores the pre-35.2 fingerprint-only behavior.

**D-02 — Relationship to existing provenance fields.** The nonce is **authoritative** for
provenance ("did this run's agent author this?"). The fingerprint and mtime remain as **secondary
signals** for staleness ("did the content change?"). They are augmented, not replaced. A nonce
tells you Validate ran this cycle; a fingerprint tells you the artifact's content matches what was
observed before. Both answer different questions. Replacing fingerprints would lose the staleness
detection that underpins the plan-count comparison. Reversibility: costly — the fingerprint/mtime
fields have callers in `select_loop_back_fix` and `verification_authored_this_run`; removing them
would require restructuring those functions rather than adding a condition.

**D-03 — Branch-naming test.** Two tests. (1) A format-string assertion on `PhaseId`'s branch name
— verifies that `PhaseId::new(7)` produces `feature/phase-07`, `PhaseId::new(35)` produces
`feature/phase-35`, and `PhaseId::new(35).with_minor` (i.e. `35.2`) produces `feature/phase-35.2`.
This catches DevFlow-side drift on every CI run with no external dependency. (2) A conditional
verification that GSD computes the same branch name — invoked via `gsd-tools` when available,
skipped with a notice when not. The single-digit padding case (criterion 3's explicit requirement)
is covered by the format-string test alone. The GSD-side test is defense-in-depth for the
cross-repo invariant. Reversibility: reversible — tests only.

**D-04 — Criterion 4, both directions in one run.** A single `#[test]` in `pipeline_outcomes.rs`
exercising `verification_authored_this_run` (or the dispatch function that reads the nonce) with
two scenarios: (A) nonce matches, fingerprint unchanged → the function returns `true` (authored
this run, dispatch `GapsOnly`); (B) nonce absent or mismatched → returns `false` (not authored this
run, dispatch `FullExecute`). Both assertions fire in one test invocation — "demonstrated in the
same run." No agent or e2e harness needed; the dispatch decision is a pure function of `State`
fields. Reversibility: reversible — tests only.

**D-05 — mtime rejection.** mtime is stated as rejected for provenance, with the reason recorded in
source: `phase_verification_mtime_nanos` already exists but a checkout or merge-back updates mtime
exactly as it updates content, so it fails on the identical scenario the nonce is designed to
catch. This is criterion 5 and is documentation, not code. Reversibility: not applicable — negative
decision.

### Pattern 1: `#[serde(default)]` for new `State` fields

**What:** every field added to `State` since Phase 17 uses `#[serde(default)]` so an older
persisted `.devflow/state-{N}.json` (written by a binary predating the field) deserializes to the
type's default rather than failing to parse.

**When to use:** any new `State` field, including `verification_run_nonce`.

**Example — the three existing precedents this phase's field should match:**
```rust
// Source: crates/devflow-core/src/state.rs:198-199, :218, :236
// [VERIFIED: crates/devflow-core/src/state.rs:196-236]
#[serde(default)]
pub last_verification_fingerprint: Option<u64>,
#[serde(default)]
pub verification_baseline_captured: bool,
#[serde(default)]
pub last_verification_mtime_nanos: Option<u64>,
```
`Option<u64>`'s serde default is `None`, which is documented (state.rs:175-218) as the
**conservative** direction for this exact family of field: absent means "don't trust the artifact
as authored," i.e. dispatch `FullExecute`. A new `verification_run_nonce: Option<u64>` following
the same pattern defaults to `None` on an old state file, which is the same safe direction.

### Pattern 2: the `(current, baseline, captured)` tuple-argument shape

**What:** `verification_authored_this_run` deliberately takes plain tuples, not `&State`, and
touches neither the filesystem nor `State` — this is what lets a truth-table test enumerate all
rows without any fixture setup.

**Verbatim current signature** [VERIFIED: crates/devflow-cli/src/pipeline_outcomes.rs:446-450]:
```rust
fn verification_authored_this_run(
    current: (Option<u64>, Option<u64>),
    run_start_baseline: (Option<u64>, Option<u64>),
    baseline_captured: bool,
) -> bool {
```
CONTEXT.md's Established Patterns note ("Adding the nonce follows the same shape") implies this
becomes either a fourth tuple/pair argument or a fourth scalar argument — the doc comment above the
function (pipeline_outcomes.rs:397-445) explicitly states the function "must touch neither the
filesystem nor `[State]`," so the nonce values must be pre-resolved by the caller
(`select_loop_back_fix`) exactly as the fingerprint/mtime pair already are, not read inside the
predicate itself.

### Anti-Patterns to Avoid

- **Reading `State` or the filesystem inside `verification_authored_this_run` itself.** The
  function's own doc comment (pipeline_outcomes.rs:401-404) states this explicitly — the moment it
  touches either, "its four rows [now: more] can no longer be enumerated" by a pure, committed
  truth-table test. Keep the nonce comparison as a value passed in, not a lookup performed inside.
- **Treating a matching nonce alone as sufficient for `authored=true`.** D-02 is explicit that the
  nonce is authoritative for provenance but the fingerprint/mtime remain the staleness signal — a
  design that drops the content check entirely would silently revert what Phase 33's `--gaps-only`
  logic depends on (a change actually occurred). CONTEXT.md's D-04 test scenario (A) requires BOTH
  "nonce matches" AND "fingerprint unchanged" to still be `GapsOnly` — read that as "both signals
  must agree," not "nonce alone decides."

## Common Pitfalls

### Pitfall 1: the "natural capture site" CONTEXT.md names fires once per `devflow start`, not once per Validate dispatch

**What goes wrong:** CONTEXT.md's Integration Points section says the nonce should be "written at
the same point" as `last_verification_fingerprint`/`verification_baseline_captured`. This research
traced that site precisely: it is **`commands.rs:387-401`, inside the `start()` command handler**
[VERIFIED: crates/devflow-cli/src/commands.rs:355-401] — not inside `launch_stage`/
`launch_stage_inner` as the CONTEXT.md canonical-refs list also suggests ("in `launch_stage` or
`evaluate_agent_result`"). This site runs **exactly once per `devflow start` invocation**, before
Define/Plan/Code/Validate have run at all — never again for the rest of that run, including every
subsequent Code→Validate loop-back cycle within the same `devflow start`.

**Why it happens:** `commands.rs`'s comment block explicitly documents this placement as load-
bearing for the fingerprint/mtime baseline ("PLACEMENT IS LOAD-BEARING… Capturing there would
record 'absent' for every worktree run…"), and it is a genuinely correct site *for that field's
job* (recording what the artifact looked like before this whole run started). But a nonce meant to
answer "did **this Validate dispatch** author the artifact" is a different question from "did
**this `devflow start` run** author the artifact" — and 999.89's scenario is explicitly about a
checkout landing **between two Validate dispatches within the same run** (Code stage runs
`/gsd-execute-phase {N}`, potentially followed by another Validate dispatch). A nonce written once
at `devflow start` and never refreshed cannot discriminate cycle 2's dispatch from cycle 1's.

**Independently verified per-dispatch alternative:** every Code→Validate hop calls `transition()`
[VERIFIED: crates/devflow-cli/src/pipeline_gate.rs:52-112], which sets `state.stage = to;` (line
95) and then calls `launch_stage(state, None, Some(from))` as its **last statement** (line 111) —
in the same function call, every single time, including every loop-back cycle. `launch_stage_inner`
[VERIFIED: crates/devflow-cli/src/pipeline_launch.rs:58-149] already has an established precedent
for a per-dispatch reset at this exact call: `state.checkpoint_resumes = 0;` (line 139), documented
as resetting "only [by] `launch_stage_inner`" on "every ORDINARY fresh stage launch." A
`state.stage == Stage::Validate` check immediately before that line, setting
`state.verification_run_nonce = Some(next_value)`, would refresh the nonce on every Validate
dispatch rather than once per run — closing the multi-cycle scenario 999.89 describes, at the cost
of touching a different file (`pipeline_launch.rs`) than CONTEXT.md's discussion implied.

**How to avoid:** the planner should explicitly decide (CONTEXT.md marks this "Claude's
Discretion") between (a) the once-per-`devflow-start` site in `commands.rs` — smaller diff, matches
CONTEXT.md's literal text, closes the original `--force` re-run scenario (999.79) because
`State::new()` zeroes the nonce on a fresh start — or (b) the once-per-dispatch site in
`launch_stage_inner` — closes the narrower, harder within-run multi-cycle scenario 999.89 is
centrally about, at the cost of a second touch point. Given the phase's own success criterion 2 is
worded around "no Validate agent having run" (singular dispatch, not "run" as in the whole
`devflow start` invocation), option (b) is the closer literal match to the stated criterion, but
CONTEXT.md's own worked example test (D-04, scenario A/B) is a pure-function unit test that does
not by itself force either choice — it constructs whatever nonce/fingerprint tuple it wants. Record
whichever is chosen, and why, in the plan's own decision log — this is exactly the kind of thing
`/gsd-code-review` should be asked to double check against 999.89's literal scenario wording.

**Warning signs:** a plan or implementation that captures the nonce only in `commands.rs` and
claims criterion 2 is closed without an accompanying test that specifically exercises a SECOND
Validate dispatch within one simulated run (not just the first) has not actually demonstrated the
multi-cycle case 999.89 names.

## Code Examples

### The current predicate this phase augments

```rust
// Source: crates/devflow-cli/src/pipeline_outcomes.rs:446-470
// [VERIFIED: crates/devflow-cli/src/pipeline_outcomes.rs:446-470]
fn verification_authored_this_run(
    current: (Option<u64>, Option<u64>),
    run_start_baseline: (Option<u64>, Option<u64>),
    baseline_captured: bool,
) -> bool {
    let (current_hash, current_mtime) = current;
    let (baseline_hash, baseline_mtime) = run_start_baseline;
    let written_since_baseline = match (current_mtime, baseline_mtime) {
        (Some(now), Some(baseline)) => now != baseline,
        _ => false,
    };
    match (current_hash, baseline_hash) {
        (None, _) => false,
        (Some(_), None) => baseline_captured,
        (Some(now), Some(baseline)) => now != baseline || written_since_baseline,
    }
}
```

**Why they agree today, and what makes them fragile:** `.planning/config.json` on this branch
carries `"git": {"branching_strategy": "phase", "phase_branch_template": "feature/phase-{phase}"}`
[VERIFIED: .planning/config.json:14-22, read this session]. This is NOT GSD's default — a sibling
`UPSTREAM-GSD-ISSUES.md` entry (see Sources — this project's own tracked symlink target is dangling
in this sandbox; content cross-checked from two sibling `gsd-core` worktree checkouts of the same
file, both agreeing) documents that `git.branching_strategy` defaults to `"none"` when unset, in
which case GSD's `execute-phase` **does not create or switch any branch at all** and simply
continues on whatever branch is currently checked out. This project had that exact failure once
already (phase 28, "all 55 phase-28 commits landed directly on `develop`") and fixed it by setting
`branching_strategy: "phase"` explicitly. **This is a second, independent point of possible drift
beyond the zero-padding coincidence 999.89 names**: if `.planning/config.json`'s
`git.branching_strategy` or `phase_branch_template` keys are ever removed or changed, GSD's branch
computation changes or disappears entirely, independent of any zero-padding logic. The criterion-3
pinning test should assert against the LIVE `init.execute-phase` output (as this research did),
not against a hardcoded assumption that `branching_strategy` stays `"phase"` — a test that
hardcodes the expected string without also confirming `branching_strategy` is still `"phase"` would
pass today and go silently irrelevant if that config key regresses to unset.

     to review, but weaker against the specific multi-cycle scenario) or the per-dispatch
     alternative (stronger match to the literal criterion 2 wording, touches an additional file).
   - Recommendation: resolve explicitly in the plan, with a test that specifically drives a SECOND
     Validate dispatch (not just the first) if the once-per-dispatch design is chosen, or an
     explicit written rationale for why the once-per-run design is accepted as sufficient if not.

   - What we know: D-01 says "a nonce that differs from what was written means Validate did not
     run" — but the nonce lives only in `State` (`.devflow/`, gitignored, immune to checkout), so
     nothing external can ever make it "differ" from itself within one process's view unless a

     `last_verification_fingerprint`'s update pattern at `pipeline_outcomes.rs:389-390`) is
     introduced alongside it.
   - What's unclear: whether this companion "last-authored" value is a new field or whether the
     existing `last_verification_fingerprint`/`last_verification_mtime_nanos` pair already serves
     that role and the nonce is a THIRD, independent gate (e.g., "was `Some` at all," not "matches
     a prior observation").
   - Recommendation: the planner should write out the exact decision table for the augmented
     `verification_authored_this_run` (mirroring the existing 6-row truth table at
     `pipeline_outcomes.rs:3926`) before writing the implementation, the same way the existing
     function's doc comment does — this makes the comparison target concrete and testable.

3. **Should Phase 35.1 merge before Phase 35.2 executes?**
   - What we know: `feature/phase-35.1` is unpushed, unmerged, and edits the same `commands.rs`
     region D-01 targets (Pitfall 2).
