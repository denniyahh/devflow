# Phase 35.3: Drain Gate Concurrency Measurement — Context

**Gathered:** 2026-08-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Get a real, evidence-based answer to whether the drain gate — the v2.4.0 stream-json safety net —
actually observes concurrent child work. This is investigation-shaped: design and run the right
experiment, then record what it found, rather than apply a predetermined fix.

The honest result may be negative ("the gate does not see concurrency"), and a negative is a valid
deliverable — it must be recorded as-is, not assumed away.

**In scope:**
- A measurement that establishes which event families the Claude CLI actually emits for each kind
  of concurrent child work — sub-agent dispatch and backgrounded shell — from live production
  evidence, n>1 where feasible
- An honest, version-pinned record of the answer, including negative/inconclusive results
- The per-phase Validate-failure count observation (the same ask 35.1's criterion 6 made)

**Out of scope:**
- Widening `CloseRule::observe` itself. If the measurement confirms the refutation, the widening
  is a SEPARATE `999.x` backlog item, not part of this phase. This phase delivers the measurement
  record; it does not implement the fix.
- A CLI version matrix. Pin to the current CLI version and record it; do not chase a range.
</domain>

<decisions>
## Implementation Decisions

### Evidence-gathering method

- **D-01:** Use a drill-style disposable fixture (the 35.1 `unattended-drill.sh` pattern), not a
  live dogfood run. A drill controls the workload shape — it can force both the sub-agent path and
  the backgrounded-shell path deterministically — and it is repeatable to n>1, where Phase 34's
  live-run approach produced exactly one observation.

  The drill inherits 35.1's precedent: same throwaway-fixture scaffolding, same
  refuse-to-scaffold-inside-this-checkout destination guard (T-23-01), same capture-to-evidence-file
  flow. It is smaller than 35.1's: scaffold a throwaway repo, launch `claude -p` against a prompt
  that deliberately dispatches sub-agents AND backgrounds a shell, capture the raw stream, and count
  the `background_tasks_changed` / `task_started` / `task_progress` / `task_notification` events.

  **The synthetic-prompt caveat is load-bearing.** A drill prompt is synthetic, and Phase 34's whole
  refutation is that the synthetic fixture does not match what production emits. The drill must
  therefore be paired with at least one real capture (a real GSD `execute-phase` workflow) to
  validate that the synthetic prompt triggers the same event families the real one does. The
  synthetic prompt establishes the event-family mapping; the real capture confirms it is the right
  mapping to have established.

### Event-family coverage

- **D-02:** Cover BOTH concurrent-work mechanisms, because they are mechanistically different and
  one is untested:
  1. **Sub-agent dispatch** (`Agent` tool → `task_started`/`task_progress`/`task_notification`) —
     Phase 34 already refuted this path (8 dispatches, zero `background_tasks_changed`). The goal
     here is to *confirm* that refutation at n>1, not re-establish it.
  2. **Backgrounded shell** (`Bash` with `run_in_background: true`) — never exercised by Phase 34,
     and its "what this does not establish" section flags this explicitly as the one path where
     "the gate may well work exactly as designed."

  The gate keys on exactly one event shape (`type: "system", subtype: "background_tasks_changed"`,
  `tasks: [...]`). If backgrounded shells emit it but sub-agents do not, the gate is only half-blind,
  and that materially changes the widening decision. Covering only the sub-agent path would leave
  the most interesting unknown unanswered.

### On confirmation of refutation

- **D-03:** If the measurement confirms production does not emit `background_tasks_changed` for one
  or both paths, the widening of `CloseRule::observe` is filed as a **separate `999.x` backlog
  item**, not performed inside this phase. The phase delivers the measurement record and the backlog
  filing; it does not implement the fix.

  Rationale: the widening is itself a small design problem with its own correctness questions
  (event-family mapping, `task_type: local_agent` recognition, terminal-status tracking against
  `TERMINAL_TASK_STATUSES`, arity). Bundling that into an observation phase turns observation into
  implementation. This also keeps the phase small, matching the operator's decision that this work
  does not merit a whole phase to itself (renumbered 36 → 35.3).

### CLI version

- **D-04:** Pin to the current CLI version and record it in the evidence. Do not build a version
  matrix. A version-pinned negative ("on CLI X, sub-agent dispatch emits no
  `background_tasks_changed`") is actionable — it says *your current CLI* does not feed the gate.
  A matrix would only matter to prove a historical claim, and nothing here needs one.

### Claude's Discretion

- The exact fixture prompt text and the number of repetitions (n) — the plan should aim for n≥2 per
  path where the run cost permits, and record the actual n honestly.
- Whether the real capture rides on an existing dogfood run or a dedicated minimal
  `devflow start --no-worktree` probe (Phase 34's `34-evidence/` README records the layout and PII
  scrub conventions to reuse).
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`scripts/unattended-drill.sh`** — the 35.1 drill: throwaway fixture scaffolding, T-23-01 destination guard, two-arm structure, evidence-file writing. This phase's drill is a smaller single-path variant of it.
- **`34-evidence/` layout** — `raw_output.jsonl` + `run.log` + `stderr.log` per stage, with the PII scrub (`home_path`/`os_username`/`session_identifier`) and the required `run.log` fields (argv, stage, CLI version, build commit, outcome).
- **`BackgroundTaskState` / `CloseRule::observe`** — the code the measurement is *about*. The event-key shape to count (`type: "system", subtype: "background_tasks_changed"`) and the synthetic fixture's `task_type: "local_agent"` value.

### Established Patterns
- **Synthetic-vs-production validation** — a synthetic fixture must be validated against at least one real capture, or its measurement is a proxy for the fixture, not for production (the exact lesson Phase 34's DRAIN-ANALYSIS records).
- **Negative results are results** — Phase 34 recorded the refutation instead of assuming the answer resolved toward "the gate works." This phase inherits that posture.
- **PII scrub before commit** — anything copied into `.planning/` is a permanent public artifact on push; the three-field scrub (`home_path`, `os_username`, `session_identifier`) is mandatory.

### Integration Points
- The drill produces capture files that land in the phase's own evidence directory (following `34-evidence/`), not in `.devflow/` — copy out, never `git add -f` the live capture.
- If the measurement confirms the refutation, the output includes a new `999.x` backlog entry (the widening), filed through the normal backlog path — but the widening itself is not implemented here.
</code_context>
