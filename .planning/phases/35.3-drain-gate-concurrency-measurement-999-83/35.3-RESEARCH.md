## Summary

This phase changes **no production logic** — the widening already landed (`47ea511`). It is a
measurement: build a disposable drill that forces each concurrent-work path, capture the raw
`stream-json`, count which event families the current CLI actually emits, validate the synthetic
prompt against one real capture, and record the answer honestly (a negative is a valid
deliverable). The only possible code edit is a **doc-comment correction** to the synthetic
fixture's provenance label (criterion 3).

**Three facts this research established that the plan must build on:**

1. **The drain gate is now two arms ANDed, and the two arms read different event families.**
   `should_close()` requires `marker_seen` AND `background_tasks` ∈ {`NeverAnnounced`,
   `Pending(0)`} AND `open_tasks.is_empty()`. The `background_tasks_changed` arm is the legacy
   synthetic signal; the `open_tasks` arm is `47ea511`'s addition reading the per-task vocabulary
   (`task_started`/`task_progress` open, `task_notification`/`task_updated` close).

2. **`background_tasks_changed` is a *legacy* event family, not an invented one.** The fixture's
   provenance claim is real: Phase 30's archived capture (`30a-evidence/raw_output_v3.jsonl`, an
   older CLI) contains 4 `background_tasks_changed` events, including line 8 with
   `task_type: "local_agent"` and line 44's drained `tasks: []`. The current CLI (2.1.222 / 2.1.228)
   does **not** emit it — 34-evidence (1063 events, 0 occurrences) and 47ea511's capture
   (`task_started` ×1, `task_progress` ×61, `task_notification` ×1, `task_updated` ×1,
   `background_tasks_changed` ×0) both show this. So the drain arm regressed from "reads a real
   event" to "reads a vacuous event" between CLI versions, and `47ea511` compensated with the
   per-task arm. Criterion 3's "correct the SYNTHETIC fixture label" is therefore a **CLI-version
   pin on the fixture's provenance comment**, not a fabrication retraction.

3. **The backgrounded-shell path is genuinely unmeasured.** 34-evidence recorded 8 `Bash` calls,
   all `run_in_background: false` — zero `true`. No capture anywhere in this repo shows what a
   `run_in_background: true` shell emits. That is D-02's "most interesting unknown," and the drill
   must make a genuine attempt to force it.

### Pattern 1: the two-armed close rule (what the measurement is about)

`CloseRule` (monitor.rs ~590-660) ANDs three conditions. The `background_tasks_changed` arm reads
the **synthetic** drain signal; the `open_tasks` arm (added in `47ea511`) reads the **per-task
vocabulary the CLI actually emits**. The doc comment at monitor.rs ~589-593 records the production
capture that motivated it: `task_started` ×1, `task_progress` ×61, `task_notification` ×1,
`task_updated` ×1, `background_tasks_changed` ×0, and states "Every occurrence of
`background_tasks_changed` in this repository is a test fixture synthesising it."

### Pattern 2: the synthetic fixture's provenance (criterion 3's correction target)

The close-rule test fixtures (monitor.rs ~1330-1360) claim their shapes come from
`.planning/phases/30-keep-the-session-alive-past-turn-end/30a-evidence/raw_output_v3.jsonl` lines
5, 8, 19, 44, 54. **This session verified that claim is TRUE for that capture** — line 8 is
`background_tasks_changed` with `tasks:[{task_id, task_type:"local_agent", description}]`, line 44
is the drained `tasks:[]`. But that capture is from the **Phase 30-era CLI**. The current CLI does
not emit this family. The fixture comment does not say which CLI produced the capture, so a reader
could mistake a legacy shape for a current one — exactly the confusion criterion 3's label
correction exists to remove.

### Pattern 3: the drill's launch shape

The drill must reproduce DevFlow's own launch verbatim so the measurement is of the *same* child
argv DevFlow runs (claude.rs:40-68): `claude -p --input-format stream-json --output-format
stream-json --verbose --dangerously-skip-permissions`, with the initial user turn written to stdin
as `{"type":"user","message":{"role":"user","content":<prompt>}}` (monitor.rs `user_turn_line`).
A drill that launches `claude` with a different argv measures a different child.

### Anti-Patterns to Avoid

- **String-grep event counting.** The 35.1 drill's `captures_contain` false-positived by matching
  GSD reference-doc strings that every agent reads during Plan. Count events by **parsing each
  JSON line and reading `type`/`subtype`/`task_type`/`run_in_background`**, with a positive
  control (a family known to be present) so a zero is a real zero, not a broken probe (34-evidence
  did exactly this and documented it in the `BackgroundTaskState` run.log line).
- **Assuming the answer resolves toward "the gate works."** 34-evidence's whole posture is
  "record the refutation as-is." A negative ("backgrounded shells emit neither vocabulary") is a
  valid, actionable deliverable. The plan must pin honesty, not a direction.
- **Committing the live capture from `.devflow/`.** `.devflow/.gitignore` is `*`; the correct
  route is copy-out-then-commit, never `git add -f` (34-evidence README).
- **Running the drill inside this checkout.** T-23-01: the destination guard must refuse any
  path inside the worktree AND the primary checkout (the 35.1 drill widened this beyond
  `scratch-dogfood-repo.sh`'s original guard; inherit the widening).

## Common Pitfalls

### Pitfall 1: the fixture's provenance is real but stale — do not "fix" it by deleting it

The synthetic fixture's comment is **correct** about its source (Phase 30's capture really did
emit `background_tasks_changed`). A naïve correction that replaces the provenance note with "this
event family is invented" would be *wrong* — it is a real, observed, legacy family. The correct
correction is a **CLI-version pin**: state that the shape is from the Phase 30-era capture, that
the current CLI (2.1.228) does not emit it, and that the per-task arm (`observe_task_event`) is
what tracks the current vocabulary. Verify against the drill's own capture before writing it.

### Pitfall 2: `run_in_background: true` may not be forceable — and that is a finding, not a failure

A synthetic prompt can *ask* the agent to background a shell, but whether the CLI honors it (and
what it emits) is exactly the unknown. The drill must (a) request it explicitly, (b) record
whether any emitted `Bash`/tool event actually carries `run_in_background: true`, and (c) record
a negative honestly if the CLI refuses or runs it synchronously. "The backgrounded-shell path
cannot be produced by a synthetic prompt" is itself evidence about what the drill can and cannot
establish (criterion 4's scope statement).

### Pitfall 3: one real capture is the minimum, not the goal

D-01 requires *at least* one real capture to validate the synthetic mapping. A real `devflow
start` run is expensive and may stop short of the concurrent stages (35.1's drill never reached
Validate). Prefer a dedicated minimal `devflow start --no-worktree` probe on a scaffolded
single-file phase (34's precedent) so the workload is controlled, and record which stages it
actually reached — a capture that never dispatched a sub-agent validates nothing about
sub-agent dispatch.

### Pitfall 4: `cargo test` is not the verification surface for this phase

This phase's deliverable is evidence, not a code behavior change. The only code edit (the
doc-comment correction) changes no testable behavior; `cargo test` verifies it did not break
compilation, not that the measurement is right. Do not write a `cargo test` that asserts the
measurement's answer — that would encode the untested assumption as a fixture again (the exact
defect 999.83 names). The verification is the evidence record's internal consistency (counts,
positive controls, scope statement).

## Code Examples

### The gate under test — `should_close` and the task-vocabulary fold (verbatim shape)

```rust
// crates/devflow-core/src/monitor.rs (~613-660)
pub fn observe(&mut self, line: &str) {
    let Ok(event) = serde_json::from_str::<serde_json::Value>(line) else { return };
    if crate::agent_result::event_is_top_level_result_marker(&event) { self.marker_seen = true; }
    if event.get("type")… == Some("system")
        && event.get("subtype")… == Some("background_tasks_changed") {
        self.background_tasks = match event.get("tasks")… {
            Some(tasks) => BackgroundTaskState::Pending(tasks.len()),
            None => BackgroundTaskState::Unreadable,
        };
    }
    self.observe_task_event(&event);
}

fn observe_task_event(&mut self, event: &serde_json::Value) {
    // task_started | task_progress  → open_tasks.insert(task_id)
    // task_notification | task_updated → status ∈ TERMINAL_TASK_STATUSES
    //   ? open_tasks.remove(task_id) : open_tasks.insert(task_id)
}

const TERMINAL_TASK_STATUSES: &[&str] =
    &["completed","killed","failed","stopped","cancelled","canceled","error"];

pub fn should_close(&self) -> bool {
    self.marker_seen
        && matches!(self.background_tasks,
                    BackgroundTaskState::NeverAnnounced | BackgroundTaskState::Pending(0))
        && self.open_tasks.is_empty()
}
```

## Open Questions

1. **What does a `run_in_background: true` shell actually emit?** Unknown by construction — no
   capture in the repo shows it (34-evidence: 8 `Bash` calls, all `run_in_background: false`).
   This is the phase's primary open question; the drill exists to answer it. The honest possible
   answers: (a) `task_started`/`task_progress` (the per-task arm already covers it), (b)
   `background_tasks_changed` (the legacy arm covers it — would contradict 34/47ea511 for
   sub-agents but not for shells), (c) neither (the widened gate is still blind to this path →
   file a 999.x backlog item), or (d) not forceable synthetically.

2. **Does the sub-agent path's n>1 measurement confirm 47ea511's n=1 capture?** 47ea511's
   per-task vocabulary is from one Plan-stage capture. n≥2 sub-agent dispatches across ≥2 runs
   will confirm or perturb that mapping.

3. **Can the real capture be produced deterministically?** A dedicated `devflow start
   --no-worktree` probe on a scaffolded single-file phase is deterministic but small; a real
   dogfood run is rich but uncontrolled. D-01 leaves this to the planner; the research
   recommendation is the dedicated probe (34's precedent), recorded with which stages it reached.
