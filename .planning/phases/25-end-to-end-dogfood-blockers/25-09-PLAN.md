<objective>
Close GAP 2 of `25-VERIFICATION.md`: truth 5 — "`release_range_start`'s commit-range anchor
stays correct (excludes pre-release develop history) across realistic release topologies" —
is FAILED.

**CR-03**, independently confirmed by the verifier from source (`version.rs:258-313`):
the function inspects only the ancestry path's FIRST commit (`C1`) and tests whether the
baseline tag is an ancestor of `C1`'s first parent. When a commit lands directly on trunk
between the tag and the sync-merge-back (a hotfix pushed straight to `main`, or a tag not
sitting on the literal last pre-sync commit), that intervening commit becomes `C1`; its
first parent IS the tag commit, so `git merge-base --is-ancestor <tag> <tag>` trivially
returns true, the function concludes the tag already sat on mainline, and it returns the
literal `tag..HEAD` range — reintroducing exactly the measured "677 non-merge commits,
62 `feat`" pathology the whole D-08 amendment was built to eliminate.

Neither existing regression test constructs this topology.

Purpose: make the anchor robust to every release topology this repository can actually
produce, not just the two its current fixtures happen to build.
Output: a generalized anchor rule, two new real-git topology fixtures, and a live-history
check proving the change is behavior-preserving on today's actual repository.
</objective>

<deviation_from_verification_missing_entry>
**READ THIS BEFORE TASK 2. This plan deliberately does NOT implement the fix sketch
quoted in `25-VERIFICATION.md` and `25-REVIEW.md`, because that sketch is wrong on this
repository's real history. The deviation is evidence-backed, measured live, and pinned by

`25-REVIEW.md` CR-03's sketch (echoed verbatim in `25-VERIFICATION.md`'s `missing:` list)
says: *"walk the whole `--ancestry-path` list and anchor at the **last** merge commit in it
(the commit with more than one parent, closest to `HEAD`), falling back to `baseline_tag`
only when the ancestry path contains no merge commit at all."*

`GitFlow::merge_feature_into_develop` (`crates/devflow-core/src/git.rs:86`) merges every
phase branch into `develop` with `git merge --no-ff`, so **ordinary post-release work
produces merge commits on the ancestry path too** — not just the sync-merge-back. Measured
against this repository on 2026-07-28, `git rev-list --ancestry-path --reverse v2.0.0..develop`
returns, oldest first:

| # | commit | subject | parents |
|---|--------|---------|---------|
| 1 | `c92229e` | `merge: sync main back into develop after release` | 2 |
| 2 | `c20b198` | `Merge pull request #45 from …/sync/main-to-develop-v2.0.0-retry` | 2 |
| 3 | `7c6fcbf` | `docs: file 999.52 sync gap, re-size 25b …` | 1 |
| 4 | `819987b` | `Merge pull request #46 from …/fix/sync-gap-and-25b-sizing` | 2 |

The correct anchor is `c92229e`. The literal "last merge commit" rule returns **`819987b`**,
whose range `819987b..HEAD` **silently drops `7c6fcbf`** from classification. Today that
dropped commit is a `docs:` commit and the version is unaffected; a `feat!:` in that same
position would be dropped instead — a false negative that lets a major bump ship unattended,
which is precisely the failure D-09 exists to prevent. The sketch would therefore trade
CR-03 for a strictly worse defect.

**The rule this plan implements instead** is a strict generalization of the CURRENT
predicate — the same first-parent test, applied to every commit on the ancestry path
instead of blindly to `C1`:

> Walk the ancestry path oldest-first and return the FIRST commit `C` for which the
> baseline tag is NOT an ancestor of `C`'s first parent (or for which `C` has no first
> parent at all). If no commit qualifies, return `baseline_tag`.

Verified against the same live path (`git merge-base --is-ancestor v2.0.0 <C^1>`):
`c92229e` → NO (qualifies, returned), `c20b198` → NO, `7c6fcbf` → YES, `819987b` → YES.
The rule returns `c92229e`, matching both the correct answer and what the current code
already returns today. The change is therefore **behavior-preserving on this repository's
present history** and only differs in the topologies the current code gets wrong.

Task 1's second test (`feature_merge_after_sync_merge_does_not_move_the_anchor`) exists
solely to pin this deviation: it is GREEN under the current code and GREEN under the rule
above, and goes RED under the literal "last merge commit" sketch. Do not "simplify" the
implementation into the sketch — that test is the tripwire.

Replace `release_range_start`'s `C1`-only heuristic with the generalized walk. Keep the
public signature exactly as it is:
`pub fn release_range_start(project_root: &Path, baseline_tag: &str) -> Result<String, VersionError>`.

Implementation shape:
- Keep the existing `git rev-list --ancestry-path --reverse {baseline_tag}..HEAD` spawn and
  its existing `VersionError::Git` error mapping byte-for-byte. Collect ALL non-empty lines
  into a `Vec<String>` (oldest first) instead of taking only the first.
- If the vector is empty, return `Ok(baseline_tag.to_string())` — unchanged semantics
  ("nothing after the tag; it sits at HEAD").
- Iterate the vector in order (oldest first). For each candidate commit `c`:
  - Run `git rev-parse {c}^1`. If it exits non-zero, `c` is a root commit with no first
    parent — return `Ok(c)`, preserving the existing root-commit branch's behavior exactly
    (today's code returns `c1` in that case).
  - Otherwise run `git merge-base --is-ancestor {baseline_tag} {first_parent}`, mapping a
    spawn failure to `false` via `.map(|out| out.status.success()).unwrap_or(false)` — the
    same expression the current code uses; do not change its fail-closed behavior.
  - If the tag is NOT an ancestor of `c`'s first parent, `c` is where the tag's line joined
    HEAD's line — return `Ok(c)` immediately. This is the sync-merge-back.
  - Otherwise `c` is on the mainline the tag already sat on: continue to the next candidate.
- If the loop completes with no qualifying candidate, return `Ok(baseline_tag.to_string())`
  — the ordinary, non-squashed release case, unchanged from today.

`fn first_parent(project_root: &Path, commit: &str) -> Result<Option<String>, VersionError>`
