## MEASURED CORRECTION to D-08's commit range — read before Task 1

D-08 specifies classification over `--no-merges` commits in `baseline..HEAD`. That literal
range was **measured against this repository on 2026-07-27 and produces a wrong answer**,
for a structural reason that will recur on every future release:

| Range | Non-merge commits | Oldest | `feat` count | Classified bump |
|---|---|---|---|---|
| `v2.0.0..HEAD` (D-08 literal) | **677** | 2026-06-20 | **62** | minor → `2.1.0` — WRONG |
| `c92229e..HEAD` (anchored, see below) | **5** | 2026-07-27 | 0 | none → patch floor → `2.0.1` — correct |

**Why.** Every release squash-merges `develop` → `main`, so **no develop-side commit is
ever an ancestor of any release tag**. The `-X ours` sync merge-back restores ancestry in
the other direction only: the tag becomes an ancestor of `HEAD` (which is what makes D-07's
reachability filter work), but the commits the tag *released* stay outside its ancestry.
`baseline..HEAD` therefore re-includes the entire pre-release history, permanently and
monotonically — `v1.8.1..HEAD` is 678 of the repository's 796 total non-merge commits.

**Why it is not merely cosmetic.** The moment any commit anywhere in project history carries
`!` or a `BREAKING CHANGE:` footer, it stays inside every future range forever, so D-09's
major-bump gate would fire on **every subsequent ship** — converting the unattended run this
phase exists to unblock into a permanent halt.

**The correction, and why it is not a re-litigation of D-08.** D-07 (baseline = highest
reachable semver tag) is unchanged; D-08's classification rule (conventional-commit
precedence) is unchanged. Only the *set of commits fed to the classifier* changes, restoring
D-08's evident intent — "the commits added since the last release". `--first-parent` was
measured and does **not** fix it (383 commits). The two-branch anchor below was verified
correct on both topologies present in this repository.

**Anchor rule (verified live, 2026-07-27):**
- Let `C1` = the earliest commit on the ancestry path from the baseline tag to `HEAD`
  (`git rev-list --ancestry-path --reverse <tag>..HEAD`, first line).
- If `C1` does not exist → range start is the tag (tag is at `HEAD`).
- If the tag is an ancestor of `C1`'s **first parent** → the tag already sat on this
  mainline; range start is the **tag**. (`git merge-base --is-ancestor` is reflexive, so
  the ordinary non-squashed case takes this branch and is unchanged.)
- Otherwise the tag entered `HEAD`'s history through `C1` (the sync merge-back); range
  start is **`C1`**.

Verified: for `v2.0.0`, `C1` = `c92229e` (`merge: sync main back into develop after
release`), whose first parent `d2831a1` does **not** have `v2.0.0` as an ancestor → range
start `c92229e` → 5 commits. For the ordinary pair `v1.8.0..v1.8.1`, `C1` = `229ece2` whose
sole parent **is** `v1.8.0`'s commit → range start is the tag → unchanged behaviour.

This also strengthens D-12: the sync merge is now load-bearing in a *second* way — it is
the range anchor, not only the ancestry restorer. 999.52 stays in the backlog; D-10's
refuse-on-unreachable remains the mitigation.
</measured_correction>
