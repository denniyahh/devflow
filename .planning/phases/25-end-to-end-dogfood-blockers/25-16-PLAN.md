<objective>
Stop this phase's own test suite from manufacturing the orphan class the phase exists to eliminate.

`mid_run_stage_transition_does_not_readjudicate_staleness` (25b, `staleness.rs:689-786`) drives a
real `launch_stage_inner`, which spawns a real detached monitor wrapper with stdio on `/dev/null`,
asserts its result, reads some events, and returns. The wrapper is never recorded, never signalled,
never waited on. The test's `TempDir` guard then deletes the project root out from under it. That is
999.44's reproduction shape verbatim, produced on every `cargo test --workspace` run. Two
independent counts on this machine — 21 (reviewer) and 22 (verifier) live `trap cleanup TERM INT`
processes, several rooted at deleted `/tmp/.tmp*` paths — are consistent with exactly that.
`pipeline_launch.rs:395-431` has the identical omission and the shared fix.

Purpose: this is a Warning, not a gap, and it is folded into this round for one concrete reason
rather than tidiness. `25-15-PLAN.md` — the CR-01 fix, running in parallel in this same wave —
asserts against a live `/proc` census. A machine whose stray population is replenished by every full
suite run is a worse instrument for that assertion, and every leaked wrapper is a live Layer-1
match in every subsequent census read. The verifier said so directly: the leak *"actively degrades
confidence in any future CR-01 fix's own test suite until closed."*

Output: one shared `#[cfg(test)]` reap helper, wired into both launch-driving tests, with verified
death and no weakening of either test's existing assertions. Test-only; no production behaviour
changes.
</objective>

<scope_boundary>
**This plan changes test code only. It must not change production behaviour.**

Specifically it must NOT: change `launch_stage_inner`, change `monitor::spawn_monitor`, change when
or whether `state.monitor_pid` is written, or add any teardown to production paths. The monitor
wrapper is *supposed* to outlive the call that spawned it — that is the design. What is wrong is
that a TEST spawns one and abandons it.

If closing the leak appears to require a production change, that is a finding: stop, record it, and
report rather than widening the diff. `git diff` for this plan must show changes confined to
`#[cfg(test)]` regions and to the `#[cfg(test)]`-gated `test_support` module.
</scope_boundary>

<abstraction_note>
A shared helper for two call sites is close to the "no abstractions for single-use code" line, so
the choice is recorded rather than assumed.

`crates/devflow-cli/src/test_support.rs` already exists for exactly this purpose — it is declared
`#[cfg(test)] mod test_support;` on the `mod` item in `main.rs` (so the non-test binary never
compiles it) and it already holds `ENV_MUTEX`, `init_repo`, `stub_agent_binary`, `prepend_path` and
`stage_launched_count`, all shared across sibling test modules since the 19c–19f split. It already
imports `devflow_core::state::State`, which is the helper's only parameter type. Adding one function
there costs no new module, no new import, and no new visibility surface.

The alternative — an inline reap block duplicated at both sites — was considered and rejected:
`25-REVIEW.md` §WR-03 recommends the shared helper explicitly ("so no future test that drives a
launch path can forget it"), the two sites are in different modules so the duplication cannot be
seen from either, and the correct block is not one line (it must handle `Option`, escalate rather
than bare-`SIGTERM`, and verify death). Duplicating a three-part discipline is how the second site
drifted from the first in the first place.
</abstraction_note>
