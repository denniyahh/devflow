**Decision: BOTH the test-side barrier (this plan) and a production tolerance (plan 25-12)
are in scope. The production window is reachable. Stated, justified, and not assumed either
way — which is the failure mode `25-CI-OBSERVATION.md` §"Limits of this evidence"
deliberately refused to commit on.**

`25-CONTEXT.md` **D-02** states 999.47's production risk is already closed, because
`looks_like_devflow_process` has *no production callers* — `stop` moved to
`lock::holder_identity`'s recorded `(pid, starttime)` pair. **That was accurate on
2026-07-27, about `stop`.** It was then invalidated by this phase's own 25d work
(**D-17**): plans 25-02 and 25-07 introduced `agent::discover_stray_devflow_processes`, a
**new** `/proc`-cmdline-derived inference, in production, with two live consumers —
`commands::gate_sweep`'s `--reap-strays` pass (`commands.rs:1149-1151`) and `doctor`'s
`collect_stray_process_findings` (`commands.rs:2998-2999`). D-13's own reasoning applies to
it verbatim: *"Any `/proc`-derived inference races exec."*

The reachable production hazard is the **false-positive** direction, and it is destructive:

1. `monitor::spawn_monitor_inner` (`monitor.rs:134-160`) spawns `sh -c <script>` where the
   script contains `MONITOR_WRAPPER_MARKER` verbatim.
2. That wrapper shell forks for the agent (`"$@" ... &`) and again for the trailing
   `devflow advance`. `agent.rs`'s own doc comment (`:175-187`) states the rule: between
   `fork()` and `execve()` *"the child is a copy of its parent: `/proc/<pid>/cmdline`
   reports the PARENT's argv."*
3. So each of those transient children, mid-window, presents `sh`, `-c`, and a script
   containing the marker — exactly `classify_stray_layer`'s Layer 1 test
   (`agent.rs:373-380`). It is classified `MonitorWrapper`. Symmetrically, a child forked by
   `devflow advance` presents argv[0] basename `devflow` and argv[1] `advance` — Layer 2.
4. `reap_stray_candidates` (`commands.rs:1273-1314`) re-confirms `is_same_process`. That
   guard **passes**: it is genuinely the same process with the same start time. The guard
   defends against pid *recycling*, not against fork-inheritance.
5. `terminate_and_verify` then sends `SIGTERM`, escalating to `SIGKILL`.

Net: `devflow gate sweep --reap-strays` can kill a healthy, just-launched agent or monitor.
The test at `commands.rs:3663-3667` states outright that this command is expected to run
while *"this machine's live process table legitimately contains other, unrelated devflow
activity (concurrent phases in sibling worktrees)"* — so the co-occurrence this needs is not
hypothetical, it is the documented operating condition.

The **false-negative** direction (the test-side shape: a census miss during the window) is
NOT a production concern — a process created microseconds ago is by construction not a
stray, and `gate_sweep` re-runs discovery after each pass. So the production mitigation
targets the false-positive direction only, and it lives in plan 25-12, not here.

**This plan is scoped to (a), the test-side barrier.** It is what unblocks the push.
</scope_decision>

**Step 2 — write the barrier's tests first (RED), then the barrier.**

In `crates/devflow-core/src/agent.rs`, add the four tests described in `<behavior>` to the

Then add, next to `process_start_time` and `is_same_process`:

- `pub const EXEC_VISIBILITY_WAIT: std::time::Duration` — 10 seconds. Rationale to state in
  the doc comment: the window is sub-millisecond in the normal case and returns immediately,
  so a generous ceiling costs nothing; the ceiling exists only so a pathological case fails
  loudly instead of hanging a test binary.
- `pub const EXEC_VISIBILITY_POLL: std::time::Duration` — 2 milliseconds.
- `pub fn wait_for_exec_visibility(pid: u32, expected_argv0_basename: &str, wait: std::time::Duration, poll: std::time::Duration) -> bool`

Its contract, in the doc comment, in this codebase's own voice: it polls `/proc/<pid>/cmdline`
until the named process's argv is its OWN, and returns whether that happened within `wait`.
It returns `true` only when BOTH hold: (i) argv[0]'s basename equals
`expected_argv0_basename`, using the same `argv_basename` helper `classify_stray_layer` uses,
and (ii) the observed argv is not byte-identical to the caller's own `/proc/self/cmdline`.
Condition (ii) is the guard against the degenerate case where the caller's own argv[0]
basename happens to equal `expected_argv0_basename` — it makes the barrier's answer
unambiguous rather than probabilistically-correct. Parse the NUL-separated cmdline with the
same idiom `discover_stray_devflow_processes` uses at `:337-341`. An unreadable cmdline is
not a failure — keep polling until `wait` elapses, because a pid that is not yet readable is
exactly the state being waited out.

Cross-reference the doc comment to `process_start_time`'s 999.47 explanation rather than
restating the mechanism, and state plainly that this is the barrier a test must cross before
asserting on a `/proc`-cmdline census, and that `agent_running` is NOT such a barrier
because `kill(pid, 0)` succeeds for a forked-but-unexec'd child.

<threat_model>
ASVS level 1; blocking threshold: `high`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| kernel `/proc` -> `devflow-core` | argv bytes read from another process's `/proc` entry are attacker-influenced on a shared machine and are parsed as UTF-8-lossy strings |
| test fixture -> the process table | a test spawns a real process on the developer's or runner's live machine, where unrelated DevFlow activity legitimately runs |
| new public API -> published crate consumers | `devflow-core` has no `publish = false`; anything added to `pub mod agent` becomes public API of a published crate |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-25-11-01 | Tampering | the barrier masking a real defect | high | mitigate | The barrier is bounded by `EXEC_VISIBILITY_WAIT` and returns `bool`; every call site asserts on the return with a pid-naming message, so a timeout is a named failure. Acceptance requires reading each call site to confirm the result is consumed, not discarded |
| T-25-11-02 | Spoofing | `/proc/<pid>/cmdline` of a recycled pid | medium | accept | The barrier is only ever called on a `Child` the caller owns and has not yet reaped, so the pid cannot be recycled while the handle is alive. Documented in the function's doc comment; `is_same_process` remains the guard for any pid not owned by the caller |
| T-25-11-03 | Spoofing (degenerate self-match) | caller's own argv[0] basename equals `expected_argv0_basename` | medium | mitigate | Condition (ii): the observed argv must also differ from the caller's own `/proc/self/cmdline`. Behaviour test 4 asserts a self-pid call returns `false` even when the basename matches by construction |
| T-25-11-04 | Elevation of Privilege | new public API on a published crate | medium | mitigate | Additive only — no existing public signature changes, so `git-conventional` classification stays non-breaking and D-08's classifier is not tripped. | T-25-11-05 | Information Disclosure | reading `/proc` of an arbitrary pid | low | accept | Read-only, returns a `bool`, discloses nothing to a caller that could not already read the same file. Mirrors `process_start_time`'s existing posture |
| T-25-11-06 | Denial of Service | an unbounded poll hanging the test binary | high | mitigate | `wait`/`poll` are required parameters with a bounded ceiling; behaviour tests 2 and 3 assert it returns within roughly `wait` for both a never-matching pid and a dead pid |
| T-25-11-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan adds **no dependency**. `libc` and `tempfile` are already in the workspace.
