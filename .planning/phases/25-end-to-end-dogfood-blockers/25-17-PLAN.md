<objective>
Make the monitor reap survive an unwind at both sites 25-16 fixed, by replacing a plain trailing
call with an RAII `Drop` guard bound before the assertions.

25-16 wired `reap_spawned_monitor(&state)` into two launch-driving tests and stated the must-have
that the reap runs "on every exit path — including paths on which a later assertion panics." The
call it wrote cannot do that. In `pipeline_launch.rs` the reap at `:440` stands behind four
panicking checkpoints (`:423`, `:425`, `:429`, `:430`); in `staleness.rs` the reap at `:802` stands
behind two (`:777`, `:792`). Rust abandons the remaining statements the moment a panic begins
unwinding, so the reap runs on the success path and only on the success path — precisely inverted
from where it is needed. If a future regression reintroduces the bug either test exists to catch,
the assertion that detects it panics first, and the test that was written to prevent orphaned
monitor wrappers manufactures a fresh one on its way out, against a project root the `TempDir` is
about to delete. That is 999.44's reproduction shape, produced by the guard against it.

Purpose: close G-25-2 / WINDOWS.md item 3 by moving the reap into a destructor, where the language
runs it on both exit paths, and prove that it actually does with a test that fails if it does not.

Output: one `ReapMonitorOnDrop` guard and one shared private reap in `test_support.rs`, two
discriminating tests (guard-reaps-on-unwind, plus a control proving the trailing form does not),
and both existing call sites converted. Test-only; no production behaviour changes.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test process → OS process table | The guard sends `SIGTERM`/`SIGKILL` to a pid. A wrong pid signals someone else's process. |
| test process → its own children | A spawned `sleep 300` becomes a zombie if never waited on. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-25-17-01 | Denial of Service | `ReapMonitorOnDrop::drop` → `terminate_and_verify` | high | mitigate | The pid is only ever the one the guard captured from `state.monitor_pid`, which the test's own launch wrote. `terminate_and_verify` and `agent_running` both reject `pid <= 0` and out-of-`pid_t` values before signalling, so a `0` can never reach `kill` and signal the caller's whole process group, and a wrapped-negative can never reach `kill(-1, …)`. No scanning, no `/proc` sweep, no pid guessed or reused. |
| T-25-17-02 | Denial of Service | `Drop` panicking during an unwind | high | mitigate | A panic in `Drop` while unwinding calls `abort()`, killing the test binary and destroying the results of every other test in the process. The `std::thread::panicking()` interlock downgrades the survivor complaint to `eprintln!` on that path. Verified by Task 1's guard test, which drops the guard during a real unwind. |
