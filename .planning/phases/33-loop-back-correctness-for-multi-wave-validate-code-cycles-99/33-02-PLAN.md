## Decisions this plan locks (CONTEXT.md "Claude's Discretion")

CONTEXT.md left the exact shape of the new `State` field(s) to Claude's discretion. Locked here so
the executor implements rather than re-derives:

**Field:** `pub last_validate_failure_commit_count: Option<u32>`, attributed `#[serde(default)]`.

**Why `Option<u32>` and not a bare `u32`:** the distinction between "never observed" and "observed
zero" is load-bearing, not cosmetic. `None` must mean no prior failure has been recorded — the
first failure of a phase, or the first after resuming state written before this field existed —
and must be treated as progress so that first failure never mis-accumulates. `Some(0)` means a
failure *was* recorded and the branch genuinely carried zero commits at that moment; the next
failure with zero commits must then accumulate. A bare `u32` defaulting to 0 collapses those two
into one and would make the very first failure of every phase behave like the second.

**Why not reset by `transition()`:** the field is a baseline observation, not a counter, and its
reset semantics live entirely in the compare-and-update at the increment site. This matches
`preflight_retries` and `checkpoint_resumes`, both of which `transition()` deliberately leaves
alone; `consecutive_failures` and `infra_failures` are the two that `transition()` does touch, and
this is not one of them.

**Reversibility (CONTEXT.md rates D-03 one-way):** correct — this changes the shape of persisted
`.devflow/state-NN.json`, and a phase already in flight when the fix ships will have state without
the field. That is exactly what `#[serde(default)]` plus the `None`-means-no-prior-record semantics
above exist to absorb, and Task 1's absent-defaults test is the proof rather than the claim.
**No `checkpoint:decision` is inserted before this task — a deliberate omission, not an oversight.**
The structure checker will warn about it; the warning is expected and the two reasons below are the
answer to it.

1. *The decision it would gate is already answered, twice.* Which forward-progress signal to use
   was deferred by CONTEXT.md's D-03 to research, and 33-RESEARCH.md resolved it with a
   two-candidate tradeoff analysis and a firm recommendation. The only residue was the field's
   naming and type, which CONTEXT.md explicitly assigns to Claude's discretion. A gate on an
   already-answered question is theatre.
2. *A blocking checkpoint would wedge this very phase's own unattended run.* `checkpoint:decision`
   with `gate="blocking-human"` has no mechanism for receiving an operator's answer under DevFlow's
   one-shot `claude -p` launch model — filed as backlog 999.57 / DEN-82, still open, with
   hand-authoring the plan's SUMMARY as the only interim workaround. Phase 33 exists to make
   unattended multi-wave runs work; inserting a construct that halts an unattended run would defeat
   the phase while planning it.

The decision is recorded above in full instead, so it can be overridden by inspection rather than
by interrupting execution.

  <action>
Add `pub fn consecutive_failures_made_progress(previous: Option<u32>, current: u32) -> bool` to
`mode.rs`, placed immediately after `transition_resets_consecutive_failures` so the two
gate-affecting predicates sit together. Body: `previous.is_none_or(|p| current > p)`.

Keep the signature free of `Path`, git handles, and every other I/O-derived type. The caller
performs the I/O and passes in the already-computed numbers. 33-RESEARCH.md names widening this
module's predicates to accept I/O-derived data as an explicit anti-pattern, and the existing tests
in this module call their predicate with bare values and no filesystem setup — that property is
what makes them trivially deterministic and must be preserved.

Doc-comment it to the standard `transition_resets_consecutive_failures` sets — that comment
explains not just what the function returns but why the alternative is wrong, and a reader arriving
at this predicate needs the same. Cover:

- What it decides: whether a Validate failure begins a fresh streak (Code produced new commits
  since the last recorded failure) or continues the existing one (nothing new landed).
- Why `None` reports progress: it means no prior failure has been recorded, so there is no streak
  to continue; the first failure of a phase, and the first after resuming state written before the
  baseline field existed, must both begin a streak rather than extend a nonexistent one.
- Why the comparison is strictly greater rather than not-equal: a count that went *down* means the
  branch was rewound or rebuilt, which is not evidence that the problem Validate reported was
  addressed. Treating it as progress would hand a free counter reset to exactly the situation least
  likely to deserve one.
- **What this predicate does not establish.** Say plainly that a `true` result means new commits
  exist, not that those commits addressed anything. An agent that commits something trivial on
  every cycle resets the streak every cycle and never reaches `MAX_CONSECUTIVE_FAILURES`. This is
  the accepted, documented weakness of the commit-count signal recorded in 33-RESEARCH.md's D-03
  Recommendation and Assumptions Log A1 — the same weakness `evaluate_layer2`'s own "no work done"
  gate already carries, which a single trivial commit also already defeats today. It is a real
  narrowing of ROADMAP criterion 4's guarantee and must be legible in source, not only in a
  planning document. Do not attempt to strengthen it here with a lines-changed or files-touched
  threshold: 33-RESEARCH.md assesses that as a follow-up if the assumption proves wrong, and adding
  it speculatively would put an unmeasured heuristic in the safety gate's path.

Add two tests. Follow the module's established discipline of enumerating cases explicitly rather
than writing one test as the negation of another:

- `made_progress_treats_no_prior_record_as_progress` — assert `None` with a zero current count and
  `None` with a non-zero current count both report progress. The zero case is the one that matters:
  it is the state of a brand-new phase whose feature branch does not exist yet.
- `made_progress_requires_a_strictly_higher_count` — assert the strictly-greater case reports
  progress, and assert the equal case and the lower case both report no progress. Include the equal
  case with both operands zero as a distinct assertion from the equal case with both operands
  non-zero: the first is what the existing `consecutive_failures_reaches_ceiling_across_cycles`
  regression guard actually exercises (a repo with no feature branch, counting zero every cycle),
  and it is the single case ROADMAP criterion 4 most depends on.
