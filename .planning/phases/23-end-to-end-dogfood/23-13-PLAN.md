<objective>
Get the guard onto `develop` and prove the binary that will drive the acceptance
attempt actually contains it.

Requirement tokens: **23f** (the guard reaching `develop`) and **23-acceptance**
(the binary-freshness precondition the retry depends on).

Purpose: the acceptance run forks its worktree from `develop` and is driven by
whatever `devflow` binary is on the operator's PATH. Two independent things can
therefore invalidate it, and this project has been bitten by both:

- **Stale binary.** `23-VALIDATION.md` records it plainly — "validating a
  dogfood fix against a stale binary is a known repeat failure here" — and the
  operator's own working notes carry the same warning. A rebuild that is assumed
  rather than performed and measured is worth nothing.
- **Code on an unmerged branch.** `23-FINDINGS.md`'s closing "Ordering lesson"
  is exactly this: *"Promoting a backlog item to a numbered phase on a feature
  branch makes it invisible to `devflow start`. Either merge the promoting
  branch to `develop` first, or land the promotion on `develop` via its own PR
  before launching."*

Shipping a guard against that failure mode on an unmerged branch, and then
running the acceptance attempt from it, would repeat the lesson the guard exists
to teach. So the guard merges first, then the binary is rebuilt from the merged
tip, then its refusal is demonstrated at runtime.

Output: `23-GUARD-SHIP-RECORD.md` — the PR number, the CI conclusion, the merge
commit on `develop`, the rebuilt binary's version and content hash, and the
verbatim runtime refusal.

**Visible skip, recorded per protocol:** spec-less probe fallback skipped —
phase has no requirement IDs to probe (visible skip).

## The one hard rule in this plan

**No autonomous step writes to `develop`.** The executor may push the feature
branch (`--force-with-lease`, per this project's git-workflow rules) and may
open a pull request. It must not `git push origin develop`, must not
`git merge` into a local `develop`, and must not `gh pr merge`. The merge is
Task 2's blocking human checkpoint. GitHub's branch protection on `develop`
(`enforce_admins: true`, `allow_force_pushes: false`, `allow_deletions: false`)
is a second layer, not the primary control — the primary control is that the
executor stops.
</objective>
