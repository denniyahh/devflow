<objective>
Bound gate lifetime. Give DevFlow a way to end an abandoned run without
`kill(1)`, and without a supervisor. This is the acting half of re-aimed unit
**23b**; plan 23-03 built the enumeration this plan acts on.

Purpose: `23-ORPHAN-FORENSICS.md` found 27 orphaned process pairs (54
processes, 168.6 MB resident, oldest gate 30 hours) on one operator's machine.
In every one, `wait $apid` had already returned — the agent was finished and
reaped. What was still running was the trailing `devflow advance`, and every
one sat on a root with `gate_pending: true`. Verified against live source this
session: `advance()` acquires a per-phase lock
(`crates/devflow-cli/src/pipeline_launch.rs:290`) and holds it through
`run_gate_with_timeout`'s `Gates::poll_response` call
(`crates/devflow-cli/src/pipeline_gate.rs:284`), whose `timeout_secs` defaults
to `gate_timeout_secs()` — **7 days**
(`crates/devflow-cli/src/config_parse.rs:19-28`). `lock.rs:8-9`'s own doc
comment names this as deliberate: the lock is held "across a gate's multi-day
blocking wait." The defect is not an unbounded wait; it is a wait bounded so
loosely it is operationally indistinguishable from unbounded.

Output: `devflow gate sweep`, and a `Gates::reap` helper that is
structurally incapable of approving anything.

**The mechanism, and why it needs no process signalling — verified line by line
this session, not taken on trust from RESEARCH.md:**

1. `run_gate_with_timeout` persists `state.gate_pending = true` and calls
   `Gates::write_gate` **before** it starts polling (`pipeline_gate.rs:250-252`).
   So an open gate on disk is a reliable indicator of a live poller.
2. `Gates::poll_response` (`gates.rs:222-248`) checks for the response file
   **first**, then sleeps, with backoff doubling from 1s and capped at 60s. A
   response written at any moment is therefore observed within at most 60
   seconds.
3. `Gates::respond` (`gates.rs:179-198`) writes that file atomically, refusing
   only when no gate is open (`NoOpenGate`) or a response already awaits pickup
   (`AlreadyResponded`).
4. `GateAction::from_response` (`gates.rs:69-79`) maps `approved: false` plus a
   note whose lowercase form contains the substring for aborting onto
   `GateAction::Abort`.
5. `run_gate_with_timeout`'s `Some(response)` arm clears `gate_pending`, acks,
   and emits `gate_resolved` (`pipeline_gate.rs:285-305`); the caller then runs
   `abort()` (`pipeline_gate.rs:322-335`), which cleans up the gate files,
   clears state, and emits `workflow_aborted`.
6. The `sh -c` monitor script has nothing after its `devflow advance` line
   (`crates/devflow-core/src/monitor.rs:148-160`), so once `advance` exits the
   monitor shell falls off the end and exits behind it.

The whole teardown is code that already exists and is already exercised by
`gate_respond`, `ship_override`, and the `respond_writes_a_response_poll_response_consumes`
test in `gates.rs`. This plan adds a caller, not a mechanism.

**Visible skip, recorded per protocol:** spec-less probe fallback skipped —
phase has no requirement IDs to probe (visible skip). `must_haves.truths` are
derived from the ROADMAP phase goal and the probe/forensics evidence.

**Open Question 3 resolved, explicitly (`23-RESEARCH.md` § Open Questions):**
the sweep ships **on-demand only** this phase. No cron, no systemd timer, no
background daemon. A mechanism that auto-rejects human gates without a human
asking it to is a strictly larger safety argument than this phase's evidence
supports, and the operator can wire the command into their own scheduler if
they want it. Automation is recorded as a natural follow-up, not a blocker.

**Open Question 1 resolved, explicitly:** rate-limit gates that are
unresolvable by construction (a probe died at `define` with
`status: "ratelimited"`, no parseable retry time, no scheduled auto-resume —
`23-ORPHAN-FORENSICS.md`) are **deferred to the backlog, not fixed here**. The
sweep does partially relieve them — an abandoned rate-limit gate is now reapable
like any other — but designing auto-resume is a separate piece of work with its
own failure modes. Recorded as a decision, not silently dropped.

Add to `crates/devflow-core/src/gates.rs` a single narrowly-typed reaping entry point on `impl Gates`:

`pub fn reap(project_root: &Path, phase: u32, stage: Stage, note: &str, responded_by: &str) -> Result<PathBuf, GateError>`

It constructs a `GateResponse` with `approved` hard-coded to `false` at the literal, `note: Some(note.to_string())`, `responded_by: Some(responded_by.to_string())`, and delegates to `Gates::respond`. This typing is the mitigation for threat T-23-41 below: the sweep must not share a generic `respond(approved: bool, ...)` call site with any approving path, because a future refactor could otherwise wire it to the approving branch. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sweep → another project's `.devflow/gates/` | the sweep writes into roots it did not create, discovered from a registry file |
| gate response file → a live `advance` process | a written response is a control instruction the target process obeys without further authentication |
| operator → `devflow gate sweep` | a single invocation can terminate every gated run on the machine |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-41 | Elevation of Privilege | `Gates::reap` | high | mitigate | A buggy or refactored sweep writing `approved: true` would become an unauthorized `--yes-ship`, auto-merging a phase nobody approved. Mitigated structurally, not by convention: `Gates::reap` takes no boolean, hard-codes `approved: false` at the literal, and is the sweep's only write path. Task 1 acceptance criteria assert both the absent `bool` parameter and the literal. |
| T-23-42 | Denial of Service | `gate_max_unattended_age_secs` | high | mitigate | A threshold of zero — from a typo, an empty env var, or a `0` — would reap every open gate on the machine on the next invocation, destroying in-flight work. Mitigated by treating both an unparsable value and an explicit zero as unset, falling back to six hours. Task 2 acceptance criteria assert both cases. |
| T-23-43 | Repudiation | reaped gates | medium | mitigate | A gate that vanishes with no record breaks DevFlow's never-fail-silently guarantee. Every reap emits `gate_reaped` in the sweep's process and causes `gate_resolved` with `responded_by: devflow-reap` in the target's process — two independent, timestamped, attributed records. |
| T-23-44 | Tampering | concurrent response writes | medium | accept | A human, `--yes-ship`, and the sweep can all target the same gate. `Gates::respond` already resolves this first-writer-wins by refusing to clobber an unconsumed response (`gates.rs:189-191`). Accepted rather than coordinated: adding locking between them would be new, unaudited machinery to solve a race the existing API already resolves safely. |
| T-23-45 | Spoofing | registry-supplied `project_root` | medium | mitigate | The sweep operates on paths from a file, so a tampered registry could aim it at an unrelated directory. Mitigated by scope rather than validation: the sweep's only possible effect on a non-DevFlow directory is `read_dir` on a `.devflow/gates` subpath that will not exist, and `Gates::list_open` returns an empty `Vec` for an unreadable directory (`gates.rs:142-144`). It writes only where a parseable `GateFile` already exists. |
| T-23-46 | Denial of Service | unattended automation | medium | mitigate | Wiring the sweep into a cron or timer would let it reject human gates with no human present. Mitigated by scope: on-demand only this phase (Open Question 3, resolved in the objective). No scheduler integration ships. |
| T-23-SC | Tampering | cargo installs | high | mitigate | **No package installs in this plan** — `Gates::reap` and the sweep use only already-resolved workspace dependencies. `23-RESEARCH.md` § Package Legitimacy Audit: "Not applicable." |
