<objective>
Ship `devflow stop --phase N` — the missing primitive. Re-aimed unit **23c**.

Purpose: `23-ORPHAN-FORENSICS.md` is blunt about why 54 processes accumulated:
*"`devflow stop` is the missing primitive, and its absence is why this
population exists. Nothing could clean these up. They were removed with
`kill(1)`."* `devflow cleanup --force` deliberately refuses to touch a live
agent or monitor — verified this session at
`crates/devflow-cli/src/commands.rs:372-443`, where the refusal is documented
as a hard property with no override flag, added by an earlier phase's review
specifically to close a race where cleanup could delete a worktree a live agent
was still writing into. That refusal is correct and this plan does not weaken
it. Stop becomes the verb that changes a phase from live to dead; cleanup keeps
refusing to touch anything still live, and is usable afterwards.

Output: a new `devflow stop` verb, and one small `devflow-core` helper.

**The critical correctness detail, and why the obvious implementation is wrong.**
`23-RESEARCH.md` reports a newly discovered bug. It was re-verified against
live source this session and is confirmed: the monitor script generated by
`spawn_monitor_inner` (`crates/devflow-core/src/monitor.rs:148-160`) is

`apid=''; cleanup() { [ -n "$apid" ] && kill "$apid"; exit 0; }; trap cleanup TERM INT; cd <workdir> || exit 1; "$@" > <stdout> 2><stderr> & apid=$!; echo $apid > <pid_file>; wait $apid; echo $? > <exit_file>; <binary> advance <root> --phase N`

The trap closure captures `$apid` — the **agent** — and nothing else. By the
time the trailing `advance` is the shell's foreground child, `$apid` names a
process that exited long ago. Sending SIGTERM to `state.monitor_pid` therefore
does **not** stop `advance`; the shell's handler kills an already-dead PID and
the `advance` process keeps holding the per-phase lock and polling the gate.
`state.monitor_pid` is the PID `devflow status` already displays, which makes it
the natural — and wrong — thing to signal.

The correct target already exists and needs no new writer. `lock::acquire`
(`crates/devflow-core/src/lock.rs:84-89`) writes `std::process::id()` into
`.devflow/lock-{phase:02}`, and `advance()` acquires that lock as its first act
(`crates/devflow-cli/src/pipeline_launch.rs:290`) and holds it for the entire
gate wait. `lock::holder(project_root, phase)` is already public and already
returns that PID. That is the process to stop.

**Reversibility: costly.** `devflow stop` is a new user-facing verb on a
crates.io-published binary. Removing it later breaks any operator or script
that adopts it. Flagged, not gated — adding a verb is materially less
consequential than removing one (which is why plan 23-07's deletion of
`sequentagent` does carry a checkpoint), and the forensics evidence for needing
it is unambiguous.

**Visible skip, recorded per protocol:** spec-less probe fallback skipped —
phase has no requirement IDs to probe (visible skip). `must_haves.truths` are
derived from the ROADMAP phase goal and the forensics evidence.

**Requirement-token redefinition, stated explicitly as required:** `23c` no
longer means "`devflow stop`, blocked on the socket supervisor landing first."
The dependency is gone. It now means **"`devflow stop`, built directly against
the existing per-phase lock file and the existing gate-response protocol."**
`23-RESEARCH.md` Question B establishes this requires zero new dependency, zero
new process-lifecycle primitive, and none of the socket-supervisor spike's
mechanism.

Add to `crates/devflow-core/src/agent.rs`:

`pub fn terminate(pid: u32) -> bool` — sends SIGTERM via `libc::kill`, returning whether the signal was delivered. It must apply exactly the same guards `agent_running` already applies and for the same documented reasons: convert through `libc::pid_t::try_from` and reject the error case, and reject any value not strictly greater than zero. `pub fn looks_like_devflow_process(pid: u32) -> bool` — reads `/proc/<pid>/cmdline` and reports whether any NUL-separated argument's file name component starts with `devflow`. Returns false when the file cannot be read, which is the fail-closed direction. Document that this is a Linux-only best-effort identity check and that a false return must be treated as "do not signal", never as "signal anyway".

| Boundary | Description |
