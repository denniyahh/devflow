<objective>
Run the phase's acceptance criterion.

**Acceptance here is behavioural, not code-shaped.** CONTEXT.md says it
directly: *"The phase is done when one phase has actually been driven
start-to-finish by devflow, unattended, reaching a completed Ship stage — not
when the supervisor compiles and its unit tests pass."* Everything `cargo test`
can prove is already proven by plans 23-05 through 23-10. What no test can prove
is this: a real Claude Code invocation, consuming real GSD slash commands, over
real wall-clock time, driven by the supervisor, through all five stages, with
nobody watching.

The record to beat, from `.devflow/events.jsonl` and ROADMAP.md's run table:
**no phase has ever completed a full five-stage devflow-driven run.** Phase 17
reached Ship, looped back to Code, and died to two silent monitor deaths (~4h
lost). Phase 21 stopped after Define. Phase 22 stopped dead at a Plan relaunch
with no `advance_evaluated`. Two of the three were blocked at least once by the
self-dogfood staleness guard.

Purpose: prove the loop, or record precisely where it still breaks.
Output: `23-ACCEPTANCE.md`, and a human verdict on whether this phase met its
own criterion.
</objective>

  <action>
Launch one unattended run against the phase chosen at plan 23-11's checkpoint,
on **this** repository, and observe it to termination without intervening.

Launch, exactly:
`devflow start --phase <N> --agent claude --mode auto --yes-ship`
where `<N>` is the phase named in `23-ACCEPTANCE-SETUP.md`.

**Observation protocol** — the same one 23-VALIDATION.md prescribes and plan
23-02's probe used, so the two runs are comparable:
- Poll `devflow status` and `tail` `.devflow/events.jsonl` every **30-60
  seconds**. Short enough to catch a stage transition, long enough not to
  interfere.
- **Do not** run `devflow advance`. **Do not** answer a gate. **Do not** use
  `ps` or `kill` to inspect or nudge anything. The whole claim being tested is
  that none of that is necessary any more; using any of them invalidates the
  run. If you need process facts for the record, get them from `devflow status`
  and `devflow doctor` — which is the point.
- Record, at each poll, what `devflow status` reported: the socket state, the
  derived liveness, and the current stage. This series is the direct evidence
  for the "a stall is distinguishable from a pause" claim, and it is what
  Finding 1 says was impossible before.
- **If the run stalls**, do not rescue it by hand. Use `devflow stop --phase N`
  — the verb plan 23-10 built — and record that you did. A stall that has to be
  killed with `kill` is a finding about `devflow stop`, and it belongs in the
  record.
- **If the run does something destructive or clearly wrong**, stop it with
  `devflow stop`, restore `develop` using the literal command recorded in
  `23-ACCEPTANCE-SETUP.md`, and record the whole sequence. Restoring is not a
  failure of this plan; failing to record it would be.

**Evidence to capture into `23-ACCEPTANCE.md`** — D-03's standard, and it is not
optional:
- Verbatim `events.jsonl` lines spanning **every** stage transition:
  `transition`, `stage_launched`, `advance_evaluated`, `gate_fired`,
  `gate_resolved`, `workflow_finished` — plus an explicit list of which did not
  appear. Include the `ship_gate_pre_authorized` event, which is the auditable
  proof that D-06 held: the gate fired and was answered, not skipped.
- The `.devflow/phase-N-*` capture files (`stdout`, `stderr.log`, `exit`,
  `agent-pid`) for at least the stage where the run succeeded or first failed.
  Truncate long stdout, keeping head and tail, and say how much was elided.
- The full `devflow status` poll series with timestamps.
- The staleness guard's behaviour: whether `self_dogfood_stale_blocked` appeared
  and, if so, what happened next. If it never fired, say why — a run against a
  freshly built binary on a clean tree may legitimately not be stale, and that
  is a different observation from "the guard is fixed."
- The final `git log --oneline` on `develop` showing exactly what the run
  merged, and the diff of the version and changelog commits it made.
- Whether the phase's worktree was removed by `Hook::WorktreeRemove` (plan
  23-10) — this run is the first ever to reach that path on success.

**Then write the verdict section.** It must state:
- **Did it reach a completed Ship stage, unattended?** Yes or no, with the
  event that proves it.
- **If no: where and why**, attributed to a specific mechanism, and whether
  that mechanism is in this phase's scope or is a new finding.
- **Which of the phase's four units are proven by this run**, and which are
  proven only by `cargo test`.
- **What is still not proven.** Be direct. A single successful run is one
  sample; say so rather than generalising from it.

**Redact before committing.** The captures contain raw agent output, which on
this project has previously carried absolute home paths and OS usernames into
committed artifacts (999.10 / WR-02, three prior instances). Scan the excerpts
and redact them.
