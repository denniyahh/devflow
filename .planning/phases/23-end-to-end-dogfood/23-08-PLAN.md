<objective>
Make the supervisor's state visible to the operator.

This is the observability half of 23b, and it is what turns a mechanism into an
answer to the phase's actual problem.
`.planning/OPERATOR-OBSERVABILITY-FINDINGS.md` § Finding 1 records the Phase 17
incident in the operator's own words: two silent monitor deaths, ~4h lost,
because **a dead monitor was indistinguishable from a healthy between-stages
pause.** `kill(pid, 0)` cannot tell those apart, and reports a zombie as alive
(F6). A socket probe can: GONE, STALE and ALIVE are three different answers.

Today `liveness()` (`commands.rs:517-526`), `check_dead_agent` (:1770),
`check_dead_monitor` (:1793) and `status`'s probe all key off
`state.monitor_pid` — which, after plan 23-07, nothing writes. Left unchanged,
every one of them would report Unknown forever. This plan re-points them.

It also lands **Claude's Discretion item #3** — in-flight-phase behaviour across
the D-08 upgrade — as a named `doctor` finding rather than as silence.

Purpose: make a stalled unattended run visible without `ps`.
Output: `status`, `doctor` and `cleanup` all answering from the socket, plus a
dedicated finding for the one-time upgrade shape.

## Recorded decision — Claude's Discretion item #3: in-flight phases across the D-08 upgrade

**DECIDED: `#[serde(default)]` semantics plus a dedicated, named `doctor`
finding. Not a refusal, and not folded into the generic Unknown bucket.**

CONTEXT.md left open whether a phase whose `state.json` predates the
`supervisor` field should be *refused with guidance* or handled otherwise.

Refusing is wrong. `state.rs` has one consistent, well-tested precedent for
every field added since 17-01: `#[serde(default)]`, defaulting to a value that
downstream consumers already treat as "unknown, never assume Stuck or Healthy".
`liveness()`'s `None` arm resolves `Unknown`, and that is directly guarded by
the existing `liveness_unknown_when_no_monitor_recorded` test. A hard refusal
would make an old `state.json` un-inspectable by the very commands an operator
would reach for to understand it.

But "absent field defaults to None" does not cover the genuinely new risk. A
phase whose monitor was spawned by the **old** mechanism carries a *populated*
`monitor_pid` and no `supervisor`. The new binary correctly reports Unknown —
while the old shell monitor may still be alive and is now unreachable by any
new-binary command. That is not data corruption; it is a **silent loss of
control**, and DevFlow self-dogfoods, so it is plausible rather than
theoretical.

So: a dedicated `doctor` finding for exactly `monitor_pid: Some(_) &&
supervisor: None`, named and worded so the operator is told what to do — locate
and signal the process by hand, or let it complete naturally — rather than being
handed a generic Unknown. It is a one-time transition concern (D-08's big-bang
carries no long-term dual-path cost) and costs one more finding alongside the
existing `check_dead_agent` / `check_dead_monitor` pair.

| Boundary | Description |
|----------|-------------|
| `status` / `doctor` output → operator decisions and notifications | The operator acts on what these say; a wrong "healthy" is worse than no answer |
| `state.json` from any binary version → the reconciliation findings | Findings must handle absent, populated-old and populated-new handles without misclassifying any |
| `cleanup`'s live-check → destructive worktree and branch removal | A false "not live" lets cleanup delete a running phase's worktree |
| rendered output → committed planning documents and desktop notifications | Absolute paths and usernames have leaked through this surface three times |
