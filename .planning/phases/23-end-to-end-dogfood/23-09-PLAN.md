<objective>
Add the pre-authorization flag that makes an unattended Define-through-Ship run
possible at all. Requirement token **`yes-ship`**; decisions **D-04**, **D-05**,
**D-06**, with **D-07**'s accepted risk carried into plan 23-10's checkpoint.

Purpose: this is not optional polish, it is a structural precondition for the
phase's acceptance criterion. Verified this session at
`crates/devflow-core/src/mode.rs:96-99`: `Mode::should_gate` returns `true` for
`Stage::Ship` unconditionally, in **both** modes, and the enclosing doc comment
states it plainly — "Ship always gates (both modes)". `Mode::Auto` suppresses
Validate gates only. So without this flag, a Define-through-Ship run parks at
the Ship gate and waits for a human, and the ROADMAP goal — "no manual `ps`, no
manual `devflow advance`, no silent stall" — is unreachable by construction, not
by defect.

`23-RESEARCH.md` records this unit as unchanged by the re-aim but **more**
load-bearing than before: it is now the last thing standing between the pipeline
and the acceptance run, since the probe proved the mechanism reaches Ship
reliably and plans 23-03 through 23-06 addressed what happens when it gets
there.

Output: a per-run flag, a persisted authorization, and one auto-answered gate.

**Reversibility: costly (D-04, D-05).** A new user-facing flag on the
irreversible merge, version-bump, and changelog path. Removing it later breaks
any operator or script that adopted it, and D-05's prohibition on making it
config-persistable is far easier to relax later than to tighten after operators
depend on a persisted setting. Flagged, not gated — the checkpoint that matters
for this capability is D-07's, and it sits in plan 23-10 immediately before the
run that actually exercises it.

**Visible skip, recorded per protocol:** spec-less probe fallback skipped —
phase has no requirement IDs to probe (visible skip). `must_haves.truths` are
derived from the ROADMAP phase goal and the probe evidence.

## The two traps, both named in RESEARCH.md and both confirmed against source

**Trap 1 — auto-approving the wrong gate.** `finish_workflow_with_gate_timeout`
reopens a gate that is also tagged `Stage::Ship` when a terminal hook fails
(`pipeline_gate.rs:194-205`). A naive check keyed on `stage == Stage::Ship`
anywhere inside `pipeline_gate.rs` would auto-approve **both** the routine Ship
approval and the post-failure retry gate, converting "the merge could not be
completed, a human should look" into "approved, try again forever". The
authorization must be scoped to one call site, not to a stage tag.

**Trap 2 — writing the response before the request exists.** `Gates::respond`
returns `GateError::NoOpenGate` when no gate request file is present
(`gates.rs:185-187`), and `run_gate_with_timeout` writes the request at
`pipeline_gate.rs:252`. An auto-response injected before that line always fails;
one injected after `poll_response` at `:284` is never observed. The only correct
window is between those two calls. The cross-AI review raised this as a HIGH
finding on the original plan and it is specified here rather than left to
discovery.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator invocation → persisted authorization | a decision typed once is stored and consumed by a different process, later |
| pre-authorization → irreversible git operations | the answered gate leads directly to merge, version bump, and changelog commit |
| configuration file → run authority | a config-settable authorization would become standing, silent policy |
