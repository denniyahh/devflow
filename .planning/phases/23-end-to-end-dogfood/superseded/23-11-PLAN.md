acknowledgement immediately before it.

not in a scratch repo — and that is deliberate coverage repair, not convenience.

dogfood killer, which stopped two of the three recorded runs — is structurally
unreachable in a scratch repo.** So are the build-provenance and worktree-aware
paths. A scratch-only acceptance would ship this phase without ever exercising
the case that broke every prior run.

D-07 is the price: combined with D-02, `--yes-ship` on this repository means the
acceptance run will **unattended-merge a real phase into `develop`, bump the
version, and append the changelog** here. The operator considered a
self-dogfood refusal guard and **explicitly declined it**, on the grounds that a
genuine hands-off proof is the point of the phase and D-06 keeps the decision
auditable. That is a recorded, deliberate acceptance, not an oversight.

The operator specified two mitigations. This plan **encodes** them; it does not
re-decide the risk and it does not add a refusal guard.

Purpose: make the irreversible run recoverable and attributable before it
starts.
Output: a verified recovery point, a chosen low-stakes target, a rebuilt binary
and a green tree — all recorded.

  <action>
Create the pre-run recovery point the operator specified, in the form confirmed
at the checkpoint, and **prove it works** rather than assuming it does.

1. Record the current `develop` head SHA.
2. Create the recovery point at that SHA — a tag or a branch, per the
   checkpoint's answer. Name it so its purpose is obvious to a future reader
   and so it cannot be mistaken for a release tag (a release-shaped name would
   collide with this project's tag conventions and could confuse
   `devflow release --check`).
3. Push it to `origin` if the checkpoint said to, so it survives local loss.
4. **Verify the recovery point actually restores.** Do not assert this — do it:
   in a throwaway clone or a scratch worktree (never in the primary checkout,
   and never with a force-push), check out the recovery point and confirm its
   tree matches `develop`'s current tree exactly. `git diff --stat <point> develop`
   returning empty is the proof. A recovery point that has never been exercised
   is not a mitigation.

   **Local restorability is not remote restorability — establish the remote half
   too (review finding — OpenCode, divergent view, adopted).** The throwaway
   clone proves the *content* can be reconstructed. It does not prove the
   *remote* can be moved back, and on this repository it probably cannot be
   moved back the obvious way: `develop` is a **protected branch**, so
   `git push --force origin develop` will be refused. Discovering that during
   an emergency, after an unattended merge has landed, is exactly the wrong
   time. So:
   - **Name the intended restore target explicitly** in the document. It is
     `develop` on `origin`, and the mechanism is not a force-push.
   - **Determine and record the actual refusal behaviour** without performing a
     destructive operation. `git push --force-with-lease --dry-run origin
     <recovery-point>:develop` exercises the server's refusal path without
     moving anything; capture its verbatim output, whether it succeeds or is
     rejected. If your git or remote configuration makes even a dry run
     unsafe or unavailable, record that and fall back to reading the branch
     protection settings for `develop` and quoting them.
   - **Record the mechanism that actually works under branch protection**: a
     revert-and-PR restore — branch from the recovery point or revert the run's
     merge commit, open a PR into `develop`, and merge it through the normal
     protected path. Write out the literal commands for that sequence, because
     it is what an operator will really run.

   **Prefer a non-release-shaped recovery ref.** The acceptance criteria already
   forbid a `v<major>.<minor>.<patch>` name; prefer a **branch** over a tag for
   this purpose unless the checkpoint said otherwise, since a branch is what a
   restore PR is opened from, and a stray tag on this repository is more likely
   to be mistaken for a release by `devflow release --check` and by a human
   skimming `git tag`.
5. Write `23-ACCEPTANCE-SETUP.md` recording: the recovery point's name and SHA,
   whether it was pushed, the verbatim output of the restore verification, the
   named remote restore target and the captured evidence of what the remote does
   when asked to move it, the literal revert-and-PR restore sequence, the phase
   chosen at the checkpoint and the standard it was judged against, and the
   exact `git` command an operator would run to restore `develop` from it.
   That last item is the whole point of the document — if the run goes wrong,
   nobody should have to reconstruct the command under pressure, and nobody
   should discover the branch is protected while under it.

Do not modify `develop` itself. Do not force-push anything — including during
the remote-behaviour check, which is dry-run only.
