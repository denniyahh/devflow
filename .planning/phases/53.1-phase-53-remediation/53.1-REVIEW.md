## Warnings

### WR-01: A `phase.complete` that wrote files is recorded as "did not mark phase complete" and its writes are left uncommitted

**File:** `crates/devflow-cli/src/pipeline_outcomes.rs:420-434`, `:470-474`, `:541-559`
**Issue:** `gsd_reader::phase_complete(..).and_then(|reply| gsd_written_files(&reply))` runs both steps in one `Result`. When `phase.complete` succeeded (GSD already rewrote ROADMAP.md and STATE.md), a reply that lacks any one of the four flags, or holds a non-boolean, makes `gsd_written_files` return `MissingField`. That error lands in `completion_refused`, which then:
- prints `GSD did not mark phase {phase} complete`, which is false;
- records `{"ok":false,"failure":"gsd_reader_missing_field"}`;
- skips the commit.

The run is left with modified planning files that nothing commits and an event that says the opposite of what happened. The dirty worktree then makes `cleanup` keep the worktree. A second way in: GSD's auto-prune failure path (`phase.cjs` ~7121-7128) can leave STATE-ARCHIVE.md written with `auto_pruned: false` and an `auto_prune_error` key. DevFlow ignores that key, so the archive is never added to `--files` and stays dirty.
**Scenario:** a GSD release that renames or drops `auto_pruned` (or emits it only when pruning is enabled), after which every finish reports a refusal while ROADMAP.md and STATE.md are modified on disk.
**Fix:** Keep the two failure classes apart. Once `phase_complete` returns `Ok`, GSD has written files, so a flag problem must stay `ok: true` with a commit failure:
```rust
let reply = match gsd_reader::phase_complete(home, root, phase) {
    Ok(reply) => reply,
    Err(failure) => return completion_refused(phase, &failure, root, Some(home)),
};
match gsd_written_files(&reply) {
    Ok(files) => commit_completion(home, root, phase, &files),
    Err(failure) => {
        eprintln!("GSD marked phase {phase} complete, but its reply does not say what it wrote ({failure}); commit .planning/ by hand");
        serde_json::json!({ "ok": true, "committed": false, "commit_failure": failure.label() })
    }
}
```
Also add `.planning/STATE-ARCHIVE.md` to the files when `reply["auto_prune_error"]` is present, or report that key.

### WR-02: A refused or failed GSD completion never reaches the operator's channels

**File:** `crates/devflow-cli/src/pipeline_gate.rs:232-241`; `crates/devflow-cli/src/pipeline_outcomes.rs:444-457`
**Issue:** `record_gsd_phase_complete` reports its outcome only in two places: the runner's stdout/stderr, which in a systemd user unit is the journal, and one `gsd_phase_complete` event. `notify_run_end` runs right after it with a fixed message, `phase N finished: Validate passed; the worktree and branch are kept`. Nothing else in the crate reads `gsd_phase_complete` (`rg gsd_phase_complete` finds only the emitter and the tests).

OPERATIONS.md (`### GSD marks the phase complete`, the last paragraph) names a common case: a fix committed after Validate makes the verification stale, so `phase.complete` refuses. In that case the operator gets a "finished" notification, and `status` says finished. Neither tells them that ROADMAP.md and STATE.md were not updated or that a hand step is needed. This is the never-silent rule failing in practice, even though a line does go to stderr.
**Fix:** Pass the payload's outcome into the notify message, for example by appending `; GSD did not mark the phase complete (<failure>/<reason>): see devflow history` when `ok` is false, or `; GSD's commit failed: commit .planning/ by hand` when `commit_failure` is set. Better still, have `status` show it for a finished run.

### WR-03: A resume advance commits the move to Code before the agent-binary check, so a failed launch loses the halted-stage label 999.251 fixed

**File:** `crates/devflow-cli/src/pipeline_launch.rs:2196-2210` (with `resume_loaded` `:2539-2555`)
**Issue:** `archived_stage` is computed from `reserved.state` before `resume_loaded`. `resume_loaded` then commits `stage = Code, stop_until = None` (and emits `transition`). Only after that are `ensure_agent_binary`, `ensure_ask_registration` and `archive_prior_capture` run. If either of the first two fails, `re_mark_stopped_after_failed_launch` records `stop_reason = "resume launch failed: …"` with the stage already at Code, and the Plan capture has not been archived yet. On the next `resume` (say, after the operator installs the binary):
- `until_cap_fired` is false, because `stop_until` is now `None`;
- so `archived_stage` is `None`;
- so `archive_prior_capture` labels Plan's capture `"stage": "code"`.

That is the mislabel 999.251 was meant to remove. The `--agent` path is covered, because `handoff_refusal` checks the target binary before any write. The same-agent path is not covered.
**Scenario:** `start --until plan` on claude, the operator's PATH changes before `resume`, `resume` fails, PATH is fixed, `resume` again: `history` shows the Plan output archived as Code's.
**Fix:** When `advance.is_some()`, run `ensure_agent_binary` and `ensure_ask_registration` for the agent the resume will launch (`handoff_to.unwrap_or(state.agent)`) among the pre-write checks in `resume_loaded`. Alternatively, archive the capture under `from` before the advance commit.

## Info

### IN-01: The `human_needed` post-run sign-off route gives DevFlow-specific advice on every project's gate

**File:** `crates/devflow-cli/src/pipeline_outcomes.rs:1565-1572`; `OPERATIONS.md` (How Validate decides, "Sign-offs that can only run after the run ends")
**Issue:** Every `human_needed` gate, in any project DevFlow drives, now tells the operator to "run it with a build installed to a separate root while this gate waits". OPERATIONS.md spells that out as `cargo install --path crates/devflow-cli --locked --root <scratch>`. That is the Phase 53 dogfood close-out for this repository, not a generic step for a product published on crates.io.
**Fix:** Word the gate sentence generically ("a sign-off that needs this run to end: do it while the gate waits, then answer with `gate reject N --note …`"), and move the cargo recipe to the dogfooding notes.

### IN-02: `event_safe_text` replaces the GSD home as a raw substring

**File:** `crates/devflow-cli/src/pipeline_outcomes.rs:583-598`
**Issue:** Only empty needles are dropped. With `HOME=/`, every `/` in GSD's message becomes `~`. With `HOME=/home/u`, a sibling path `/home/u2/x` becomes `~2/x`. Either way the recorded message is garbled. This needs an unusual HOME, so it is low impact.
**Fix:** Skip needles that are a bare root (`/`), and replace only at a path boundary: the needle followed by `/`, whitespace, a quote, or the end of the text.

### IN-03: GSD writers run under the 60 s reader timeout and are SIGKILLed by process group

**File:** `crates/devflow-core/src/gsd_reader.rs:691-737` (`phase_complete`, `commit_files` use `GSD_READER_TIMEOUT`; `run_bounded` -> `end` -> `kill_group`)
**Issue:** `phase.complete` writes ROADMAP.md and STATE.md, and `query commit` runs `git add` and `git commit`, including the repository's pre-commit hook (gitleaks here). Each runs under the bound that was sized for read-only queries, and expiry SIGKILLs the whole group. A kill mid-commit can leave `index.lock` behind, which blocks every later git operation in that worktree. The reply fields `warnings` and `has_warnings` are also dropped without being printed.
**Fix:** Give the writers their own, longer named bound, and print GSD's `warnings[]` when `has_warnings` is true.

### IN-04: Phantom requirement in the docs: the "Plan->Validate halt resumes at Code" caveat describes a state that cannot occur

**File:** `crates/devflow-cli/src/pipeline_gate.rs:47-49`, `crates/devflow-cli/src/pipeline_launch.rs:2507-2508`, `OPERATIONS.md` (resume row)
**Category:** necessity
**Issue:** `stop_until` is set only by `start` (`commands.rs:344`). A fired cap's resume clears it (`pipeline_launch.rs:2543-2546`). A Plan->Validate transition comes only from `Step::ValidateAgain` at a verification gate on Plan (`pipeline_outcomes.rs:2048-2055`), and those gates are the gap-closure Plan gates, which need a Validate to have run first. So a capped run cannot halt on a Plan->Validate move before its cap is spent. This rests on reading the call sites, not on a test, so it is Info. The caveat tells operators about a case that cannot happen.
**Fix:** Drop the caveat from the doc comments and the OPERATIONS.md row, or replace it with a one-line invariant note saying why the case cannot occur.
