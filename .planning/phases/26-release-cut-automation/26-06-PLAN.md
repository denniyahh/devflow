<objective>
Build the release executor: one library function that composes, in order, the
five steps of the release cut — version bump and direct push to `develop`, the
human-gated `develop`->`main` boundary, the signed tag, the sync back, and the
crates.io publish — reusing every primitive this phase already built rather
than reimplementing any of them (backlog `999.25`, `999.52`).

Purpose: `26-VERIFICATION.md` Truth 9 is FAILED — `push_ref`,
`release_tag_state` and `create_signed_release_tag` are substantively
implemented and well tested but have **zero non-test callers**, "exactly as
production-uncalled today as `GitFlow::push`/`delete_remote_branch` were before
this phase (the state RESEARCH.md identified as the problem to fix)." This plan
is the caller. It is the plan that turns three orphans into a sequence.

Output: `crates/devflow-core/src/release.rs` with `execute_release` and its
typed step report, plus the two small enabling changes its predicates need
(`version::version_in_contents`, and `pub(crate)` visibility on 26-03's SSH
signing test fixture).

**Both operator authorizations are already on record — cited, not re-asked.**
Direct push to `origin/develop` (D-01/D-08): `direct-push`, double-confirmed,
`26-01-SUMMARY.md` Decision 1 / coverage id `D1`. Unattended `cargo publish`
(D-04, one-way): `automate-publish`, double-confirmed, `26-01-SUMMARY.md`
Decision 2 / coverage id `D2`. No checkpoint is emitted for either.

**Resolved: how the executor detects that the human merged the release PR
(D-02).** `main` accepts squash merges only, so `main`'s release commit is never
a descendant of `develop`'s — an ancestry test would report "not merged"
forever. The predicate is therefore content-based: read the version file **as
it exists at `origin/main`** and compare the version it declares against the
computed release version. Until they match, the executor halts cleanly with an
actionable report and creates no tag. It never opens or merges that PR.

**Resolved: `compute_version` returns `UnreachableBaseline` mid-sequence, and
that error is the resume signal.** Once the release tag is created on
`origin/main`'s tip and before the sync lands, that tag is unreachable from
`develop` by construction (squash merge), so `compute_version`'s D-10 guard
(`version.rs:670-680`) refuses rather than silently falling back. This is not a
defect to route around: the tag it names is precisely the release in flight.
The executor treats `VersionError::UnreachableBaseline { tag }` at step 1 as
"resume the release identified by `tag`", parses the version out of it, and lets
step 3's `release_tag_state` validate that the tag really does belong to
`origin/main`'s tip — fail-closed if it does not.

**Consequence, stated plainly rather than hidden:** once a release is fully
complete (its tag reachable from `develop` after the sync), a re-run computes
the NEXT version and begins a new release. D-06's auto-skip resumes an
*in-flight* release; it is not a "the last release already finished" detector.
