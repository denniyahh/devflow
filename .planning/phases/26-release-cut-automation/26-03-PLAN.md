Add the three git primitives the release executor needs and DevFlow has never
had: pushing a ref to `origin`, creating the maintainer-signed release tag in the
exact documented form, and deciding whether a tag of that name already represents
a real, pushed, verified release.

production code anywhere has ever created a tag or pushed one. This plan is the

orchestration that will call it.

bare-remote test fixture every later push-mutating test reuses.

`hooks_after_ship`'s Ship-time lightweight-tag creation has ever fired against
this repository's real `develop` is not resolvable without the operator, and this

name collisions ARE possible. This is not merely defensive — RESEARCH.md verified
that of this repository's 12 `vMAJOR.MINOR.PATCH` tags, exactly one (`v1.3.69`)

of the collision's provenance.

    `pub fn release_tag_state(project_root: &Path, tag: &str, released_commit: &str) -> ReleaseTagState`. Never panics; every subprocess failure degrades to a non-`Released` variant. Evaluate in this order, short-circuiting:

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DevFlow process → `origin` refs | `push_ref` is the first production code that can move a ref on a shared remote. |
| DevFlow process → release provenance | `create_signed_release_tag` decides which key signs the artifact humans and GitHub treat as the release's proof of origin. |
| existing local refs → skip decision | `release_tag_state` decides whether a real signed tag gets created at all. |
