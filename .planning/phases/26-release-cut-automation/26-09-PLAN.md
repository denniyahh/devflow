<objective>
Stop `devflow release --execute --yes-release` and `devflow sync` from silently
acting on a repository the operator never named, per the recorded decision
**D-13**.

Purpose: `26-REVIEW.md` **C-06** is Critical and open. `project_root`
(`crates/devflow-cli/src/main.rs:662-683`) walks *up* to the nearest `.devflow`
ancestor. A phase worktree (`.worktrees/phase-NN/`) has no `.devflow`; the parent
checkout does. Phase 26 newly routed `release --execute` (`main.rs:629`) and
`sync` (`:637`) through that resolver — the first *irreversible* commands ever to
use it. A maintainer running the release command from a phase worktree, which is
this project's ordinary working posture, cuts a release from the **main
checkout's** branch, commits, and manifest, and is never shown the resolved path
before the mutation.

The compounding fact is what makes this Critical rather than surprising: **all
four entry guards — clean tree, on-develop, has-remote, and the pre-gate — test
the redirected root**, so a dirty worktree with a clean parent makes the executor
*more* likely to proceed, not less. The safety checks validate the wrong
repository.

Output: a distinct root resolver for mutating commands, wired into exactly two
call sites, an end-to-end regression test driving the real binary from a linked
worktree, and one sentence in CONTRIBUTING.md's existing preconditions list.

**The operator decision this needs is already recorded — cited, never re-asked.**
`26-CONTEXT.md` **D-13** (recorded 2026-07-30, commit `0e5df91`): a mutating
command must **refuse** when the project root resolves to a directory different
from the one it was invoked in, printing both paths and directing the operator to
`cd` or pass `--project`; read-only commands keep today's upward-walking
behavior unchanged. The audit-fix pass correctly escalated rather than picking a
cross-cutting policy unilaterally; the policy now exists in writing. This plan
emits **no** checkpoint and asks **no** question.

**Resolved, using the latitude D-13 grants: resolve mutating commands via
`git rev-parse --show-toplevel`.** D-13 explicitly permits this as "an acceptable
— arguably cleaner — way to satisfy this, since it makes a silent redirect
structurally impossible rather than merely detected", provided the refusal is
loud and names both paths. Two properties decide it. First, it is what these
commands actually need: D-13 records the verified fact that neither `release.rs`
nor `sync.rs` reads `.devflow` at all — zero references to `devflow_dir`,
`.devflow`, or `events::emit` in either module. They want a **git repository
root**; `.devflow` is merely the marker the pipeline resolver happens to search
for. Second, it produces the honest outcome D-13 describes for the worktree case:
a linked worktree *is* its own toplevel, so the resolver returns the worktree, the
executor's own guards then fire on the worktree's real branch and real dirty
state, and the operator is refused for the true reason instead of having the
parent checkout silently substituted.

**Where the refusal fires, then, is a subdirectory or a non-repository.** The
comparison is between the resolved toplevel and the path the operator supplied
(`--project`, defaulting to `.`) — not the process's working directory, because
an explicit `--project` is a named target and naming it is one of the two
remedies D-13 offers. Running the release command from `crates/devflow-cli/`
refuses and names the toplevel; running it from the repository root proceeds;
running it outside any repository refuses saying so.

**What this plan deliberately does not do.** It does not change `project_root`.
Read-only commands legitimately need to find the owning `.devflow` from a
subdirectory, D-13 keeps that behavior explicitly, and its existing unit test
must pass unmodified. It adds no bypass flag: a `--force`-shaped escape hatch
would recreate C-06 for precisely the operator most likely to be in a hurry.

**planning notes:** no requirement IDs exist on this project to probe, so
`must_haves` derive from `26-REVIEW.md` C-06's failure scenario and D-13's
clauses. The regression test is mandated by the review's own emphasis: it must
assert *which* repository the refusal is about, because today's code already
refuses in the worktree case for the wrong reason, and a test asserting only
"non-zero exit" would pass against the unfixed binary. This plan is CLI-only by
construction: it shares no file with 26-08, which is core-only.
</objective>
