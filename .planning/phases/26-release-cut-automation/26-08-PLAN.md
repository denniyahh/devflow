<objective>
Make an interrupted release cut resumable, by giving the release executor a
persisted step ledger that pins the in-flight release's identity — the one fact
live git state provably cannot supply — under the amended decision **D-06a**.

Purpose: `26-REVIEW.md` **C-02** is Critical, open, and was reproduced by
execution. Publish is step 5, after the sync step has merged `origin/main` (which
now carries the release tag) back into `develop`. That merge makes the tag
reachable, so the next `compute_version` adopts it as the baseline and returns
`version + 1`; `apply_bump` floors `Bump::None` to patch+1, so a re-run *always*
computes a new version. An operator whose publish step failed and who re-runs the
identical command therefore does not resume the interrupted release — they cut a
**second** one: `v0.1.0` stays tagged, pushed, synced, and permanently
unpublished, `0.1.1` that nobody asked for gets pushed to `origin/develop`, and
the command exits **0**. If `devflow-core@0.1.0` published and `devflow@0.1.0`
did not — the exact partial failure the two-package ordering makes likely —
crates.io is left split across two versions with no automated path back.

Output: `crates/devflow-core/src/release_ledger.rs`, the wiring in `run_release`
that consults and finalizes it, and a test that reproduces C-02's two-run
sequence and asserts the second run neither computes a new version nor pushes a
second bump.

**The operator decision this needs is already recorded — cited, never re-asked.**
`26-CONTEXT.md` **D-06a** (recorded 2026-07-30, commit `0e5df91`) amends D-06 and
authorizes a persisted step ledger for the release-executor resume path. The
audit-fix pass correctly refused to design this unilaterally because D-06 as
originally written forbade it; that constraint is now lifted in writing. This
plan emits **no** checkpoint and asks **no** question — D-06a is the answer.

**What D-06a permits is narrower than "a progress file".** The ledger is the
authority on *what this in-flight release already did*; live-state predicates
remain the authority on *what is actually true in git and on the registry*, and
**where the two disagree, live state wins**. The design consequence is sharp and
worth stating before any code is written: the ledger must never be the reason a
step is skipped. Every step keeps the live predicate it has today. The ledger
contributes exactly two facts that no amount of git archaeology can recover —
**which version this cut is for**, and **whether a cut is in flight at all** —
and nothing else.

**The mid-flight/finished distinction is the ledger's primary job, not a
detail.** D-06a says so explicitly. Without it the known gotcha stands: because
`UnreachableBaseline` is by-construction true mid-sequence, a re-run after a
*complete* release is indistinguishable from a fresh start and quietly begins the
next release. This plan closes that with a live-corroborated anchor rather than
by trusting the file: the ledger records `HEAD` at completion, and the refusal
fires only when live `git rev-parse HEAD` still names that commit.

**Format choice is a deliberate, documented decision (D-06a: reversibility
`costly`).** Once a released binary persists a ledger, later versions must read
what earlier ones wrote. This plan therefore fixes three things in writing: JSON
via `serde_json` (already a `devflow-core` dependency, and the format every other
persisted DevFlow record uses — `state-NN.json`, gate files, the registry), an
explicit `ledger_version` integer, and a stated compatibility contract — an
unrecognized `ledger_version` **refuses** rather than being ignored, because
ignoring it silently restores exactly the C-02 behavior being removed.

**Location is a correctness constraint, not a preference.** The ledger lives
under the repository's git common directory (`git rev-parse --git-common-dir`),
not in the working tree. `run_release`'s first entry guard requires
`git status --porcelain` to be empty; a ledger file in the working tree would be
untracked output that makes the resume run refuse with `DirtyWorkingTree` — the
fix defeating itself on its own second invocation. The common directory is also
shared across linked worktrees, which is the right scope for "a release of this
repository", and is never committed or pushed.

**Deliberately not in scope, and why.** This plan does not touch `version.rs`:
`apply_bump`'s `Bump::None` -> patch+1 floor is 25-D-10's deliberate behavior for
every ship, and narrowing it here would change the version every non-release
caller computes. The fix is to stop *asking* while a cut is in flight, not to
change the answer.

**planning notes:** no requirement IDs exist on this project to probe, so
`must_haves` derive from `26-REVIEW.md` C-02's reproduced failure scenario and
`26-CONTEXT.md` D-06a's four stated constraints (live state wins; mid-flight vs
finished; executor-only scope; no compensating action). `26-VALIDATION.md` row
B11 (fail-fast, no rollback) is owned by 26-06 and is cited here as a
non-regression, not re-tested. This plan is core-only by construction: it shares
no file with 26-09, which is CLI-only.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| persisted ledger -> release identity | A file on disk now influences which version is written, committed, pushed, tagged, and published. It is the first persisted input to an irreversible sequence. |
| ledger -> live git/registry state | The two can disagree. Which one wins, and whether the disagreement is visible, decides whether a stale file can cause a wrong release. |
| ledger file -> operator terminal | Persisted step details are read back and printed by the CLI, so untrusted git/cargo stderr can round-trip through the filesystem to a terminal. |
| ledger file -> the executor's own clean-tree guard | A file written by the executor is an input to the guard that decides whether the executor may run at all. |
