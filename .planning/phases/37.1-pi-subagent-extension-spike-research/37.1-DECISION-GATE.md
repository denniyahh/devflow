# Phase 37.1 — Decision Gate

**Verdict date:** 2026-08-17
**Verdict:** **NOT VIABLE** — there is no defensible "full-dispatch arm" for Pi in this
milestone. Phase 39 ships the already-scoped **reduced-capacity baseline** (D-02:
`Legacy`/`-p` + a new Pi-specific structured-completion parser), as the *only* arm.

## What the gate asked

> dispatch viable → full-dispatch arm; not viable → reduced-capacity is shipped.

## Evidence for the verdict (from `37.1-RESEARCH.md`, all code-verified against installed `pi` 0.84.1)

1. **Pi ships no subagent/dispatch tool in core.** Its toolset is `read`/`bash`/`edit`/`write`
   only. Dispatch is exclusively extension-provided (`pi.registerTool()`).
2. **The only credible implementation is the bundled example** (`examples/extensions/subagent/`
   inside `@earendil-works/pi-coding-agent@0.84.1`), explicitly example-not-product, not
   installed anywhere. All six third-party "pi-subagent" npm packages fail the
   package-legitimacy gate (SUS).
3. **DevFlow's drain-gate machinery cannot see Pi dispatch.** `CloseRule`/`PipeOwning` are
   hard-coded to Claude's `task_started`/`task_progress`/`background_tasks_changed` subtype
   vocabulary (`monitor.rs:582-609`); Pi's top-level `--mode json` is single-shot print mode, and
   `PipeOwning`'s stdin wire protocol deadlocks it (established independently by the Phase 38
   adversarial review against the same binary). A vendored `subagent` tool would surface only as
   an ordinary named `tool_call`/`tool_result` pair — invisible to `CloseRule` without new,
   Pi-specific code.

## Consequences

- **Phase 39 baseline is unchanged and unblocked:** `Legacy`/`-p` + `parse_pi_result`
  completion parser (the plan already carried this as D-02 with "no drain-gate claim").
- **Full Pi dispatch becomes an independently-scoped future phase**, requiring three
  separately-buildable pieces that none of the current milestone phases own:
  1. a vendored/authored `registerTool`-based dispatch extension, installed strictly at **user
     scope** (`~/.pi/agent/extensions/`, `~/.pi/agent/agents/`) — never project-local, to
     preserve `PiDriver`'s `--no-approve` trust boundary;
  2. a new Pi-specific completion/parser recognizing that extension's tool-call shape;
  3. a new Pi-specific drain predicate (name-string matching on a `subagent` tool call), since
     Pi has no task-lifecycle event vocabulary to reuse.
- **No package is installed and no code is written by this phase** — the six SUS packages are
  recorded as "do not adopt without human review + full source read."

## Open questions surfaced for Phase 39 (recorded, not decided here)

1. Whether the "full-dispatch arm" follow-on gets scheduled as a real phase now or moves to the
   backlog (roadmap call, not a research call).
2. What Pi's raw `--mode json` NDJSON looks like when a *registered extension* (not a built-in)
   tool is called — a ~15-minute live smoke test that should precede any future
   full-dispatch planning (see RESEARCH.md Assumption A1).

## Gate disposition

`dispatch viable → full-dispatch arm` is **closed as false**. `not viable → reduced-capacity
shipped` is the operative branch, and Phase 39 is released from this gate with the baseline
arm intact.
