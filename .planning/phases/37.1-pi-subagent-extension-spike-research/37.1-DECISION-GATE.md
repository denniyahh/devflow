# Phase 37.1 — Decision Gate

**Verdict date:** 2026-08-17 (REVISED — original NOT VIABLE verdict refuted by primary-source research)
**Verdict:** **VIABLE** — a working Pi subagent/dispatch extension exists: **`@bacnh85/pi-subagent`**
(synchronous, in-process, fails closed headless). Phase 39 ships the **full-dispatch arm**, re-scoped
to drop the `CloseRule`/drain-gate machinery that the original verdict was built around.

## What the gate asked

> dispatch viable → full-dispatch arm; not viable → reduced-capacity is shipped.

## What changed the verdict (see `research/RESEARCH-SUMMARY.md` + the per-reviewer logs in `.planning/reviews/phase-37.1/research/`)

The original NOT VIABLE verdict rested on two claims that primary-source research overturned:

1. **"No credible extension exists."** Wrong — the real npm registry holds 20+ installable
   Pi-subagent extensions, several actively maintained. The original research catalogued only 6 and
   dismissed all on metadata heuristics, without reading a line of source.
2. **"Full dispatch requires reusing `PipeOwning`/`CloseRule`."** Wrong framing — a *synchronous*
   extension whose `execute()` awaits its children keeps the parent `pi -p --no-approve` process
   alive until subagents finish, so **`MonitorLaunch::Legacy` process-exit supervision is
   sufficient**. No drain gate, no `PipeOwning`, no monitor change.

## Evidence for the verdict (file:line, source-verified)

- `@bacnh85/pi-subagent` is **in-process** (SDK sessions, not child processes —
  `extensions/index.ts:11`), **synchronous** (`await`), default `agentScope: "user"`
  (`index.ts:480`), and **fails closed headless** — project agents are refused without UI
  ("Project agents require explicit user approval", `index.ts:586-615`). It keeps a
  `DENIED_CHILD_TOOLS` recursion guard (`security.ts`).
- Because it is in-process, there is **no child `pi` argv** to re-trust project extensions, and the
  parent emits `DEVFLOW_RESULT` as plain text — caught by Layer 1's existing generic marker scan.

## Consequences

- **Phase 39 ships both arms:** Stage 1 baseline (`Legacy`/`-p` + `litellm` provider fix + completion
  detection) and Stage 2 dispatch (`@bacnh85` at user scope, no drain gate).
- **The `CloseRule`/`PipeOwning` "full-dispatch arm" is dropped** — it was the false premise, and a
  synchronous in-process extension needs none of it.
- **Trust boundary:** `@bacnh85` is the only finalist that works as-shipped; the process-spawning
  alternatives (`@dreki-gg`, `@smoose`, the bundled example) need a one-line `--no-approve`
  child-argv patch, and `@mystilleef` must NOT be used (it passes `--approve` to children and
  defaults `agentScope: "both"`).

## Open questions (carried to Phase 39 execution)

1. Whether `@bacnh85` is **installed** user-scope or **vendored-and-pinned** (a standing decision,
   not a gate — install at acceptance-test time).
2. In-process sessions share the parent's context window; that is a capability difference from
   Claude's isolated-context `Task`, not a blocker for this milestone.

## Gate disposition

`dispatch viable → full-dispatch arm` is **closed as true**, with the arm re-scoped to
"synchronous in-process extension under `Legacy` process-exit supervision — no drain gate."
Phase 39 is released from the gate with **both** stages in scope.
