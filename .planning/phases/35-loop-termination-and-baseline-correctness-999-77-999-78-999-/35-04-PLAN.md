<objective>
Give the Code↔Validate loop a bound that trivial per-cycle commits cannot defeat, and make the
Supervise gate message say how long the loop has actually been running.

Purpose: the only unconditional bound is gone. The streak resets whenever the commit count rises,
and the Code stage's fix command is a GSD command, which routinely commits planning artifacts even
when no source changed — so "commits something trivial every cycle" is the ordinary behaviour of the
thing in that slot. Meanwhile the gate message interpolates the streak, so it reads "failed 1 time"
at the 2nd, 5th and 9th gate alike, in the one mode where a human sees every occurrence.

Output: a never-reset per-phase total with a real persistence story, a ceiling that gates rather
than aborts, a message led by the cumulative number, and a distinct loop-back reason for the
absent-baseline case.
</objective>

<planner_findings>
**F-3 — the counter's lifetime, RESOLVED HERE rather than escalated. This is the decision A-11
demands be stated explicitly.**

The problem is real and was re-verified in source during planning: `State::new`
(`crates/devflow-core/src/state.rs`) zeroes every counter, and `commands::start()` calls it
unconditionally at `commands.rs:124`, `--force` included. A plain `State` field is therefore
**per-RUN**, while D-07 specifies a **per-PHASE** bound. Those are different lifetimes, and a bound
that resets on restart does not bound the case D-07 exists for.

`35-RESEARCH.md` presents two options and recommends the cheaper one — accept the reset, and
document a `--force` restart as a deliberate budget reset. **That option is rejected here**, because
it fails A-11's own stated test on its face: A-11 requires the reset event to be a real event
(phase completion, or operator approval at the ceiling gate) and specifically **not** "whenever a
new process starts". A `--force` restart is a new process start.

**Decision: the total is carried forward, and it is genuinely per-phase.** Two facts verified during
planning make this cheap rather than speculative:

1. State is persisted **per phase**, at `.devflow/state-{NN}.json` (`workflow::state_path`), so a
   prior run's value for this phase is on disk and readable at `start()` time.
2. `workflow::clear_state` is called on genuine workflow completion at
   `crates/devflow-cli/src/pipeline_gate.rs:225`, which deletes that file.

So the two reset events A-11 names both fall out as real events with no extra machinery: phase
completion deletes the file, so the next start for that phase finds nothing to carry and begins at
zero; and operator approval at the ceiling gate resets it explicitly. A `--force` restart on its own
resets nothing. Cost is one read site in `start()` and one reset site at the gate.

**F-6 — how a ceiling gate is told apart from an ordinary Supervise gate. Added after the second
cross-AI review pass (C2); without it this plan's reset rule has no defined behaviour.**

Re-verified in source during this revision: `crates/devflow-core/src/mode.rs:170-179` returns `true`
for `Stage::Validate` + `Mode::Supervise` **unconditionally** (`:174`). So in Supervise mode the
ceiling condition and the ordinary-gate condition overlap completely, and "the gate fired" carries
no information about *why*. A reset keyed on "a gate fired" therefore either fires at every
Supervise gate — so the total is cleared at every failure and never accumulates, defeating criterion
2 in precisely the mode where an operator sees every occurrence — or never fires at all.

**Decision: the ceiling is a named predicate of its own, used in exactly two places.** Add to
`mode.rs`:

- `pub fn phase_failure_ceiling_reached(phase_validate_failures: u32) -> bool`, returning
  `phase_validate_failures >= MAX_PHASE_VALIDATE_FAILURES`.

`Mode::should_gate`'s `Stage::Validate` arm calls it as a mode-independent disjunct **ahead of** the
existing per-mode match, so the ceiling gates in Auto and is a no-op in Supervise (which already
gates). Every site that needs to know *why* — the gate message's ceiling clause and the reset —
calls the same predicate directly against `state.phase_validate_failures`, never inferring it from
`should_gate`'s boolean.

This is deliberately not a second copy of the comparison: one function, two callers, so the
"call-site disjunct drifts from the predicate" hazard the finding below rejects does not reappear in
a new form. It is additive `pub` surface for `35-06` to record.

**F-7 — `print_dry_run` is a `should_gate` caller and needs an explicit answer, not a compile fix.
Added after the second review pass (A-M2); opencode's own enumeration of `should_gate` call sites
counted ten and missed these two.** Verified in source: `crates/devflow-cli/src/pipeline_gate.rs`
`print_dry_run` (`:523`) calls `should_gate` at `:534` and `:536`. Both are **prediction probes**,
not live reads — they pass literals (`0`, then `MAX_CONSECUTIVE_FAILURES`) to ask "would this stage
gate now?" and "would it gate after the streak ceiling?". The compiler forces them open; if the
executor closes them by passing a placeholder, `devflow start --dry-run` silently stops predicting
the new gate.

**Decision: a third probe branch, keeping the literal-probe idiom.** In order:
`should_gate(s, 0, 0)` → the unconditional-gate label; else `should_gate(s, MAX_CONSECUTIVE_FAILURES,
0)` → the existing after-N-failures label, reworded to say *consecutive*; else
`should_gate(s, 0, MAX_PHASE_VALIDATE_FAILURES)` → a new label naming the per-phase total. Pass
literals, not `state.phase_validate_failures`: the preview answers "what will this pipeline do", not
"where is this run right now", which is why the existing two probes use literals. No test in the
workspace asserts on this text (checked: `rg 'GATE after'` matches only the source line), so the
rewording is safe.

The other two callers take the live value: `run_gate` (`pipeline_gate.rs:309`, computing whether a
gate is "unexpected") and the Validate decision in `pipeline_outcomes.rs:428` both pass
`state.phase_validate_failures`.

**A third finding, which changes the shape of the gating check.** The gating condition is currently
`state.mode.should_gate(Stage::Validate, state.consecutive_failures)`, and at least four tests
(`pipeline_outcomes.rs:1682`, `:1764`, `:1836`, `:2428`) re-derive that same expression to mirror
the production decision. Adding the ceiling as an extra disjunct **at the call site** would leave
every one of those mirrors compiling untouched while silently no longer mirroring anything — which
is exactly the failure mode 34/D-06 names when it prefers structural guards over hand-audited
equality tests, and which this phase's own `Option<u32>` decision was taken to avoid. Therefore
**widen `Mode::should_gate` to take the per-phase total**, so the compiler enumerates every mirror
instead of a hand audit. This is a fourth `pub` signature change in `devflow-core`; under D-08 the
break is already bought and a version bump is a fixed cost rather than a per-item one, so the
marginal cost is documentation, which `35-06` collects.
</planner_findings>

<assumption_delta_decision>
The `assumption-delta scan` fired (`detected: true`, kind `pluralization`). The genuine transition
here is **one loop-termination signal becoming two**.

- **Primary noun:** `consecutive_failures`, the streak, remains primary.
- **Decision: `add-alongside`, deliberately, not `promote`.** The usual correct move on a
  generalization is to promote — but here promotion would contradict a locked decision. D-07 and the
  999.78 backlog entry both specify the new total as a **backstop meaningfully above**
  `MAX_CONSECUTIVE_FAILURES`, explicitly "rather than a competing primary bound". Promoting it would
  make the coarser signal primary and change when ordinary runs gate, which is not what was decided.
- **Accepted debt, and what would force a later promote:** two bounds means two numbers an operator
  must hold in mind, and the gate message now has to carry both without confusing them — which is
  why WR-04's headline requirement is part of this plan rather than cosmetic. If the streak bound is
  ever found to be defeated in the ordinary case rather than only under trivial per-cycle commits,
  the total becomes the primary bound and the streak demotes to a diagnostic.
</assumption_delta_decision>
