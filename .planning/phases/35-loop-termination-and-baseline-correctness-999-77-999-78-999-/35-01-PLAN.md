Three further findings, resolved here before the review pass:

**F-1 — the guard must make `git` ABSENT, not failing.** CONTEXT.md's A-13 says "a failing-`git`
shim placed first on `PATH`". That is the wrong shape and would produce a green test over an
unfixed defect. `phase_commit_count` reads the branch-existence probe as
`.output().map(|o| o.status.success()).unwrap_or(false)` — a shim that RUNS and exits non-zero
returns `Ok(status)`, so `unwrap_or(false)` is never reached and the function returns a real
observation, which under A-06 is `Some(0)`. Only `.output()` returning `Err` is the
could-not-measure case. That requires the binary to be unresolvable. Hence an empty-directory
`PATH`, never a script. This is NC-4 in `35-VALIDATION.md`.

**F-2 — the harness crate placement, DECIDED HERE.** The orchestrator's briefing stated that
`crates/devflow-core/src/test_support.rs` is exposed by a bare `pub mod test_support;` and is "not
feature-gated", and proposed a single shared guard on that basis. **That premise is false and was
checked against source during planning:** `crates/devflow-core/src/lib.rs:79` carries
`#[cfg(any(test, feature = "test-support"))]` directly above the `pub mod test_support;` at `:80`,
and the module's own header comment says so. Two consequences kill the shared-guard option:

1. `tempfile` is a **dev-dependency** of devflow-core (`crates/devflow-core/Cargo.toml`, under
   `[dev-dependencies]`). When devflow-cli builds devflow-core with `features = ["test-support"]`
   as a dev-dependency, `cfg(test)` is false for devflow-core and its dev-dependencies are absent —
   so a `tempfile`-based guard living under that feature gate would not compile for devflow-cli.
   Making it compile would require promoting `tempfile` to an optional real dependency of a
   crates.io-published crate: a fifth surface change in a phase whose deliverable is an exact
   enumeration of surface changes (D-08).
2. The shared option is also what creates the two-mutex `PATH` race the briefing warns about.

**Decision: one `NoGitPath` per crate, each using that crate's own single `PATH` mutex, and
devflow-core's is `#[cfg(test)]`-only.** The race is prevented *structurally*, not by discipline:
devflow-core's guard does not exist in any build devflow-cli can link, so a devflow-cli test can
never reach two guards holding two mutexes. Within devflow-cli there remains exactly one mutex
(`ENV_MUTEX`); within devflow-core there is exactly one (the new `PATH_MUTEX`); across crates cargo
gives each crate's tests a separate process. Criterion 6 gets the same harness *shape* rather than
the same symbol — recorded as a deliberate deviation from criterion 6's "the same harness" wording,
with this compile-level reason.

**F-1b — a residual risk this phase's source artifacts do not name, surfaced rather than hidden.**
`NeutralPath` is safe to hold while sibling tests run because it keeps a real `git` resolvable.
`NoGitPath` is the first guard in this workspace that makes `git` unresolvable process-wide, and
devflow-core has had **zero** `PATH` mutations until now (verified: `rg` for `set_var("PATH"` over
`crates/devflow-core/src/` returns nothing, while the same search over `crates/devflow-cli/src/`
returns six files — a real zero, not a broken search). Sibling tests in either crate that shell out
to `git` without holding the same mutex can therefore fail spuriously if they run inside a guarded
window. The mitigation is scope minimisation, enforced as an acceptance criterion below: each guard
region wraps exactly the one call under test. If flakes appear anyway, the recorded fallback is to
drive the `Err` branch through a non-existent `project_root` instead —
`hermetic_command` sets `cmd.current_dir(dir)` (`crates/devflow-core/src/git.rs:89`), so a
non-existent directory makes `.output()` return `Err` with no environment mutation at all. Do not
switch to that fallback pre-emptively; it deviates from F-1's directive and is recorded as an
escape hatch, not a plan.
</planner_findings>
