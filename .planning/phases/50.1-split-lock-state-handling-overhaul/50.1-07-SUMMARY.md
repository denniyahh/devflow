**The launcher now reserves a launch id, socket and held liveness file before it spawns, the real `__monitor` re-exec adopts that lock at fd 3 before it starts its agent, and the launcher drops its copy after the publish.**

- D-01's handoff works through the real launch path: `launch_stage` to `spawn_monitor` to the harness `__monitor` entry to `run_monitor`.

## What This Does Not Establish

- **A failed launch leaves its liveness file.** If `spawn_monitor` fails, or a supervisor errors before `run_monitor`'s last act, the hold drops and the file stays, reading `Abandoned`. This comes from reading the code; no test exercises it. The plan's threat register names `recover --clean` (50.1-21) for the SIGKILL leftover, and the same sweep rule covers this one. It is not swept until that plan lands.
- **No test pins the launcher's drop order.** Dropping the reservation earlier than the publish would pass the tracer, because the supervisor holds the lock by then. The order comes from the code and its comment, and it first matters once 50.1-16 and 50.1-17 read a pending record.
- **The liveness assertions ran through the harness entry only, in the capture shape.** E2e tests that run the real `devflow start` (for example `supervisor_e2e`) go through `spawn_monitor` and `--liveness-fd`, and they passed, but none of them asserts on the liveness file. So the real binary launches with the flag, and no test reads its lock. The stream shape's lock was not read by a test either.
- **An advance's supervisor (S(N) launching S(N+1)) was not driven with a lock on both sides by a test of its own.** The non-fd-3 path of `pass_to_child` is pinned by 50.1-05, and the suites that advance through the harness passed.
- **Passing runs are single runs,** so they say little about flake rates.
- **No guard reads the reservation yet.** That is 50.1-16 and 50.1-17, as the plan states.
