Decisions inside D-17 (Claude's remit, recorded here): the file is `.devflow/.holder-NN` (dot-prefixed; neither
`remove_stale_locks`' `lock-` prefix nor 50.1-21's `supervisor-*.live` sweep matches it; never removed). A contended
claim refuses that process at once rather than waiting (after 50.1-05's bounded wait past a probe's momentary lock, so
`stop` or `status` probing the file never makes a claim fail): the holder excludes a second foreground process for the
phase, as the long lock did for these four entry points, but no state write consults it. `start`/`resume` claim it
before `reserve_launch` and before any other workflow work, so a launcher refused by the holder writes nothing: no
pending record it would then have to give back, and none that a racing holder's own `spawn_next_supervisor` could
meet. Two concurrent `start`s are therefore decided by the holder while both are in their pre-spawn window and by the
reservation guard once the first has spawned; V-05 calls `reserve_launch` directly, so the reservation's own atomicity
proof and its lock-skipping control are unchanged. The holder's identity record (like the liveness and waiter records
of 50.1-05/-08) is advisory and outside D-09's scope: it is no state or gate file, its lock and not its bytes decides
liveness, and it is rewritten in place under the held lock through 50.1-05's `liveness::write_identity_record(&file)`
(`set_len(0)`, then one positional `write_all_at(.., 0)`; R-01: a rewrite at the descriptor's current offset would leave a
NUL hole that `live_holder` reads as `InvalidData`). A reader that races the rewrite sees an empty or partial record,
which `live_holder` reports as unreadable or which fails the start-time identity check, so `stop` refuses and signals
nothing. `.holder-NN` is not a `Hold::take` file and is never removed, so 50.1-05's temp-then-link publish (R-06) does
not apply to it: R-06's hazard needs a removal between a creator's `open` and its lock, and nothing removes this name,
so every claimer opens and contends on the same inode.

Decisions inside D-18 (Claude's remit, recorded here; D-18 itself is the operator's): the handler is
`liveness::install_holder_stop_handler` beside `supervisor::runtime::install_signal_pipe` in core (the CLI has no signal
code; core already does), and it is simpler than the supervisor's pipe because nothing waits on it: one `extern "C"`
handler for SIGTERM and SIGINT whose only act is an atomic store of the signal number, installed once per process with
`SA_RESTART` and an empty mask; exec resets a caught signal to its default, so the supervisors, agents and hook commands
a holder spawns are unaffected. It is installed by `commands::claim_foreground_holder` before the claim, so from the
moment the holder record names a pid that pid catches the signal. The safe points are the ones that exist: advance safe
points 1-6 (the hand-run `advance`; safe point 2, before `spawn_monitor`, for `start`, `resume` and a `devflow ship`
loop-back; 6 for finalization), and the foreground gate wait (safe point 4). `stop` keeps sending one SIGTERM
(`agent::terminate`); what changes is that a holder still running after `stop`'s bounded release wait is now the normal
case while it finishes a hook or a git step, so that outcome's message says what will happen. A safe-point return keeps
today's return value (safe point 1 returns `Ok(())`, so a stopped hand-run `advance` exits 0 after printing the
safe-point line); no new exit code is introduced. Limit, recorded for the docs plan (50.1-25): a terminal Ctrl-C reaches
the whole foreground process group, so a hook's own `git` child receives that SIGINT directly; D-18 covers `devflow stop`
and a signal sent to the holder's pid.
