<objective>
Retarget `stop`'s lock-holder arm to a per-phase holder file (CONTEXT D-17, operator 2026-10-24): every foreground
process that does workflow work outside a supervisor and outside a gate wait holds it for its lifetime, and `stop`
signals that holder after the same identity check it applies to the lock holder today.

Purpose: with the per-phase lock gone (D-08: 50.1-16 drops it from `start`/`resume`, 50.1-19 from `advance`, 50.1-20
from `devflow ship`), OPERATIONS.md's third `stop` arm — "the process holding `.devflow/lock-NN` is signalled" — would
reach nothing: a `start` busy before its spawn, a `devflow ship` finalizing and a hand-run `advance` would have no stop
path, while `status` and the launch guard tell the operator to run `devflow stop`. This plan must land before 50.1-20
deletes the last lock path. OPERATIONS.md's arm-3 wording is rewritten in 50.1-25. The long advance lock also kept a
hand-run `advance` from running beside a live supervisor (it waited, then failed); 50.1-19 deleted it, so this plan's
`advance_command` restores that exclusion with the launch guard's supervisor half (D-08, D-17), checked after the claim.
Output: `liveness::{phase_holder_path, claim_phase_holder, HolderError}`; the four entry points claim it (`start`/`resume`
before reserving); `advance_command`'s live-supervisor refusal; `stop_via_holder`; the V-29/V-30/V-31/V-32 tests; three
`stop_e2e` lock-holder tests rewritten onto the holder, five gate and stale-gate tests and the `hold_lock_by_a_child`
pair re-premised onto it, four `stop_via_lock` unit tests deleted as superseded; `supervisor_e2e`'s concurrent-start
assertion. `stop`'s and `devflow ship`'s help text and the help snapshot are 50.1-22's: that plan runs after 50.1-20 has

Decisions inside D-17 (Claude's remit, recorded here): the file is `.devflow/.holder-NN` (dot-prefixed; neither
`remove_stale_locks`' `lock-` prefix nor 50.1-21's `supervisor-*.live` sweep matches it; never removed). A contended
claim refuses that process at once rather than waiting (after 50.1-05's bounded wait past a probe's momentary lock, so
`stop` or `status` probing the file never makes a claim fail): the holder excludes a second foreground process for the
phase, as the long lock did for these four entry points, but no state write consults it. `start`/`resume` claim it
before `reserve_launch` and before any other workflow work, so a launcher refused by the holder writes nothing: no
pending record it would then have to give back, and none that a racing holder's own `spawn_next_supervisor` could
meet. Two concurrent `start`s are therefore decided by the holder while both are in their pre-spawn window and by the
reservation guard once the first has spawned; V-05 calls `reserve_launch` directly, so the reservation's own atomicity
proof and its lock-skipping control are unchanged. The holder's identity record (like the liveness and waiter records
of 50.1-05/-08) is advisory and outside D-09's scope: it is no state or gate file, its lock and not its bytes decides
liveness, and it is rewritten in place under the held lock (`set_len(0)`, then one `write_all`). A reader that races the
rewrite sees an empty or partial record, which `live_holder` reports as unreadable or which fails the start-time
identity check, so `stop` refuses and signals nothing.
