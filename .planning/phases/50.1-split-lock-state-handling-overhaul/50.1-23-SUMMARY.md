# Phase 50.1 Plan 23: resume close-and-report, status/doctor listing Summary

**`resume` now closes every stage's gate before it relaunches and names each answer it set aside or found claimed, and `status` and `doctor` list set-aside answers. However, R2-05's premise fails in three reachable cases, in which `resume` calls an applied answer "never applied".**

## Needs attention: R2-05's semantics check found counter-examples

The plan required this check and required any counter-example to be raised, not worked around. The premise is that every applied decision closes its gate before the stage runs again, or moves `state.stage` on. It does not always hold, so the "claimed but never applied" line can be wrong in these cases:

1. **`--until validate`, measured.** An approved Validate gate reaches `transition`, whose `stop_until == Some(from)` early return records the stop and closes nothing. A temporary test ran `run_gate_with_timeout` with an approval, then `transition`, then a real `resume`. The claim survived, and one `resume_found_unapplied_answer` event was written for an answer the run had acted on. The test did not go through a real supervisor and was not committed. Round 1's `gate_pending` conjunct hid this case, and dropping it exposed it.
2. **SIGKILL during Ship finalization, read not exercised.** `finish_workflow` runs the terminal hooks with the claim still on disk and closes the gate only after they pass. The line would then say "never applied" although a merge, bump or tag may have run. This is the wording most likely to mislead an operator.
3. **A close that fails, read not exercised.** The three sites the plan named:

| Site | What it does at HEAD | Stage afterwards | Ruling |
|------|----------------------|------------------|--------|
| `pipeline_outcomes.rs` L929, `handle_stage_failure` retry | `let _ = close_gate(..)`, still ignored | unchanged | Counter-example |
| `pipeline_outcomes.rs` L938, `handle_stage_failure` loop-back arm | `let _ = close_gate(..)`, still ignored | unchanged | Counter-example |
| `pipeline_gate.rs` L187, `prepare_loop_back_to_code` | `let _ = close_gate(..)`, still ignored | moves to Code | Not at an unchanged stage. The production callers fire from Validate and Ship. The pair would be misreported only if the run returns to that stage before a new gate opens there |

The same ignored close, at an unchanged stage, is also at `preflight.rs` L1421 and L1460, `pipeline_gate.rs` L299, and the re-scan arm in `pipeline_launch.rs` ("CR-01: close the gate now"). The plan did not name these. A smaller window of the same kind: `park_auto_rescan_repair` commits the stop before its close.

**Effect:** a wrong line and event on a run that is about to ask again. No answer is applied or lost by it. All of this is logged in `deferred-items.md`. None of these files were changed here.

**What holds:** the two crash windows the plan targets are reported correctly, and a pair at a stage the run has left stays silent.

## Carry-over from 50.1-18: the `status` hint

The hint is still true. `status` hints `devflow resume` for a stopped phase with a gone or unrecorded supervisor, and `resume` still relaunches there: the seeded tests use `stopped = true` with no supervisor record, and they launch.

One limit: for a stopped phase holding a stored Ship approval, the hint names only `resume`, which now sets that approval aside instead of leaving it for `devflow ship`. Nothing is lost, because the answer's bytes are kept, the rerun's gate asks again, and `resume`'s Ship line explains it. An operator who wanted the no-rerun path gets no hint of it from `status`. This comes from reading `status_hints`; no test covers it.

## Decisions Made

- `Severity::Info` is new. The plan asks for an info-level finding and the enum had none.
- The Ship line reads "next time, to apply a stored Ship approval without a rerun, run `devflow ship --phase N` instead of `resume`". The plan's action text omits "next time" and its must-have includes it. Without those words the line could read as a way to apply the answer just set aside.
- An operator's note is printed with `{note:?}`, so a typed control character reaches the terminal escaped.
- The un-stop commit also clears `gate_pending`, so that is one state write, not two. After a close error the flag still clears, as the plan says, and `doctor` reports any gate file left behind as an orphan.
