#### Unrecorded supervisor (ownership handoff)
- **D-01 (Operator): record before spawn.** Before spawning a supervisor, the launcher saves a *pending* supervisor
  record carrying the new launch id, under the write lock. The supervisor publishes under that id. This applies to
  `start`, to `resume`, and to stage N's supervisor spawning stage N+1.
  - A launcher that dies anywhere between the save and the publish leaves a record that the start/resume guard probes.
  - That closes A7 and C4 by construction, rather than by a socket sweep.
  - *Verified:* today the guard, given a loadable state, probes only `state.supervisor`
    (`crates/devflow-cli/src/commands.rs:3309-3321`). Its doc comment says the unrecorded case is "accepted until
    Phase 50.1" (`:3273-3274`).
  - *Scout:* the window runs from `monitor.rs:527` (spawn) to `pipeline_launch.rs:1747` (`publish_record` save).
  - Criterion 1's negative control stands: with no such supervisor, the launch proceeds.
  - The constraint: at every instant the state names every supervisor that might be live for this phase. At a stage
    handoff, S(N) and the pending S(N+1) are both live. So the pending record is a **separate field**, not a
    replacement of `state.supervisor`. (External review 2026-10-23, the DeepSeek lane: one slot cannot satisfy the
    constraint.)
  - **A pending record must be probeable before its socket exists (Claude, remit, from the review).**
    - *Verified:* `supervisor::probe` on a missing path returns GONE, and the guard maps GONE to "not live"
      (`commands.rs:3377-3378`). The record holds no pid (`state.rs:453-464`).
    - So a pending record probed by socket alone reads GONE during exactly the window it exists for, and A7/C4 move
      instead of closing. All three review lanes found this.
    - The mechanism: a per-launch liveness file (named by the launch id) whose `flock` is held continuously from
      before the pending save until the supervisor exits. The launcher takes it, the spawned supervisor inherits the
      descriptor deliberately and keeps it for life, and the launcher releases its copy after publish.
    - The guard reads a held lock as live, even before the socket is published. An unheld lock with no socket is an
      **abandoned** reservation (the spawn failed, or the launcher died before spawning). It reads GONE, and the next
      launch or `stop` clears it.
    - The planner may substitute an equivalent mechanism. It must answer both "spawned, not yet published" (live) and
      "reserved, never spawned" (abandoned) without a pid read.
  - **Check-and-reserve is one atomic step (Claude, remit, from the review).** The live-run guard and the pending save
    run under the same short write lock, so two concurrent launchers cannot both pass the guard. Two lanes showed both
    reserving once the long lock no longer excludes launches. This is mandatory, not discretionary.
  - **Fixture note (Verified, codex lane).** The guard also refuses on a live agent pid from the pid file
    (`commands.rs:3291-3294`), and the supervisor writes that file before it publishes (`monitor.rs:1493-1503`). So
    unchanged code can refuse an A7/C4 fixture merely because the agent is alive.
    - Each criterion-1 fixture must make the agent pid unable to cause the refusal: hold the supervisor before agent
      spawn, or end the agent.
    - A separate live-agent control must still refuse.
    - The crash table's "a second launch is not refused" wording for A7/C4 holds only for that window. Re-derive
      those rows.
  - — **Reversibility:** costly — every launch path changes its save order, and the crash-table rows must be
    re-derived.
- **D-02 (Operator): the repair is `stop`.** When the guard finds a live supervisor, recorded or pending, it refuses
  and names `devflow stop`. `stop` reaches a pending-record supervisor through its socket, exactly as it reaches a
  recorded one; once that supervisor is GONE, `resume` is safe. Criterion 2 also stands: neither `status` nor `stop`
  suggests `devflow resume` while that supervisor is live. Adopting the orphan was offered and not chosen.
  - `stop` over an **abandoned** pending record clears it, and reports what it cleared. The agy lane showed the wedge
    otherwise: today `persist_stopped_state` never clears `state.supervisor`.
  - Criterion 2's negative control: once the supervisor is GONE, `status` does suggest `resume`.
- **D-03 (Operator): a superseded supervisor writes nothing.** A supervisor whose launch id is not the one the state
  records ends without writing state, and logs an event saying why. This covers its advance and every other state
  write. This is the ownership-token half of the handoff.
  - *Scout:* today `advance_with` binds only by stage (`pipeline_launch.rs:2508-2532`) and never reads
    `state.supervisor.launch_id`.
  - *Verified (correcting an earlier "Claude's call"):* the launch id already travels to the supervisor by argv, and
    it is the socket's file-name segment. `record_supervisor_stop` already refuses a launch the state does not name,
    checking before and under the lock (`names_this_launch`, `pipeline_launch.rs:1430-1458`). D-03 generalises that
    existing check; it does not invent one.
  - **The fence covers more than state writes (Claude, remit, from the review).** Gate side effects are not state
    writes, yet they consume shared run state. Before any of these, a superseded supervisor ends instead:
    - consuming a gate answer;
    - writing an ack;
    - cleaning up gate files;
    - spawning the next stage.

    It also ends its own agent group, as a socket `stop` does (Phase 50 D-05). Otherwise its agent keeps changing the
    worktree. (Agy and codex lanes.)
  - A superseded but live supervisor cannot record its own stop (the existing refusal). That case needs a crash-table
    row and a stated outcome.
  - Criterion 5's negative control: a supervisor with the matching launch id writes normally and logs no refusal.

#### Gate answer binding (gate-waiter registration)
- **D-04 (Claude, remit): what registration means.** Opening a gate writes a fresh gate id into the gate file and
  registers the waiter against it.
  - This replaces Phase 48 D-02's side effect, where every waiting process holds the per-phase lock. The CLI answer
    writers (`gate respond`, `gate sweep`, `stop`) relied on that through `lock::holder_status`. With D-08 removing the
    long lock, they must identify the live waiter some other way.
  - **How (Claude, remit, settled after the review):**
    - The waiter holds a `flock` on a per-gate registration file for as long as it waits. A crashed waiter's
      registration therefore dies with it, unlike a plain marker file (agy lane).
    - Foreground waits register the same way: preflight gates in `start`, and `devflow ship`'s finalization retry.
      They have no supervisor socket (agy lane). So the supervisor socket alone is not enough, because `PingReply`
      carries no gate identity.
  - *Verified (DeepSeek lane): what goes stale once no gate wait holds the long lock.* Five call sites read
    `lock::holder_status` as "a waiter is live":
    - the `gate respond` refusal and its Ship `NoHolder` exception (`commands.rs:1535-1546`);
    - `gate_sweep_may_reap` (`commands.rs:1857-1859`), which would silently never reap;
    - `stop_via_gate`;
    - `answered_gate_contention_message`.

    All five move to the registration check, and T-48-16-02's mitigation text is rewritten.
  - **Writers pass the gate id they observed (Claude, remit, codex lane).** The id is taken from the gate they listed
    or were shown, not re-read at publish. They re-check it at publish, so a decision made about G1 cannot be
    relabelled onto G2 that opened at the same stage. `Gates::respond` and `Gates::reap` gain the observed id as a
    parameter.
  - **One atomic consumption claim (Claude, remit, codex lane).** Consuming an answer means publishing the ack
    exclusively (hard-link). The supervisor's wait and `devflow ship` (`ship_override`, a second consumer) both take
    it, so they can never both drive finalization from one approval. Today only the long lock separates them
    (`pipeline_gate.rs:556-559`).
  - The Phase 49/50 rig scripts drive gates through the CLI (`50-RUNBOOK.md`, `49-…/tools/negctl.sh`). They are
    updated with the new writers; otherwise D-12's live run cannot reach Ship (DeepSeek lane).
- **D-05 (Operator): the gate id is required.** An answer must carry the id of the gate it decides.
  - `devflow gate approve` and `devflow gate reject` fill it in. A hand-written `response.json` must copy it from the
    gate file; README, OPERATIONS and ARCHITECTURE must document this.
  - An answer with a missing or different id is refused loudly and logged. It is never silently consumed and never
    silently deleted.
  - **Refused answers are set aside, not left in the slot (Claude, remit, from the review).**
    - *Verified:* there is one response path per phase and stage (`gates.rs:131-136`). While it exists,
      `Gates::respond` refuses with `AlreadyResponded` (`:219-222`) and `list_open` hides the gate (`:170-172`).
    - So a refused answer left in place wedges the live gate: it can never receive a valid answer, and `gate list`
      shows nothing (DeepSeek and codex lanes).
    - Response storage is keyed by gate id. A refused answer is renamed to a quarantine name beside it, logged, and
      reported by `status` and `doctor`. That rename is not a silent deletion.
    - Criterion 4's test shows both halves: the stale answer is refused, **and** a valid answer is then accepted.
  - *Verified:* `GateResponse` today is `{approved, note, responded_by}` with no id (`crates/devflow-core/src/gates.rs:41-50`).
    The README documents hand-writing it without one (`README.md:171`).
  - *Verified:* no script in the repo writes a response file outside the CLI, by an `rg` for `response.json` outside
    `crates/` and `.planning/`. Only README, ARCHITECTURE and OPERATIONS matched.
  - Each stale-answer path in 999.130 and AR-48-04 gets a failing-then-passing test:
    - a waiter killed after an answer is written, then `resume`;
    - a late `Gates::respond` racing consume-and-cleanup;
    - the check-to-write window in the three CLI writers;
    - `start` failing to delete a leftover gate file.
  - — **Reversibility:** costly — this changes the documented operator interface and `devflow-core`'s public
    `GateFile`/`GateResponse`, which are not `#[non_exhaustive]` (Scout).
- **D-06 (Operator, revised 2026-10-23 after the review): a rerun asks again.** `resume` reruns the stage as today.
  The pending gate is closed, and any answer for it that was never used is set aside (D-05's quarantine), logged and
  reported. It is never applied to the gate the rerun opens, which has a new id. The operator re-answers after the
  rerun.
  - **Ship keeps its late path through `devflow ship`.** That path drives the stored Ship answer without rerunning

  - **Why the first answer was revised.** In the discussion the operator chose "keep the late-answer promise", on
    Claude's statement that `resume` re-opens the pending gate. That statement was wrong.
    - *Verified:* `resume` saves state and calls `launch_stage` (`pipeline_launch.rs:2334-2335`), and
      `resume_relaunches_without_consuming_a_pending_gate_answer` pins it.
    - So the README promise *was* AR-48-04 path (a): the leftover answer decides the rerun's new gate.
    - All three review lanes found the contradiction. The operator chose this option over "resume returns to the same
      gate", which would need every gate kind to persist its question and continuation.
  - README §gates ("a later answer still works, it just needs a `devflow resume`") and OPERATIONS are rewritten to
    match.
- **D-07 (Operator, after Claude's analysis at the operator's request): no answer carry-over.** A Supervise rejection

  - *Why (Verified):* the two gates ask different questions.
    - The re-scan gate asks "approve the changed human-only checkpoint set?" (`pipeline_launch.rs:2664-2740`).

    - *Verified (DeepSeek lane):* the Supervise `LoopBack` arm does no `Gates::cleanup` (`pipeline_launch.rs:2726-2742`).

      So the carried "no, needs review first" relaunches Code at once on the plan the operator just rejected.
    - The relaunched agent would then reach the same checkpoint, and the re-scan gate would ask again.
  - This reverses the Phase 48 review's "refuted as a defect — intended" note
    (`.planning/reviews/48-code-review-2026-09-22/VERIFIED.md` row C). It also changes the test

  - Auto mode's `park_auto_rescan_repair` path is unchanged.

#### Lock split
- **D-08 (Operator): split the lock.**
  - **Ownership:** the long-held per-phase lock no longer represents ownership. Ownership is the recorded launch id
    (D-01, D-03).
  - **Writes:** every state change goes through one `update_state(root, phase, |s| …)` that takes a short OS lock,
    re-reads the file, applies the closure, writes temp+fsync+rename+directory fsync, and releases the lock. No gate
    wait, agent run or lock wait holds that lock.
  - *Scout, clarified:* today `advance_with` takes the per-phase lock with `acquire_blocking`
    (`pipeline_launch.rs:2452`). It waits up to 600 s to *acquire* it (`:57`) and then *holds* it through every gate
    wait, up to `gate_timeout_secs`, which defaults to 3 days.
  - *Verified:* the copy loaded before a multi-day wait is saved back afterwards, merging only `gate_notify_cmd` from
    disk (`crates/devflow-cli/src/pipeline_gate.rs:466-474`). That is a lost update for any other change made during
    the wait.
  - **Hand edits: narrowed after the review (codex lane).** A hand edit that *completed before* a write's re-read
    survives. Examples: the `yes_ship` revoke, and `gate_notify_cmd`.
    - A hand edit that races an `update_state` can still be lost, because an editor that ignores the advisory lock
      cannot be excluded.
    - That residual stays an accepted gap, as Phase 48 D-03 recorded it. 50.1 shrinks the window from a multi-day
      wait to one write; it does not close it.
  - Launch exclusion is D-01's atomic check-and-reserve under the write lock; no other coarse lock is required. The
    constraint stands: no lock is held across a wait that a human or an agent controls.
  - The write lock's descriptor is close-on-exec and is never inherited by a spawned child. That is unlike D-01's
    liveness lock, which is inherited on purpose. Today's `lock.rs:216-224` documents the fork-inheritance hazard
    (DeepSeek lane).
  - Criterion 3's "no gate wait holds a lock" gets a test with a control. A test hook planted inside a gate wait
    tries the write lock and must get it; a control that holds the lock across the wait must fail that test.
  - — **Reversibility:** costly — this rewrites every state-writing call site and the CLI answer writers' liveness
    check.
- **D-09 (Claude, remit; corrected after the review): durability means three operations, not one.**
  - **Replace** (state, gate, ack where overwriting is correct): fsync the temp file, rename, then fsync the
    directory.
  - **Exclusive publish** (responses, and anything that is first-wins): fsync the temp file, hard-link, then fsync
    the directory. It never falls back to rename, which would break first-answer-wins (*Verified* by codex,
    `gates.rs:536-562`).
  - **Remove** (`clear_state`, gate cleanup, quarantine): unlink or rename, then fsync the directory. Otherwise a
    crash can resurrect a deleted record (`workflow.rs:364-371`, `gates.rs:378-389`).
  - The supervisor sidecar's hard-link publish also gets its directory fsync (`supervisor.rs:493-495`, agy lane).
  - *Verified:* `write_state_atomic` fsyncs neither the file nor the directory today (`crates/devflow-core/src/workflow.rs:239-252`).
  - A Rust source-scan test, in the style of `doc_check.rs`, fails on any `fs::write`, `rename`, `hard_link` or
    `remove_file` under the state and gate modules outside these three helpers. Its negative control is a planted
    bypass that must fail the test.
  - Power loss itself is not testable here, and the test does not claim to prove it.

## Summary

The phase replaces one coarse mechanism (a per-phase pid lockfile held by `advance` for up to 3 days, which today
supplies ownership, launch exclusion, waiter liveness, *and* write serialisation at once) with four narrow ones:
a short per-phase **write flock** around a re-read-modify-write (`update_state`); a **per-launch liveness flock**
inherited by the supervisor (ownership plus "spawned, not yet published"); a **per-gate registration flock** held by
whoever waits on a gate (waiter liveness); and **gate ids** carried by gate files, responses and acks (answer binding).
Every one of these needs only Rust std (`File::lock`/`try_lock`, stable since 1.89; the repo pins 1.97.1 and already
calls `File::try_lock` in `lock.rs:208`) plus the `libc` crate already in `devflow-core`'s dependencies for `fcntl`/
`dup2` in a `pre_exec` hook. **No new package is needed.**

The biggest planning risk is not the primitives but the call-site surface: 29 production `save_state` sites in 19
functions, 2 `clear_state` sites, 2 `clear_state_with_partial_result` sites, 22 production calls into the per-phase lock
(`acquire`, `acquire_blocking`, `holder_status`, `holder_identity`, `holder`) across `commands.rs`, `pipeline_gate.rs`,
`pipeline_launch.rs` and `recover.rs`, and 95 non-comment references to `.supervisor` under the two crates' `src/` (test modules included). All of these sites are
listed below with their functions. Two behaviours that today come *implicitly* from the long lock must be rebuilt on
purpose, or the phase regresses: (1) a fresh supervisor's in-process `advance` is ordered after its launcher's publish
save only because it blocks on the lock the launcher holds (doc comment `pipeline_launch.rs:1476-1480`); (2) `devflow
ship` and the live Ship waiter are kept from both finalizing one approval only by that lock (`pipeline_gate.rs:556-559`).

Two probes run this session changed the recommended mechanics. First, a std `File` opened as a process's first file
gets fd 3, so `dup2(fd, 3)` in `pre_exec` is a no-op that leaves `FD_CLOEXEC` set, and the "inherited" lock is silently
dropped at exec. Second, `File::unlock()` on the launcher's copy releases the lock the supervisor inherited, because
`flock` locks belong to the shared open file description. The launcher must only *drop* its copy. Both are reproduced
below, with negative controls.

**Primary recommendation:** Build bottom-up in `devflow-core` first (a durable-I/O module, the write flock and
`update_state`, gate identity and registration, the pending record and liveness flock, plus a `spawn_monitor` that takes
a caller-made reservation). Then migrate the CLI call sites file by file in one deliberate order. Carry the ownership
fence through the existing `with_stop_token` thread-local context rather than through 19 signatures. Close with docs,
the rig scripts, the crash-table re-derivation, and the human-action live run.

### Pattern 1: `update_state` with a short write flock and re-read

### Pattern 2: pending record plus inherited liveness flock (D-01)

**What:** before spawn, the launcher:
1. creates the launch id itself (today `spawn_monitor` makes it internally: `let launch_id =
   crate::supervisor::new_launch_id();`, `monitor.rs:458` `[VERIFIED]`), so `spawn_monitor` must accept it;
2. opens `liveness_path(launch_id)` and takes `File::lock()` (exclusive);
3. runs check-and-reserve inside `update_state` (Pattern 3), recording `pending_supervisor = { launch_id,
   socket_path, liveness_path }`;
4. spawns `__monitor` with a `pre_exec` that places the liveness fd at a fixed number and clears `FD_CLOEXEC`
   (probe-verified code below), and passes `--liveness-fd 3` (`[ASSUMED]` flag name);
5. waits for publish; promotes inside `update_state` (`supervisor = Some(record)`, `pending = None` if the pending
   launch id still matches); then **drops** its `File` (never `unlock()`; Pitfall 2).

The supervisor, first thing in `run_monitor`, re-marks fd 3 `FD_CLOEXEC` (so the agent and every hook it spawns never
inherit the lock), keeps it in a `File` for its whole life, and lets process exit release it.

The guard's liveness read for a pending record: open `liveness_path` separately (its own open file description) and
`try_lock()`. `WouldBlock` means live (launcher or supervisor holds it). `Ok` means abandoned. Release at once, then
clear the pending record in the same `update_state`. A missing liveness file also means abandoned. No pid is read.

```rust

`.devflow/supervisor-<launch_id>.live` `[ASSUMED]`), with the path recorded verbatim in the pending record. That
follows the existing rule for the socket ("passed to `probe` as recorded, never re-derived", `state.rs:283-291`). Use

plan must expose or mirror) before ever building a path from an id
read off disk.

**What a reservation means across the launcher's lifetime (recommendation):** take the liveness lock and reserve at the
point where `start`/`resume` take the long lock today (`commands.rs:367`, `pipeline_launch.rs:2241`), not just before

gates, so a concurrent `start` refuses before doing side effects (branch, worktree, state). D-01 says "before spawning";
reserving earlier also satisfies that. The guard's message for a held reservation with no socket must name `stop`

foreground launcher the way `stop_via_lock` reached a foreground `advance`. That is Open Question 2.

### Pattern 3: atomic check-and-reserve

`refuse_launch_over_a_live_run` (`commands.rs:3277`) and `possibly_live_sockets` (`:3309`) run **inside** the
`update_state` closure. They probe `supervisor`, `pending_supervisor` (liveness flock), the agent pid file, and, when
the state does not load, the socket sweep. Then they write the reservation in the same closure. The probes are bounded
socket round-trips (`IO_TIMEOUT: Duration = Duration::from_secs(2)`, `supervisor/protocol.rs:27` `[VERIFIED]`), so the
write lock can be held for a few seconds of probe I/O. That is not a wait a human or an agent controls, so D-08's
constraint holds. State it in the plan.

Fixtures must hold the second launcher between its probe and its reservation (a `test_hold` point inside the closure)
to show the first reservation makes it refuse. The control is the same fixture with the write lock bypassed, which
must let both reserve. That is a mutation-style negative control; see the Validation Architecture.

### Pattern 4: ownership fence through the stop-token context (D-03)

`run_monitor` already engages a thread-local context for the advance: `let stop_guard =
StopTokenGuard::engage(run.supervisor.token()); let advanced = advance_for_stage(project_root, Some(phase), stage);`
(`pipeline_launch.rs:1253-1254` `[VERIFIED]`), and the safe points read it through `with_stop_token`
(`:1045-1059`). Carry the supervisor's launch id in that same context, and have every write made under an engaged
context go through `update_owned_state`. The fence then reaches all 19 writing functions without changing their
signatures. A hand-run `devflow advance` (no context) uses the unfenced variant, as today.

The fence must also gate, before they run: consuming an answer (the exclusive ack), `Gates::cleanup`, `Gates::ack`,
and `spawn_next_supervisor`. A `NotOwner` result must: emit an event (for example `supervisor_superseded`
`[ASSUMED]`) with both launch ids; end its own agent group through the same path a socket stop uses; return without
writing. `record_supervisor_stop`'s existing `names_this_launch` (`pipeline_launch.rs:1430-1435`) becomes the closure's
check.

**Promotion timing (Pitfall 5).** Today a production supervisor's advance cannot start until its launcher releases the
long lock after the publish save (`/// A production supervisor gets the same ordering from \`advance\`, which takes the
per-phase lock its launcher holds until after the publish.`, `pipeline_launch.rs:1476-1480` `[VERIFIED]`). Without the
lock, a fast agent can finish before the launcher promotes `pending → supervisor`. The fence must therefore treat "my
id is `pending`" as *wait (bounded) for promotion*, not as *superseded*. The test build already has this wait
(`wait_for_launch_record`, `LAUNCH_RECORD_WAIT: Duration = Duration::from_secs(15)`, `:1474-1494`); reuse it in
production. What happens when the wait expires (launcher died: A7; S(N) died: C4) is Open Question 1.

### Anti-Patterns to Avoid
- **Full-copy commit under the lock:** writing a whole `State` loaded before a wait inside `update_state` keeps the
  lost update. Set only the changed fields.
- **Locking the state file itself:** it is replaced by rename, so the lock and the file diverge. Lock a never-replaced
  sidecar.
- **Spawning or waiting inside the `update_state` closure:** a child forked while the write lock is held keeps the
  lock until it execs (`lock.rs:220-224` documents exactly this for the coordination fd). Gate waits inside the
  closure violate D-08.
- **`unlock()` on the launcher's liveness copy:** it releases the supervisor's inherited lock (probe run 3).
- **Deriving "waiter live" from the supervisor socket alone:** `PingReply` carries no gate identity, and foreground
  waits have no socket (D-04).
- **Building a path from an unvalidated gate id or launch id read from disk:** path traversal (see Security).

## Common Pitfalls

### Pitfall 1: the fd-3 `dup2` no-op silently drops the inherited lock
**What goes wrong:** the liveness `File` is the process's first open file, so it is fd 3; `dup2(3, 3)` returns 3 and
leaves `FD_CLOEXEC` set; exec closes it; the guard reads the reservation "abandoned" while the supervisor runs.
**Why:** `dup2` with `oldfd == newfd` does nothing.
**How to avoid:** the branch in Pattern 2. Add a unit test that spawns a real child with the liveness fd as the first
open file, so the collision case is covered.
**Warning signs:** an A7 fixture passes only when some other file happens to be opened first.

### Pitfall 2: `unlock()` on any duplicate releases everyone's lock
**What goes wrong:** the launcher "releases its copy" with `file.unlock()`, which releases the supervisor's inherited
lock too (probe run 3).
**How to avoid:** the launcher drops the `File`. Add a source-scan assertion that no `unlock(` call exists on the
liveness handle.

### Pitfall 3: the write lock leaks into a child between fork and exec
**What goes wrong:** std opens with `O_CLOEXEC` (probe: `FD_CLOEXEC: true`), but a child forked while the lock is held
keeps it until exec (`lock.rs:220-224`). A spawn inside an `update_state` closure would hold the write lock for
however long that child takes to exec.
**How to avoid:** no spawn, wait or hook inside the closure. The criterion-3 test (a gate-wait hook that must acquire
the write lock) catches the wait case.

### Pitfall 4: the lost update survives as a full-copy commit
**What goes wrong:** mechanical migration replaces `save_state(&state)` with `update_state(.., |s| *s = state.clone())`.
**How to avoid:** a review checklist item per site, and a test in which a `stop` (`stopped = true`) lands during a
gate wait and survives the waiter's post-wait write. That is the direct regression for
`pipeline_gate.rs:466-474`.

### Pitfall 5: the supervisor's advance loses its ordering behind the launcher
**What goes wrong:** with no long lock, S(N)'s advance can run before `pending → supervisor` promotion, read itself as
"not recorded" and refuse.
**How to avoid:** a bounded wait for promotion (Pattern 4); a fixture with `test_hold("before_record_save")` and a
fast-completing agent.

### Pitfall 6: the rig scripts assume the long lock and the unkeyed response path
**What goes wrong:** `fault-arm.sh` asserts `[ "$lock_before" = live ]` and defines `gate_parked()` as gate file present
**and** `lock_status` live. It also uses `GATE_RESPONSE_REL=.devflow/gates/01-define.response.json` and
`LOCK_REL=.devflow/lock-01` `[VERIFIED: .planning/phases/50-addressable-monitor-liveness/tools/fault-arm.sh:46-48,
455-457, 533, 539]`. `kill9-at-gate` cannot pass unchanged.
**How to avoid:** a plan task that rewrites these to the registration flock and keyed paths, re-runs the script's own
selftest if it has one, and updates `50-RUNBOOK.md`. The CLI calls in the runbook (`"$BIN" gate approve 1 --stage
define …`, lines 152 and 160) and `negctl.sh:249` (`gate reject`) keep working if the CLI fills the id.

### Pitfall 7: `doctor` calls the pending socket "superseded"
**What goes wrong:** `doctor`'s sweep labels a socket whose launch id differs from the state's as `"its phase's state
records another launch (superseded)"` (`commands.rs:5742` `[VERIFIED]`). A legitimately pending S(N+1) would be
reported as an orphan.
**How to avoid:** every classifier of sockets against `state.supervisor` also consults `pending_supervisor`. There are
95 `.supervisor` references to audit.

### Pitfall 8: concurrent `start`s both scaffold before either reserves
**What goes wrong:** without the long lock, the guard at `commands.rs:377` no longer excludes a second `start`, which
then creates a branch and worktree, runs preflight gates and saves state (`:700`, create-or-replace), all before
reaching a pre-spawn reservation.
**How to avoid:** reserve at the top of `start`/`resume` (Pattern 2 recommendation), with a create-if-absent state
write.

### Pitfall 9: test-name gates that pass on zero matches
Integration tests have no module path: `cargo nextest run -p devflow --test start_lock_e2e --no-tests=fail -E
'test(=resume_refuses_a_phase_whose_recorded_monitor_is_alive)'`. Unit tests are module-qualified
(`pipeline_launch::tests::…`). One test per command.

### Pitfall 10: `#[non_exhaustive]` on gate structs breaks the CLI's struct literals
`GateResponse` is built by struct literal in the CLI (`commands.rs:1550-1554`) and in `Gates::reap`. Adding a field is
already a break (D-10 allows it). If the plan also adds `#[non_exhaustive]` (as `State` and `SupervisorRecord` have),
it must add a constructor, because `non_exhaustive` blocks literals from other crates, `devflow` included.

### Pitfall 11: a new directory entry is not durable until its parent is fsynced
`ensure_devflow_dir` can create `.devflow/` or `.devflow/gates/` on the first write. Fsyncing the file's directory does
not make the new directory's own entry durable; that needs an fsync of the parent. Low impact (first write of a run
only), but `fsync_dir` should cover it when it creates the directory `[CITED: fsync(2), same sentence as above]`.

// [VERIFIED: workflow.rs:205-208]. The function name is a proposal.
pub(crate) fn replace_durably(path: &Path, contents: &[u8]) -> std::io::Result<()> {
    let dir = path.parent().ok_or_else(|| std::io::Error::other("no parent"))?;
    let (tmp, mut file) = crate::workflow::create_unique_temp(path, std::process::id(), &TEMP_SEQ)?;
    let written = file.write_all(contents).and_then(|()| file.sync_all());
    drop(file);
    if let Err(e) = written.and_then(|()| std::fs::rename(&tmp, path)) {
        let _ = std::fs::remove_file(&tmp);
        return Err(e);
    }
    std::fs::File::open(dir)?.sync_all() // directory fsync: probe-verified Ok on this host
}
```

`remove_file(tmp)`, then the directory fsync. `remove_durably` is `remove_file` or `rename`, then the directory fsync.

## Open Questions

1. **What does a supervisor do when its own launch id is still only `pending` after the promotion wait expires?**
   (The orphan of A7/C4: its launcher died after spawning it.)
   - What we know: D-02 rejected adoption by the operator; D-03 says "a supervisor whose launch id is not the one the
     state records ends without writing state".
   - What's unclear: whether "recorded" includes `pending`. If the orphan may self-promote, A7/C4 self-heal; if not,
     it must refuse, end its agent group, exit (reading GONE afterwards) and leave the run for `resume`.
   - Recommendation: refuse, end the agent group, log, exit. This is the reading closest to D-02/D-03 and needs no new
     concept. **This is an operator decision**: it changes what an A7/C4 run does without intervention.
2. **Retire `stop_via_lock`, or retarget it?** With no long lock there is no lock holder to signal. A foreground
   `start` waiting at a preflight gate is reachable through its gate registration (an abort answer). A foreground
   launcher outside a gate (scaffolding) would have no stop path unless the liveness file records a pid and start
   time for identity-confirmed signalling. Recommendation: record the holder identity in the liveness and registration
   files, and retarget `stop_via_lock` to them. This is Claude's remit (D-02 says "the repair is `stop`").
3. **999.166 item 6's exit-file code:** fix it, or accept "the exit file keeps the agent's own code" with a reason.
   Accepting goes to the operator (D-13). Recommendation: propose acceptance with the reason that the exit file
   records the agent's exit, not the stop outcome.
4. **Release timing:** D-10 holds only if 3.0.0 is not cut before 50.1 merges (an operator decision, recorded in
   CONTEXT as such).
