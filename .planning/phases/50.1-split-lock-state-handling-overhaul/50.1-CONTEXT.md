# Phase 50.1: Split-Lock State-Handling Overhaul - Context

**Gathered:** 2026-10-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Every state write is serialised and durable, a gate answer can decide only the gate it was written for, and a live
supervisor is never joined by a second one, including a supervisor whose record was never saved. The five-part design
from backlog 999.130 is the spine:
- a short OS lock around every state write;
- an `update_state` API that re-reads under that lock;
- a launcher-to-monitor ownership handoff;
- gate-waiter registration, with answers bound to one gate;
- fsync of the file and its directory.

It closes Phase 50's two accepted OWNERSHIP rows (`50-CRASH-TABLE.md` A7 and C4, threats T-50-90 and T-50-91) and
rows D1 and D2 (power loss, stale gate answer).

are folded in (D-13).

## Implementation Decisions

### Carried forward (not re-opened)
- **Phase 50 D-20 (Operator): no migration.** No compatibility with state, gate or lock files written by an earlier
  binary. A new field may simply be required. Install the new binary only while no run is live.
- **Phase 48 D-04 (Operator): first answer wins.** Response publishing stays exclusive (hard-link). D-05 below adds

- **Phase 50 D-05/D-06 (Operator): teardown through the socket; only an explicit verb acts.** The sweep reports and

### Unrecorded supervisor (ownership handoff)
- **D-01 (Operator): record before spawn.** Before spawning a supervisor, the launcher saves a *pending* supervisor
  record carrying the new launch id, under the write lock. The supervisor publishes under that id. This applies to
  `start`, to `resume`, and to stage N's supervisor spawning stage N+1.
  - A launcher that dies anywhere between the save and the publish leaves a record that the start/resume guard probes.
  - That closes A7 and C4 by construction, rather than by a socket sweep.
  - *Verified:* today the guard, given a loadable state, probes only `state.supervisor`
    (`crates/devflow-cli/src/commands.rs:3309-3321`). Its doc comment says the unrecorded case is "accepted until
    Phase 50.1" (`:3273-3274`).
  - *Scout:* the window runs from `monitor.rs:527` (spawn) to `pipeline_launch.rs:1747` (`publish_record` save).
  - Criterion 1's negative control stands: with no such supervisor, the launch proceeds.
  - The constraint: at every instant the state names every supervisor that might be live for this phase. At a stage
    handoff, S(N) and the pending S(N+1) are both live. So the pending record is a **separate field**, not a
    replacement of `state.supervisor`. (External review 2026-10-23, the DeepSeek lane: one slot cannot satisfy the
    constraint.)
  - **A pending record must be probeable before its socket exists (Claude, remit, from the review).**
    - *Verified:* `supervisor::probe` on a missing path returns GONE, and the guard maps GONE to "not live"
      (`commands.rs:3377-3378`). The record holds no pid (`state.rs:453-464`).
    - So a pending record probed by socket alone reads GONE during exactly the window it exists for, and A7/C4 move
      instead of closing. All three review lanes found this.
    - The mechanism: a per-launch liveness file (named by the launch id) whose `flock` is held continuously from
      before the pending save until the supervisor exits. The launcher takes it, the spawned supervisor inherits the
      descriptor deliberately and keeps it for life, and the launcher releases its copy after publish.
    - The guard reads a held lock as live, even before the socket is published. An unheld lock with no socket is an
      **abandoned** reservation (the spawn failed, or the launcher died before spawning). It reads GONE, and the next
      launch or `stop` clears it.
    - The planner may substitute an equivalent mechanism. It must answer both "spawned, not yet published" (live) and
      "reserved, never spawned" (abandoned) without a pid read.
  - **Check-and-reserve is one atomic step (Claude, remit, from the review).** The live-run guard and the pending save
    run under the same short write lock, so two concurrent launchers cannot both pass the guard. Two lanes showed both
    reserving once the long lock no longer excludes launches. This is mandatory, not discretionary.
  - **Fixture note (Verified, codex lane).** The guard also refuses on a live agent pid from the pid file
    (`commands.rs:3291-3294`), and the supervisor writes that file before it publishes (`monitor.rs:1493-1503`). So
    unchanged code can refuse an A7/C4 fixture merely because the agent is alive.
    - Each criterion-1 fixture must make the agent pid unable to cause the refusal: hold the supervisor before agent
      spawn, or end the agent.
    - A separate live-agent control must still refuse.
    - The crash table's "a second launch is not refused" wording for A7/C4 holds only for that window. Re-derive
      those rows.
  - — **Reversibility:** costly — every launch path changes its save order, and the crash-table rows must be
    re-derived.
- **D-02 (Operator): the repair is `stop`.** When the guard finds a live supervisor, recorded or pending, it refuses
  and names `devflow stop`. `stop` reaches a pending-record supervisor through its socket, exactly as it reaches a
  recorded one; once that supervisor is GONE, `resume` is safe. Criterion 2 also stands: neither `status` nor `stop`
  suggests `devflow resume` while that supervisor is live. Adopting the orphan was offered and not chosen.
  - `stop` over an **abandoned** pending record clears it, and reports what it cleared. The agy lane showed the wedge
    otherwise: today `persist_stopped_state` never clears `state.supervisor`.
  - Criterion 2's negative control: once the supervisor is GONE, `status` does suggest `resume`.
- **D-03 (Operator): a superseded supervisor writes nothing.** A supervisor whose launch id is not the one the state
  records ends without writing state, and logs an event saying why. This covers its advance and every other state
  write. This is the ownership-token half of the handoff.
  - *Scout:* today `advance_with` binds only by stage (`pipeline_launch.rs:2508-2532`) and never reads
    `state.supervisor.launch_id`.
  - *Verified (correcting an earlier "Claude's call"):* the launch id already travels to the supervisor by argv, and
    it is the socket's file-name segment. `record_supervisor_stop` already refuses a launch the state does not name,
    checking before and under the lock (`names_this_launch`, `pipeline_launch.rs:1430-1458`). D-03 generalises that
    existing check; it does not invent one.
  - **The fence covers more than state writes (Claude, remit, from the review).** Gate side effects are not state
    writes, yet they consume shared run state. Before any of these, a superseded supervisor ends instead:
    - consuming a gate answer;
    - writing an ack;
    - cleaning up gate files;
    - spawning the next stage.

    It also ends its own agent group, as a socket `stop` does (Phase 50 D-05). Otherwise its agent keeps changing the
    worktree. (Agy and codex lanes.)
  - A superseded but live supervisor cannot record its own stop (the existing refusal). That case needs a crash-table
    row and a stated outcome.
  - Criterion 5's negative control: a supervisor with the matching launch id writes normally and logs no refusal.

### Gate answer binding (gate-waiter registration)
- **D-04 (Claude, remit): what registration means.** Opening a gate writes a fresh gate id into the gate file and
  registers the waiter against it.
  - **Order (Claude, remit, plan-phase 2026-10-25):** the waiter registers under the fresh id *before* the gate file is
    published, so a visible gate file always has a registered (or dead) waiter. Publish-then-register leaves a gap the
    removed per-phase lock used to cover, in which a CLI writer answering at once is refused "no registered waiter"
    (focused plan check after round 3). Implemented by `Gates::open_registered` (50.1-08), used by 50.1-14.
  - This replaces Phase 48 D-02's side effect, where every waiting process holds the per-phase lock. The CLI answer
    writers (`gate respond`, `gate sweep`, `stop`) relied on that through `lock::holder_status`. With D-08 removing the
    long lock, they must identify the live waiter some other way.
  - **How (Claude, remit, settled after the review):**
    - The waiter holds a `flock` on a per-gate registration file for as long as it waits. A crashed waiter's
      registration therefore dies with it, unlike a plain marker file (agy lane).
    - Foreground waits register the same way: preflight gates in `start`, and `devflow ship`'s finalization retry.
      They have no supervisor socket (agy lane). So the supervisor socket alone is not enough, because `PingReply`
      carries no gate identity.
  - *Verified (DeepSeek lane): what goes stale once no gate wait holds the long lock.* Five call sites read
    `lock::holder_status` as "a waiter is live":
    - the `gate respond` refusal and its Ship `NoHolder` exception (`commands.rs:1535-1546`);
    - `gate_sweep_may_reap` (`commands.rs:1857-1859`), which would silently never reap;
    - `stop_via_gate`;
    - `answered_gate_contention_message`.

    All five move to the registration check, and T-48-16-02's mitigation text is rewritten.
  - **Writers pass the gate id they observed (Claude, remit, codex lane).** The id is taken from the gate they listed
    or were shown, not re-read at publish. They re-check it at publish, so a decision made about G1 cannot be
    relabelled onto G2 that opened at the same stage. `Gates::respond` and `Gates::reap` gain the observed id as a
    parameter.
  - **One atomic consumption claim (Claude, remit, codex lane).** Consuming an answer means publishing the ack
    exclusively (hard-link). The supervisor's wait and `devflow ship` (`ship_override`, a second consumer) both take
    it, so they can never both drive finalization from one approval. Today only the long lock separates them
    (`pipeline_gate.rs:556-559`).
  - The Phase 49/50 rig scripts drive gates through the CLI (`50-RUNBOOK.md`, `49-…/tools/negctl.sh`). They are
    updated with the new writers; otherwise D-12's live run cannot reach Ship (DeepSeek lane).
- **D-05 (Operator): the gate id is required.** An answer must carry the id of the gate it decides.
  - `devflow gate approve` and `devflow gate reject` fill it in. A hand-written `response.json` must copy it from the
    gate file; README, OPERATIONS and ARCHITECTURE must document this.
  - An answer with a missing or different id is refused loudly and logged. It is never silently consumed and never
    silently deleted.
  - **Refused answers are set aside, not left in the slot (Claude, remit, from the review).**
    - *Verified:* there is one response path per phase and stage (`gates.rs:131-136`). While it exists,
      `Gates::respond` refuses with `AlreadyResponded` (`:219-222`) and `list_open` hides the gate (`:170-172`).
    - So a refused answer left in place wedges the live gate: it can never receive a valid answer, and `gate list`
      shows nothing (DeepSeek and codex lanes).
    - Response storage is keyed by gate id. A refused answer is renamed to a quarantine name beside it, logged, and
      reported by `status` and `doctor`. That rename is not a silent deletion.
    - Criterion 4's test shows both halves: the stale answer is refused, **and** a valid answer is then accepted.
  - *Verified:* `GateResponse` today is `{approved, note, responded_by}` with no id (`crates/devflow-core/src/gates.rs:41-50`).
    The README documents hand-writing it without one (`README.md:171`).
  - *Verified:* no script in the repo writes a response file outside the CLI, by an `rg` for `response.json` outside
    `crates/` and `.planning/`. Only README, ARCHITECTURE and OPERATIONS matched.
  - Each stale-answer path in 999.130 and AR-48-04 gets a failing-then-passing test:
    - a waiter killed after an answer is written, then `resume`;
    - a late `Gates::respond` racing consume-and-cleanup;
    - the check-to-write window in the three CLI writers;
    - `start` failing to delete a leftover gate file.
  - — **Reversibility:** costly — this changes the documented operator interface and `devflow-core`'s public
    `GateFile`/`GateResponse`, which are not `#[non_exhaustive]` (Scout).
- **D-06 (Operator, revised 2026-10-23 after the review): a rerun asks again.** `resume` reruns the stage as today.
  The pending gate is closed, and any answer for it that was never used is set aside (D-05's quarantine), logged and
  reported. It is never applied to the gate the rerun opens, which has a new id. The operator re-answers after the
  rerun.
  - **Ship keeps its late path through `devflow ship`.** That path drives the stored Ship answer without rerunning
    the stage (*Verified*, `pipeline_gate.rs:618-651`). It now goes through D-04's consumption claim.
  - **Why the first answer was revised.** In the discussion the operator chose "keep the late-answer promise", on
    Claude's statement that `resume` re-opens the pending gate. That statement was wrong.
    - *Verified:* `resume` saves state and calls `launch_stage` (`pipeline_launch.rs:2334-2335`), and
      `resume_relaunches_without_consuming_a_pending_gate_answer` pins it.
    - So the README promise *was* AR-48-04 path (a): the leftover answer decides the rerun's new gate.
    - All three review lanes found the contradiction. The operator chose this option over "resume returns to the same
      gate", which would need every gate kind to persist its question and continuation.
  - README §gates ("a later answer still works, it just needs a `devflow resume`") and OPERATIONS are rewritten to
    match.
- **D-07 (Operator, after Claude's analysis at the operator's request): no answer carry-over.** A Supervise rejection
  at the checkpoint re-scan gate no longer also answers the stage-failure gate that follows. That gate gets its own id
  and waits for its own retry-or-abort answer.
  - *Why (Verified):* the two gates ask different questions.
    - The re-scan gate asks "approve the changed human-only checkpoint set?" (`pipeline_launch.rs:2664-2740`).
    - The follow-on gate asks "stage failed: retry, loop to Code, or abort?" (`pipeline_outcomes.rs:903-930`). There,
      any non-abort answer relaunches the stage.
    - Supervise mode's unattended-launch check always returns `Ok`. This is stated in its doc comment
      (`preflight.rs:1096-1098`); the returning code line was not pinned. It covers only that check, not every
      preflight gate.
    - *Verified (DeepSeek lane):* the Supervise `LoopBack` arm does no `Gates::cleanup` (`pipeline_launch.rs:2726-2742`).
      Under per-gate ids, the follow-on gate's new id simply never matches the leftover rejection, so no cleanup is
      needed for correctness.
  - *Reasoned, not run:*
    - Preflight's other gates (major version bump, preflight-failure retry) do not ask about the rejected checkpoint.
      So the carried "no, needs review first" relaunches Code at once on the plan the operator just rejected.
    - The relaunched agent would then reach the same checkpoint, and the re-scan gate would ask again.
  - This reverses the Phase 48 review's "refuted as a defect — intended" note
    (`.planning/reviews/48-code-review-2026-09-22/VERIFIED.md` row C). It also changes the test
    `rejecting_the_rescan_gate_records_nothing_and_falls_through` (`pipeline_launch.rs:6169`): it must now show the

  - Auto mode's `park_auto_rescan_repair` path is unchanged.

### Lock split
- **D-08 (Operator): split the lock.**
  - **Ownership:** the long-held per-phase lock no longer represents ownership. Ownership is the recorded launch id
    (D-01, D-03).
  - **Writes:** every state change goes through one `update_state(root, phase, |s| …)` that takes a short OS lock,
    re-reads the file, applies the closure, writes temp+fsync+rename+directory fsync, and releases the lock. No gate
    wait, agent run or lock wait holds that lock.
  - *Scout, clarified:* today `advance_with` takes the per-phase lock with `acquire_blocking`
    (`pipeline_launch.rs:2452`). It waits up to 600 s to *acquire* it (`:57`) and then *holds* it through every gate
    wait, up to `gate_timeout_secs`, which defaults to 3 days.
  - *Verified:* the copy loaded before a multi-day wait is saved back afterwards, merging only `gate_notify_cmd` from
    disk (`crates/devflow-cli/src/pipeline_gate.rs:466-474`). That is a lost update for any other change made during
    the wait.
  - **Hand edits: narrowed after the review (codex lane).** A hand edit that *completed before* a write's re-read
    survives. Examples: the `yes_ship` revoke, and `gate_notify_cmd`.
    - A hand edit that races an `update_state` can still be lost, because an editor that ignores the advisory lock
      cannot be excluded.
    - That residual stays an accepted gap, as Phase 48 D-03 recorded it. 50.1 shrinks the window from a multi-day
      wait to one write; it does not close it.
  - Launch exclusion is D-01's atomic check-and-reserve under the write lock; no other coarse lock is required. The
    constraint stands: no lock is held across a wait that a human or an agent controls.
  - The write lock's descriptor is close-on-exec and is never inherited by a spawned child. That is unlike D-01's
    liveness lock, which is inherited on purpose. Today's `lock.rs:216-224` documents the fork-inheritance hazard
    (DeepSeek lane).
  - Criterion 3's "no gate wait holds a lock" gets a test with a control. A test hook planted inside a gate wait
    tries the write lock and must get it; a control that holds the lock across the wait must fail that test.
  - — **Reversibility:** costly — this rewrites every state-writing call site and the CLI answer writers' liveness
    check.
- **D-09 (Claude, remit; corrected after the review): durability means three operations, not one.**
  - **Replace** (state, gate, ack where overwriting is correct): fsync the temp file, rename, then fsync the
    directory.
  - **Exclusive publish** (responses, and anything that is first-wins): fsync the temp file, hard-link, then fsync
    the directory. It never falls back to rename, which would break first-answer-wins (*Verified* by codex,
    `gates.rs:536-562`).
  - **Remove** (`clear_state`, gate cleanup, quarantine): unlink or rename, then fsync the directory. Otherwise a
    crash can resurrect a deleted record (`workflow.rs:364-371`, `gates.rs:378-389`).
  - The supervisor sidecar's hard-link publish also gets its directory fsync (`supervisor.rs:493-495`, agy lane).
  - *Verified:* `write_state_atomic` fsyncs neither the file nor the directory today (`crates/devflow-core/src/workflow.rs:239-252`).
  - A Rust source-scan test, in the style of `doc_check.rs`, fails on any `fs::write`, `rename`, `hard_link` or
    `remove_file` under the state and gate modules outside these three helpers. Its negative control is a planted
    bypass that must fail the test.
  - Power loss itself is not testable here, and the test does not claim to prove it.

### Added at plan-phase (2026-10-24, from the research's open questions)
- **D-15 (Operator): an orphaned pending supervisor ends itself.** A supervisor whose launch id is still only in the
  pending slot when its bounded promotion wait expires (its promoter died: A7, or C4's S(N+1)) ends its agent group,
  logs an event saying why, and exits. It writes no state, consumes no gate answer, and does not promote itself
  (self-promotion is the "adopt it" option D-02 rejected). Afterwards it reads GONE: `status` suggests `resume`, and
  `stop` or the next launch clears the abandoned pending record (D-02). Staying alive until `stop` was offered and not
  chosen, because an unstopped orphan would live indefinitely.
  - The crash table's "S(id)'s promotion wait expires" row takes this as its outcome.
  - Within the wait, "my id is pending" means wait, not superseded (RESEARCH Pitfall 5).
- **D-16 (Operator): 999.166 item 6 is fixed, not accepted.** After a safe-point stop, the run's exit file records the
  stop outcome (143) rather than the agent's own exit code, with a failing-first test; Phase 50 plan 26's test E3,
  which pins today's behaviour, changes with it. The "agent group ended" success-line half of item 6 is fixed as
  before.
- **D-17 (Operator): `stop`'s lock-holder arm is retargeted, not retired.** With the per-phase lock gone (D-08),
  every foreground DevFlow process that does workflow work outside a supervisor and outside a gate wait — `start`
  and `resume` before their spawn, `devflow ship` during finalization, a hand-run `devflow advance` — holds a
  per-phase holder file for its lifetime: flock-held, recording its pid and start time, and never used to serialise
  state writes. `stop`'s third arm signals that holder after the same identity check it applies to the lock holder
  today (a recycled pid, or a record with no start time, is refused); no pid read from the state file is signalled.
  Retiring the arm and documenting the gap was offered and not chosen. (Plan-checker round 1, W4; RESEARCH Open
  Question 2.)
- **D-10 release timing (Operator, 2026-10-24):** 3.0.0 is cut only after 50.1 merges, so D-10 stands.

### Added after the external plan review (2026-10-25)
- **D-18 (Operator): a stop never lands inside a `devflow ship` finalization hook.** Today `stop`'s holder arm (lock
  arm before D-17) sends a bare SIGTERM (`agent::terminate`) and the foreground `ship_override` engages no stop token,
  so a stop can cut a merge, version bump, tag or push in half (pipeline_gate.rs safe point 6 comment). Every D-17
  holder process turns SIGTERM/SIGINT into a stop flag checked at safe points; `devflow ship` checks it between
  finalization hooks, so a stop lands before a hook starts or after it ends, never inside one. A fixture stops
  `devflow ship` during a finalization pass and asserts each hook either did not start or completed. Backlogging it
  was offered and not chosen.
- **D-19 (Operator): `stop` and `status` name an orphaned agent honestly.** When the supervisor is gone but the
  phase's agent still runs (supervisor SIGKILLed), `stop` and `status` name the live agent pid and the manual kill,
  never "nothing is running" or a `resume` that would refuse. A dead-supervisor + live-agent fixture pins it. A `stop`
  arm that ends the agent is backlog 999.170, not this phase. A full arm in 50.1 was offered and not chosen.

### Claude's Discretion
- **Reservation point (Claude, remit, 2026-10-24; RESEARCH assumption A3).** The atomic check-and-reserve runs at the
  top of `start`/`resume`, before scaffolding, not only immediately before spawn, so two concurrent starts cannot both
  scaffold and the second cannot overwrite the first run's state.
- The OS lock primitive and lock file for D-08: `flock` on a per-phase coordination file is the existing pattern,
  `lock.rs:196-212` (Scout).
- The `update_state` signature. 999.130 sketches `State` consumed by value across blocking calls; the goal is that no
  caller holds a `State` copy across a wait and then saves it.
