### CR-01: `status` and `doctor` send a `start` killed during preparation to a `resume` that launches an agent with no branch or worktree

**File:** `crates/devflow-cli/src/commands.rs:414` (reservation writes the fresh state), `:865`, `:1433`, `:1458`, `:6200`; `crates/devflow-cli/src/pipeline_launch.rs:3145-3247` (`resume_loaded`)

**Issue:** Before this phase `start` wrote no state until preparation had passed (the old `workflow::save_state` sat after all of it). `reserve_launch` now writes `fresh`, the whole unprepared state, before `start_reserved` runs. That state has `worktree_path: None`, no resolved base branch and no `workflow_started` event. Preparation can take a while: `ensure_base_ref_current`, `git worktree add`, the build staleness check.

Triggering sequence:

1. `devflow start --phase N` passes the reservation (commands.rs:414), so `state-NN.json` exists at Define with `pending_supervisor` set and `created = true`.
2. The process dies during `start_reserved` by SIGKILL, an OOM kill or SIGHUP. `install_holder_stop_handler` (liveness.rs:399-414) catches only SIGTERM and SIGINT, so closing the terminal is enough. `abandon_reservation` never runs.
3. `devflow status`: `probe_phase` maps no record plus a pending record to `GoneWhileActive` (commands.rs:1433), and `recovery_hints` prints `devflow resume --phase N` (commands.rs:1458). `doctor`'s `check_supervisor` names the same repair (commands.rs:6200).
4. `devflow resume --phase N`: the guard reads the reservation as abandoned, `reserve_launch` replaces it, and `resume_loaded` calls `launch_stage` (pipeline_launch.rs:3247). I found no branch or worktree guard on this path: `rg` for `current_branch|feature_start|ensure_phase_worktree|on_feature|branch_exists` in production `pipeline_launch.rs` and `preflight.rs` returned nothing, and `generic_preflight_checks` (preflight.rs:1258) checks none. The launch root falls back to `project_root` (`worktree_path.unwrap_or(project_root)`).

Result: an agent runs Define in the primary checkout on whatever branch is checked out, typically `develop`, with the prep guards (`ensure_phase_reachable_on_base`, `enforce_build_staleness`, the worktree fork) skipped.

The same applies after a `stop`: `clear_abandoned_reservation` leaves the state and `stop` marks it stopped, so `recovery_hints` still names `resume` (commands.rs:1475).

**Callers read:** `start`, `start_reserved`, `reserve_launch`, `resume`, `resume_loaded`, `launch_stage_inner` (first 40 lines), `generic_preflight_checks`, `probe_phase`, `recovery_hints`, `check_supervisor`. `tests/gate_wedge_e2e.rs:575-582` asserts that a killed start leaves its reservation in the state, then recovers with `recover --clean`; no test I found resumes it.

**Not established:** not run. A check deeper in `spawn_monitor` or the stage prompt could still refuse; I did not read `monitor::spawn_monitor` in full.

**Fix:** Mark a state whose run was never created, and refuse to resume it. An additive `State` field set only by `create_run_state`, or, better, do not write `fresh` as a full state at reservation:

```rust
// resume_loaded, before anything is mutated
if !state.run_created {
    return Err(CliError::Message(format!(
        "phase {phase}: its `devflow start` never finished preparing the run, so there is nothing \
         to resume; run `devflow start --phase {phase}` again"
    )));
}
```

Have `recovery_hints` and `check_supervisor` name `devflow start` for that state. Add a regression test: kill a `start` held at `holder_claimed`, then assert that `status` does not name `resume` and that `resume` refuses.

### WR-01: `doctor` calls a stored Ship approval "no gate file is open" and repairs it with the `resume` that sets the approval aside

**File:** `crates/devflow-cli/src/commands.rs:6071-6087`, `:6200-6202`, `:1458-1461`; `crates/devflow-core/src/gates.rs:1202-1210`

**Issue:** `Gates::list_open` hides a gate once a bound answer is in its slot. `build_phase_facts` derives `open_gate_stages` from that list. So in the exact scenario `devflow ship` exists for (operator ran `gate approve`, supervisor is dead, `gate_pending` still true):

- `check_gate_pending_without_gate` fires as a `Problem`: "gate_pending is true at stage ship but no gate file is open". The gate file is there.
- Its repair is `devflow resume --phase N`, and `check_supervisor`'s `GoneWhileActive` repair is the same.
- `resume` closes the gate and sets the approval aside (`close_gates_for_resume`), and OPERATIONS says "once `resume` has set that answer aside, `devflow ship` cannot apply it".

So following `doctor` loses the path OPERATIONS names, and reruns the Ship stage. The answer is set aside, not deleted, and `resume` reports it, so this is lost work rather than lost data.

`status` is better but still lists `resume` first and `ship` second (commands.rs:1458-1461), with nothing saying `resume` costs the stored answer.

**Trigger:** `gate approve N ship` with no waiter, or a supervisor killed after the answer landed, then `devflow doctor`.

**Callers read:** `doctor_in`, `build_phase_facts`, `check_gate_pending_without_gate`, `check_supervisor`, `recovery_hints`, `close_gates_for_resume`, `ship_override`, `claim_ship_answer`.

**Fix:** Give `PhaseFacts` a fact for a bound, unclaimed answer at `state.stage`. With no live supervisor and `stage == Ship`, name `devflow ship --phase N` alone, and word the detail as "holds a stored answer". In `recovery_hints`, name `ship` alone when that answer exists.

### WR-02: A `start` refused during preparation deletes a state file that does not load

**File:** `crates/devflow-cli/src/commands.rs:865`, `:413`; `crates/devflow-cli/src/pipeline_launch.rs:2083-2091`

**Issue:** `(Existing::Unloadable(_), Some(fresh)) => (fresh.clone(), true, true)` overwrites the unloadable file at reservation, before any preparation guard, and sets `created = true`. If `start_reserved` then fails (`ensure_agent_binary`, base-branch refusal, phase not reachable on base, staleness block), `abandon_reservation` calls `clear_state`, so the file is gone and no copy is kept. The note printed at :893 says only "replaced".

At the base commit the overwrite sat after preparation, so a refused `start` left the file alone. A loaded state already gets this right: its reservation is cleared and the old state stays. The comment at :413 says "a refusal changes nothing".

This matters because `stop` tells the operator to "repair or remove it" (commands.rs:2728), and because a state a different binary wrote can read as unloadable.

**Trigger:** a hand-damaged or other-version `state-NN.json`, then `devflow start --phase N` with, for example, a missing agent binary.

**Callers read:** `start`, `start_reserved`, `abandon_reservation`, `clear_reservation`. The tests at commands.rs:15277-15360 cover only a successful replacement and a refusal beside a live lock, not a refusal during preparation.

**Fix:** Move the unloadable file aside at reservation (for example `state-NN.json.unloadable-<launch_id>`), as gate answers are set aside, and name that path in the note. A narrower alternative is to defer the overwrite to `create_run_state`, which needs another way to carry the pending record while the file does not load.

### WR-03: 999.172's "only a hand edit" is wrong: `stop` can record `stopped` beside a supervisor it did not end, and exit 0

**File:** `crates/devflow-cli/src/commands.rs:3827-3834`, `:2720-2723` (`stop_in`, the gate arm)

**Issue:** ROADMAP 999.172 and deferred-items say the production writers of `stopped` are safe because "`devflow stop`'s write refuses a launch it did not end". The `PublishedUnconfirmed` arm returns `Some((stage, observed, run_launch))`, and `stop_in` adds `run_launch` to `known_launches` before `persist_stopped_state`. So the recorded launch counts as addressed though nothing ended or confirmed it.

The comment there says "the persisted `stopped` flag halts the run at its next safe point". 999.172 measured the opposite: safe points read the stop token, not the field, and an approved gate launched the next agent under a state reading `stopped`.

Triggering sequence:

1. `stop` passes `require_open` in `answer_with_hook`.
2. The waiter consumes an earlier approval and closes the gate, leaving the slot empty.
3. `stop`'s exclusive publish succeeds.
4. `.gates-NN.lock` is held past `GATE_LOCK_WAIT` (5 s), for example by a suspended `gate approve`.

Result: `stop` exits 0, the supervisor keeps going and launches the next stage, and `advance_with` refuses only when that stage's agent exits (pipeline_launch.rs:3394). One paid agent stage runs under a state reading `stopped`.

Without a wedged lock this path is `GateClosedAfterPublish`, which falls through to the socket correctly. So the window needs a race plus a wedge; it is narrow. It is reported because the record is wrong and the code comment states something measured false.

**Callers read:** `stop_in`, `stop_reap_observed_gate`, `persist_stopped_state`, `unaddressed_launch_refusal`, `answer_with_hook`, `advance_with`. Not exercised.

**Fix:** In that arm, return `Ok(None)` after printing, so the socket and holder arms still run and a live supervisor is shut down through its socket. If the abort did reach a waiter, the shutdown is harmless. Correct the comment and 999.172's Reach line.

**Merged:** two shards found this independently, by reading different callers. The second also cites `crates/devflow-cli/src/pipeline_launch.rs:1225-1227`, where `stop_requested_at_safe_point` reads only the stop token and holder signal.

**Checked at merge:** the cited lines were re-read against HEAD by the review orchestrator. Not run.

### WR-04: Recovery and the launch guard never ask the recorded supervisor's held liveness file

**File:** `crates/devflow-core/src/recover.rs:446` (also `crates/devflow-cli/src/commands.rs:4504`,
`possibly_live_sockets`)

**Issue:** For `state.supervisor`, `phase_may_be_live` probes only the recorded socket. A `Gone`
socket then counts as "nothing says it is live", although the supervisor still holds
`.devflow/supervisor-{launch_id}.live` for its whole life: `run_supervised_stage` adopts it
(`monitor.rs:1677`), and `run_monitor` releases it only after `finish` (`pipeline_launch.rs:1652-1655`).
That flock is the stronger signal, and the record's `launch_id` is enough to find it. Only the
pending record's liveness file is probed.

**Trigger:**

1. A supervisor is parked in a stage, with its agent finished or its pid file absent, and no gate
   waiter is registered yet.
2. Its socket under `~/.cache/devflow/sock/` is removed by something outside DevFlow, for example a
   cache cleaner or `rm -rf ~/.cache/devflow`. No in-tree path that removes a live supervisor's
   socket was found.
3. `devflow recover --clean --phase N` reads `Gone`. It passes `refuse_a_live_supervisor` and
   `explicit_decision`, closes the gates and deletes the state under a live supervisor.
4. `devflow start` also passes `refuse_launch_over_a_live_run`, because `recorded_live_socket`
   reads the same socket.

**Limits on the damage:** the fence should stop the old supervisor's next write, with `MissingState`
or `NotOwner`, but its agent can run on until the promotion watch or the next fenced step. The
trigger needs an outside deletion, which is why this is a warning and not a blocker.

**Callers read:** `recover::explicit_decision`, `sweep_decision`, `commands::refuse_a_live_supervisor`,
`possibly_live_sockets`, `monitor::run_supervised_stage`, `pipeline_launch::run_monitor`. Not
exercised.

**Fix:** probe the file in `phase_may_be_live`, and do the same in the launch guard:

```rust
if let Some(record) = &state.supervisor {
    if let Some(reason) = socket_may_be_live("supervisor", &record.socket_path) {
        return Some(reason);
    }
    if let Some(path) = crate::liveness::launch_liveness_path(project_root, &record.launch_id) {
        let held = crate::liveness::probe(&path);
        if let Some(reason) = hold_may_be_live("supervisor", &path, held) {
            return Some(reason);
        }
    }
}
```

Take care that a `stop_stale_launch` repair still finishes: a held `.live` should keep the phase
until the supervisor is ended, including after its socket is gone. That case needs a path to signal
it, because `stop` has no socket to use.

**Checked at merge:** the cited lines were re-read against HEAD by the review orchestrator. Not run.

### WR-05: A persistent read error on an answer slot ends a multi-day gate wait

**File:** `crates/devflow-core/src/gates.rs:1133-1134`, `crates/devflow-cli/src/pipeline_launch.rs:1401-1411`, `crates/devflow-cli/src/pipeline_gate.rs:617-622`
**Issue:** `read_answer` reports every I/O error other than `NotFound` as `AnswerRead::Unbound("unparsable")`, so
`await_answer` returns `Unbound`. `await_bound_answer` then runs `fenced(set_aside_unbound)`, which takes the write
lock and gate lock and reads the file again. If that also fails, the error ends the wait and `run_gate_with_timeout`
finishes the registration and returns `Err`.

Trigger: the slot read fails with `EIO`, `ESTALE`, `ENFILE` or `EMFILE`, and the failure persists through the
set-aside step. A wait lasting days can cross such an episode. `runtime.rs` already treats persistent `EMFILE` as a
real state for this process (`accept_all`).

Result: the supervisor unwinds with an error naming a file that "does not bind ... (unparsable)", although the body may
be a valid answer. The gate file stays open with no waiter and `gate_pending` true. The pre-phase poll loop ignored
read errors and kept waiting, so this is a regression in robustness.

A single transient failure recovers, because the second read succeeds and the bound answer stays. No answer is lost:
the file stays in the slot.

Callers read: `wait_for_gate_response`, `await_bound_answer`, `run_gate_with_timeout`. Not exercised.
**Fix:** separate "unreadable" from "does not bind". Log the error and keep waiting, reading again at the next backoff:
```rust
Err(error) => {
    warn!("could not read gate answer {}: {error}", path.display());
    AnswerRead::Unreadable(error.to_string()) // await_answer: treat as None, keep waiting
}
```
Other `read_answer` callers (`list_open`, `stop_with_existing_response`, `claim_ship_answer`) need the new arm too.

**Checked at merge:** the cited lines were re-read against HEAD by the review orchestrator. Not run.

### WR-06: A pre-authorized answer's waiter abandons its own open gate, and a fenced answer can hold the write lock past the stated bound

**File:** `crates/devflow-cli/src/pipeline_gate.rs:603-615`, `crates/devflow-core/src/gates.rs:1014`, `:1034`, `:182`, `:3201`, `crates/devflow-core/src/workflow.rs:646`

Err(GateError::AlreadyResponded { .. } | GateError::PublishedUnconfirmed { .. }) => Ok(()),

### WR-09: A signal to a foreground `start` parked at a preflight gate records a resumable stop, then deletes the state

**File:** `crates/devflow-cli/src/commands.rs:774-779`, with `crates/devflow-cli/src/pipeline_gate.rs:690-703` and `crates/devflow-cli/src/preflight.rs:1407-1421`

**Issue:** `start_reserved` removes the state on any `launch_stage` error. A stop honoured at safe
point 4 is such an error, by design: it returns `Err` after recording `stopped`, and the comment at
`pipeline_gate.rs:695` says it does this because "a stopped run keeps its state for `devflow resume`".
On this path the state is deleted a few statements after it was written.

**Sequence:**

1. `devflow start` hits a failing preflight check. `launch_stage` calls `run_preflight`, which calls
   `run_gate` in the foreground with the multi-day timeout.
2. The operator presses Ctrl-C or sends SIGTERM to the pid. `install_holder_stop_handler` catches both
   (`liveness.rs:400`). This is new in this phase: at `949f848` the only SIGTERM/SIGINT handling in `crates/` was the supervisor's, so a foreground `start` took the default action.
3. `wait_for_gate_response` returns `Stopped`. `record_advance_stop(state, 4)` writes `stopped` and
   emits `advance_stopped`, and an `Err` unwinds.
4. `start_reserved` runs `workflow::clear_state`. The state is gone, while the event stream shows a
   stop at a safe point. `devflow resume` then fails with a missing state.

`devflow stop` takes the gate-answer arm instead and aborts, so only a direct signal reaches this.

**Reach:** I read the callers listed above. The existing test
`commands.rs:17056` (`stop_signals_a_start_that_has_not_spawned_its_supervisor`) covers safe point 2
only, which returns `Ok` and keeps the state. I found no test for this safe-point-4 path, by a search
of `commands.rs` and `stop_e2e.rs` for the holder reason, not an exhaustive read.

**Limit:** no agent has run at this point, so no agent work is lost. What is lost is the run record and
its resumability. What a following `start` does over the leftover branch was not traced for worktree
mode; the deferred items record that a plain `start` stopped on the existing branch in one measured case.

**Fix:** keep the state when the launch ended as a stop:

```rust
if let Err(err) = launch_stage(&mut state, None, None) {
    if crate::pipeline_launch::stop_requested_at_safe_point() {
        return Err(err); // the stop is recorded; `devflow resume` continues it
    }
    // existing clear_state path
}
```

Note that `stop_requested_at_safe_point` reads the holder's flag here, which is what this needs.
Add a test that signals a `start` parked at a preflight gate and asserts the state survives.
