## Deviations from Plan

**1. [Rule 2 - Missing Critical] An unconfirmed shutdown at safe point 3 keeps the pending record**
- **Found during:** Task 2
- **Issue:** the plan clears the record and discards the reservation after `shut_down_unpublished`, which only warned on a failure. Clearing would hide an N+1 that may still run, against this plan's own success criterion.
- **Fix:** `shut_down_unpublished` returns whether the stop was confirmed. `end_unpublished` clears and discards only then, and otherwise just drops the launcher's copy of the lock.
- **Verification:** `an_unconfirmed_stop_at_safe_point_3_keeps_the_pending_record`, with the control above. It uses an absent socket, not a `HandedOff` or `Refused` answer.
- **Committed in:** `c2ab424`

**2. [Rule 2 - Missing Critical] The publish save enforces the plan's prohibition**
- **Issue:** the prohibition says the promotion only happens while `pending_supervisor` still names N+1, but `save_publish_fields` wrote the record unconditionally.
- **Fix:** it refuses unless the state names the launch as pending or already records it, which `publish_record`'s second save needs. `publish_record` then runs its existing shutdown path.
- **Test change:** the fixture of `the_publish_save_commits_only_the_record_and_a_stop` now plants a pending record, as every real launch has. Its assertions are unchanged.
- **Committed in:** `1a8f52d`

**3. [Rule 1 - Bug] A refusal over a live pending record would have cleared that record**
- **Issue:** `record_failed_launch` clears whatever pending record its in-memory copy names, so the plan's refusal would have erased a live launch's record on the way out.
- **Fix:** on `Err`, `commit_pending_record` drops the record from the caller's copy only, since this launch wrote nothing. It also emits `launch_refused_over_live_pending`, because a supervisor's stderr is `/dev/null`.
- **Committed in:** `1a8f52d`

**4. [Rule 1 - Bug] The bridge from 50.1-16 now covers a handoff**
- **Issue:** `wait_while_launch_is_pending`'s comment said a handoff does not wait. With a pending record it does, which is the ordering the brief flagged.
- **Fix:** comment corrected. No code change was needed, since the wait is keyed on the launch id.
- **Note:** N still holds the per-phase advance lock across the publish, so a handoff has two orderings today. 50.1-19 removes the lock and replaces the wait.
- **Committed in:** `1a8f52d`

**5. [Rule 3 - Blocking] Order of work differs from the plan's task split**
- `test_hold("after_pending_save")` went in with Task 1's GREEN, because the save it follows is there. That is why two of Task 2's tests have no RED run.

**6. [Additions] Tests and a case beyond the plan**
- `the_publish_save_refuses_a_launch_the_state_no_longer_names`, `a_launch_over_a_live_pending_record_is_refused_and_keeps_it`, `an_unconfirmed_stop_at_safe_point_3_keeps_the_pending_record`.

## Behaviour Change To Check In 50.1-19

A launch whose launcher died used to advance after its 15 s wait and launch the next stage. It now reaches its next handoff with its own pending record, which is live because it holds that lock, so the launch is refused and the error names both ids. `supervisor` is cleared, the pending record stays until that supervisor exits, and the next launch clears it. This matches 50.1-19's rule that an orphan does not advance, but it is not 50.1-19's end state, because that supervisor neither ends its agent early nor emits `supervisor_superseded`. `start_lock_e2e` and the other suites pass, and none of them exercises this path.

## Not Established

- **The orphan path above was not run end to end.** The refusal logic is unit-tested with another launch's record, not with a supervisor refusing over its own.
- **`devflow stop --phase N` in the C4 window was not checked.** The refusal names it, as the plan requires, and 50.1-18 makes it work with no socket. V-02 ends N+1 through its socket.
- **C4 is tested with N+1 held before its agent spawn.** A kill after N+1's agent spawn and before the publish was not driven; the record and lock are the same there, and the pid file may also refuse.
- **V-02 and the window tests run through the test harness's `__monitor` entry,** not the real binary.
- **The fast-agent ordering at a handoff is not forced end to end,** and today's advance lock would mask a broken wait. 50.1-19's V-24 covers it.
- **One run of each suite is weak evidence for timing.** The RED runs and controls show these tests can fail, not that they are free of flakes. The fixed-point kills land at hold points, so they do not sample the rest of each window.
- **`.supervisor` destructuring** was not searched in the audit.
