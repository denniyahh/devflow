# Phase 50.1 Plan 01: Durable File Helpers Summary

**Every state and gate write, publish and removal in `devflow-core` now goes through `durable.rs`, which fsyncs the file and the directory, and a source scan keeps it that way. The tests prove the fsync calls are made in order; they do not prove survival of a real power loss.**

## Accomplishments

- `save_state` and the gate request/ack writer use temp, fsync, rename, directory fsync, proven by an ordered recorder.
- A gate response is published by fsync, hard link, directory fsync, with no rename fallback. First answer wins is unchanged.
- `clear_state`, gate cleanup and the legacy migration remove and rename through the helpers. The migration's decisions are unchanged; 50.1-09 deletes it.
- `create_dir_all_durably` fsyncs the parent on every successful return, including when the directory already existed (R2-08). `ensure_devflow_dir` does the same for the `.devflow` entry when given a directory below it.
- `rename_to_unique_durably` is ready for 50.1-06's quarantine: a no-replace hard link with a retry on a taken name.
- The `ensure_devflow_dir` deleted-marker note was wrong and is corrected: the next call recreates a deleted `.gitignore`. A new test pins this.

## Not Established

- **Power loss.** No power loss is reproduced. The recorder shows the calls are made, in order, on this host's filesystem.
- **Container parity.** `scripts/check-in-container.sh` was not run; the plan does not ask for it. Directory fsync was exercised only on this host's filesystem, so a filesystem that refuses it is untested.
- **fsync failure paths.** No test injects a failing fsync or a failing temp write, so the temp removal after a failed write or file fsync is not exercised. By reading the code: if the directory fsync fails after a successful unlink, `remove_durably` returns `Err`, so `clear_state_with_partial_result` and `cleanup_with_partial_result` report `removed = false` for a file that is gone, and a retry reads `Ok(false)` without syncing. The error is still surfaced to the caller. Likewise a replace or publish whose directory fsync fails returns `Err` with the new bytes in place, so a retried publish gets `AlreadyResponded`.
- **A new way to fail.** Every `ensure_devflow_dir` caller now needs read access to the parent of the directory it is given, and a directory fsync that succeeds. Either failing is an error at callers where `create_dir_all` used to succeed; `events::emit` logs a warning and drops the line. No test covers an unreadable parent. The existing suites pass, which shows only that none of them hits this.
- **A real two-process race.** The racing-creator branch is tested by calling `create_component_durably` on an existing directory, not by racing two processes. The two-process quarantine test is 50.1-06's.
- **Intermediate components.** One another process made, other than `.devflow`, is not re-synced. DevFlow has none. This is the plan's stated limit.
- **The scan's reach.** It is a text scan of `workflow.rs` and `gates.rs`. A renamed import (`use std::fs as f; f::write(`) or an `OpenOptions` write is not seen.
- **Routing under mutation.** The mutation pass covered `durable.rs` only, not the call sites in `workflow.rs` and `gates.rs`. Those rest on the recorder tests and the scan.
- **Cost under load.** The R2-08 cost table is read from the code, not measured.
