# Phase 52.2: Foreground Runner - Context

**Gathered:** 2026-11-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Each stage runs in the foreground of the DevFlow runner process that started it; the detached supervisor and the
liveness machinery that exists only for it are removed. Every run is a user service (`systemd-run --user`), which is
what covers a hard kill. The decisions carried from Phase 52.1 are rebuilt on the simpler runner, and the phase ends
with 52.1's proof: a supervised run drives a phase from Plan to a finished Validate without hand-run stages or
hand-edited state. Not dogfooded itself (operator, 2026-11-11). No REQ IDs; plans bind to the decisions below and to
the carried 52.1 decisions.

</domain>

<decisions>
## Implementation Decisions

Provenance is per item: **(operator)** = the operator chose it in this discussion; **(agent)** = decided inside the
agent's remit and stated to the operator during the discussion.

### Run shape
- **D-01 (operator):** Every run is a user service. `start` and `resume` always launch the runner with
  `systemd-run --user`, a fixed unit name derived from project and phase, `-p KillMode=control-group` and `--collect`;
  they print the unit name and the `devflow status` / `devflow logs` lines and return. There is **no user-facing
  terminal-held run and no `--foreground` flag.** Operator's reasoning: a held terminal accepts no DevFlow commands and
  only shows progress lines (agent output goes to `.devflow/` files), so it is a log tail, not a run type.
  — **Reversibility:** reversible — the CLI is `4.0.0-alpha.1` and unpublished.
- **D-02 (agent, follows D-01):** The runner's foreground entry point is an internal hidden subcommand: the unit's
  command, and what tests call directly (`scripts/check-in-container.sh` runs plain `docker run` with no user
  manager: all three review lanes, round 1). It replaces the hidden supervisor subcommand, hidden `__monitor` and
  hidden `advance` (see Reusable Assets).
- **D-03 (agent):** On a host where `systemd-run --user` is unavailable, `start` and `resume` refuse and say what is
  missing (never fail closed silently). No fallback launch.
- **D-04 (agent; measured 2026-11-16, one run on this host, systemd 262):** A `systemd-run --user` unit does **not**
  get the caller's environment: a variable set only in the caller read `absent` inside the unit, and the unit's cwd was
  `$HOME`. So the launch passes, explicitly: `--working-directory` = the project root, the runner as an absolute path
  (`std::env::current_exe`), and the environment the runner and agent need. How credentials are passed without putting
  secret values on a command line (`--setenv NAME=value` is visible in `/proc/*/cmdline`; `--setenv NAME` copies the
  caller's value by name) is for research. Control: the agent on the caller's PATH only, and a required
  `DEVFLOW_*` variable set only in the caller, must both reach the agent.
  — An external lane (DeepSeek, review round 1) measured the opposite; the control above refutes it on this host.
- **D-04a (agent, review round 1):** The launch reports a failure to start instead of returning success over a dead
  unit: the runner only counts as launched once it holds D-07's lock (e.g. `Type=notify` with readiness sent after the
  lock is taken, or `Type=exec` plus a wait for the lock; research picks and verifies that `systemd-run` blocks until
  then). Negative control: a nonexistent runner path makes `start` exit non-zero naming the unit and the error.
- **D-04b (agent, review rounds 1–2):** Keep `KillMode=control-group` (D-01; the spike's hard-kill result was
  measured with it). Round 1 found that under it `systemctl stop` also SIGTERMs the agent directly, which can end it
  before the runner's control thread records the stop, so the stage reads as failed (exit 143) instead of `stopped`
  (DeepSeek lane, measured; not re-run by the agent). Round 1's answer, `KillMode=mixed`, was withdrawn in round 2:
  after an abnormal runner exit, `mixed` may leave the agent running until `TimeoutStopSec` (agy lane, from
  systemd.kill(5); unmeasured). The fix is in the runner instead: it classifies an agent exit only after draining its
  own pending stop signal, so an agent killed by the unit's SIGTERM during a stop reads `stopped`. Test: a stop whose
  SIGTERM reaches the agent first still records `stopped`; control: an agent that exits 143 with no stop requested
  records a stage failure. `TimeoutStopSec` is set explicitly on the unit, and D-07a's wait is bounded above it.
- **D-04c (agent):** If user lingering is off, `start` warns that the run ends at logout. It does not refuse.

### Stopping a run
- **D-05 (operator):** `devflow stop --phase N [PROJECT]` stays and stops whichever run the operator names. It stops
  that phase's unit; the runner traps SIGTERM (and SIGINT), ends the agent's process group, records `stopped` (event
  and state), and exits non-zero. Operator: having to stop a unit with `systemctl` by hand is unacceptable UX.
  Stopping the runner always ends its agent first: an agent without its runner has nothing capturing output or verdict.
  - (agent) `stop` stays idempotent on a phase with no live run. `--launch` goes with the sockets it addressed.
  - The spike's stop path recorded nothing without a supervisor record (`record_supervisor_stop`), so the
    stopped-recording code is new, with a test that a stopped run reads `stopped` and `resume` continues it.
  - **(agent, review round 1) Existing stop semantics carry unchanged:** a permitted finish wins over a late stop
    (`finish_run`, `pipeline_gate.rs`, operator 2026-11-11); a stop at a pending gate closes the gate and keeps the
    state resumable, never `Abort` (`open_and_await`); the stop token spans the whole run, not one stage, and exactly
    one SIGTERM/SIGINT handler is installed (today `install_holder_stop_handler` and `install_signal_pipe` replace each
    other). Tests: stop before a gate answer, after approval, during the next stage's launch, after finish permission.
  - **(agent) A runner that does not honour SIGTERM** is SIGKILLed by systemd after `TimeoutStopSec`; that leaves
    the run reading `crashed` (lock free, stage recorded running), and `stop` says so instead of claiming `stopped`.
- **D-06 (operator; corrected in review round 1):** `devflow recover` the verb is removed. Its listing duplicates
  `status`; its state deletion duplicates `discard`. Corrections: `recover.rs` helpers still used elsewhere
  (`format_age`) move, not vanish (plan review round 1: `inspect_all`'s only caller is `recover_cmd`, so it goes with the verb); the gate waiter's lifetime lock (`Gates::register_waiter`)
  survives, so gate files and `Hold::take`'s `*.hold-tmp` temps can still be left by a kill. `discard` removes a phase's
  orphan gate files and hold temps, including a gate-only phase with no state, worktree or branch (today it refuses
  that), with a test for each.

### One liveness signal (999.237)
- **D-07 (operator):** One per-phase lifetime lock is the only liveness signal. The runner holds it for its whole life,
  opened close-on-exec so the agent never inherits it. Held = live, free = not live. Every verb that asks (`start`,
  `resume`, `discard`, `stop`, `cleanup`, `status`) asks through one function. This is 999.237's fix.
  - Evidence required: the spike saw a lock read "held" while a child with an inherited descriptor lived. A test shows
    the agent child does not hold the lock, with the negative control (a child given the inherited descriptor keeps it
    held).
  - Table test, per 999.237's fix shape: every verb × lock (held, free) × state (none, reservation-only, running,
    stopped, finished, unloadable), one test walking the table. Held-lock/no-state and held-lock/unloadable are
    required rows. "One liveness signal" means liveness; the state still says which verb applies.
  - **(agent, review rounds 1–2) Two files, two jobs.** Liveness and exclusion are different locks, so the hand-off
    cannot deadlock (round 2: one file cannot be held by both launcher and runner):
    - the **runner lock** (`.devflow/.runner-NN`): taken by the runner at its start and held for its whole life. It
      is the one liveness signal. Readiness (D-04a) is sent only after it is taken.
    - the **phase holder** (`.devflow/.holder-NN`, today's `claim_phase_holder` file): exclusion only. A verb that
      mutates (`start`, `resume`, `discard`, `cleanup` per phase in turn) takes it before its checks and keeps it
      across its mutation; `start`/`resume` keep it until the launch reports ready, then release it. The runner
      never takes it.
    - Both files follow `claim_phase_holder`'s invariant: never removed, replaced or `unlock()`ed, excluded from every
      cleanup, so no two processes lock different inodes.
    - Tests: two concurrent `start`s (one launches, one refuses); `start` racing `discard`; `status` reads live for a
      service run after `start` has returned.
  - **(agent)** A lock that cannot be probed (I/O error) reads as an error, never as free.
  - **D-07a (operator, 2026-11-16, review round 1):** The lock frees a moment before systemd finishes killing the
    unit's remaining processes. Verbs that delete or relaunch (`start`, `resume`, `discard`, `cleanup`) therefore also
    wait, bounded, until the phase's unit reads inactive before acting; the lock stays the liveness signal. Test: a
    descendant that ignores SIGTERM keeps the unit deactivating, and `discard` must not act until it is gone.
- **D-07b (operator, 2026-11-16, review round 1):** The service path is tested by a small set of host-only named
  tests that start real user services (launch, stop records `stopped`, hard kill leaves no agent, launch failure
  reported, D-07a's wait). The pinned container runs everything else through the hidden runner entry point.
  **Mechanism (operator, 2026-11-16, review round 2):** a separate named target, `scripts/check.sh service`, not an
  environment switch, so `all` stays identical everywhere (`check.sh`'s header, `ci_parity_guards.rs`). `all` does not
  include it. The pre-push hook runs it on the host beside the container gate. It fails, never skips, when no user
  manager exists. **Plus a CI job** on a GitHub-hosted VM runner that enables lingering and runs the same target, as a
  required check. Unverified: that a hosted runner can run a user systemd manager. The plan proves this first, with a
  negative control (the job fails when the manager is absent), before making the check required. The
  `.planning/user/DEV-SETUP-CHECKLIST.md` is updated in the same change. The new job also needs the job list in
  `ci_parity_guards.rs` (`job_splitter_finds_exactly_the_live_ci_jobs`) updated (review round 3, pi).
- **D-08 (agent, follows D-01):** No orphan-agent check. With every run a unit under `KillMode=control-group`, a hard
  kill of the runner takes the whole unit down: the spike (real program, one run) found no member of the agent's
  group left and the unit inactive. The orphan case (a killed terminal runner leaving its agent working the tree while
  `resume` starts a second agent there) existed only for terminal runs, which D-01 drops. Outside reach, as today: a
  process the agent itself places in another unit or container (its own `systemd-run`, podman) survives the unit.

### Status and logs
- **D-09 (operator, scope by the operator's rule "per project now if needed for usability"; agent applied it):**
  `status` shows each run's single liveness answer (live, stopped, finished, crashed) and the one verb that applies.
  The agent-pid and supervisor-probe lines go. Needed now because `stop` acts on what `status` shows and the old lines
  are deleted anyway. Naming stays project + phase.
- **D-10 (operator; corrected in review round 1):** `devflow logs --phase N [-f]` is how a run is watched.
  It **already exists** (`Command::Logs`, `main.rs`, with `--phase`, `-f`, `--stderr`). (agent, narrowed in review
  round 2) The one change: when `-f` ends because the agent exited, it prints the run's state line read from the state
  file (next stage launched, gate pending with the `gate approve` line, finished, stopped, crashed). No cross-stage
  multiplexing. `start`'s launch line names `logs` and `status`.
- **D-09a (agent, review round 2):** A phase with orphan gate files and no state is shown by `status` as debris
  naming `discard`, not as an answerable gate; the gate banner offers approve/reject only for a gate with a live
  waiter. Repair text never names the removed `recover`.

### Gates
- **D-11 (agent, follows D-01):** A gate is answered from any shell with `devflow gate approve` / `reject` (proven by
  the spike with a separate process). No inline prompt, since no terminal is held. Announcement is unchanged: the
  notify hook and the pending-gate banner in `status`.
