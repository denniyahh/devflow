Main concerns:

- `--expand-environment=no` needs systemd 254 or later, and nothing checks or documents that.

The necessity rubric (`necessity-review.md`) was read and applied.

## Critical Issues

### CR-01: A stop during an `--until` run, then `resume`, drops the `--until` cap and the run passes the boundary

**File:** `crates/devflow-cli/src/pipeline_launch.rs:2545-2550` (with `pipeline_launch.rs:1369-1389`, `pipeline_launch.rs:1033-1044`, `pipeline_gate.rs:76-79`)
**Issue:** `resume_loaded` clears `stop_until` whenever the state reads `stopped`:
```rust
if s.stopped {
    s.stopped = false;
    s.stop_reason = None;
    s.stop_until = None;
}
```
That rule is meant for the `--until` halt, which `transition` records as `stopped = true` with `stage == from` and `stop_until == Some(from)` (`pipeline_gate.rs:76-79`). The runner's new stop recorders (`record_runner_stop`, and `record_advance_stop` at a gate wait) write the same shape for an operator `devflow stop` in the middle of the capped stage: `stopped = true`, `stage` unchanged, `stop_until` untouched. Only `stop_reason` tells the two apart. So `start --until plan`, then `stop` during Plan, then `resume` clears the cap. The resumed run finishes Plan and goes on into Code, launching an agent that commits, past the boundary the dogfooding convention relies on: an external review between Plan and Code. `resume_preserves_unfired_until_cap` covers only the `stopped == false` case, so no test catches this. The clearing rule predates the phase, but D-05 makes stop-then-resume the normal path, and this phase wrote the recorders that produce the shape.
**Fix:** Clear the cap only when the cap is what stopped the run. One way is an explicit marker that only `transition`'s halt sets:
```rust
// transition's --until halt
s.stopped = true;
s.until_fired = true;            // new field, or compare a dedicated reason constant
// resume_loaded
if s.stopped {
    s.stopped = false;
    s.stop_reason = None;
    if s.until_fired { s.stop_until = None; s.until_fired = false; }
}
```
Add a test: an `--until plan` run stopped by SIGTERM during Plan keeps `stop_until == Some(Plan)` after `resume`. Control: a run halted by the cap still clears it.

## Warnings

### WR-01: A stage-start failure leaves the token in `AgentRunning` with a reaped pgid, so a later stop signals a possibly recycled process group

**File:** `crates/devflow-core/src/monitor.rs:1133-1165`, `crates/devflow-core/src/stop.rs:764-775`
**Issue:** `run_stage` calls `token.begin_agent(pid)`, which sets `AgentRunning`, `agent_exited = false` and `agent_pgid = Some(pid)`. If `drive_stream_io` or `wait_owned_agent` then fails, `abandon_agent` SIGKILLs and **reaps** the child and returns `Err`, but the token is never told the exit was observed. The runner goes on through `failed_start` and `handle_infra_outcome`. A SIGTERM or SIGINT before the next `enter(...)` or `begin_agent` reaches `stop_on_signal`, which matches `(KillAgentGroup, false, Some(pgid))` and calls `signal_group(pgid, SIGTERM)` on a pid that is no longer this process's child. `kill_group_unless_exit_observed` then waits `TERMINATE_VERIFY_WAIT` on a condvar nobody will notify and SIGKILLs that group. This breaks the module's own rule R-13 (`stop.rs:373-380`: signal only an unreaped leader's group), and it blocks the dispatcher for the whole wait.
**Fix:** On every path in `run_stage` that reaps after `begin_agent`, mark the exit observed under the owner lock before the reap. For example, give `StopToken` a `pub(crate) fn abandon(&self, reap: impl FnOnce())` that sets `agent_exited = true`, notifies `exited`, sets the phase to `Advancing` and then runs the reap, and use it in place of the bare `abandon_agent` calls at `monitor.rs:1152` and `monitor.rs:1163`.

### WR-02: `manager_available` treats any exit-0 `systemctl` as a live manager, though `check.sh` documents the pinned image's exit-0 shim

**File:** `crates/devflow-cli/src/service.rs:235-257`, `crates/devflow-cli/src/service.rs:273-289`, `crates/devflow-cli/src/commands.rs:2139-2144`
**Issue:** `scripts/check.sh:93-103` says the pinned devcontainer ships a `/usr/local/bin/systemctl` shim that prints a "systemd is not running" notice and exits 0, so that script requires the answer to start with a digit. `manager_available` only checks `status.success()`. On that image it reads "manager answers", and D-03's refusal never fires. `unit_active_state` then returns the shim's notice as the `ActiveState`. `runner_liveness` maps anything that is not `inactive` or `failed` to `Stopping`, so `status` shows "live (stopping)" with the notice as the state. `start`, `resume`, `discard` and `cleanup` each wait `UNIT_STOP_WAIT` (15 s) and then refuse with "reads <notice> again". The e2e tests replace `systemctl` with a fake on PATH (`tests/common/mod.rs:33-44`), so no test reaches this path.
**Fix:** Apply `check.sh`'s rule in Rust. Count the Version probe as an answer only when the trimmed stdout starts with an ASCII digit, and otherwise sort it through `classify_unanswered` with the stdout text. Also reject an `ActiveState` value outside systemd's fixed set (`active`, `reloading`, `inactive`, `failed`, `activating`, `deactivating`, `maintenance`, `refreshing`) as a read error rather than `Stopping`.

### WR-03: `devflow logs -f` right after `resume` reads the previous stage's exit file and stops following the resumed stage

**File:** `crates/devflow-cli/src/commands.rs:4088-4096`, `crates/devflow-cli/src/pipeline_launch.rs:1564`, `crates/devflow-cli/src/pipeline_launch.rs:2477-2564`
**Issue:** `resume` does not archive the stopped stage's capture. Only `begin_runner_stage` does that, through `archive_prior_capture`, after READY, `load_state` and `launch_stage`, and `launch_stage` includes the canary and preflight. During that window `phase-NN-exit` still holds the old code (143 for a stop). `follow_capture` sees the exit file on its first quiet poll, prints "== agent exited with code 143 ==" and calls `post_exit_line`. That keeps waiting while the run is live at the same stage, which the resumed stage is, until `POST_EXIT_WAIT` (60 s). It then prints the live line and returns without following the new agent. `start` and `resume` themselves print `devflow logs --phase N -f` as the way to watch the run (D-10).
**Fix:** Have `resume` archive the previous capture under its holder before `launch_runner_unit`, the same `agent_result::archive_phase_files` call `begin_runner_stage` makes. Or have `follow_capture` ignore an exit file older than the capture file it is following. Add a test: `logs -f` started right after `resume` does not print the old exit code.

### WR-04: The unit argv needs systemd 254 or later (`--expand-environment=no`), and nothing checks or documents that

**File:** `crates/devflow-cli/src/service.rs:556`
**Issue:** The local NEWS (`/usr/share/doc/systemd/NEWS:7644`, under "CHANGES WITH 254") records `systemd-run gained a new switch --expand-environment=no`. Older user managers (systemd 249 to 253) answer the Version probe, so D-03 passes, and then `systemd-run` rejects the option. That happens after `start_reserved` has already created the worktree and branch (see WR-05). The failure shows as a raw "systemd-run could not start unit ..." line, not a refusal that names what is missing. The docs searched (README, OPERATIONS, ARCHITECTURE, `docs/guides/`) state no minimum systemd version.
**Fix:** Parse the Version probe's leading number in `manager_available` (the same probe WR-02 fixes). If it is below 254, refuse before any mutation with "systemd user manager N is older than 254, which DevFlow's unit launch needs". Document the minimum in README and `docs/guides/unattended-mode.md`.

### WR-05: A start whose unit launch fails clears the state but leaves the worktree and branch, and the comment says start can run again

**File:** `crates/devflow-cli/src/commands.rs:417-439`
**Issue:** `start_reserved` creates the phase worktree and `feature/phase-NN` before `launch_runner_unit`. When the launch fails, only `workflow::clear_state` runs. The comment claims "`start` can run again", but the next `start` is refused by `launch_guards`' leftover-worktree or leftover-branch row (`commands.rs:1023-1033`), because `start` removes nothing (52.1 D-09.1). The failure line ("start: phase N was not launched: ...") does not mention what was left, so the operator learns of it only from the next refusal.
**Fix:** In the error branch, name what remains and the verb that removes it, and correct the comment:
```rust
Err(CliError::Message(format!(
    "start: phase {phase} was not launched: {why}; its worktree and branch were created and are kept — \
     run `devflow discard --phase {phase}` before starting it again"
)))
```

### WR-06: The `systemd-run` launch is the one service call with no deadline

**File:** `crates/devflow-cli/src/service.rs:600-604`
**Issue:** Every other `systemctl` and `loginctl` call goes through `run_bounded` (codex-7: "every process this module starts" gets a deadline). `launch_runner_unit` uses plain `.output()`. `TimeoutStartSec=30s` bounds the unit's start, not `systemd-run`'s own wait on a stalled bus or manager. While it waits, `start` or `resume` holds the phase holder, so `discard` and `cleanup` for that phase are blocked too.
**Fix:** Call `run_bounded(command, Duration::from_secs(30) + SYSTEMCTL_CALL_BOUND)`, derived from `TIMEOUT_START_SEC`, and on `TimedOut` report that the unit's state is unknown and name `devflow status`.

### WR-07: Impossible-state guard — the "foreground holder" stop branch cannot run in a production build

**File:** `crates/devflow-cli/src/pipeline_launch.rs:1009-1027`, `pipeline_launch.rs:1099-1102`, `pipeline_launch.rs:874-878`
**Category:** necessity
**Issue:** `holder_stop_requested()` and the `None => holder_stop_signal()` arm of `wait_for_gate_response` fire only when the thread has no engaged token but the process caught SIGTERM or SIGINT. The only non-test caller of `devflow_core::stop::install_signal_pipe` is `run_runner` (`pipeline_launch.rs:1235`; the other hits are tests at `monitor.rs:3962` and `liveness.rs:788`). `run_runner` engages its token at `pipeline_launch.rs:1254`, before any safe point or gate wait. `claim_foreground_holder` installs no handler (`commands.rs:3936-3937`, D-12). So a non-runner process never has `CAUGHT_SIGNAL` set, and the runner always has a token: the branch, `HOLDER_STOP_REASON` and the `"foreground_holder"` event source never run.
**Fix:** Remove the branch and `HOLDER_STOP_REASON`, and let `stop_requested_at_safe_point` read the engaged token only. Or, if in-crate tests drive `advance_with` without a token, give those tests an engaged token rather than keeping a production path for them.

## Info

### IN-01: Stop text and help shown to users still name the removed supervisor

**File:** `crates/devflow-cli/src/pipeline_launch.rs:874`, `pipeline_launch.rs:1035-1039`, `crates/devflow-cli/src/main.rs:77-78`, `main.rs:121-122`, `docs/guides/configuration.md:47`, `docs/guides/unattended-mode.md:78-81`, `OPERATIONS.md:586`, `OPERATIONS.md:675`
**Issue:** A stop at a gate records `ADVANCE_STOP_REASON` = "stopped through the supervisor during advance", and `devflow stop` prints that reason. `advance_stopped` events carry `"source": "supervisor"`. `--fallback-agent` help says "before the first supervisor spawns", and `resume` help says "whose supervisor has ended". `OPERATIONS.md:675` says the supervisor records `phase-NN-agent-pid`, but no production code writes that file any more: `agent_result.rs:3676` only removes it.
**Fix:** Change the strings to "runner" (for example "stopped by a stop signal to the runner during advance", `"source": "runner"`) and update the help and the docs rows.

### IN-02: `stop.rs` keeps public API from the socket protocol that nothing uses

**File:** `crates/devflow-core/src/stop.rs:51-58`, `stop.rs:66`, `stop.rs:107`, `stop.rs:164-165`, `stop.rs:277-285`
**Issue:** `StopSource::Socket`, `StopAction::ReplyHandedOff` (which `on_stop_request` never returns), `OwnerPhase::as_str` ("the protocol's owner label"), `StopToken::ended_stopped`, `StopToken::note_group_signalled`, and the `group_signalled` field (written, never read) have no callers anywhere in `crates/`. They describe the socket and ping replies this phase removed.
**Fix:** Remove them in this semver-breaking alpha (list them in `52.2-SEMVER-REMOVALS.txt`), or mark them `#[deprecated]` if they must stay.

### IN-03: A stop during a stage's launch is logged as a lost-ownership kill

**File:** `crates/devflow-core/src/stop.rs:381-392`, `crates/devflow-core/src/monitor.rs:1133-1135`
**Issue:** `run_stage` uses `end_group_while_running` for "a stop arrived while the stage was launched". That function logs "ending agent group …: this process does not own the run" and calls `request_stop_locked(..., StopSource::Ownership)`. The source is harmless, because `get_or_insert` keeps the earlier signal, but the log line names the wrong cause.
**Fix:** Take the reason as a parameter, or add a `end_group_for_pending_stop` variant with its own log line.

### IN-04: The write-lock barrier's comment names the removed `recover`

**File:** `crates/devflow-cli/src/commands.rs:3939-3943`
**Issue:** The doc justifies the `update_state_with_within` pass as "a barrier against a recovery … that may be deleting the state". `devflow recover` is gone (D-06). The barrier may still protect against the runner's `abort()`, which deletes state without the holder, but the comment no longer says what it protects against.
**Fix:** Name the writer it now orders against (the runner's `abort`), or remove the barrier if none remains.

### IN-05: `stop` can exit non-zero over a run that finished between its liveness read and `systemctl stop`

**File:** `crates/devflow-cli/src/commands.rs:3841-3874`
**Issue:** `stop_report` reads `Live` and then calls `stop_unit`. If the runner finishes in between, `--collect` unloads the unit, `systemctl --user stop` on an unloaded unit fails, and `stop` reports "unit … was not stopped", though the run finished cleanly. The window is short but real.
**Fix:** When `stop_unit` fails, read `runner_liveness` and the state again. If the lock is free and the unit inactive, print `stop_outcome`'s line instead of the error.

### IN-06: The bounded-call kill test can fail under load before the child records its pid

**File:** `crates/devflow-cli/src/service.rs:919-941`
**Issue:** The child gets a 200 ms deadline, and the test then `expect`s the pid file `sh` writes as its first action. On a loaded CI host, `sh` may be killed before that write, and the test fails with "the child recorded its pid" rather than on the property under test.
**Fix:** Before calling `run_bounded`, wait until the pid file exists (spawn the command and poll), or raise the deadline to about 1 s and keep the "under 2 s" assertion.
