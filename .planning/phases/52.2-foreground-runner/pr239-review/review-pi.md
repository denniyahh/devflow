All probe units are collected; no leftover files (the probes wrote nothing outside systemd's transient unit registry).

## CONFIRMED

**1. major — `devflow discard` / `cleanup` / `stop` / `status` refuse in any shell whose `XDG_RUNTIME_DIR` is unset or not this user's own dir; the doc says the lock alone answers.**
- `crates/devflow-cli/src/commands.rs:2244` — `Err(unavailable) if unavailable.kind == ...::Absent => { … NotLive }`; every other kind (including `Unreachable`) returns `Err` from `runner_liveness`, and `crates/devflow-cli/src/commands.rs:2493` turns that into `"refusing to discard phase {phase} — {why}, so a live runner cannot be ruled out"`.
- `crates/devflow-cli/src/service.rs:200` `classify_unanswered`: `None => ManagerUnavailableKind::Unreachable`; the module's own test asserts this at `crates/devflow-cli/src/service.rs:1087` — `("unset", None, Unreachable)`.
- Doc promise, `OPERATIONS.md:108-110`: "When no systemd user manager runs for the user, the lock alone answers and the verb says so on stderr (`checked by its runner lock only`)".
- Input that breaks it: `env -u XDG_RUNTIME_DIR -u DBUS_SESSION_BUS_ADDRESS devflow discard --phase 7` in a container / cron / systemd-timer shell. The runner lock probes `Held::Abandoned`, i.e. the run is *provably* not live, but `discard` refuses, `cleanup` keeps the phase and exits non-zero, `stop` errors out, `status` prints `error`. There is no escape hatch: this PR removes `cleanup --force` and `discard`'s forbears, so the operator must hand-delete `.devflow/state-NN.json` and `git worktree remove` — the thing the design forbids.
- Expected per doc: proceed on the lock, printing `checked by its runner lock only`. Actual: refusal. Why the suite cannot see it: every container child gets a fake manager first on `PATH` (`crates/devflow-cli/tests/common/mod.rs:402-404`, `with_fake_service_manager`), so no test ever runs these verbs against a real "no manager" shell.

**2. major — a failed transient unit is read as "gone", but it stays loaded for ~120 ms and systemd then refuses the same unit name; `start` reacts by deleting the run state and telling you to `discard`.**
- `crates/devflow-cli/src/service.rs:642` — `"--collect".into()`; `crates/devflow-cli/src/commands.rs:2206-2210` — "`/// The lock is free and the unit is gone.` / `NotLive`"; `crates/devflow-cli/src/commands.rs:2255` — `"inactive" | "failed" => RunnerLiveness::NotLive`.
- Reproduced here on systemd 262 (no devflow build needed): `systemd-run --user --collect --unit=N /bin/sh -c 'exit 1'`, then re-run the identical `--unit=N` immediately — **5 of 10 attempts failed** with `Failed to start transient service unit: Unit N.service was already loaded or has a fragment file.`, and the unit reads `ActiveState=failed, LoadState=loaded` for ~120 ms before `--collect` unloads it (`not-found`).
- Consequence in code: `launch_runner_unit` maps any non-zero `systemd-run` to `LaunchError::Failed` (`crates/devflow-cli/src/service.rs:800-806`), and `start` answers with `clear_after_failed_launch` (`crates/devflow-cli/src/commands.rs:468-477`), i.e. it deletes the state it just wrote and prints "…its worktree and branch were created and are kept: run `devflow discard --phase N` before starting it again".
- Contradicts `OPERATIONS.md:69-70` — "A launch that fails names the unit and systemd-run's error; `start` then leaves no state behind, so it can be run again". It cannot be run again for ~120 ms; the retry fails with a message about a unit name, and the advice it gives (`discard`) throws away the worktree/branch that are perfectly good. Trigger: any automated retry after a runner that ended in error — `devflow start && devflow start`, a wrapper loop, shell `!!`, or a stop+start in one script line.

**3. minor — operator-facing text still names the removed supervisor, and `resume`'s help still describes the old supervisor-era purpose.**
- `crates/devflow-cli/src/main.rs:121-123`, rendered by `devflow resume --help`: `/// … Accepted on a run /// that is not live (stopped, or whose supervisor has ended);`.
- `crates/devflow-cli/src/pipeline_outcomes.rs:148`: a rate-limit **gate** context shown to the operator — `"rate limited with no usable fallback; once this waiting supervisor has ended, `devflow resume --phase {phase}{agent}` relaunches the stage; {reset}. Cause: "`. There is no supervisor to wait for; the correct action is `devflow stop`.
- `crates/devflow-cli/tests/snapshots/devflow-help.txt:7` — `resume   Resume a phase from its saved stage after a rate limit or infrastructure pause` — unchanged, while `devflow stop` now prints "run `devflow resume --phase N` to continue it" (`OPERATIONS.md:47`).
- These survive the PR's own scans because `crates/devflow-cli/tests/help_snapshot.rs:names_the_user_service_stop` only rejects the literal `"supervisor socket"` on the single `stop` help line, and `crates/devflow-cli/tests/removed_surface_scan.rs` only scans `--force`/`git branch -D`. The `resume --help` text is in no snapshot at all.

**4. minor — the only real-systemd `stop` test asserts a unit state the design does not guarantee, and that is the admitted flake.**
- `crates/devflow-cli/tests/service_e2e.rs:855-859`: `assert_eq!(unit_property(&guard.unit, "ActiveState"), "inactive", "the unit is not inactive after stop")`.
- `PR-BODY.md:38`: "Known: `service_e2e` fails intermittently on stop (a unit reads `failed`)."
- The two terminal paths the code allows both spend time `failed` before collection: a runner SIGKILLed at `TimeoutStopSec` (=10 s, `crates/devflow-cli/src/service.rs:28`) under `KillMode=control-group`, and any non-zero main-process exit outside a stop job (measured: `failed`/`loaded` for ~120 ms). A single read taken the instant `devflow stop` returns therefore races the collection, and there is no negative control separating "unit inactive" from "unit not yet collected but failed" — `wait_inactive` (`service_e2e.rs:288-299`) treats only `inactive` as done and would spin, which is why the assertion flakes rather than reporting. Net: the PR's headline claim that `stop` "records `stopped` and the unit is down" has no deterministic real-manager test, and `scripts/repeat-named-test.sh` is shipped to measure it but no N is reported.

**5. minor — `stop` has no path to a live runner that has no loadable unit, yet `status` tells the operator to use it.**
- `crates/devflow-cli/src/commands.rs:3983-3986`: with `RunnerLiveness::Live` the only action is `crate::service::stop_unit(&unit)`, which is `systemctl --user stop <derived name>` (`crates/devflow-cli/src/service.rs:884-898`).
- Verified here: `systemctl --user stop probe-nonexistent-xyz.service` → `Unit probe-nonexistent-xyz.service not loaded.` exit 5. So `stop_unit` returns `Err`, and `devflow stop` prints "`stop: unit {unit} was not stopped: …`" while the runner keeps running and holds its lock — after which `discard`, `start` and `resume` all refuse on the held lock.
- Reachable through a path this PR's own suite exercises: `crates/devflow-cli/tests/runner_e2e.rs:310` "`devflow __runner` run directly, with `NOTIFY_SOCKET` unset", which `crates/devflow-cli/src/service.rs:notify_ready` explicitly supports ("A no-op when `NOTIFY_SOCKET` is unset: the runner verb run outside a unit"). `status` reports it `live` and prints the verb `devflow stop --phase N` (`crates/devflow-cli/src/commands.rs:2338-2340`), which cannot work. No fallback to the runner pid the lock records.

## SUSPECTED (speculation — interleaving not reproduced)

- **A start/resume within the ~120 ms failed-unit window additionally reports `crashed`.** In `resume`'s `LaunchError::Unknown → TimedOutLaunch::NotLive` arm (`crates/devflow-cli/src/pipeline_launch.rs:2306-2310`) the state is re-marked `stopped` under a unit that may still be starting (a submit-but-queued start job reports `ActiveState=inactive`; `unit_active_state` reads only `ActiveState`, `crates/devflow-cli/src/service.rs:322-345`). The runner then loads a `stopped` state. I could not force a queued job to prove the interleaving.
- **A stop can be silently lost when the write lock is stalled at `record_runner_stop`.** `record_runner_stop` writes through `workflow::update_state` → `block_on_write_lock` with no timeout (`crates/devflow-core/src/workflow.rs:333-341`), while the manager SIGKILLs at `TimeoutStopSec` = 10 s, exactly `WRITE_LOCK_REPAIR_WAIT` (`crates/devflow-core/src/workflow.rs:264`). A stalled lock holder makes the manager kill the runner before `stopped` lands, and `stop_outcome` then reports `crashed` and exits non-zero (`crates/devflow-cli/src/commands.rs:4024-4034`). Plausible cause of 4's flake; not demonstrated.
- **`stop`'s holder read is advisory and can refuse spuriously.** `stop_report` calls `liveness::live_holder(&holder)` and errors on `Err` (`crates/devflow-cli/src/commands.rs:3961-3966`), but the record is rewritten with `set_len(0)` + write while only the flock is held (`crates/devflow-core/src/workflow.rs:374-388`, `crates/devflow-core/src/liveness.rs:181-191`); a reader landing in that window gets an unparsable record and `stop` refuses with "its holder file could not be read".

## CHECKED AND FINE

- `systemd-run` without `--pipe` does not hand the unit the caller's stdio (man: `--pipe` is what inherits them), so `run_bounded`'s `wait_with_output()` cannot block until the run ends — the one thing that would have made `start` hang for hours.
- A runner exit code of `143` (`STOPPED_EXIT_CODE`, `crates/devflow-core/src/stop.rs:32`) under an explicit stop job is *not* a failed unit: measured `Result=success`, `ActiveState=inactive`, collected.
- `--setenv NAME` (bare, value inherited) is supported since systemd 211 and `--expand-environment` gates 254 as `MIN_SYSTEMD_VERSION` claims.
- Runner-lock and holder publish/lock invariants: flock on a never-removed per-phase file, unique temp + hard-link publish, `Held::Live` decided by `try_lock_shared` alone, no `unlock()`.
- `commit` applies only the fields a site names, so a gate answer written by the `gate approve` process is not clobbered by the runner's next write.
- `resume` clears `stop_until` only when `until_cap_fired` (`crates/devflow-cli/src/pipeline_launch.rs:2530-2540`) — the operator's cap survives a plain `devflow stop`.
- Guard ordering: manager probe → phase holder → facts (with the stopping-unit wait) → write-lock reservation → `create_run_state` → launch, with the holder held across the launch; `start --dry-run` reads none of it destructively.
- `cleanup` cannot lose uncommitted or unmerged work: `cleanup_worktree_holds` requires `commits_not_in_develop == 0` and a clean `git status --untracked-files=all`, and the removal is a non-force `git worktree remove` (`git` re-checks). `discard` deletes uncommitted work only after listing it, which is what `OPERATIONS.md:49` promises.
- `sweep_merged_branches` is fed every checked-out branch, so a live or `--no-worktree` run's branch is never swept.
