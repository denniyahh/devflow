1. **P1 — A free runner lock does not mean its agents have stopped.** [D-07/D-08](.planning/phases/52.2-foreground-runner/52.2-CONTEXT.md#L54) say “free = not live” and remove orphan checks because killing the runner “takes the whole unit down.” These events are not atomic: the runner releases its descriptor when it dies; systemd then terminates remaining processes, potentially waiting until `TimeoutStopSec` before SIGKILL. This applies to normal main-process exit too. Consequently, `discard` can observe “dead” while descendants still touch the worktree; `resume` can encounter the old fixed-name unit still deactivating. This follows from the documented lifecycle, rather than a reproduced DevFlow failure. Require a control with a SIGTERM-resistant descendant and attempt both verbs during deactivation. [systemd.kill](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html), [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#ExitType=).

## Lane: pi

## CONFIRMED

**1. D-07's lifetime lock has no owner at the moment it matters, and the code says the handover it needs is impossible under D-01.**
Today the phase lock is handed *through a direct fork*: `spawn_monitor` calls `crate::liveness::pass_to_child(&mut child_cmd, &reservation.liveness)` (monitor.rs:664), which `dup2`s the fd to 3 and **clears close-on-exec** (liveness.rs:233-252), and the child `adopt_inherited`s it (monitor.rs:2020, liveness.rs:271-285). `systemd-run --user` execs the unit from the user manager, so nothing crosses that boundary. D-07 says "The runner holds it for its whole life" and D-12 removes `claim_foreground_holder` (commands.rs:4880) — the *only* caller of `claim_phase_holder` (liveness.rs:342). So nothing in CONTEXT says who claims, or when. The window is real: `start`'s guard reads free, `systemd-run` returns before the runner has executed, and a second `start`/`resume`/`discard` also reads free — precisely 999.237's shape, moved rather than closed. The two candidates are not interchangeable either: `Hold::take` **refuses an existing name** ("AlreadyExists if `path` exists, which is never replaced", liveness.rs:83-89; pinned by `a_take_never_replaces_an_existing_name`, liveness.rs:1369), so a per-phase lock reused across runs can only be `claim_phase_holder`, whose own doc warns "The file is never removed, replaced or `unlock()`ed: a removed file lets two claimers lock different inodes" (liveness.rs:330-335) — and CONTEXT leaves "where the lock file lives under `.devflow/`" to discretion, i.e. the one directory whose entries `cleanup`/`discard` are allowed to churn.

**2. Every verb × every state table in D-07 still reads the state file, so "one liveness signal" is false as stated.**
D-07 defines `crashed = lock free with a stage recorded running` and lists `unloadable state` and `no state` as rows. The answer is lock **+** state (+ `Existing`'s three values, + `write_lock_status`, which `status` still prints — commands.rs:2229-2233, not in D-09's removal list). That is fine engineering, but the decision text ("One per-phase lifetime lock is the only liveness signal") is not what the table implements, and D-09 then enumerates only four answers with "the one verb that applies" — no verb is named for `crashed`, `no state`, or `unloadable`. The two decisions do not compose as written.

**3. `run_supervised_stage` cannot be "the one function" run in the foreground: it publishes a socket and returns a supervisor, which D-05 + D-07 delete.**
`StageSpec` requires `pub socket: SocketPath` (monitor.rs:1549) and `pub launch_id` (1551); the function unconditionally does `crate::supervisor::write_sidecar(&spec.socket, &sidecar)` (1744) and `Supervisor::serve_written(spec.socket.clone(), sidecar)` (1747), and returns `StageRun { supervisor, promotion, .. }` (1606-1629) whose `Promotion::{Recorded,Superseded,OrphanedPending}` (1592-1604) exists only because launcher and supervisor are different processes. The six in-process tests the brief counts (monitor.rs:5805, 7101, 7138, 7187, 7394, 7604) all construct a socket for that reason. And the tail of the run is not in this function at all: `pipeline_launch::run_monitor` (1494) owns the advance, the handoff fence, `take_successor`/`forward_stop_to_successor` (1555-1612), `advance_with`'s three safe points (3658-3686) and `spawn_next_supervisor` (2545), which re-execs the next `__monitor`. D-02's "Whether hidden `advance` survives … may make moot" treats as an open question what is in fact the run's entire state machine.

**4. `KillMode=control-group` puts a second SIGTERM on the agent, which is exactly the case where the run is *not* recorded `stopped`.**
Measured on this host (systemd 262): with `-p KillMode=control-group`, `systemctl --user stop` delivers SIGTERM to the main process **and** to a child in its own session (runner trap and child trap both fired). In the code the outcome is decided *only* by the stop token: `on_agent_exit(stop_requested, code)` (runtime.rs:147-155) and `observe_exit` reads `state.stop_requested` (274-279), which is set **only** by `request_stop_locked` (306-310) driven by the control thread fed from the signal-pipe handler (463-486, 492-521). When systemd's own SIGTERM kills the agent before the runner's control thread consumes the pipe byte, `observe_exit` sees `false` and returns `Completed(143)` — a stage failure, not `stopped`, and D-05's "records `stopped` (event and state)" fails. `KillMode=mixed` is the setting that matches D-05's design (SIGTERM to the main process only; SIGKILL to the rest when it exits, so D-08's hard-kill case still holds). Also measured: a runner exiting 143 makes the unit `Failed with result 'exit-code'` and fires `OnFailure=` dependencies on every `devflow stop`.

**5. D-13's evidence "the unit is gone" cannot fail, so it is not evidence.**
Measured: with `--collect`, a unit that exited normally, a unit stopped with `systemctl --user stop`, and a unit never started all read identically — `systemctl --user is-active <unit>` prints `inactive` and exits 4, and the name is immediately reusable ("Running as unit: …" on reuse). A crashed run, a killed run and a successful run produce the same "gone". The falsifiable form is lock-free **and** state `finished` **and** the last event not `supervisor_failed` — plus a negative control: a run killed mid-stage must also show the unit gone while the state is not finished, or the check proves nothing.

**6. The service path — the only thing standing behind D-08 — has no automated coverage anywhere in this project.**
`scripts/check-in-container.sh` runs the pinned image under plain `docker run` ("Requires Docker (a real daemon)", no init, no user session), and D-02 itself records the same for CI. So `KillMode=control-group` taking the agent's group down on a hard kill is exercised by two stand-in spikes and one proof run, and by no test, forever. D-08's "No orphan-agent check" is therefore a one-run claim, while the *unprotected* shape (the hidden subcommand started directly, which is what every test uses) is the one the suite covers.

**7. One process cannot be both holder and supervisor: the two code paths install conflicting process-global SIGTERM handlers, and each says so.**
`claim_foreground_holder` installs `install_holder_stop_handler` (commands.rs:4884), whose doc states: "A supervisor process never calls this: it installs `crate::supervisor::runtime::install_signal_pipe`, which this would replace, and claims no holder (D-17)" (liveness.rs:385-387). `run_supervised_stage` calls `install_signal_pipe()` unconditionally (monitor.rs:1720), which `sigaction`s over SIGTERM/SIGINT (runtime.rs:506-519). Whichever runs second wins, while `install_holder_stop_handler`'s `OnceLock` (liveness.rs:401) caches "installed". The fallback used when no token is engaged — `stop_requested_at_safe_point()`'s `holder_stop_requested()` and `wait_for_gate_response`'s `None => liveness::holder_stop_signal()` (pipeline_launch.rs:1215, 1356) — then reads a flag nothing sets. Note the gate-wait stop path itself is already right (safe point 4 closes the gate and records the stop, pipeline_gate.rs:930-945), but only through the token: the token must now span the entire run, which no decision states.

**8. `recover.rs` as a removal target is wrong, and removing `recover` removes the only remover of lock-temp litter.**
`recover::format_age` is used by `status` and by gate output (commands.rs:2202, 2478, 2514, 2559, 2604, 4950), and `recover::inspect_all` by `doctor` (5857); wholesale deletion as listed breaks them. Separately, `remove_orphan_hold_temps` (liveness.rs:486) has exactly one caller, `recover.rs:168`, and `Hold::take` creates `.devflow/.{name}.{pid}.{seq}.hold-tmp` before linking (liveness.rs:108-119, 145-155). Post-D-06 nothing removes a temp left by a `start` killed in that window; `discard`/`cleanup` remove only the state file (workflow.rs:883-908). Small, but it is a stated consequence of two decisions that CONTEXT does not mention.

**9. D-14 (D-10): `devflow logs` already exists — it is not a new verb.**
`Command::Logs { phase: Option<PhaseId>, follow, stderr, project }` is at main.rs:193-206, dispatched at 609, with follow semantics already tested (commands.rs:17211, 17241). D-10's "New verb `devflow logs --phase N [PROJECT] [-f]`" is false, `--phase` is `Option` today (defaults to the single active phase, else the latest capture) so D-10 silently changes existing behaviour, and the `doc_check` obligation it cites ("A new `Command` variant must be documented") does not apply. Only the `-f` pending-gate line is new work, and it needs a writer that does not exist.

**10. D-20 + D-12 make two concurrent `start`s both legal, and the loser is decided by systemd's unit name — a second liveness signal.**
D-20 (carried): a reservation-only state "counts as no run: `start` proceeds", and `ReserveOutcome.abandoned` (commands.rs:1046) shows the second start replaces it. `refuse_stateless_launch_beside_a_live_lock` (commands.rs:1012) refuses only over a *held launch lock*, which D-12 deletes. So between `start` A's launch and A's runner taking the lock, `start` B passes every guard. Measured what happens next: `systemd-run --user --unit=<same>` while active fails with `Failed to start transient service unit: Unit … was already loaded or has a fragment file.` Whichever `start` loses gets that raw text, and if the state was replaced the winner runs with a state that names nobody — the case `Promotion::Superseded` used to kill (monitor.rs:1592-1604), which goes with the supervisor.

## SUSPECTED

**S1. D-04's premise is backwards on this host, so the plan will pass the wrong things explicitly.** Measured (systemd 262): `systemd-run --user` transfers the **caller's whole environment** (111 vars, same `PATH`/`HOME`), not the user manager's — D-04's "believed to start with the user manager's environment, not the caller's" is false here. The real hazard is the reverse: whatever env `start` was invoked with (an agent's shell, a stale `DEVFLOW_*`, `--keep-env` names) is frozen into the unit, and the unit's default working directory is `$HOME`, not the caller's cwd (measured from two different caller directories), so `--working-directory` and an absolute binary path are mandatory and are not in D-01's flag list. Cross-version behaviour unverified; one line in the plan fixes it either way.

**S2. With `--collect`, a launch that never started is invisible.** `start` prints "Running as unit…" and returns; if the exec fails (binary path, workdir, agent binary missing from the unit's PATH), the unit is collected, the lock is never taken, and the state holds only a reservation which D-20 says counts as no run — `status` will read `idle`. That is the "never fail closed silently" shape D-03 forbids, at the launch boundary. Not traced end-to-end through `reserve_launch`.

**S3. `control-group` does not contain every grandchild the agent starts.** A process the agent spawns into *another* user unit (its own `systemd-run --user`, a container) is outside the unit's cgroup and survives the kill; D-08's "no member of the agent's group left" was measured on one run of a stand-in, which cannot have produced that case.

**S4. `resume` while the unit is deactivating.** The runner keeps the lock through its own SIGTERM handling, so `resume` refuses with "live", then succeeds on retry; harmless, but D-09 promises "the one verb that applies", and there is no state that says "deactivating", so the refusal will name `stop` for a run that is already stopping.

**S5. Removing `recover` leaves `discard` as the only route to unloadable state, and D-06's gate-file residue is delegated without a check.** `doctor`'s `check_gate_pending_without_gate` already detects a `gate_pending` with no gate file, which is what a unit SIGKILLed mid-gate leaves; CONTEXT's "The planner checks whether orphaned gate files can still be written" pushes that to planning, where it will be decided without a decision.
