# Phase 52.2 Plan 14: one launch guard sequence Summary

**`devflow start` takes every refusal from one pure function, `launch_guards`, in the order live runner lock, finished (close-out or `discard`), incomplete (`resume`), unloadable (`discard`, file left in place, no copy), orphan gate files (`discard`), leftover worktree or branch (`discard`); a reservation-only state still counts as no run; `resume` refuses a finished run naming the close-out and `discard` and a missing state naming `start`. No systemctl or git spawn runs under the state write lock.**

## What changed

- `gather_guard_facts` runs under the phase holder: `wait_out_a_stopping_unit` (the one call on `start`'s path), then `phase_gate_files`, then whether `.worktrees/phase-NN` and `feature/phase-NN` exist. `reserve_launch` takes the facts and its closure fills `state` (`StateFact::of`) before calling `launch_guards` (start) or `resume_guards` (resume).
- `GuardFacts` has no unit-state field; `GuardFacts::from_liveness` reads `Stopping` as no live runner, because the wait already ran.
- Deleted: `refuse_launch_over_a_live_run` (folded into the live row; its `runner_liveness` call no longer runs under the write lock), `refuse_resume_of_a_finished_run`, `keep_unloadable_state`, `replaced_state_notice` and the "replaced the state file" note, `ReserveOutcome`.
- `phase_gate_file_stage` is the one name classifier for a phase's gate files, shared by `discard_debris` and `phase_gate_files`.
- OPERATIONS.md's `devflow start` row lists the refusals in order instead of the removed replace notice.
