## Stopping a run

| Option | Description | Selected |
|--------|-------------|----------|
| Remove it | Ctrl-C or `systemctl --user stop` | |
| Keep, service only | `stop` stops the named unit, refuses terminal runs | |
| Keep, both shapes | signal a terminal runner by pid too | ✓ (as "stop whichever run is named") |

**User's choice:** Keep the verb. "The intent of devflow stop is to stop devflow processes, not the coding harness."
"Having to kill the unit with sysctl is terrible user experience." `stop` must stop whichever run the user names.
**Notes:** The agent explained that today `stop` stops the supervisor, which ends the agent; and that under the
foreground design Ctrl-C works only because `start` holds the terminal (the operator had seen the detached 3.x
behaviour). On signal: "Record stopped" chosen. `recover`: "Remove it if it no longer can do anything differently
than resume"; after the agent showed its remaining jobs duplicate `status` and `discard`, removed.

Run naming and listing: the operator asked whether naming and display of runs is sound. The agent found runs are
named project + phase, `status` is per project only, and on this repo prints `idle` beside phase 51 leftovers and
runless worktrees. Operator: "per project now if it's needed to make devflow usable; if it can wait, next phase."
Agent applied it: liveness answer + verb in `status` now; leftover listing deferred.

## Service launch

| Option | Description | Selected |
|--------|-------------|----------|
| Flag on start | `--service`, terminal-held by default | |
| Service by default | `--foreground` to opt out | ✓ (then narrowed, below) |
| Always a service | no terminal runs | ✓ (final, via the liveness area) |

**User's choice:** "What's the benefit to devflow holding a terminal? … service by default with a foreground flag."
Watching: "status shows it" chosen over a follow verb or journalctl.

## One liveness signal

| Option | Description | Selected |
|--------|-------------|----------|
| Lifetime lock | one close-on-exec lock, held = live | ✓ |
| Unit state + lock | two signals by launch shape | |
| Unit state only | foreground runs unguarded | |

**User's choice:** "One lock." Then: "Are users even able to enter devflow commands when a terminal is held, or does
it just tail output? … this should not be supported as a run type, and we should just create a log tail verb."
On the orphan question: "How does this allow two agents to work one tree?" The agent explained the killed-terminal-
runner case and that `KillMode=control-group` removes it for service runs. Final choice: "Service only + logs verb."
